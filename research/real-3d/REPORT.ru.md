# Настоящий 3D вместо 2.5D: исследование Houseplan

19 ноября 2026 · [задача #1471](https://github.com/Matysh/houseplan-card/issues/1471).
База: `f4f474cf489015af967bbd6fa03cda62c07bc975`, опубликованная линия 1.85.3-beta.2.
Исследовательская ветка: `issue/1471-real-3d-research`. Изменений продукта, слияния в dev и релиза нет.

## Вывод

Переход технически оправдан и не требует второй сохраняемой модели дома. Рекомендую **Three.js + WebGL2, настоящие сетки стен/проёмов/мебели и существующий HTML-интерфейс поверх сцены**. Для первого этапа оставить ортографическую камеру, нынешние четыре поворота и срез стен. Получить **примерно тот же вид** реально: это подтверждает запускаемый MVP на существующей геометрии.

Переход даст более естественное разрешение перекрытий непрозрачных объектов и возможность сложнее показывать проёмы без растущего числа SVG-масок. Большая сцена в лаборатории быстрее SVG-контроля, но **доказательства, что весь продукт ускорится во столько же раз, нет**. Простая сцена в неизменённом продукте уже работает быстро на этой машине. Перед заменой нужны сложный реальный дом, слабый планшет и промышленная обработка света/прозрачности.

Ориентир для первого продуктового этапа — **15–25 инженерных дней**, порядка 3–5 рабочих недель одного опытного разработчика. Это предварительная оценка полного переноса View с проверками, не обещание срока и не оценка создания ещё одного MVP.

## Что меняется относительно нынешнего 2.5D

Нынешнее решение уже сложнее «повернуть плоскую картинку CSS». Канонический план остаётся двумерным, но `iso-scene-geometry`, `iso-openings`, `iso-lab-furniture` строят объёмные поверхности. Затем они проецируются в SVG, раскладываются по глубине, обрезаются для видимости, дополняются масками и HTML-представлениями устройств. Структурная геометрия кешируется отдельно от состояний и камеры. Это полезная подготовка для 3D, а не код, который надо выбросить.

Текущая камера по [ISOMETRIC.md](../../docs/ISOMETRIC.md): yaw 35° + четверть оборота, elevation 40°, срез стен 140 см. В MVP получено математическое совпадение проекций тестовых точек во всех четырёх поворотах: максимальная ошибка `4,55×10⁻¹³` условных единиц. Отличия картинки связаны с материалами и интерфейсом, а не необходимостью другого ракурса.

| Аспект | Нынешний SVG/CSS | Предлагаемый WebGL + HTML |
|---|---|---|
| Источник правды | 2D-план и его связи | Тот же 2D-план; сетки производные |
| Непрозрачные перекрытия | Сортировка, геометрическая обрезка, маски | Depth buffer GPU |
| Стены и отверстия | Проецируемые физические поверхности | Триангулируемые поверхности; канонические вырезы сохраняются |
| Двери и створки | Перестроение/перепроекция поверхностей | Трансформации узлов/буферов; состояния из прежнего resolver |
| Текст, фокус, тултипы | HTML/SVG | HTML остаётся; положение выводится из камеры |
| Плавные повороты | Пересчёт проекции и сложные слои | Обновление одной камеры; политика поворотов прежняя |
| Прозрачная мебель и стекло | Управляемое наложение SVG | Нужна отдельная политика прозрачности; depth buffer не решает её целиком |
| Нагрузка | DOM, SVG paint/raster, compositing | GPU draw calls/fill rate + HTML + подготовка сеток |
| Отказ графики | Обычный браузерный рендеринг | Нужны обработка потери контекста и безопасный Flat fallback |
| Экспорт SVG/PDF | Векторный путь уже есть | Его сохранить отдельно; WebGL не становится векторным экспортом |

3D не исправит ошибочную геометрию стен, неверный host проёма или дорогую обработку HA. Наличие [#1470](https://github.com/Matysh/houseplan-card/issues/1470) само по себе не доказательство необходимости сменить движок: ремонт SVG и переход на 3D — разные решения.

## Коммерческие планировщики

### Remplanner

Проверены [2D-планировщик](https://remplanner.ru/planner/) и [страница 3D](https://remplanner.ru/planner/visual/) в анонимном браузере. В 2D действительно загружаются SVG.js, pan/zoom и drag-модули. Запуск 3D проходит отдельную подготовку чертежа; без построенного дома он дошёл до проверки комнат и сообщил о недостатке данных. Отдельный 3D-рендерер на этом пустом плане не был запущен. По доступному wrapper-коду нельзя достоверно назвать его движок.

Официальное [видео режима 3D](https://www.youtube.com/watch?v=15adx2qg6wE) и интерфейс показывают навигацию камерой, покомнатный режим, настройки отображения, виртуальный тур, составные материалы мебели и анимацию открывания. Перенимать стоит связь «чертёж → производная 3D-сцена» и уровни качества. Фотореалистичный каталог, туры и конструктор отделки выходят за первый этап Houseplan. Скорость их сцены здесь не измерена.

### Planner 5D

Проверены [официальная страница](https://planner5d.com/) и [редактор](https://planner5d.com/editor). В удалённом браузере часть статических ресурсов не загрузилась; повтор на Windows загрузил приложение, затем запросил вход. Аккаунт не создавался, маркетинговые согласия не принимались.

В реально полученном публичном `build/app.js` найдены признаки Three.js/WebGL. Это подтверждает присутствие технологии в клиентском bundle, но не даёт версии движка и полной архитектуры рендера. SHA и результат чтения сохранены в `competitors-observed.json`.

Продукт сочетает планирование в 2D/3D, материалы, модели и отдельные качественные рендеры/360°-сцены. Для Houseplan полезны разделение интерактивного просмотра и дорогого рендера, простое переключение представлений и единый проект. Облачная обработка и интерьерный редактор не нужны для первого этапа. FPS, память и качество собственного проекта в Planner 5D не проверены.

**Практический вывод:** оба сервиса — ориентиры поведения и подачи, а не готовые встраиваемые движки для Houseplan. Коммерческие каталоги/модели не использовались в MVP.

### Что взять из NextFloor

Самый полезный пример для нашей архитектуры — [viewer3d.ts](https://github.com/therealMRBK/NextFloor/blob/main/frontend/src/viewer/viewer3d.ts), [quality-governor.ts](https://github.com/therealMRBK/NextFloor/blob/main/frontend/src/viewer/quality-governor.ts), [labels.ts](https://github.com/therealMRBK/NextFloor/blob/main/frontend/src/viewer/scene/labels.ts) и [geo.ts](https://github.com/therealMRBK/NextFloor/blob/main/frontend/src/viewer/geo.ts):

- Отдельный viewer с явным `dispose`, освобождением геометрии/материалов/контекста.
- Общий scheduler и остановка вне экрана; короткие анимации не требуют постоянного игрового цикла.
- Снижение DPR по наблюдаемому времени кадров, а не по названию устройства.
- Большие общие буферы вместо отдельного mesh на каждую грань.
- Положение HTML-подписи меняется только при изменении экранных координат.

Это архитектурные ориентиры. Код NextFloor и его мебель в MVP не копировались. Он также не доказывает производительность Houseplan: у проектов разные сцены и правила отображения.

## MVP и его границы

[Галерея](review.html) показывает исходный 2.5D, WebGL с устройствами и четыре поворота геометрии. Все планы синтетические, файлы пользователя и реальный HA не использовались.

Работает:

- Настоящий WebGL2 renderer, ортографическая камера и GPU depth test.
- Стены с вырезами из `createIsoStructuralSource`, через штатные `spaceModels` и `geometryOpenings`; T/X-связность не пересчитывается отдельным планировщиком.
- Физические вершины существующих рам, створок, ручек, откосов и перемычек; локальная смена раскрытия.
- Шесть видов мебели из существующего реестра и его `furnitureVolumeFaces`; дополнительные 3D-модели не загружаются.
- Четыре поворота, pan/zoom, fit, фон темы; HTML-подписи и 44px-кнопки устройств с локальным состоянием.
- 6 комнат / 80 устройств и 24 комнаты / 200 устройств; 8,8 тыс. и 34,2 тыс. треугольников соответственно, около 20 draw calls.
- Render-on-demand: в простое новые кадры не рисуются; изменение подписи не пересобирает стены.
- Изолированная проверка освобождения ресурсов при смене состояния проёмов и переключение на SVG-контроль при потере WebGL-контекста.

**Пока отсутствует:** реальная интеграция HA и её actions/ACL; полный набор текущих устройств, safe lock policy, LED, радары, пылесос, все состояния неизвестности/ставен; солнечные лучи и комнатный свет; точные материалы нынешней прозрачной мебели; cast shadows; индивидуальные заливки/текстуры и импорт изображений; сохранение камеры/киоск, переходы в редакторы, SVG/PDF export. Редакторы не переносились. Это список промышленной работы, не скрытые «готовые» возможности.

Вид примерно похож по геометрии и ракурсу, но мебель MVP преимущественно непрозрачная, оттенки упрощены, устройства — screen-facing HTML-badges. Это намеренные границы эксперимента, а не согласованная замена дизайна продукта. HTML-текст не обрезается мебелью как в текущем продукте. SVG-контроль — маленький лабораторный painter, без всей системы масок Houseplan; он также не является продуктовым fallback. В промышленном варианте fallback должен включать существующий Flat.

## Измерения

### Среда и метод

Windows, мощный настольный ПК, **аппаратный NVIDIA GPU через ANGLE/D3D11**, Chromium 151.0.7922.34 / Playwright 1.62.0. GPU подтверждён `WEBGL_debug_renderer_info`. Первоначальный headless-shell использовал SwiftShader; его пробные числа не включены в итоговый отчёт.

Для каждой пары сцена/разрешение/renderer: отдельная страница, DPR 1, три последовательные серии, 30 кадров прогрева + 120 учитываемых кадров pan/zoom, локальное обновление части значений каждые 10 кадров. Нет profiler/tracing или `gl.finish` в измеряемой серии. Сцена и набор HTML-badges общие. У SVG нет проверки заслонения badges; WebGL кеширует её и не повторяет на pan/zoom. Поэтому сравнение даже лабораторных режимов не является идеальной эквивалентностью всех эффектов.

### Устойчивое перемещение, медиана трёх медиан

| Сцена / viewport | Three.js, интервал rAF | SVG-контроль, интервал rAF | WebGL CPU submission |
|---|---:|---:|---:|
| 6 комнат, 1480×1080 | 8,3 ms | 8,4 ms | ≈0,4 ms |
| 24 комнаты, 1480×1080 | 8,3 ms | 33,4 ms | ≈0,5 ms |
| 6 комнат, 3840×2160 | 8,3 ms | 8,4 ms | ≈0,4 ms |
| 24 комнаты, 3840×2160 | 8,3 ms | 33,4 ms | ≈0,5 ms |

Большая SVG-сцена имеет 10 215 path против примерно 20 draw calls. Для неё отдельные медианы серий доходили до 41,6 ms, p95 — до 50 ms; у WebGL p95 около 8,4–8,5 ms. Это демонстрирует запас GPU-подхода на множестве поверхностей, **не «Houseplan стал в четыре раза быстрее»**. Полка 8,3 ms ограничена rAF данной среды; она не измеряет предельный FPS движка. CPU submission не включает отложенный GPU/raster/compositor. GPU duration, энергопотребление и общий VRAM/JS heap не измерялись.

Начальный instrumented frame WebGL: примерно 0,15–0,60 секунды в этих запусках, включая геометрию и первую отрисовку, но **без загрузки/parse модулей до входа в viewer**. Это не холодный старт карточки. Стек MVP держит скрытый SVG-контроль даже в WebGL-режиме; его размер DOM не выдаётся за оптимальный размер будущего 3D-продукта.

В первой версии MVP проверка каждого устройства raycast-ом на каждом кадре стоила около 15 ms CPU на небольшом плане. После переноса на изменения геометрии/ракурса submission упал примерно до 0,4–0,5 ms. Это демонстрирует значение архитектуры обновлений: смена библиотеки сама по себе не гарантирует быстродействия.

### Контроль настоящего текущего продукта

Дополнительно собран **неизменённый** текущий bundle и открыт обычный demo harness на том же плане: 6 комнат, 80 виртуальных устройств, 6 предметов мебели. Три серии из 45 настоящих pointer move; проверено, что камера действительно сдвинулась. В Flat серия занимала около 398–453 ms, в текущем 2.5D — 452–493 ms. Медиана rAF в обоих около 8,3 ms; p95 у 2.5D доходил до 16,7 ms.

Это другой сценарий измерения: продуктовые плитки, эффекты и состояния отличаются от лабораторных badges. Числа pointer-series нельзя делить на времена лабораторной анимации. На этом простом доме **сильная продуктовая регрессия #1470 не воспроизвелась**. Устройство мощное, состояния виртуальные; актуальный частный дом с LQI/сводной панелью здесь не проверялся. Счётчик `.dev` включает повторные оболочки, поэтому в отчёте ориентируемся на 80 заданных markers, не на 108 найденных DOM-узлов.

### Что не доказано на планшетах

390px viewport проверен без горизонтального переполнения, но на том же настольном GPU. Это не измерение мобильного GPU, батареи или HA Companion WebView. CPU throttling также не заменил бы такой тест. До включения по умолчанию нужны Android wall tablet, iOS/WKWebView и хотя бы одно старое устройство без WebGL2; DPR 1/2, фон/возврат, потеря контекста и смена этажей. DPR увеличивает число пикселей квадратично, поэтому ограничение разрешения важнее красивого названия движка.

## Архитектура первого этапа

1. **Сохранить каноническую 2D-модель и редакторы.** Геометрия, размеры, связи HA и положения остаются в прежнем формате. 3D-сцена — кешируемый одноразовый результат чтения snapshot, не отдельный файл дома.
2. **Выделить renderer границу.** Передавать готовую геометрию, материалы и разрешённые resolved state. Renderer управляет камерой, сетками, render-on-demand и cleanup; не вызывает HA service и не интерпретирует права.
3. **Пакетировать статическое.** Общие материалы/буферы стен и мебели, отдельные группы двигающихся створок. Не пересобирать весь этаж на HA tick или смене масштаба. Перенести тяжёлую подготовку в существующий geometry worker там, где это действительно нужно.
4. **Сохранить HTML-устройства и диалоги.** Проецировать якоря одной камерой; прежние actions, hover, focus, more-info и подтверждение замков живут в существующих владельцах. Протестировать hit targets и политику видимости, а не заменять их кликом по случайному mesh.
5. **Не заменять оптическую модель.** Солнечные/комнатные области сначала рисовать на полу из нынешних resolver/полигонов. Не добавлять point light на каждое HA-устройство и shadow map каждой лампе. Состояние света и физическое прохождение через дверь — продуктовая логика, её не следует отдавать декоративному освещению движка.
6. **Определить материалы.** Отдельно opaque, cutaway и glass; определить порядок/маски для прозрачной мебели. Движок сортирует прозрачные объекты, но пересекающиеся прозрачные треугольники [остаются нетривиальны](https://threejs.org/manual/pages/transparency.html).
7. **Жизненный цикл и ресурсы.** [Отрисовка по запросу](https://threejs.org/manual/pages/rendering-on-demand.html), приостановка скрытой карточки, лимит DPR, освобождение geometry/material/texture при смене этажа, bounded cache. Three.js требует [явного cleanup](https://threejs.org/manual/pages/cleanup.html); отдельная политика для нескольких карточек и потери контекста.
8. **Оставить Flat и векторный экспорт.** При недоступности WebGL2 или ошибке возвращаться в существующий Flat без изменения preference и конфигурации. Не тащить новый движок в начальную загрузку Flat. SVG/PDF сохраняют собственный read-only путь.

На первом этапе не нужны свободная камера, крыши, 3D-редактор, импорт тяжёлых интерьерных моделей, физический движок и серверный рендер. Настоящий 3D полезен и при фиксированной ортографической камере: «3D» определяется геометрией/рендерингом, а не возможностью летать по комнате.

## Сложность, риски и следующий шаг

| Блок промышленного этапа | Предварительно |
|---|---:|
| Контракт renderer, единицы, камера, кеш/worker, сетки | 3–5 дней |
| Проёмы, подвижные части, мебель и прозрачность | 3–5 дней |
| HTML-устройства, hits, повороты, touch и lifecycle | 3–5 дней |
| Существующий свет, заливки, подложки и темы | 2–4 дня |
| Регрессии View/киоск/редакторы, экспорт, замеры и слабые устройства | 4–6 дней |
| **Всего** | **15–25 инженерных дней** |

Оценка опирается на переиспользование существующих физических поверхностей, а не написание нового CAD. Её могут увеличить сложные пользовательские планы, прозрачность и обязательная поддержка WebGL1. Независимый режим свободного 3D или новые 3D-модели мебели в неё не входят.

Плюсы: меньше ручной борьбы с непрозрачными перекрытиями; устойчивый путь для сложных проёмов; общая камера; запас на много поверхностей; перспектива дальнейшего развития без увеличения SVG-дерева.

Минусы: новый графический backend и дополнительный bundle; зависимость от GPU/WebGL2; новая ответственность за контексты и память; текст остаётся отдельным слоем; прозрачность и свет не решаются автоматически; векторный экспорт надо сохранить параллельно. Если ограничиться только скоростью простого дома, текущий SVG может оказаться дешевле после адресных оптимизаций.

Предлагаемый следующий шаг после решения владельца: отдельная продуктовая задача на opt-in View backend с Three.js. До окончательного ТЗ выбрать один сложный дом и целевой слабый планшет, подтвердить желаемую прозрачность мебели и плитки устройств. Техническую базу MVP можно переиспользовать, но интеграционный слой и тесты ещё предстоит написать. Это исследование не меняет текущий режим и не включает такую задачу в реализацию автоматически.

## Запуск и доказательства

Из корня этой ветки:

```powershell
npm ci --prefix research/real-3d --ignore-scripts
npm run build --prefix research/real-3d
npm start --prefix research/real-3d
# http://127.0.0.1:8317
```

Только исследовательские зависимости установлены отдельно. Для повторения диагностики неизменённого продукта также нужны его обычные зависимости и `npm run bundle:sync`.

Фактически выполнено:

- Сборка MVP и reference probes — успешно; [размеры](evidence/sizes.json).
- `node research/real-3d/measure.mjs` — успешно: 8 конфигураций × 3 серии, [measurement.json](evidence/measurement.json). Камера 4 поворота, отсутствие кадров в простое, локальный state без structural build, cleanup проёмов, потеря WebGL-контекста — проверены.
- `node research/real-3d/product-probe.mjs` — успешно: неизменённые Flat/2.5D, камера действительно перемещалась, [product-probe.json](evidence/product-probe.json).
- `node research/real-3d/capture.mjs` — успешно: четыре поворота, 390px viewport, работа без внешних сетевых запросов; [capture-checks.json](evidence/capture-checks.json). Браузер всё ещё локально получает HTML/JS с исследовательского сервера.
- `node research/real-3d/inspect-competitors.mjs` — публичные наблюдения и ограничения доступа сохранены в [competitors-observed.json](evidence/competitors-observed.json).
- `npm run bundle:sync` — успешно, продуктовый source не менялся. Адресные `node --check` исследовательских модулей — успешно. Полный stable/beta-набор не запускался: продуктового изменения и выпуска нет.

Изображения в [галерее](review.html) просмотрены; они иллюстрируют исследование и не приняты за продуктовые golden-эталоны. Репозиторий продукта вне `research/real-3d/` не изменён. Исходный MVP можно удалить целиком без миграции данных и изменения поведения пользователей.
