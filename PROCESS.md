# Процесс разработки Houseplan

Это короткая инструкция для владельца и агентов по решениям [#1105](https://github.com/Matysh/houseplan-card/issues/1105).
Это единственное описание текущих правил процесса. Снимок решений: [process-next/decisions/1105.json](process-next/decisions/1105.json).
Исполняемая обвязка находится в `process-next/`; старые workflows, hooks и гейты перенесены в `legacy/process-v1/`.
Сведения о переключении и восстановлении — [CUTOVER.md](process-next/CUTOVER.md); фактически подключённые внешние сервисы и границы проверки — [отчёт подключения](process-next/evidence/cutover-status.md).
Сохранённая полезная автоматика перечислена в [AUTOMATION-PARITY.md](process-next/AUTOMATION-PARITY.md). Запуск обычной задачи не требует повторного разрешения на использование процесса; публикация версии начинается по отдельной команде владельца.
При расхождении с историческими ТЗ, отчётами или инструкциями внутри старых скриптов применять этот документ и последующие прямые решения владельца. Исторические результаты не становятся заданиями на повторный прогон.

## Как дорабатывать обвязку

**Сбой исправляем в самом механизме, а не обстраиваем новыми гейтами.**
Если нужен регрессионный тест, он проверяет конкретный дефект и запускается при изменении этого механизма.
Он не становится обязательным прогоном каждой продуктовой задачи. Баг сам по себе не основание для нового этапа,
сертификата, повторного Validate или ещё одного слоя проверок результатов предыдущих проверок.
При доработке сначала ищем упрощение: убрать лишнее состояние, объединить дублирующие действия, сократить передачу данных.
Эта инструкция — принцип проектирования; отдельной джобы для проверки соблюдения инструкции нет.

## Задача и трек

Задача живёт в GitHub issue; восемь статусов сохраняются:
S1 — новая → S2 — анализ → S3 — ТЗ → S4 — ревью ТЗ → S5 — готова → S6 — реализация и проверки → S7 — ревью кода → S8 — завершена.
Трек определяет нужные шаги; пропущенный шаг не изображаем выполненным.
`blocked` дополняет текущий статус, не заменяет его.

Установленный `track:ship/show/ask` определяет маршрут. Если метки нет, агент ставит её; если есть — работает с ней и не меняет.
Отсутствующую метку назначает исполнитель через команду `finish`. Координатор её не добавляет; S3/S4 без метки трактуются как ask.
Нет автоматического повышения трека, проверки авторства метки или требования повторно подтвердить ship.
Источник решения из чата можно сохранить как контекст, но отдельная запись не условие быстрого маршрута.

При отсутствии метки агент может сам выбрать ship, если одновременно выполняются четыре условия:

1. Один конкретный результат: одна простая правка интерфейса, перевода или локального участка кода.
2. Понятное решение: требования однозначны, не нужно проектировать новое поведение или выбирать архитектуру.
3. Простая проверка: нужное «до → после» непосредственно подтверждается глазами или короткой адресной проверкой в рамках принятого S6; документация сохраняет ноль прогонов.
4. Простой откат: отмена правки не требует восстановления данных или исправления пользовательских установок.

Отдельного ограничения по затронутым подсистемам нет: предложенное условие «ограниченное влияние» владелец исключил.
Количество строк/файлов само по себе не определяет трек. При сомнении в этих четырёх условиях агент первоначально выбирает show.
Это инструкция для выбора отсутствующей метки, без отдельной анкеты, джобы или гейта; установленный трек по ней не пересматривается.

Ship: короткое описание → реализация → очередь → короткие проверки S6 → merge → S8.
У него нет индивидуального ревью ТЗ/кода, нового формального ТЗ или лишних гейтов из-за старого WIP.
Для show достаточно конкретного ожидаемого результата; для ask автор готовит ТЗ по [шаблону](docs/process/SPEC-TEMPLATE.md) в разделе `## ТЗ` тела issue.
Ревью ТЗ — для ask; обычное код-ревью — для show/ask.

Цель от взятия до merge: ship около 10 минут, show 20–30 минут, ask около часа.
Сложная задача может занять до пары часов. Реальную ошибку не игнорируем ради срока.
Ожидание очереди видно отдельно; нулевое ожидание не обещаем.

## Где выполнять проверки

Основное место — подготовленный Ubuntu WSL, агент запускает обычную общую команду.
GitHub хранит задачу/очередь/ревью, выполняет merge и служит резервом исполнения при недоступности WSL.
В резерве те же определения наборов, версии и команды. Постоянный self-hosted runner не требуется.
Успех не повторяется только из-за перехода этапа, другого оформления отчёта или смены среды.
Реальный FAIL сначала разбирается; запуск в другом месте не способ скрыть его.
Временный понятный сбой допускает один адресный повтор. Поломка обвязки — прямой запуск или резерв с результатом.
Отсутствующее окружение, прерванный/неполный запуск и неожиданно пустая обязательная выборка не PASS.
«Проверки не требуются» — нормальный результат для чистой документации.

| Событие | Что выполняем | Что не добавляется автоматически |
|---|---|---|
| Продуктовая задача, S6 | Сборка с типами, критичные данные/права, один стартовый View smoke, малая выборка изменённой области | Полный product/tooling, бюджеты, golden, HA E2E, Validate |
| Инфраструктурная задача, S6 | Синтаксис/типы изменённых инструментов, поведенческие тесты затронутого механизма | Продуктовые тесты без объяснённого влияния, полный tooling |
| Чистая документация | Чтение/правка; для show/ask ревью текста | Любые тесты, build, lint, ссылки, Validate, включая косвенные hooks |
| S4 | Содержательное ревью ТЗ | Продуктовые проверки и механическая приёмка оформления |
| S7 | Ожидание ревьюера, затем содержательное ревью кода | Сборки, тесты, Validate, установка зависимостей, проверки реестров |
| Бета | Все быстрые поведенческие проверки продукта; фиксированные browser/golden/HA E2E; размеры и время | Повтор успешного набора без изменения входов; квота «30%» |
| Stable | Весь оставленный после ревизии набор; зачёт применимых результатов беты; backend coverage | Обязательный полный повтор уже проверенного кандидата |
| Hotfix | Короткий набор по дефекту и ревью; адресный HA E2E при необходимости | Обязательная бета или полный stable-набор |
| Фон | Мутации ночью, JS/TS coverage как диагностика | Блокирование обычной задачи этими результатами |

Сборка уже включает проверку типов. Подготовка `test-build` не требует второй продуктовой сборки.
Критичное ядро защищает сохранение/конфликты/устаревшие ответы, связи данных, права и безопасные действия.
Стартовый smoke проверяет готовый View непустого сохранённого дома, read-only и отсутствие необработанных ошибок.
Синтетический HA не подменяет серверные ACL/хранение; изменённому backend нужны соответствующие реальные проверки.
Один кейс выполняется один раз; цель продуктового минимума вместе с выборкой — до пяти минут в подготовленном WSL.
Это целевой бюджет, а не выдуманный замер всей новой обвязки.

## Очередь и завершение

Подготовка параллельна в отдельных ветках/worktrees. В очередь входим **до** финального rebase и проверок S6.
Лимитов числа задач по статусам или исполнителям нет. Единственное последовательное место — финальный участок очереди ниже.
Среди ожидающих готовые ship первые; внутри ship и остальных — порядок готовности.
Новый ship не прерывает допущенную задачу. Другие задачи не пишут в dev, пока слот занят.
В слоте: актуализировать dev при необходимости → свои проверки S6 → ревью, если требуется → merge → удалить рабочую ветку → S8.
При переходе в S8 после успешного слияния снимается `to_release`, если она есть. Это личная метка владельца: агенты её не ставят; процесс не использует её для запуска, допуска, выбора задачи или приоритета. Сбой записи повторяет только обновление меток.
Для ship после успеха S6 сразу merge; для чистой документации проверок нет.
S7 может ждать ревьюера; это видно как «ожидает ревьюера», затем «идёт код-ревью».
Отказ, конфликт или возврат ревью освобождает слот: правки параллельно, затем новый вход с сохранением применимых результатов.
Исполнитель использует одну команду `finish`: она показывает место в очереди, выполняет актуализацию и S6, передаёт на ревью и ждёт итог.
Ожидающий агент читает очередь раз в минуту и не обслуживает чужую задачу. Heartbeat продлевается отдельно, а не каждым опросом.
Если исполнитель пропал на актуализации/S6, допуск истекает и задача остаётся на S6 вне очереди; вернуться можно новой командой `finish`.
Одна и та же служебная ошибка не держит слот дольше 30 минут. Незавершённому ревью даётся один автоматический повтор, затем причина показывается и слот освобождается.
После устранения сбоя новый явный `finish` разрешает новый запрос ревью даже для того же кода. Дубли события и автоматическое продолжение такой попытки не создают; принятое ревью сохраняется при прежних входах.
Комментарий не меняет идентичность ревью ТЗ: новый раунд нужен при изменении отправленного материала в теле issue. Обсуждение остаётся контекстом.
Пустое обслуживание очереди ничего не записывает; завершённые записи и история ограничены. Шаблон расписания подхватывает пропущенные события.
Сбой API/комментария и истечение служебного lease не равны замечанию к коду: уже полученный отчёт сохраняется.
При чистом rebase неизменного diff содержательный результат ревью сохраняется; изменённый код требует нового ревью.
Повтор события не повторяет merge; сбой комментария не отменяет успешный merge; зависший обработчик не держит вечный lock.
Все записи в dev идут через один механизм. Сам выпуск очередь задачи не держит.
`dev` — интеграция, `dev-build` — быстрый стенд, `main` — стабильная линия.
После продуктового merge отдельная доставка обновляет dev-build; её сбой повторяет доставку и не отменяет завершённую задачу.
При настроенном HA webhook опубликованная сборка будит стенд. Сбой уведомления повторяет только HTTP-запрос, без пересборки.

Автор сохраняет `Issue: #номер` в коммите и короткую техническую запись в RU/EN changelog.
Классификация в текущем `docs/release-ledger/` нужна только продуктовым задачам. Чистые docs/infra не требуют записи и назначения пользовательского milestone; уже поставленный вручную milestone сохраняется.
После merge автоматика назначает пользовательский milestone для `major/stable-fix`; `infra/line-fix` в него не включает.
Цикл берётся из слитого коммита. Недостающую запись можно исправить позже в том же цикле: это видимое незавершённое оформление, без задержки merge и новых проверок. Отсутствующую классификацию перепроверяем при изменении dev; одинаковый результат не создаёт новые коммиты состояния и комментарии.
Комментарий о merge, milestone и публикация отчёта ревью восстанавливаются отдельно. Уже закрытой задаче S8 не возвращается.

## История задачи и служебные сообщения

Лента issue — последовательная история событий, а не редактируемая карточка текущего состояния.
Новый раунд ревью, исправление автора и восстановление после сбоя получают новые сообщения;
старые отчёты и статусные записи не переписываются. Актуальное ТЗ остаётся редактируемым в теле issue.
По прямому поручению владельца можно свернуть уже опубликованный отчёт без изменения
его содержания, вердикта, ссылок и порядка сообщений; это не новый раунд ревью.
Повтор доставки того же события не создаёт комментарий. Разные реальные попытки не склеиваются
из-за похожего текста: указываются раунд/вход в очередь, конкретная причина и ссылка на результат.

Сообщение объясняет, что произошло, **какой фактический статус и метки изменились**, почему и что дальше.
«S6 → S7» пишется после успешной смены меток; если она не состоялась, это явно отмечается.
При неизменном статусе пишем «статус остаётся S6». Исходный статус не выводится из трека.
Вердикт ревью и вызванный им возврат/переход — одно сообщение, а не отчёт и рядом общий дубль.
Перед повторной передачей исполнитель отдельным комментарием описывает исправления по замечаниям.
Свою работу описывает исполнитель; у каждого автоматического события один издатель.
Результаты ревью и события очереди публикует существующий последовательный координатор;
локальный `finish` не дублирует серверную публикацию. Выпуск и фон используют свои существующие издатели.
Комментарий о merge завершает ленту разработки: сначала публикуются относящиеся
к завершению отчёты ревью, затем итог слияния. Сбой доставки задерживает только
комментарий об итоге, а не само слияние. Позднейшие события выпуска и доставки
могут создавать свои сообщения.

Завершённый раунд сохраняется и после изменения ТЗ/кода или перехода задачи дальше.
При задержанной доставке указываются время события, материал и более поздний результат, если он есть;
поздний комментарий не откатывает текущий статус. GitHub не позволяет вставить запись задним числом.
Сбой сообщения не отменяет merge и не повторяет тесты или модель: восстанавливается только оформление.
Опросы, heartbeat и проценты остаются в окне прогресса/логе, без комментария на каждый шаг.
[Шаблоны сообщений](docs/process/SERVICE-COMMENTS.md) помогают исполнителю и описывают стиль автоматики;
это варианты для произошедших событий, не новый обязательный набор этапов или гейтов.

## ТЗ и ревью

Полное ТЗ хранится в теле issue: снаружи остаются `## ТЗ` и короткое описание цели,
разделы шаблона — внутри закрытого по умолчанию `<details>` с понятным `<summary>`.
Пустые строки отделяют HTML-теги от Markdown. Содержание не заменяется ссылкой или
вложением: исполнитель, проверка формы и ревьюер получают все разделы из тела issue.

Раунд ревью ТЗ — содержательное рассмотрение одной редакции отправленного тела issue,
включая ТЗ и контекст исполнителя. Первая редакция получает раунд 1; новая — следующий номер.
Технический повтор того же запроса остаётся попыткой того же раунда; повтор публикации не создаёт раунд.
Штатный путь исправлений: получить результат S4 → вернуться на S3 → изменить ТЗ и оставить
комментарий «замечание → исправление» → передать новую редакцию на S4.
Пока идёт S4, исполнитель не редактирует уже отправленный материал в обычном ходе работы.
Если владелец или исполнитель всё же изменил тело issue во время S4, действующее поведение сохраняется:
при следующей обработке нового материала начинается раунд N+1, а прежний запрос и его результат не стираются.
В истории отдельно поясняется, что материал изменён во время предыдущего раунда.
Это обработка исключения, без запрета редактирования через права, дополнительного гейта или нового триггера.

Автор до S4 проверяет существующий шаблон ТЗ: разделы, заполнение, поведение до/после, нумерованные AC.
`checkSpecFormat` проверяет форму, а не качество требований. Это не проверка каждой документационной задачи.
Независимая новая сессия ревью получает требования/решения владельца, base/head, связанные исходники/тесты,
результаты S6 и прошлый раунд. История доступна через diff/show/log/blame, определения и вызовы — через поиск.
Ревьюер разбирает логику и окружение, риски ошибок, читаемость, сложность, сопровождение и разумные альтернативы.
Результаты ревью ТЗ и код-ревью оформляются на русском языке: выводы, замечания,
обоснования, альтернативы и границы анализа, включая заголовки отдельных найденных дефектов.
Язык исходников и контекста исполнителя этого не меняет. Код, идентификаторы, пути,
служебные поля/значения JSON и дословные цитаты сохраняются без перевода.
Замечание содержит условие, последствие, место и направление исправления; улучшения отделены от блокеров.
Полезные комментарии объясняют неочевидную причину/контракт. Нет квоты замечаний, обязательного рефакторинга или сокращения строк.
Отчёт подробно объясняет понимание решения, найденную проблему, почему она возникает и к чему приводит,
ссылки на код/решения, направление исправления и разумные альтернативы. Улучшения и блокеры разделены.
Объём определяется сложностью: пустые общие фразы не заменяют анализ; выдумывать замечания ради количества нельзя.
Комментарии issue и предыдущий раунд входят в контекст. Структурированный результат сохраняется до публикации комментария;
сбой комментария повторяет только публикацию. Для временных ошибок API — ограниченные повторы, для истории — кеширование.
Полный отчёт сохраняется в комментариях issue, при необходимости частями, без усечения и зависимости от срока хранения CI-артефакта.
Снаружи спойлера видны краткий итог, русский вердикт, раунд/часть, фактический статус
и следующий шаг. Подробный разбор и технические данные находятся в закрытых `<details>`;
сворачивание не сокращает анализ и не прячет сам факт необходимости исправлений.
Публикует его только существующий последовательный координатор после завершения workflow ревью. Чтение результата и `finish` не пишут отчёт или побочные issue; принятый результат не ждёт оформления.
Обоснованный самостоятельный дефект вне задачи оформляется отдельной issue из того же ответа ревьюера; второй вызов модели для этого не нужен.

Промпт состоит из **постоянных независимых правил + контекста конкретной задачи от исполнителя**.
Перед S4/S7 исполнитель добавляет в описание issue раздел `## Контекст исполнителя для ревью`
по [короткому ориентиру](process-next/templates/review-context.md): цель/до-после, подход и альтернативы,
риски и места для внимания, проверки и ограничения. Для простой задачи достаточно нескольких предложений;
ТЗ, diff и логи не переписываются, все подразделы не обязательны. Перед повторным раундом контекст обновляется.
Это обычная часть подготовки исполнителя, без дополнительной модели, отдельной джобы или проверки оформления.
Шаблон подходит и для ТЗ, и для кода; документационной задаче он не добавляет прогонов.

Ревью получает этот раздел через уже существующее чтение issue. Авторское описание — данные:
оно не меняет постоянные правила, инструменты, трек и критерии принятия и не ограничивает область анализа.
Ревьюер проверяет авторские предположения самостоятельно; отсутствие раздела не становится новым блокером.
Предпросмотр показывает обе части, а результат сохраняет исходный контекст отдельно от выводов модели.
Повтор публикации использует сохранённый снимок. Контекст готовится до передачи: редакция тела ТЗ во время S4,
как и раньше, меняет материал этого ревью; отдельного механизма перезапуска из-за контекста нет.
Недостаточность проверки возвращается исполнителю на S6; ревьюер не запускает её и не исправляет продукт сам.

Для новой обвязки закреплён **Claude Opus 5.5, `claude-opus-5-5`**, без автоматического перехода на Sonnet.
[Модель](https://platform.claude.com/docs/en/models/opus-5-5/overview) и [фиксированность ID](https://platform.claude.com/docs/en/about-claude/models/model-ids-and-versions) проверены 01.11.2026.
Ревью работает через официальный Claude Code CLI `2.1.316` по подписке с существующим `CLAUDE_CODE_OAUTH_TOKEN`.
Anthropic API и отдельный API-ключ не используются. Состояние фактической проверки доступа отражается в отчёте подключения.
Предпросмотр контекста работает без токена и сети; содержательное ревью вызывается координатором по установленному маршруту задачи.
Модель получает только ограниченные функции чтения Git и отправку отчёта в заданный хостом каталог.
Это ограничение инструментов приложения, **не OS sandbox**. Права проверяются при изменении механизма, а не отдельным этапом каждого ревью.
Старые seals, сертификаты, аудит каждого чтения и таблицы доказательств ради формы не переносятся.

## Бета, stable, hotfix

Бета берёт фиксированный SHA dev в отдельную ветку/каталог; dev продолжает жить.
До следующей успешной беты сохраняется ветка последней опубликованной; неудачный кандидат её не удаляет.
Во время прогона материал не меняется. Независимые группы завершаются даже после первого отказа.
После сводки: разбор → исправление → новый кандидат → упавшие и связанные проверки.
Продуктовый фикс проходит короткое независимое ревью; новые задачи dev не подмешиваются в кандидат.
Исправления выпуска возвращаются в dev через общую очередь слиянием точного опубликованного тега.
Для чистого автоматического слияния уже опубликованного кода достаточно S6 результата слияния; второго платного ревью нет.
Если Git не поддерживает доказательство такого слияния или оно не удалось, зачёт не применяется и действует обычное ревью по треку; сама актуализация из-за этого не блокируется.
Ручное разрешение конфликтов или дополнительные изменения требуют обычного ревью по треку.
Это сохраняет историю stable/hotfix: cherry-pick и rebase ветки возврата не используются. Stable строится из выбранной беты, а не свежего dev.
Успехи применимы при неизменных значимых входах; недостающие/затронутые проверки дополняются.
Смена только номера beta → stable не отменяет проверки поведения. Сборка, ZIP и проверка обновления версии выполняются для новой версии.
Готовность выпуска читается из одного завершённого отчёта запускателя для зафиксированного кандидата; второй таблицы результатов нет.
Backend coverage собирается в том же запланированном запуске беты, порог проверяется только на stable.
JS/TS coverage диагностический, без порога. Отсутствующий замер не изображаем отчётом.
Hotfix начинается от stable; при уже готовящемся выпуске владелец останавливает его и включает исправление в новый кандидат.
После beta/stable коротко подтверждаем доступность в публичном источнике обновлений HACS и правильный скачиваемый ZIP.
Для беты проверяется первая опубликованная prerelease, для stable/hotfix — latest stable. Это тот же уровень проверки,
который был в прежнем выпуске; он не утверждает, что конкретная установка HA уже обновила свой кеш.
Чтение настоящей установки HACS возможно отдельно при явной настройке, но новые доступы к HA для обычного выпуска не нужны.
Сбой сети/кеша повторяет доставку или её проверку, а не продуктовые тесты.

Перед проверками выпуска исполнитель пишет тексты изменений и вызывает `release prepare`: команда согласует версии и переносит авторский текст в notes.
RU/EN технические changelog получают раздел выпуска; пользовательские RU/EN для stable/hotfix описывают итог относительно предыдущего stable, без технического мусора и повторов промежуточных бет.
Автоматика переносит этот текст в GitHub Release и Telegram, а не сочиняет его вместо автора.
Состав выпуска определяется коммитами кандидата и сохранёнными фактами очереди, а не всеми живыми задачами с S8.
Публикуются проверенный `houseplan.zip`, отдельный `houseplan-card.js`, состав выпуска и SHA256SUMS; тег аннотированный.

Команда `release publish` публикует готовые файлы и завершает выпуск: подтверждение публичной доставки → комментарии со ссылками и закрытие вошедших S8 со снятием статусных меток → анонс stable/hotfix в Telegram → очистка прежней beta-ветки → возврат опубликованных исправлений в dev. Беты в Telegram не анонсируются. Анонс уже доступного обновления не ждёт внутренней очереди возврата.
Если Telegram-секреты находятся только в GitHub, локальная команда оставляет явный pending анонса. Исполнитель продолжает
тот же опубликованный кандидат через ручной workflow `process-next-release-complete.yml`: это вызов существующего `complete`,
без повторной публикации и тестов выпуска. Нового разрешения на уже порученный выпуск не требуется. Если возврат истории ещё нужен,
его короткий S6 выполняется существующим GitHub-резервом; обычный локальный возврат сохраняет WSL.
Выпуск ведёт один агент; повтор `publish/complete` запускается после завершения предыдущего вызова.
Возврат использует одну служебную задачу в общей очереди; она автоматически доходит через S6 до merge и закрывается. Конфликт или замечание требует исправления исполнителем.
Прежняя beta-ветка удаляется только если её SHA не изменился; последняя сохраняется. Незавершённое оформление видно отдельно от уже состоявшейся публикации.
`release complete` повторяет только оставшиеся действия: тесты, сборка, платное ревью и публикация заново не запускаются. Исключение — собственный короткий S6 ещё не слитого возврата в dev.
Если Telegram мог принять сообщение, но ответ потерялся, сначала проверяем доставку; автоматический повтор не создаёт дубликат.

## E2E, визуальные проверки и конвертеры

После задачи автор сохраняет «надо/не надо» с причиной в `Matysh/houseplan-e2e`, с поиском по исходной issue.
Если надо — сценарий/ожидаемое изменение и ссылка; для состава беты собирается список, правки отмечаются выполненными.
Реальные HA E2E дорабатываются перед бетой, быстрые unit/fake-hass smoke — в самой задаче.
Для hotfix короткий воспроизводящий случай сразу; остальное записывается на следующую бету.
Не менять ожидания просто ради зелёного: намеренное изменение связывается с требованиями, необъяснённый отказ разбирается.
Фиксированная бета: **13 HA E2E случаев в 7 группах, 75 визуальных сцен, 13 browser файлов в 9 группах**.
Основные кадры View, редакторов, диалогов, устройств, света и геометрии снимаются через настоящую панель `/houseplan`.
Размещение: 61 сцена панели, 13 карточных и одна Static. Карточный набор — три проверки самого встраивания
(обычный View, узкий повёрнутый View, редактор плана) и десять специальных fixtures первого запуска, батареек,
resize/offline/тревог, чьи условия пока зависят от карточного API. Их не выдаём за проверку панели; полную матрицу не дублируем.
Проверяем обычную узкую панель отдельно от kiosk. У новых панельных вариантов свои ID и эталоны: карточные PNG им не подходят.
Переключение обвязки не принимает новые панельные эталоны автоматически;
отсутствие эталона остаётся видимым незавершённым результатом.
Точные селекторы и назначения лежат в общем определении наборов; отдельной копии списка команд здесь нет.
Golden на задаче адресный; на stable весь осмысленный оставленный набор с зачётом беты, без массового принятия эталонов.
После просмотра владелец может принять явно перечисленные кадры командой `golden-accept`; обновляются только выбранные PNG и их происхождение.
Перенесённые на панель сцены заменяют прежние варианты карточки и в остатке stable, а не добавляют полный второй проход.
Внешние конвертеры — отдельный продукт. Перед stable их проверка обязательна, но диагностическая и не блокирует Houseplan.
Их отказ оформляется отдельно. Защита собственного импорта Houseplan от повреждённых данных остаётся продуктовой.

## Размеры и производительность

На обычной задаче обязательного бюджетного замера нет; оптимизация измеряет свою область по необходимости.
Перед бетой сравниваем с последним stable, а фиксированный v1.83.1 показываем только для накопленной диагностики.
Пауза публикации только при подтверждённом `delta > max(reference × fraction, absolute)`:

| Метрика | Процент | Абсолютный допуск |
|---|---:|---:|
| Готовый ZIP | 5% | 32 КиБ |
| Весь frontend, gzip | 5% | 16 КиБ |
| Начальная загрузка View, gzip | 5% | 8 КиБ |
| Первый устойчивый кадр | 10% | 50 мс |
| Смена этажа | 10% | 75 мс |
| Один wheel-шаг масштаба (`panZoomMs`) | 10% | 5 мс |
| Обновление состояния | 10% | 15 мс |

Для времени сравниваются медианы сопоставимых серий. Один шаг масштаба не означает FPS или всю серию перемещений.
Модули, прочие микрозамеры и накопление относительно v1.83.1 не блокируют. Нет данных — явно «нет данных».
Отсутствующая база, разные условия и неподтверждённый шум не блокируют публикацию. Это неполная диагностика, а не зелёное сравнение.
На каждом stable автоматически делаем и сохраняем диагностический замер как `measurement.json` в выпуске — база следующей беты.
Отсутствие данных или сбой этого диагностического сохранения видны в отчёте, но stable не отменяют. v1.83.1 не переизмеряем.
Сначала полный отчёт, затем владелец принимает превышение, требует оптимизацию или принимает с задачей.
Повторно разрешать тот же кандидат не требуется; dev продолжает работу, оптимизация повторяет затронутое.

## Команды и результаты

Общая точка входа: `node process-next/cli.mjs --help`. Примеры из подготовленного WSL:

```sh
node process-next/cli.mjs plan --event task --issue 1105 --track show --layer infra --changed-file process-next/lib/e2e.mjs --area-test process-next/test/e2e.test.mjs
node process-next/cli.mjs run --event task --issue 1105 --track show --layer infra --changed-file process-next/lib/e2e.mjs --area-test process-next/test/e2e.test.mjs
node process-next/cli.mjs run --event task --issue 1234 --track ship --layer product --area-test test/config-write-conflict.test.mjs
node process-next/cli.mjs plan --event beta --request release.json
node process-next/cli.mjs run --event beta --request release.json
node process-next/cli.mjs release prepare --request release.json
node process-next/cli.mjs run --event mutation --mutation-shard 1/5
node process-next/cli.mjs review preview --base BASE_SHA --head HEAD_SHA --issue 1234 --task-file task.md
# Завершение порученной задачи; GH_TOKEN задаётся безопасно через окружение:
HP_PROCESS_NEXT_ACTIVATE=1 node process-next/cli.mjs finish --config process-next/config.json --issue 1234 --request task.json --execute
HP_PROCESS_NEXT_ACTIVATE=1 node process-next/cli.mjs status --config process-next/config.json --issue 1234 --execute
# Публикация только по команде владельца:
HP_PROCESS_NEXT_ACTIVATE=1 node process-next/cli.mjs release publish --config process-next/config.json --request publication.json --execute
HP_PROCESS_NEXT_ACTIVATE=1 node process-next/cli.mjs release complete --config process-next/config.json --request publication.json --execute
# Только после просмотра и решения владельца; без --execute — предпросмотр:
node process-next/cli.mjs golden-accept --scenes=panel-example --report=artifacts/process-next/golden-beta/golden-report.json --decision=OWNER_DECISION_REFERENCE
```

`release.json`: версия/название выпуска, `e2eRoot`, `workRoot`, точный `upgradeFrom`, закреплённый `haVersion`; `metricsRequest` передаёт доступную базу и условия измерения.
Кандидат по умолчанию упаковывается из готовой сборки в `artifacts/process-next/candidate`; tracked frontend не переписывается.
При внешнем готовом кандидате указываются `candidateRoot` и `expectedVersion`; названием выпуска нельзя подменять его байты.
В `metricsRequest` — путь к измерению последнего stable и наблюдённые условия питания/машины; секреты в JSON не хранятся.
Мутации запускаются отдельной фоновой командой с явно выбранным шардом `i/n`, например `1/5`. Workflow `process-next-background.yml` задаёт ночную ротацию пяти частей и отдельную диагностику JS/TS coverage; отказ мутаций создаёт или дополняет одну issue.
Предпросмотр ничего не выполняет. В обычном процессе модельное ревью вызывает координатор; отдельный `review run` предназначен для явно порученного прямого запуска. `spec-check --file ТЗ.md` выполняет автор до S4.
Для видимого окна из PowerShell: `.\process-next\open-wsl.ps1 -Repo /home/matysh/houseplan -Request C:\work\request.json`.
Окно открывает Ubuntu, запускает тот же CLI и оставляет итог до Enter.

Результаты Node-групп переиспользуются по зависимостям; браузерный набор зависит от всей карточки, поэтому его reuse пока консервативный.
Кеш по умолчанию общий для worktree одного Git checkout: `git-common-dir/process-next`. Отдельные клоны требуют явно общего `--state-dir`.
Отчёты backend coverage и golden сохраняются с успешным результатом и восстанавливаются в новом worktree при тех же входах; сборки/ZIP не восстанавливаются.
Изменение продуктовых исходников может повторить браузерные кейсы; это ограничение текущего кеша, а не обещанная точность по каждой функции.
Проверки самой новой обвязки не доказывают прохождение целого продуктового, beta или stable набора.
Локальные тесты обвязки не заменяют проверку доступов к HA E2E и Claude Code; фактический объём проверки подключения отражён отдельно.
HA-адаптер требует подготовленные зависимости E2E/Chromium, Docker и отдельный каталог лабораторий; пользовательский `HA_URL` не принимается.
Он копирует нужные E2E-файлы, сверяет точные сценарии через `--list`, создаёт собственный seed/контейнер и удаляет только свой контейнер.
Три HA-среды последовательны, но отказ одной не отменяет независимые остальные; пустой остаток stable явно «не требуется».
Отчёты и собственные каталоги лабораторий сохраняются для разбора; старый E2E checkout и пользовательский HA не очищаются.

CI-резерв — workflow `.github/workflows/process-next-fallback.yml`; определения наборов общие с локальным запуском.
`finish --s6 github` выполняет тот же S6 на допущенном SHA и забирает фактический отчёт. Локальный набор при этом не запускается.
У ожидания/повторов транспорта есть предел; отказ подготовки освобождает слот с объяснением. Падение теста не маскируется переносом в другую среду.
Для beta/stable запрос дополнительно содержит `e2eCommit` — полный SHA `Matysh/houseplan-e2e`; зависимости ставятся без hooks.
`metricsRequest` и указанный в нём `latestStable` — относительные файлы кандидата; необязательный `measurementsCommit` берёт оба из отдельного закреплённого SHA `Matysh/houseplan-card`.
Замер запускается перед бетой и автоматически на каждом stable; отсутствие файла предыдущего замера не мешает запуску.
Подготовитель заменяет WSL-пути на каталоги CI и записывает фактические CPU/kernel. JSON не вставляется в shell-код.
Для времени нужен замер последнего stable в сопоставимом CI-окружении; WSL-замер его не заменяет. Фиксированный v1.83.1 остаётся только диагностикой.
Несопоставимость остаётся в отчёте без блокировки. `previous_run` позволяет взять сохранённые результаты CI; запускатель сам определяет применимость по входам и среде.
В артефакты CI попадают отчёты E2E, но не каталоги HA с авторизацией; OAuth-токен Claude Code хранится отдельно в GitHub Actions secrets.

Новая обвязка не вызывает старый полный Validate по умолчанию и не меняет labels/dev от одного предпросмотра.
Устройство переключения и возврата описано в [process-next/CUTOVER.md](process-next/CUTOVER.md); старые маршруты в `legacy/process-v1/` не запускаются вместе с новыми.
В видимом окне Ubuntu показываются название стадии и фактически выполненные элементы/общее число.
Проценты вычисляются из реальной завершённости; очередь, загрузка, установка и работа модели не получают выдуманного процента.
Сводка различает успех, отказ, прерывание, отсутствие данных и «не требуются»; хранит команды и ссылки на результаты.
Конкретные файлы ревизии и технические проверки новой обвязки — работа реализации, не новая процедура одобрения владельцем.
