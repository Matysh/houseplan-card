# Разработка: технический справочник

Правила работы, статусы, треки, наборы проверок и выпуск описаны только в
[PROCESS.md](../PROCESS.md). Этот документ объясняет устройство рабочего
окружения и артефактов, не добавляя этапов процесса.

Исполняемая обвязка находится в `process-next/`; прежние workflows, hooks и
гейты — в `legacy/process-v1/`. Их не устанавливают в рабочий checkout.
Устройство подключения и восстановления: [CUTOVER.md](../process-next/CUTOVER.md).

Плашка **CI** в README показывает подтверждённый результат тестов продукта,
находящегося в `main`; подробности и исходный прогон доступны по ссылке плашки.
Она использует уже выполненный набор опубликованного stable/hotfix, если продукт
в `main` ему соответствует. Для исходного `v1.83.1` сохранены адреса исторического
прогона и его обязательных шагов; их успех проверяется по GitHub, а не задаётся
вручную. При отсутствии доказательства или несовпадении продукта статус остаётся
неподтверждённым. Обновление плашки не запускает тесты и не добавляет гейтов;
CodeQL показывается отдельно.

## Окружение

Основная среда прогонов — Ubuntu WSL/Linux. Версии берём из `.nvmrc` (Node 22)
и `.python-version` (Python 3.14), зависимости — из lockfile и
`tests_backend/requirements.txt`. Расхождение окружений особенно заметно в
снимках Chromium и замерах производительности.

Для подготовки отдельного checkout:

```bash
npm ci
npx playwright install chromium
python3 -m venv .venv
source .venv/bin/activate
python3 -m pip install -r tests_backend/requirements.txt pytest-cov
```

Python и HA-зависимости нужны только наборам, которые их используют. Среда
должна предоставлять этот Python как `python3`. Установка зависимостей не
устанавливает процессные Git hooks. Эти команды подготовки не являются
проверками документационной задачи.

## Сборка и локальное приложение

`npm run build` выполняет проверку типов и Rollup; повторный `typecheck` рядом
с ним не требуется. `dist/` содержит генерируемые entry, manifest и chunks.
`npm run bundle:sync` включает сборку и готовит копию для demo. Если сборка уже
свежая, достаточно `node scripts/bundle-sync.mjs`, без повторного build. Устройство стенда:
[demo/stand/README.md](../demo/stand/README.md).

Единственный отслеживаемый снимок frontend установленной интеграции находится
в `custom_components/houseplan/frontend/`. Обычная задача не обновляет его
попутно. Подготовленная упаковка кандидата пишет результат в
`artifacts/process-next/candidate`; источник и готовый пакет — разные вещи.

Node-тесты, импортирующие `test-build/`, требуют свежей компиляции. Запускатель
сам выполняет `process-next/catalog/prepare.mjs tests`, а затем выбранные
тесты; старый каталог от другой ветки не доказывает результат текущего кода.
Технические условия разных наборов: [TESTING.md](TESTING.md).

## Команды процесса

Справка команд находится в `process-next/cli.mjs`; определения наборов — в
[каталоге](../process-next/catalog/README.md). Например, план выбранной задачи:

```bash
node process-next/cli.mjs plan --event task --issue 9999 --track show --layer product --area-test test/version-recovery.test.mjs
```

`plan` только показывает состав. `run` выполняет этот состав, `status --run-id ID`
показывает сохранённый результат. Для исправлений после ревью используется
`--phase after-review`. Выпуск передаётся через `--event beta` или `stable`,
`--version` и `--request` с параметрами кандидата. Поля запросов перечислены
в справке `process-next/cli.mjs`; не копировать фиктивные номера и пути без адаптации.

Отчёт различает реально выполненные, повторно использованные, упавшие и
недоступные шаги. Повторное использование имеет ссылку на исходный результат;
оно не объявляется новым исполнением. Состояние запускателя и его локальные
результаты не являются пользовательскими данными Houseplan.

До `finish` сохрани правки коммитом и опубликуй рабочую ветку задачи в origin.
Прямой push рабочей ветки не является слиянием в dev. Затем используй `finish`
с общим конфигом:

```bash
HP_PROCESS_NEXT_ACTIVATE=1 node process-next/cli.mjs finish --config process-next/config.json --issue 9999 --request task.json --execute
```

`task.json` содержит слой задачи, трек и адресную выборку из `plan`; текущая
ветка — рабочая ветка задачи. Например, после выбора адресного теста:

```json
{"event":"task","track":"show","layer":"product","areaTests":["test/version-recovery.test.mjs"]}
```

Трек и тест здесь заменяются фактическими для задачи; это не шаблон обязательного
теста каждой правки. Чистая документация использует `layer: "docs"` без тестов.
GitHub-токен поступает через `GH_TOKEN`, а не
через JSON или аргумент команды. Если используется GitHub CLI, можно задать
его в текущем shell через `export GH_TOKEN="$(gh auth token)"`; значение не
печатать и не сохранять в файлах. `HP_PROCESS_NEXT_ACTIVATE=1` разрешает
удалённые действия конкретной команды, а `--execute` отличает её от плана.

После `finish` не нужно отдельно запускать полный `npm test`, Validate или
повторять проверки в CI. При недоступности WSL тот же `finish --s6 github`
использует резервный workflow. Команды `queue` и `release ACTION --payload`
для локального draft-состояния не подменяют удалённую очередь.
Публикация версии выполняется по отдельной команде владельца. Токены не кладём
в request JSON, аргументы команд или отчёты.

## Доступы для завершения выпуска

Перед публикацией беты `release publish` автоматически выполняет пакетное ревью
непроверенных или изменённых ship-задач кандидата. Принятые неизменные результаты
засчитываются; повтор доставки отчёта не вызывает модель снова. Чтобы получить
отчёт раньше публикации, используй тот же запрос с ID кандидата:

```bash
HP_PROCESS_NEXT_ACTIVATE=1 node process-next/cli.mjs release review --config process-next/config.json --request publication.json --execute
```

Команду можно выполнять параллельно тестам того же кандидата: она сохраняет
контекст ревью, не меняя проверяемый SHA и состояние текущего прогона.
Это содержательное ревью через существующий Claude Code OAuth в GitHub, а не
запуск тестов или отдельный маршрут завершения ship. Состав, результат и полный
русский отчёт сохраняются в состоянии выпуска; подробности свёрнуты в сводке
Actions, а `SHIP-REVIEW.md` и `SHIP-REVIEW.json` входят в артефакты выпуска.
High останавливает публикацию беты, Medium/Low остаются неблокирующими.
Незавершённый анализ не запускается заново автоматически: сообщение даёт ссылку
на проблемный прогон. После повтора failed jobs в Actions следующая команда
`release review/publish` прочитает новый результат того же запроса.
Stable использует результат исходной беты; завершение уже опубликованного
выпуска не запускает это ревью повторно. Полные правила — в PROCESS.

Публичная проверка доставки использует GitHub release feed и скачанный ZIP:
новые URL или токен пользовательского HA для неё не нужны. Реальное наблюдение
отдельной установки HACS — необязательный режим `hacs.mode: "instance"` с
явными `HA_URL`/`HA_TOKEN`; публичная проверка не выдаётся за такое наблюдение.

`release publish/complete` выполняет Telegram локально, только если
`TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` есть в его окружении. В GitHub эти
секреты уже используются; читать их значения обратно на локальную машину нельзя.
Если локальный выпуск оставил анонс pending, после завершения локальной команды
исполнитель один раз запускает продолжение с ID того же опубликованного кандидата:

```bash
gh workflow run process-next-release-complete.yml --ref dev -f candidate=ID_КАНДИДАТА
```

Workflow вызывает тот же `complete-release` с существующими GitHub-секретами.
Он ничего не публикует заново; завершённые действия и подтверждённая отправка
не повторяются. При необходимости возврата в dev он использует существующий
S6 fallback. Не запускай локальный и hosted `complete` одного кандидата одновременно.

## Установка и идентичность сборки

HACS устанавливает артефакт опубликованного релиза. Ветка `dev-build` служит
отдельной быстрой доставкой интеграции на стенд. `DEV-BUILD.json` содержит
`source` и `integrationTree` — идентичность источника и дерева интеграции.
По ним отличают проверяемый код от того, что действительно доставлено.
Версия интерфейса сама по себе не доказывает доставку нужного коммита.

Необязательный `custom_components/houseplan/BUILD.json` описывает dev-identity
(`schema`, `channel`, `source`); dev-версия может иметь суффикс `+dev.<sha8>`.
Для публичного релиза эти признаки не подменяют его версию и опубликованный ZIP.

`scripts/ha-track-dev.sh` — POSIX-скрипт доставки `dev-build` на явно выбранный
HA. Ему нужны `curl` и `tar`; прежняя установка сохраняется в
`/config/houseplan-dev-prev`. Polling и кэш источника могут давать задержку.
Изменять пользовательскую установку можно только в рамках порученной доставки.
Регистрация ресурсов, совместимость конфигурации и восстановление версии:
[CONFIG-COMPATIBILITY.md](CONFIG-COMPATIBILITY.md),
[ARCHITECTURE.md](ARCHITECTURE.md), [руководство](USER-GUIDE.ru.md).
