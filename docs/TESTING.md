# Проверки Houseplan: технический справочник

Когда и что запускать, определяет только [PROCESS.md](../PROCESS.md).
Здесь описаны типы проверок, их входы и границы результата. Локальный и
резервный запуск используют общие определения наборов из `process-next/`.
**Для чистой документации нет прогонов, сборок, линтеров и валидаторов.**

## Какие проверки существуют

| Семейство | Что наблюдает | Что требуется |
|---|---|---|
| Node unit (`test/*.test.mjs`) | Логику, геометрию, преобразования, модели и отдельные механизмы | Node из `.nvmrc`; для импортов из `test-build/` — подготовка модулей |
| Backend (`tests_backend/`) | Валидацию, хранение, права, API, миграции и lifecycle интеграции | Python из `.python-version`, зависимости backend; HA harness для интеграционных случаев |
| Browser smoke (`demo/smoke_*.mjs`) | Ввод, DOM, переходы, рендер и взаимодействие компонентов | Собранный frontend, demo fixture, закреплённый Playwright/Chromium |
| Golden (`demo/golden/`) | Кадр и его семантические условия относительно принятого эталона | Те же входы сцены и среда рендера; осмысленный эталон |
| HA E2E | Установку, открытие, сохранение, права, команды и обновление в настоящем HA | Отдельный HA E2E checkout, доступное тестовое окружение, пакет кандидата |
| Размеры и производительность | Размер доставляемых частей и время заданных пользовательских действий | Сопоставимая сборка, фиксированная сцена и одинаковые условия замера |
| Покрытие | Какие участки кода исполнялись во время тестов | Инструментирование запланированного прогона; само по себе не доказывает корректность |
| Мутации | Способен ли тест заметить конкретную искусственно внесённую поломку | Отдельная фоновая среда и явная часть реестра |
| Обвязка (`process-next/test/` и адресные tooling-тесты) | Запуск, очередь, сохранение результатов и доставку | Среда затронутого механизма; не полный набор продукта |

Один параметризованный сценарий может выполнять несколько тест-кейсов.
Число файлов, сценариев и реально исполненных кейсов — разные величины.
Актуальный состав находится в [каталоге](../process-next/catalog/README.md),
`process-next/catalog/inventory.json` и `selections.mjs`; исторические счётчики
в документах не являются квотой или основанием для запуска.

## Окружение и запуск

[DEVELOPMENT.md](DEVELOPMENT.md) содержит установку зависимостей и устройство
артефактов. Основной путь — Ubuntu WSL/Linux; резерв GitHub использует тот же
описанный набор. Windows подходит для редактирования и совместимых отдельных
инструментов, но снимок другой ОС или другой версии Chromium не считается
эквивалентным эталону Linux. Подмена браузера или расширение допуска не лечит
ошибку окружения.

Выборка задаётся запускателю, например:

```bash
node process-next/cli.mjs plan --event task --issue 9999 --track show --layer product --area-test test/version-recovery.test.mjs
node process-next/cli.mjs run --event task --issue 9999 --track show --layer product --area-test test/version-recovery.test.mjs
node process-next/cli.mjs status --run-id ID
```

Это пример интерфейса запускателя, не требование запускать его при
чтении или правке документации. Порядок допуска задачи и передачи на ревью —
в PROCESS.md. Новое изменение теста или запускаемого инструмента является
изменением этого механизма, а не чистой документацией.

Для backend нужен `python3` из подготовленного окружения и
`tests_backend/requirements.txt` вместе с `pytest-cov`. Без HA зависимостей
`tests_backend/conftest.py` исключает `test_ha_*.py` из collection: такой зелёный
pytest **не означает прохождения HA-набора**. Backend runner
проверяет доступность harness до запуска. Он сохраняет coverage XML вместе с
запланированными backend-тестами; порог используется только перед stable.
Частичный локальный backend-набор задачи выполняется без сбора coverage.

Запускатель готовит сборку/`test-build/` один раз для зависимых шагов. Не нужно
добавлять вокруг него старый `local:gate`, полный `npm test` или второй CI.
Сборка уже содержит TypeScript-проверку. S7 не запускает тесты и механику.

## Что делает тест осмысленным

Наблюдаем поведение, а не повторяем реализацию в ассерте. Наличие класса или
DOM-узла полезно для диагностики, но само не доказывает отрисовку, доступность
действия или сохранение данных. Фикстура должна содержать защищаемые слои:
тест света без достижимого окна или кадр пустой сцены не проверяют нужный эффект.

Golden-сцена содержит семантические условия, чтобы пустой или неверный кадр не
стал хорошим эталоном лишь потому, что совпал с другим пустым кадром. Обычные
отрицательные входы проверяют неизменённую реализацию. Мутационная оценка её
чувствительности живёт отдельно в фоне; регистрация мутанта и успешный обычный
тест не являются доказательством его поимки.

Нулевой выбранный набор, совпадение `--test-name-pattern` без выполненных кейсов,
ошибка сборки/collection, недоступный браузер, timeout и отмена не обозначаются
успехом продукта. Отчёт сохраняет причину и фактический результат. После
исправления повторяют упавшие и связанную группу по правилам PROCESS.md, не
теряя первоначальные отказы.

## Браузерный фасад и пользовательский путь

`demo/helpers/hp-test.mjs` устанавливает `window.__hpTest` в тестовый harness,
но не в продуктовый bundle. Смок входит через реальный UI, события HA и
контрактные селекторы из `docs/data-hp-contract.json`. Присваивание приватному
полю вместо нажатия кнопки скрывает дефекты самого пользовательского пути.
Приватное чтение может помочь ассертам, но не заменяет наблюдение результата.

| Метод фасада | Действие |
|---|---|
| `setMode`, `setTool`, `switchSpace` | Нажимает режим, инструмент или пространство |
| `openRoomEdit`, `openMarkerDialog`, `openSpaceDialog` | Открывает редактор через соответствующий контрол |
| `input`, `close` | Вводит значение и завершает диалог через UI |
| `setServerConfig`, `setLayout` | Доставляет серверное событие и ждёт принятия ревизии |
| `waitForWrites` | Наблюдает завершение настоящих очередей записи, ничего не сбрасывая |
| `settled`, `toast`, `waitForToastClear` | Дожидается рендера и наблюдает пользовательские уведомления |

После перезагрузки страницы фасад устанавливается заново через
`installHpTestOnPage(page)`. `setServerConfig`/`setLayout` моделируют изменение
на сервере; несохранённый пользовательский draft вводят через UI. Перед заменой
серверного снимка после редактирования дожидаются `waitForWrites()`, а после
принятия config — повторно перед layout. Fixtures соблюдают `expected_rev` и
ответ `conflict`; сброс очереди ради зелёного теста искажает поведение продукта.
`ha-dialog` не предоставляет фасаду публичного крестика из своего private
shadow root: для него доступны Escape и cancel.

## Визуальные кадры, E2E и измерения

Основная поверхность снимков — панель `/houseplan`; Lovelace имеет отдельную
небольшую выборку, Static остаётся read-only. Состав выбранных кадров задаёт
`process-next/catalog/golden-selection.mjs`; полный технический справочник —
[demo/golden/README.md](../demo/golden/README.md). Эталон принимается явно после
просмотра отличий, не автоматически после любого красного сравнения.

Статичный кадр не доказывает команды HA, сохранение после перезапуска,
обновление установленной версии или работу нативной оболочки HA. Это задачи
E2E. Отсутствие E2E checkout или окружения показывается как недоступная проверка,
а не заменяется demo-смоком. Данные для публичных материалов синтетические.

Размеры и время сравниваются на выпуске по PROCESS.md. Команды замера, сцены и
ограничения описаны в [demo/performance/README.md](../demo/performance/README.md).
Время headless-сценария не является измерением реального GPU пользователя;
небольшие отклонения не создают новую обязательную проверку каждой задачи.

## Что автоматический результат не обещает

Синтетический harness не доказывает поведение всех реальных HA установок,
мобильных WebView и GPU. Важны ограничения конкретного опыта: устройство,
версия браузера, настоящий touch, размер дома, параллельные клиенты. Ручные
наблюдения полезны для таких случаев, но этот справочник не вводит обязательный
ручной маршрут на каждую задачу или выпуск.

Продуктовые контракты сохранены в [ARCHITECTURE.md](ARCHITECTURE.md),
[CONFIG-COMPATIBILITY.md](CONFIG-COMPATIBILITY.md),
[TOUCH-SUPPORT.md](TOUCH-SUPPORT.md), [VACUUM.md](VACUUM.md) и других профильных
документах. Для конкретной правки выбирают проверку её поведения; перечень
упоминаний старого issue не превращают в список дополнительных гейтов.

Фоновые мутации и смысл их исходов:
[mutation-browser-guards.md](testing-notes/mutation-browser-guards.md).
