# Служебные сообщения задачи

Правила истории находятся в [PROCESS](../../PROCESS.md#история-задачи-и-служебные-сообщения).
Это короткий справочник по [согласованному каталогу #1190](https://github.com/Matysh/houseplan-card/issues/1190).
Номера ниже соответствуют его 33 группам. Они обозначают варианты сообщений,
а не обязательные шаги каждой задачи и не требование публиковать все строки.

Пиши по-русски: **что произошло → фактический статус/метки → причина → что дальше**.
`{Поля}` заменяются известными фактами. Отсутствующие данные не выдумываются.
Ссылки нужны на существующий отчёт, запуск, коммит или задачу; полного локального
пути недостаточно для обещания доступного в GitHub отчёта.

Исполнитель описывает сделанные им действия. Автоматика сообщает свои результаты;
исполнитель не копирует их вторым комментарием. Смена статуса объявляется выполненной
после подтверждения записи. Если она не выполнена, пиши об этом прямо. Сам
вердикт, merge и оформление его меток — разные факты. Повтор доставки не является
новым событием. Номер раунда ревью, вход в очередь и техническая попытка запуска
не подменяют друг друга. Код, пути и цитаты ошибок переводить не нужно.

## Подготовка и ревью ТЗ

| № | Событие и автор | Основа сообщения |
|---|---|---|
| 01 | Начат анализ — исполнитель | **Начат анализ задачи №{номер}. S1 «Новая» → S2 «Анализ»: `S1-new` → `S2-analysis`.** Разбираю {вопрос}; результатом будет {конкретизация}. |
| 02 | Готовится ТЗ — исполнитель | **Анализ завершён. S2 → S3: `S2-analysis` → `S3-spec`.** Выбран {подход, почему}; готовлю раздел «ТЗ» в теле issue. Осталось определить {вопросы либо их отсутствие}. |
| 03 | Короткая постановка готова — автор действия | **Задача готова к реализации. {Фактический статус} → S5: {старая метка} → `S5-ready`.** Для установленного `track:{ship/show}` ревью ТЗ не предусмотрено. Ожидаемый результат: {что}; проверка: {как}. Не называть пропущенное ревью пройденным. |
| 04 | ТЗ передано — исполнитель | **ТЗ передано на ревью, раунд {N}. S3 → S4: `S3-spec` → `S4-spec-review`.** ТЗ и контекст обновлены, оформление проверено исполнителем. Ожидаем содержательного анализа {существенный вопрос}. О проверке оформления писать только после её выполнения. |
| 05 | Ревью началось — автоматика | **Началось {ревью ТЗ / код-ревью}, раунд {N}. Статус остаётся {S4 / S7}.** Анализируется {материал}; [запуск]. Если наблюдается только отправка запроса, писать «Запрос передан; ожидаем ревьюера», а не «модель анализирует». |
| 06 | ТЗ требует исправлений — автоматика | **Ревью ТЗ — нужны исправления, раунд {N}. S4 → S3: `S4-spec-review` → `S3-spec`.** {Полный отчёт: проблема, условие, последствия, основание, направление исправления; отдельно альтернативы и границы}. Далее исполнитель исправляет ТЗ и описывает изменения. Второго общего сообщения о возврате нет. |
| 07 | ТЗ исправлено — исполнитель | **ТЗ исправлено после раунда {N}.** [Предыдущее ревью]; {замечание → изменение в теле issue}, {оставшиеся вопросы}. После передачи: **S3 → S4**, раунд {N+1}. До передачи: **статус остаётся S3**, подготовка ещё не завершена. |
| 08 | ТЗ принято — автоматика | **Ревью ТЗ — принято, раунд {N}. S4 → S5: `S4-spec-review` → `S5-ready`.** Блокирующих замечаний нет. {Полный анализ, основания, необязательные предложения, ограничения}. Следующий шаг — реализация. |

Первое назначение ранее отсутствовавшего трека поясняется в ближайшем сообщении:
«Установлена `track:{трек}`: {основание}». Установленный трек агент не меняет.
Само наличие метки не требует отдельного комментария.

Штатные исправления ТЗ делаются на S3 между раундами. Если тело issue всё же
изменено во время S4, отдельное сообщение объясняет исключение:
«**Материал ТЗ изменён во время раунда N; начат раунд N+1.** Статус остаётся S4
{только если это текущий статус}. Предыдущий запрос сохранён, его результат
будет опубликован отдельно». Это новый материал, а не технический повтор.
Если сообщение доставлено позже, показывается текущий статус без возврата на S4.

## Реализация, очередь и код-ревью

| № | Событие и автор | Основа сообщения |
|---|---|---|
| 09 | Начата реализация — исполнитель | **S5 «Готова» → S6 «Реализация и проверки»: `S5-ready` → `S6-in-progress`.** Делаю {результат}; ветка `{ветка}`. Затем очередь, актуализация и {выбранные проверки / «документация: прогонов нет»}. |
| 10 | Исправлен код — исполнитель | **Исправления после код-ревью, раунд {N}. Статус остаётся S6.** {Замечание со ссылкой → изменение/ответ}; материал `{SHA}`; {реально выполненные проверки и оставшаяся работа}. Следующий шаг — завершить S6, затем передать на ревью. |
| 11 | Вход в очередь — автоматика | **Задача в очереди завершения, вход {K}. Статус остаётся S6.** Позиция на момент постановки {позиция}; {кто занимает слот / слот свободен}. После допуска — актуализация, S6 и {ревью / merge для ship}. Текущий прогресс — в WSL/логе. |
| 12 | Получен слот — автоматика | **Получен слот очереди, вход {K}. Статус остаётся S6.** {Ветка актуальна / актуализирована} относительно `{dev SHA}`. Выполняется «Тесты для задачи №{номер} ({перед ревью / правки после ревью})» в {WSL / резерве GitHub}; {выборка}. Для docs: «Изменены только документы; прогонов нет». |
| 13 | Проверки не прошли — автоматика | **Проверки S6 не прошли, вход {K}. Статус остаётся S6; слот освобождён.** {Конкретный тест/кейс}: {наблюдение}; [отчёт]. Требуется {разобрать причину / установленное исправление}. Повтор — упавший тест и небольшая связанная группа. Применимые успехи сохраняются. |
| 14 | Среда недоступна / выбран резерв — автор действия | **Локальный запуск не состоялся. Статус остаётся S6.** Причина {что недоступно}; это не результат тестов. {Тот же набор запущен в GitHub: ссылка / резерв недоступен, слот освобождён, требуется …}. Реальный FAIL не обходится сменой среды. |
| 15 | S6 завершён — автоматика | **Проверки завершены. S6 → S7: `S6-in-progress` → `S7-code-review`.** {Набор, итог, время, зачтённые результаты / «документация: проверки не требуются»}. Материал `{SHA}`. Сейчас ожидаем ревьюера, далее только код-ревью. Ship в S7 не направляется. |
| 16 | Код требует исправлений — автоматика | **Код-ревью — нужны исправления, раунд {N}. S7 → S6: `S7-code-review` → `S6-in-progress`; слот освобождён.** {Полный отчёт с основаниями и альтернативами}. Исполнитель описывает исправления новым комментарием; после адресного S6 — следующий раунд. |
| 17 | Код принят — автоматика | **Код-ревью — принято, раунд {N}.** {Полный отчёт}. **Статус пока остаётся S7**, далее merge. Если merge уже произошёл к доставке, указывать это со ссылкой, не выдавая прежний статус за текущий. |
| 18 | Чистая актуализация — автоматика | **Ветка актуализирована; применимый результат сохранён.** {Реальный переход либо неизменный статус}. Основание `{было}` → `{стало}`, собственное проверенное изменение прежнее; [принятое ревью] зачтено. {Что зачтено/дополнено}. Если собственный код изменился, требуется обычный новый раунд. |
| 19 | Конфликт актуализации — автоматика | **Завершение приостановлено: конфликт с dev.** {Статус остаётся S6 / фактический S7 → S6}; слот освобождён. Конфликт {файлы/область}. Исполнителю разрешить его и снова войти в очередь; объём повторной проверки зависит от внесённых изменений. |

Снимок позиции очереди не редактируется при каждом её движении. Близкие события
входа и немедленного допуска можно описать вместе. Проценты, heartbeat и опросы
состояния не создают новые сообщения.

## Сбои, пауза и восстановление

| № | Событие и автор | Основа сообщения |
|---|---|---|
| 20 | Технический повтор ревью — автоматика | **Ревью не завершилось из-за технической ошибки.** {Причина, запуск}; содержательного вердикта нет. **{S4 / S7} сохраняется.** Одна техническая попытка того же раунда/материала, без повторного S6. Быстро восстановленный сбой можно пояснить в итоге. |
| 21 | Повтор исчерпан — автоматика | **Ревью остановлено из-за технического сбоя.** {Что не удалось, запуск}. Для ТЗ **S4 сохраняется**; для кода **S7 → S6**, слот освобождён. Это не отрицательное ревью. {Конкретное действие для восстановления}. |
| 22 | Исполнитель исчез / повторяющийся сбой — автоматика | **Слот очереди освобождён.** Причина {перестал продлеваться допуск / повторяется служебная ошибка}; {известная длительность}. {Фактический статус}. Результаты сохранены. Продолжение: {устранить причину}, затем новый явный `finish`. |
| 23 | Пауза/возобновление/ручной статус — автор действия | **Работа приостановлена:** добавлена `blocked`, **{Sx} сохраняется**; причина {известная либо «не указана»}; {слот освобождён, если был}. **Возобновлена:** снята `blocked`, {фактический статус}, основание {команда/устранённое препятствие}. **Ручной перевод:** `{Sx} → {Sy}`, {изменённые метки}, причина и следующий шаг. |
| 24 | Поздний/частичный отчёт — автоматика | **Ревью {ТЗ/кода}, раунд {N}: доставлено с задержкой.** Завершилось {время с часовым поясом}, доставлено {время}; причина {подтверждённая/не установлена}. Материал `{SHA/редакция}`, вердикт {по-русски}; **текущий статус не изменён**. {Полный отчёт, ссылка на следующий раунд при наличии}. Для частей: «раунд N, часть 2 из 3», ссылка на первую. |
| 25 | Merge — автоматика | **Изменение слито в dev. {Фактический предыдущий статус} → S8 «Слито в dev»: {снятая метка} → `S8-merged`.** [Коммит]; {подтверждённое удаление ветки}; {конкретный milestone / не требуется}; {снята `to_release`, только если была и снята}. Для ship индивидуальное ревью не предусмотрено. |
| 26 | Оформление после merge — автоматика | В итоге merge: **Изменение уже в dev; не удалось {операция}, фактический статус {Sx}. Повторяется только оформление.** После восстановления — новый комментарий: **Оформление завершено:** {метка/milestone/ветка, реально выполненное действие}; [исходное слияние]. Тесты и ревью не повторялись. |
| 27 | Исправлена служебная ошибка — автор записи | **Уточнение к [сообщению].** Было неверно указано {что}; подтверждено {факт}. Текущий статус {Sx}; {что исправлено/требуется}. Старое сообщение сохраняется. |
| 28 | Дефект вне задачи — автоматика в отчёте | **Отдельно обнаружено: [№ — название].** {Условие и последствие}. Это самостоятельный дефект: его создание само по себе не блокирует текущую задачу и не расширяет её объём. Номер указывается после подтверждённого создания. |

Не заявляй смену статуса до подтверждения записи. Исходный статус не следует
из трека: show/ask тоже может завершаться из S6 при зачёте принятого ревью.
При конфликте milestone назови оба значения и сохрани ручной выбор до решения
владельца. Служебное восстановление не меняет старый комментарий о merge.
`to_release` — личная метка владельца; её добавление не запускает работу,
агенты её не ставят. Упоминание снятия относится только к реальному снятию на S8.

Повторяется только незавершённая операция. |

Для №33 существенные варианты текста:

- **Stable:** «Зачтены применимые результаты беты {ссылки}; выполнено недостающее
  {набор}. Требуемое полное покрытие {достигнуто/не достигнуто: причина}».
- **Метрики:** «{Метрика}: было/стало, абсолютная и относительная разница.
  Превышены оба согласованных допуска относительно последнего stable;
  публикация беты ждёт решения владельца. Сравнение с 1.83.1 — диагностическое».
- **Конвертер:** «Выявлен {дефект}, создана [issue]; отказ внешнего конвертера
  сам по себе не блокирует stable Houseplan».
- **Telegram:** «Уведомление о {версии} {подтверждено / отправка не подтверждена:
  причина}; повторяется только недоставленное уведомление».
- **Восстановление:** «Для уже опубликованной {версии} завершено {действие}.
  Общие тесты и публикация повторно не выполнялись».

№29 и №33 задают стиль существующего отчёта/прогресса, а не обещают отдельный
автоматический комментарий на каждом этапе. Не создавать issue для каждого шага
выпуска и не рассылать одинаковый общий отчёт по всем включённым задачам.
Проверка публичного источника HACS и соответствия ZIP не доказывает установку
обновления в конкретном Home Assistant. Диагностический coverage и фоновые
мутации не создают новых блокировок.

## Как выглядит история исправлений

1. Отрицательный полный отчёт ТЗ: **S4 → S3**, раунд 1.
2. Исполнитель: замечания → изменения в теле ТЗ; **S3 → S4**, раунд 2.
3. Новый полный положительный отчёт: **S4 → S5**; старый отчёт сохранён.
4. Начало реализации: **S5 → S6**; затем очередь и адресная подготовка.
5. Проверки завершены: **S6 → S7**, ожидаем ревьюера.
6. Отрицательное код-ревью и возврат одним отчётом: **S7 → S6**.
7. Авторский комментарий об исправлениях; адресный S6; повторное ревью.
8. Новый принятый отчёт, затем фактический merge → **S8**.
9. После включения в опубликованную версию — **закрыта**.

Для ship индивидуальных ревью нет; для docs нет прогонов. Задержанный отчёт
не вставляется задним числом между человеческими комментариями: обозначаются
время события и материал, текущая работа не откатывается. Полный отчёт не
сокращается ради шаблона; длинный текст сохраняется частями. Технические поля
могут быть в раскрываемом блоке после человеческого объяснения.
