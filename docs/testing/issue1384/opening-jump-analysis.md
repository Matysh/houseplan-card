# Гипотеза о переносе Resize за проём

Запрос владельца от 11.11.2026: разрешить перенос за проём, сохранив запрет
конечного положения с одним или обоими торцами в проёме. Это исследование
дополнения к #1384; правила проёмов в исправлении прохода через узлы не менялись.

## Проверенный пример

Синтетическая model-11 сцена `makeResizeJunctionFixture('partition')`: две
комнаты с общей вертикальной стеной x=0.5, окно на верхнем боковом run с
центром x=0.3. Второй опыт ставит нижний проём также на x=0.3. Размеры и
координаты проёмов сохраняются. Единица плана в опыте — 1000 render units;
полудлина проёма 50, полутолщина движущейся стены 10, требуемое расстояние
от её оси до центра проёма — не менее 60 units.

| Конечная ось стены | Положение | Текущий pure validator | Текущий graph bridge | Явный зазор торца | Диагностический результат с правильным rehost |
|---|---|---|---|---|---|
| x=0.4 | Перед проёмом | Разрешает | Принимает | Есть | Physical preflight и Python принимают |
| x=0.3 | В проёме | Запрещает | Структурно принимает | Нет | Physical preflight и Python тоже принимают |
| x=0.2 | За проёмом | Запрещает | `edit-opening-target:side-window` | Есть | Physical preflight и Python принимают |

Результаты одинаковы для одного и обоих торцов. Диагностический rehost
сконструирован отдельно на копии синтетических данных: строится конечная
геометрия, затем те же проёмы явно привязываются к содержащим их участкам
стен. Это проверка осуществимости конечного состояния, не готовый алгоритм
Resize и не сквозной прогон на работающем HA. В HA данные не записывались.

Команды: `node artifacts/resize-pass-junction/opening-study.mjs` и тот же
скрипт с `--both`. Логи: `opening-study.log`, `opening-study-both.log` в этом
локальном каталоге. Python запускается через существующий
`demo/helpers/room-write-python.mjs`: graph/config, passage/host, junction
валидаторы обычного config/set, без режима Optimize.

## Что сейчас блокирует перенос

1. `clampSafeResize` в `src/resize.ts` проверяет все шаги от начала жеста
   и останавливается на первом запрещённом. Даже допустимая позиция за
   запрещённым интервалом не достигается.
2. `sideOpeningFits` требует, чтобы боковой проём остался на боковой стене
   прежнего владельца. При переносе общей стены за проём тот целиком
   переходит на стену соседней комнаты, хотя физически никуда не сдвигается.
3. `openingTargets` в `src/graph-edit-intent.ts` ищет новый host среди
   прежнего носителя и его потомков. Соседний участок того же непрерывного
   run может не входить в этот список: одной смены clamp недостаточно.
4. Структурно корректный граф и общий physical preflight сами по себе не
   обеспечивают пользовательский запрет торца в проёме, как видно по x=0.3.
   Явная проверка торцов и зазоров остаётся обязательной.

## Рекомендуемое поведение

Проверять конечный кандидат **на каждом показываемом preview и повторно при
отпускании**, но для проёмов не требовать непрерывно допустимой траектории
от начала жеста. В запрещённом интервале оставлять последний допустимый
preview; когда указатель вышел за весь проём с нужным запасом — показывать
и разрешать новый допустимый результат. Невалидный preview не публиковать.
Отпускание в запрещённом интервале сохраняет обычное поведение последней
допустимой видимой позиции; скрытого позднего перескока быть не должно.

Начальный безопасный объём: общая стена двух комнат, непрерывный боковой
носитель полностью сохраняется, проём остаётся целиком на нём. Переносить
host по доказанной исходной связности/lineage, без поиска ближайшей стены
по координатному радиусу. Физический центр, размер, тип, контакт и прочие
поля проёма не меняются. Проверять оба торца независимо.

Для внешней стены комнаты, если после переноса проём теряет сам носитель,
прыжок остаётся запрещённым. Нельзя глобально заменить clamp на проверку
только конечной точки: это также разрешило бы перескок через реальные
углы, третьи комнаты и независимые препятствия. Для них нынешние стопы
сохраняются. Проверку только при отпускании не рекомендую: она показала бы
промежуточную геометрию, которую нельзя сохранить, и дала бы поздний откат.

Перед реализацией нужны отдельные случаи одного/обоих проёмов, точных
границ зазора, узкого промежутка между проёмами, переноса host, постоянства
мировых координат, сохранения/Undo/Redo/reload, Cancel и внешней стены,
которая после переноса оставила бы проём без носителя.
