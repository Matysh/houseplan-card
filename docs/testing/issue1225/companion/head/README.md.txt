# houseplan-e2e

Честные браузерные тесты [House Plan](https://github.com/Matysh/houseplan-card)
на **реальном Home Assistant**: контейнер HA, интеграция из того самого
`houseplan.zip`, который скачивает HACS, два настоящих пользователя, настоящий
браузер. Здесь проверяются швы, которых не видит харнес продукта (заглушка
`hass`, статическая страница): порядок монтирования панели HA, дашборды
sections/masonry/panel, роли пользователей, путь обновления, HA-версии.

Логика продукта здесь **не** дублируется — она покрыта юнитами, смоками,
golden и мутантами в репозитории продукта. Тут — пользовательские путешествия:
каждая основная функция редакторов хотя бы одним сценарием (houseplan-card#1010),
действие в настоящем браузере → запись на сервер → перезагрузка → результат
на месте. Не вторая пирамида.

## Как устроено

| что | где |
|---|---|
| Конфиг HA, с которого стартует прогон | `seed/` — производная от публичного демо-стенда (анонимизированный реальный дом: план, области, устройства на template-сущностях, дашборды). `custom_components/houseplan` в seed **нет** — она ставится на каждый прогон |
| Пользователи | `scripts/users.mjs`: `demo` (админ) и `viewer` (не админ); хэши паролей пишет `prepare-seed` в run-каталог, в репозитории их нет |
| Установка House Plan | `scripts/install-houseplan.mjs --ref=latest\|stable\|<тег>\|<ветка>\|<SHA>\|<путь>` — релизы из asset `houseplan.zip`; ветки и SHA — фронтенд собирается из исходников этого ref (закоммиченный бандл `dev` отстаёт с #657/#1016; совпавшая сборка оставляет закоммиченные байты). Рядом пишется контракт установленного ref — `run/.e2e-contract.json` |
| HA | `scripts/ha.mjs up\|wait\|logs\|down` — `ghcr.io/home-assistant/home-assistant:<tag>`, порт только на loopback; `wait` ждёт не «ядро поднялось», а «интеграция отдала бандл» |
| Тесты | `tests/*.spec.mjs`, Playwright; логин через настоящую страницу входа один раз (`auth.setup.mjs`), дальше — сохранённое состояние браузера |
| Оракулы | состояние HA — REST (`tests/lib/ha-api.mjs`); что сохранил House Plan — websocket интеграции (`tests/lib/ha-ws.mjs`: `houseplan/config/get`, `layout/get`, `trail/get`, экспорт); DOM — только объявленный контракт продукта `data-hp` (houseplan-card#489, #1011): копия в `contract/data-hp-contract.json` (`npm run contract:sync -- --ref=dev`), селекторы строятся `hp()` в `tests/lib/hooks.mjs` и проверяются по копии, `npm run contract:lint` валит прогон на необъявленном хуке ещё до старта HA |
| Гейтинг по контракту | сценарий объявляет нужные хуки (`requireHooks` в `tests/lib/contract.mjs`) и сверяется с контрактом **установленного** продукта (`run/.e2e-contract.json`). Хук новее установленной версии по `since` копии контракта (старый stable в upgrade, ночной релиз без хуков #1011) — сценарий пропускается с причиной в отчёте. Хук, который по своему `since` у этой версии уже должен быть, а его нет, — сценарий падает: хук удалён или переименован. Атрибут без собственного `since` считается неизвестного возраста — только пропуск. Падает сценарий, не загрузка всего сьюта. Контракт релиза, который не удалось скачать (кроме 404 у релизов старше контракта), останавливает установку, а не превращается в «ничего не объявлено». Снапшот `dev` несёт версию прошлого релиза, но его контракт берётся из того же исходника. Для поведения без нового hook/value применяется отдельный явный version gate; прежний пример — линия декора щелчками вместо протяжки (houseplan-card#1046) включается с версии 1.83.0-beta.2 (`drawsLinesByClicks`); каждый `dev` после этого релиза несёт её или новее, кандидат хотфикса 1.82.x — нет. Навигацию по пространствам продукт выбирает сам: Lovelace сохраняет правило #997, а основная страница в контракте beta.4 (#1120) сворачивается по фактическому переполнению содержимого; размеры окон в сценариях — входные данные, не новые продуктовые пороги. `selectSpace`, `spaceEntries` и `spaceEntry` принимают обе формы |
| Возврат плана | сценарии, которые правят план, снимают его до и возвращают после себя (`tests/lib/seed-guard.mjs`): запись документов с проверкой ревизии, а если интеграция считает это устаревшим клиентом — полный импорт собственного экспорта. Seed хранит план модели 5; `plan-model.setup.mjs` один раз поднимает его до модели продукта (правка + отмена), чтобы возврат был возможен |
| Фикстуры бэкапов | собираются кодом (`tests/lib/backup-fixtures.mjs`), описание — `fixtures/backups/README.md`; каждый использованный файл приложен к отчёту |

Контракты beta.4 для #1112 static sync и #1125 bootstrap меняют поведение
без нового hook/value, поэтому известная beta.3 и старше получают явный version
skip. Такой skip **не доказывает** новую функциональность. Проверки панели
#1119/#1120 также исполняются на исходном снапшоте до version bump, если
установленный контракт уже объявляет retirement panel-title из #1120.
Перед публикацией нужен прогон точного beta.4 кандидата с исполнением всех новых
сценариев. Неизвестный foreign HA без installed record проверяется как newest,
без молчаливого skip. Новые profile hooks #1113 дополнительно проверяются
контрактом.

Полировка #1132 использует известную установленную версию начиная с
1.83.0-beta.5:44px editor close, прямые действия узкой панели и киоск без
кнопок поверх плана. Старые релизы сохраняют свои ожидания. Неизвестная версия
не доказывает этот новый контракт; перед beta нужен точный candidate с реальным HA.

Сценарий #1125 задерживает на600ms только запрос настоящего HA app-модуля,
затем обычными действиями открывает настройки и предпросмотр импорта при холодном
и повторном входе. Байты HA и factories/registry не подменяются; ошибки
конструктора не скрываются retry, config/layout остаются прежними. В каждом
CI-сьюте сохраняется фактическая версия HA из публичного unauthenticated
WebSocket greeting и identity установленного frontend; auth/config в эту
квитанцию не попадают.

Три сьюта, у каждого свой Home Assistant (отдельные job в CI):

| сьют | seed | что проверяет |
|---|---|---|
| `journeys` (проекты `admin`, `viewer`, `mobile`) | дом | панель `/houseplan` (первый заход, возврат внутри приложения, HA→план, тап→HA), карточка panel/sections/masonry/kiosk, read-only, телефон, **рестарт HA под открытой страницей**; редакторы (#1010): комнаты — создание, удаление и повторное создание в тех же стенах, ресайз; стены и стены нулевой толщины, перенос узла; устройство — перенос с undo/redo, переименование, копия; панель свойств; магниты и общая обводка связки; подложка, мебель, свои картинки, текст с живым значением, фигуры; четыре диалога настроек; свет от ламп; след пылесоса; пространства; сводная панель; PDF и его переключатели; помощь без отправки; экспорт (полный ZIP, пространство, только планировка, отчёт о проблемах) и импорт («грязный» ZIP, JSON 1.62 модели 5, пространство обратно, отказ на битых файлах, отмена импорта) |
| `first-run` | пустой (интеграция есть, плана нет) | viewer видит спокойное read-only, админ создаёт первое пространство без картинки → оно на сервере после перезагрузки |
| `upgrade` | дом + **старая** версия | открытая вкладка → обновление до целевой версии + рестарт → навигация внутри приложения без пустого плана → обычная перезагрузка грузит новый бандл (fingerprint, `?v=`), панель работает |

Прогон внутри сьюта последовательный: один HA, одно состояние.

**Кадры-улики и диффы.** Каждый сценарий снимает кадры `<проект>/<сценарий>/<шаг>.png`
(`evidence()` в `tests/lib/ha-page.mjs`): до действия, после, после перезагрузки.
Вид стабильный: viewport, язык, часовой пояс заданы в конфиге, живые значения
заморожены в seed (template-сущности с постоянными состояниями, без часов),
пылесос едет отсчитанное число шагов. Каждый job сравнивает кадры с кадрами
последнего стабильного релиза (`scripts/evidence-diff.mjs`): эталон серым,
разница розовым, `diff.json` с долей разницы, галерея `index.html` (эталон /
текущий / дифф, сначала самые разные) и таблица в сводке job. Артефакт
`evidence-<прогон>-<сьют>-ha-<HA>` живёт 90 дней. Эталон — `evidence/stable/<тег>/`
в этом репозитории: его коммитит job `evidence-baseline` после зелёного гейта
стабильного релиза (`scripts/evidence-baseline.mjs`, хранится только последний
тег, история — в git). **Не гейт**: порогов и масок нет, разница не красит прогон
и не шлёт в Telegram. Пиксельная приёмка — забота golden-набора продукта.

## Запуск локально

```sh
npm ci && npx playwright install chromium
npm run seed                                  # seed → run/
node scripts/install-houseplan.mjs --ref=latest --out=run
npm run ha:up -- --version=stable --dir="$PWD/run"
npm run ha:wait
npm test
npm run ha:down
```

`HA_URL` перенаправляет тесты на любой другой инстанс (например, стенд), но
тогда пользователи и seed — ваша забота. Без `run/.e2e-contract.json` гейтинг
по контракту не пропускает ничего.

Кадры ложатся в `evidence-out/` (`E2E_EVIDENCE_DIR` меняет место); дифф к
эталону: `node scripts/evidence-diff.mjs --current=evidence-out --stable=evidence/stable --out=evidence-diff`,
галерея — `evidence-diff/index.html`.

## CI

`.github/workflows/e2e.yml`: по кнопке (`houseplan_ref`, `upgrade_from`,
`ha_version`), ночью (свежая бета на HA `stable` и `beta`) и при пуше в `main`
этого репозитория. Артефакты:
отчёт Playwright, трейсы/видео упавших сценариев, `home-assistant.log`,
`docker.log`. При наличии секретов `TG_BOT_TOKEN`/`TG_CHAT_ID` красный прогон
уходит в Telegram.

До запуска HA `scripts/plan-run.mjs` однократно фиксирует конкретные версии:
`latest`/`stable` становятся тегами, ветки — SHA. Если исходный `stable`
совпал с версией цели (например, сразу после выпуска stable), upgrade идёт
с предыдущего отличающегося stable. Draft и prerelease не служат такой базой.
Пара тегов/SHA и версии показаны в сводке планировщика. Явно заданный
одинаковый `upgrade_from` или отсутствие предыдущего stable — понятная ошибка
подготовки, не пропуск теста. Проверки смены версии и fingerprint, рестарта HA
и восстановления браузера не ослабляются. Имена jobs journeys/first-run
сохраняют запрошенный тег/SHA для контракта релизного гейта.
Установщик сверяет версию внутри полученного ZIP/снапшота с запланированной:
несоответствующий asset не принимается за проверку другой версии. Политика
автовыбора относится к псевдониму `stable` независимо от того, введён он
явно или оставлен по умолчанию; конкретный тег/SHA самовольно не заменяется.

`npm run test:unit` проверяет выбор пары и матрицу без Docker и браузера;
этот же набор обязателен в job планировщика перед E2E.

Роль в процессе продукта (houseplan-card #514, с 09.09.2026): **гейт
стабильного релиза**. `release.yml` в houseplan-card запускает этот workflow
по кнопке с `houseplan_ref=<тег>`, `upgrade_from=stable`, `ha_version=stable`
и ждёт зелёного (`scripts/e2e-gate.mjs`); красный — ассеты релиза не
публикуются. Гейт опознаёт свой прогон по имени job `… · HP <тег> · …` — это
контракт, имя job не переименовывать. Сьют `journeys-dev` идёт только по
расписанию: снимок `dev` не должен красить stable. Беты и мержи гейт не
проходят.
