## Атрибуция и отвергнутые гипотезы

1. В атрибуционной паре CSS `getPropertyValue` вызван21/28 раз, суммарно
   около3,0/2,2 мс. Стэки включают HA scroll/routes и разрешение CSS-значений
   Houseplan. Расход256 мс из репорта не подтверждён. Другая тема и устройство
   могут дать иной результат; общий theme cache по этим данным не вводится.
2. Функция `_i` в чанке open-spans по телу сопоставлена с
   `arrangeExact` в `src/wall-arrangement.ts`. В стэках — `_wallUnionGeometry`,
   `_innerRoomContour`, `_resolveLightBarriers`: это разные геометрические
   потребители. Self samples около12,7/22,3 мс. Другие горячие символы в том
   же чанке относятся в том числе к BigNumber. Название чанка не доказывает
   дорогой пересчёт open_spans, и суммы включённых стэков не складываются.
3. `_renderDecorLayer`: около14,2/13,0 мс self samples, согласуется с sync
   счётчиками. `_setLoadingCoordinates` не найден среди методов текущего класса
   и в этих CPU profiles; ему не присваивается выдуманное нулевое время.
4. `editor-shared`, `plan-graph`, locale и summary shared действительно
   получены, но основной editor runtime **не загружен**. `ViewRuntimes.reconcile`
   подключает live/summary; они имеют общие зависимости. `_preloadEditorIntent`
   в `houseplan-card.ts` ограничен pointerenter/focus/pointerdown на навигации
   редакторов. Удаление полезной предзагрузки не обосновано этим профилем.
5. При первом bootstrap наблюдаются **две полные пары config/layout** плюс
   два model_version preflight. Это не скрывается результатом тихого remount.
   Стэк первого `_loadFromServer` — hass intake/willUpdate, второго —
   connectedCallback из masonry `_addCardToColumn`. Между ними начальное
   чтение прерывается: новый вызов имеет busy=false/pending=true при том же
   известном пользователе. В атрибуционной cold-паре подключения разделены
   примерно20 мс, в warm —272 мс.

Последний случай — граница текущего lifecycle, а не доказанный повтор
принятия/пересборки плана. `disconnectedCallback` инвалидирует незавершённые
read/layout claims; покрытие config/layout событиями ещё не установлено до
первого принятого снимка. Простое присоединение нового lifecycle к старому
ответу или TTL-кеш не докажет актуальность данных после промежутка. В этом
исследовании такой guard не ослабляется. Сокращение этой пары потребовало бы
отдельно доказанного механизма событий/повторной проверки до первого adoption;
полученных измерений недостаточно для безопасного изменения этой границы.

## Что нужно для продолжения исходного CPU-репорта

Нужны trace с временными границами первого View, исходный план, тема,
viewport/браузер и характеристики устройства автора. Сопоставить до/после
на одном плане и устройстве; отдельно учесть время HA bootstrap, сложность
уникальных стен/стыков и режим заливки. Сохранённая локальная серия позволяет
повторить наблюдения, но не заменяет отсутствующие входные данные автора.
Трёх пар недостаточно для устойчивого p95; они не называются release metrics,
общим performance PASS или доказательством ускорения относительно v1.85.1.

Новых продуктовых эталонов/алгоритмов/регрессионных тестов без подтверждённого
исправления нет. Повторная работа, исправленная в #1386, уже защищена её
Node/native регрессиями; здесь добавлено свидетельство реального HA.
Содержимое этого изменения — отчёт исследования, без повторного тестирования
документации и без разрешения на релиз.
