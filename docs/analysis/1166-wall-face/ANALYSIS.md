## Почему один контур распознаётся, а второй нет

Обе исходные четырёхсторонние цепочки точно замкнуты. Нижняя левая область
изолирована; к верхней правой примыкают четыре ветви. Graph возвращает одну
грань: точка [350,400] в верхней области не найдена, [-200,1240] в нижней найдена.
Масштаб NORM_W=1000; GRID_PITCH=1000/240, epsilon=GRID_PITCH*0.0002.
Тот же результат получен в нормализованном масштабе.

Диагностическое исключение ветвей из входа (только копия в памяти) возвращает
обе грани. Ветвь из точной вершины не мешает; каждая из трёх Т-ветвей по
отдельности подавляет верхнюю область. Удаление одной Т-ветви не помогает,
пока остаются другие.

`sourceVertex` в `src/wall-face-graph.ts` сравнивает исходные представления
одной топологической вершины с допуском машинной арифметики
`Number.EPSILON*16*coordinateScale`. Сохранённые Т-концы отличаются от точной
проекции на проходящую стену на 8.934e-11, 2.719e-11 и 4.521e-10
нормализованной единицы; соответствующий порог около 3.553e-15.
`sourceVertex` возвращает null, а `buildWallFaceGraph` отбрасывает всю грань
при любой такой вершине. `_offerExistingWallFace` не находит предложение
комнаты и отдаёт клик обычному рисованию стены.

Fallback `planWallFaceRepair` возвращает `none`, в том числе при штатном
пределе 2 см = 8.333 render units для cell_cm=1. Микроскопический разрыв уже
меньше topology epsilon и не попадает в ветку исправления зазора. В отдельном
контрфактическом расчёте точная проекция трёх концов только в памяти возвращает
обе грани. Это свидетель причины, а не разрешение молча переписывать геометрию.

## Почему Optimize не исправляет этот файл

Вызван настоящий `optimizePlans` с payload config/layout; model_version=10
взят из оболочки space-export. Структурный граф до и после строится штатной
цепочкой `spaceModels → buildPlanSnapGeometry → buildWallFaceGraph`.

| Проверка | Исходный план | Кандидат Optimize |
| --- | --- | --- |
| Найденные грани | 1 | 1 |
| Верхняя / нижняя область | нет / да | нет / да |
| Физический preflight | проходит | проходит |
| Backend нарушения расстояния | 0 | 2 |

Optimize сообщает moved=3 и maxShiftCm=0.4330297. `alignAllToGrid`
округляет концы каждой перегородки независимо. Исходные Т-примыкания не
сохраняются как связанные ограничения, поэтому численный хвост превращается
в настоящий зазор. Backend `validate_junction_limits(candidate, previous)`
отвергает кандидат с `junction_limit_distance`: первый отмеченный зазор
0.4329667 см при пределе 5 см. Здесь 5 см — порог запрета нового близкого,
но непримыкающего узла; он не разрешает зазор до 5 см.
Повторный Optimize своего кандидата даёт changed=false, всё ещё одну грань.
Идемпотентность этого результата не означает исправление геометрии.

Итак, есть два связанных отказа: слишком строгое доказательство совпадения
в graph и независимое выравнивание связанных стен в Optimize. Оба уже входят
в согласованный объём #1166. #1168 — дубликат; данный файл дополняет #1166
публичным регрессионным примером с проблемной и контрольной областями.

## Проверки для будущей реализации

1. На неизменённом экспорте распознать обе области при сохранённых ветвях.
2. Создать обе комнаты в обоих порядках; провести materialization,
   frontend guards, backend save/reload и Undo/Redo без нового off-grid debt.
3. Optimize должен сохранить Т-примыкания, пройти backend guards, позволить
   создать обе комнаты и после принятия стать no-op.
4. Контрольный нижний контур не ухудшается; настоящий зазор, разные близкие
   узлы и неоднозначный carrier не склеиваются. Защиты #1061 сохраняются.
5. Отдельный независимо построенный синтетический корпус покрывает общий
   конец, Т к наклонной стене, поддерживаемый X, точность хранения и негативы.
