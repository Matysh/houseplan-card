# SPEC-REVIEW-897-r1

Issue: [#897](https://github.com/Matysh/houseplan-card/issues/897) — «Конвейер:
ожидаемые продолжения без красного шума, видимые отказы и актуальные правила
архивирования/диагностики». Трек: `track:ask`. Заход r1, блокирующих циклов
израсходовано 0 из 4. Материал: тело issue #897 (единственная редакция,
14.10.2026) и оба комментария автора (аналитика, хендофф на ревью). Рабочее
дерево — `ef1aeaf6cf94f2f692654e975a4ee18c40b143a7` (detached HEAD на `dev`);
ветка задачи ещё не создана, продуктовый/служебный код не менялся — это
совпадает с хендоффом автора («Файлы: перечислены в ТЗ; исходники не
изменены»).

## Скоуп

Чистая инфраструктура (класс B/C): `scripts/process-resume.mjs`,
`scripts/workflow-continuation.mjs`, `scripts/merge-candidate.mjs`,
`scripts/reviews-archive.mjs`, заголовок/terminal-route
`.github/workflows/_process.yml`, `scripts/config-field-registry.mjs` и
соответствующие PROCESS/digests/TESTING/DEVELOPMENT. Нет `src/**`, нет Python,
нет нового scheduler/модели/повторных авто-попыток, нет расширения прав, нет
обхода CAS/epoch/SHA/ledger/proof. `User-Visible: no`.

ТЗ закрывает шесть найденных дефектов самого конвейера ревью/архивации:
1. `process-resume.pendingOf` красит job исключением на обычном
   postponed-merge сценарии вместо безопасного noop.
2. generic `catch` в continuation прячет конкретный шаг отказа за ярлыком
   `unverified`.
3. `realOps.must` формирует `Error` из сырого `stderr`/`stdout` без
   централизованной редакции секретов — утечка не доказана, но граница не
   защищена.
4. `reviews-archive --through=vX.Y.Z` не переносит beta ship-review без
   одноимённого stable (два `SHIP-REVIEW-v1.80.0-beta.*` остаются навсегда).
5. Заголовок `_process.yml` требует heredoc вопреки правилу #723/#730;
   `config-field-registry` описывает безусловный cleanup там, где он условный.
6. Terminal `S7→S6` путь использует `github.token` без явного согласования
   с каноном PAT.

Задача не меняет видимое поведение ни для одной персоны `docs/SCOPE.md`
(`User-Visible: no`, файлы — исключительно `scripts/**`, `.github/workflows/`,
`docs/**` процесса); она обслуживает надёжность самого конвейера, через
который поставляется продуктовая работа, а не напрямую J1–J7.

1. Прочитаны `docs/SCOPE.md`, `AGENTS.md`, `docs/process/REVIEWER.md`,

   правило «владельцу только продуктовые вопросы»).

   поверхности, находки F55/F61/F66/F67/F68/F104/F105) и хендофф
   («Гейты: specFormatErrors → PASS… реализационные гейты пока
   неприменимы»).
3. Сверены обязательные разделы §7.1 с текстом ТЗ — присутствуют все:
   сценарий, что человек увидит до/после, проблема, скоуп и не-скоуп,
   контракт поведения (7 пунктов), UX и доступность, модель данных и

   автотестов и риски, откат, release-артефакты, «принято предположительно».
4. Построчно сверены центральные утверждения раздела «Проблема» с текущим
   кодом (не поверено на слово):
   - `scripts/process-resume.mjs:104-106` — `pendingOf` действительно бросает
     `'sealed model result exists — refusing to wake a completed review'`,
     когда запечатанный `review-result-*` артефакт уже существует —
     подтверждает дефект №1 дословно.
   - `scripts/workflow-continuation.mjs:193` — именно generic
     `catch { outcomes.push({ action: 'unverified', reason: 'verification
     failed; no success assumed…' }) }`, без сохранения исходной ошибки или
     конкретного шага — подтверждает дефект №2.
   - `scripts/merge-candidate.mjs:347-353` — `must = (r, what) => { if
     (r.status !== 0) throw new Error(`${what}: ${r.stderr || r.stdout}`); … }`
     не редактирует вывод; редакция (`classifyPushRefusal(stderr, {secrets:
     [token]})`) применяется только к `refusedPush`, то есть только к пути
     push. `fetch`/`revParse`/`mergeBase`/`diffNames`/`patchId`/`checkout`
     идут через голый `must` — граница действительно не защищена
     централизованно, а ТЗ прямо пишет «утечка не доказана», не
     переоценивая находку.
   - `scripts/config-field-registry.mjs:196-210` — запись
     `markers[].display=ripple` буквально содержит
     `enforcedBy: '… _dropLegacySegments rewrites on every write'` —
     подтверждает «описывает безусловный cleanup».
   - `PROCESS.md:460-487` — существующее правило «перенос идёт при пустой
     очереди S7-code-review» — показывает, что формулировка AC4 «при пустом
     S7 по canon» ссылается на уже принятый канон, а не изобретает новое
     условие без основания.
   - `PROCESS.md:1346-1490` (правило о тонких workflow/heredoc #723/#730,
     `HP_PROCESS_TOKEN` для review-triggering переходов, red-night логика) —
     контракт п.6/7 и AC5 согласованы с этим разделом, противоречий не
     найдено.
5. Проверено покрытие пунктов DoR §2.5 текстом ТЗ: файлы/модули — названы;
   i18n — явное «нет»; миграция/совместимость — решены; touch — не
   применяется (нет UI вообще, см. раздел UX); откат — назван; открытые
   продуктовые вопросы — обоснованно отсутствуют (см. п.7 ниже). Один пункт
   не закрыт явно — см. находку M1.
6. Проверено, что технические решения (архивный ancestry-алгоритм, именование
   reasons, граница split-helper) отнесены в «Принято предположительно,
   поменять свободно» и не эскалированы владельцу как продуктовые — согласно
   §7.1 это ровно то разграничение, которое требуется.
7. Отдельно проверено отсутствие открытого продуктового вопроса на
   осмысленность, а не на слово автора: раздел «Скоуп» перечисляет только
   `scripts/**`, `.github/workflows/`, `docs/**` процесса — ни одного пути
   `src/**` или `custom_components/**`; `User-Visible: no`. При нулевой
   видимой поверхности для любой персоны `docs/SCOPE.md` отсутствие
   продуктового вопроса владельцу — ожидаемое, а не пропущенное состояние.

## Находки

### Medium (в скоупе) — M1: в «Release-артефакты» не назван явно пункт DoR «производительность/security»

**Файл:** тело issue #897, раздел «Release-артефакты».

**Описание:** `PROCESS.md` §2.5 требует для «Готово к разработке»: «влияние
на производительность и бюджеты названо (или явно «нет»)» и отдельно в
составе release-артефактов — «performance/security — либо явное «нет»».
Текущий раздел называет только ledger (`infra v1.80.1`), отсутствие
milestone, список документов на обновление и исключение из
`Changelog_user_stable` — ни слова о производительности и ни слова о
security, даже значением «нет». Это не формальность на пустом месте: сама
задача — одна из немногих, где security-поверхность реально есть (граница
редактирования токена/credential URL в `realOps.must`, AC3; выбор
least-privilege токена для terminal-маршрута, контракт п.6) — и именно для
неё раздел release-артефактов не называет соответствующий артефакт/решение
явно.

**Почему это находка, а не придирка:** `PROCESS.md` §2.5 — «Если хоть один
пункт не выполнен — статус не «Готово к разработке»»; `REVIEWER.md` ссылается
на §2.5 как на предмет ревью ТЗ наравне с §7.1. Содержательно пробел не
блокирует реализацию (AC3/AC4 полностью описывают контракт сами по себе) —
поэтому находка Medium, а не High.

**Воспроизведение:** в теле issue нет подстрок «производ», «perf»,
«security» вне контекста самих AC/контракта; раздел «Release-артефакты»
содержит только `ledger`, `milestone`, `PROCESS/digests/…`,
`Changelog_user_stable`.

**Предлагаемое закрытие (одна строка в ТЗ):** «Производительность: нет
влияния (CI-скрипты конвейера ревью, не путь выполнения карточки в браузере).
Security: отдельного advisory нет — граница редактирования секретов
проверяется AC3/AC4 юнит-тестами, доказательство — в код-ревью.»

Других находок нет. High: 0, Medium: 1 (в скоупе), Low: 0.

## Что проверено и корректно

- Все обязательные разделы §7.1 присутствуют, в правильном порядке, ни один
  не пуст.
- Каждый AC1–AC6 называет способ доказательства (`unit` /
  `unit + read-only CLI` / `unit realOps fake exec` / `unit + ревью кода`) —
  требование §2.5 выполнено по каждому пункту.
- AC1, AC2 и AC6 дополнительно сами формулируют «чем краснеет» внутри текста
  AC (прежний `pendingOf throw`, «generic catch», «снятие identity gate») —
  это опережает требование §2.7 к будущему код-ревью, хотя на этапе spec не
  обязательно.
- Все шесть пунктов раздела «Проблема» независимо перепроверены по текущему
  коду (см. «Как проверялось», п.4) и оказались точными, включая намеренно
  скромную формулировку «утечка не доказана» там, где код действительно не
  содержит прямого доказательства утечки, а лишь незащищённую границу —
  никакого преувеличения или домысла.
- Технические решения (ancestry-алгоритм архивации, именование reasons,
  граница split-helper) корректно помещены в «Принято предположительно» и не
  вынесены владельцу — соответствует правилу §7.1 «владельцу — только
  продуктовые вопросы».
- Открытый продуктовый вопрос отсутствует обоснованно: задача не имеет ни
  одной видимой поверхности ни для одной персоны `docs/SCOPE.md`
  (`User-Visible: no`, скоуп — только `scripts/**`/`.github/workflows/`
  /`docs/**`), что проверено по списку файлов, а не принято на слово.
- Не-скоуп прямо исключает новый scheduler/модель/повторные авто-попытки,
  расширение прав, обход CAS/epoch/SHA/ledger/proof — согласуется с AC6
  («старые exact-proof/pending/CAS/unknown delivery/lease tests… остаются без
  изменений»), внутренних противоречий между скоупом и AC нет.
- Откат назван и соразмерен (обычный revert + git-recoverable archive move,
  без force-push и без удаления CAS-ссылок) — закрывает DoR-пункт «откат».
- i18n закрыт явным «нет» (нет продуктовых ключей) — соответствует формату
  DoR-пункта.
- Модель данных/миграция решены: стабильность payload/seal identity и 24ч
  intent/CAS-семантики, допуск `unknown` для новых diagnostics-полей,
  recoverable git-move для архивов без переписывания истории.

## Чего не проверял

- **Гейты кода не запускались.** На этапе `spec` диффа в `src/**`/`scripts/**`
  нет (реализация не начата — «исходники не изменены» из хендоффа автора),
  поэтому `npx tsc --noEmit`, `npm test`, `npm run build` гонять не над чем;
  они не относятся к предмету ревью ТЗ. Зависимости/Chromium на этапе spec
  не ставились (#696).
- Структурную проверку `specFormatErrors` (наличие обязательных разделов)
  я не перезапускал как скрипт — автор получил `PASS` в хендоффе; вместо
  повторного запуска я вручную построчно сверил присутствие и порядок всех
  разделов §7.1 (см. «Как проверялось», п.3) с тем же результатом.
- `docs/release-ledger/<previous-stable>/897.json` не проверялся — по §2.6
  классификация релиза пишется «до S7», во время реализации; на этапе spec
  такого файла не должно существовать, и его отсутствие не является находкой
  этого ревью.
- Golden/mutation/performance/pytest/инварианты модели — неприменимо: ни один
  AC не называет эти гейты, нет диффа в геометрии, Python или рендере.
- Содержимое внешнего источника `findings-2026-10-08.md` не проверялось —
  файл не в репозитории и недоступен мне; вместо повторения ссылки я
  независимо перепроверил сами заявления раздела «Проблема» по текущему коду
  (см. «Как проверялось», п.4), что по существу покрывает то же самое.
- Не проверялось, меняется ли реальный расход CI-минут (раннер) от этой
  задачи — это не то «влияние на производительность», которое судят бюджеты
  §8 (они о бандле/рантайме карточки); находка M1 — про формальную полноту
  раздела ТЗ, а не про скрытый реальный перф-риск.

## Вердикт

Жёлтый. ТЗ технически выверено и необычно глубоко обосновано для
инфраструктурной задачи: каждое утверждение раздела «Проблема» подтверждено
чтением текущего кода на конкретных строках, а не принято на слово; каждый
AC однозначен и снабжён способом доказательства; открытых продуктовых
вопросов нет обоснованно, поскольку задача не имеет видимой поверхности ни
для одной персоны. Единственная находка M1 — формальный пробел DoR §2.5
(не назван явно пункт «производительность/security» в release-артефактах),
в скоупе задачи, устраняется одной строкой текста без изменения контракта
или AC. High: 0, Medium: 1 (в задаче).
