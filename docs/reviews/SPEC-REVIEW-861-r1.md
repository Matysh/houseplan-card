раздел `## ТЗ`, редакция 2 от 14.10.2026 (заменяет редакцию 1 от 10.10.2026).
Авторская сверка — `origin/dev ee6717a8`. Рабочая копия на момент ревью —
`9ca904b0` (ancestor-проверкой подтверждено: `ee6717a8` — предок `9ca904b0`,

## Скоуп ревью

Оцениваю только ТЗ этапа Э1 (владельцы двух жестов редактора: тела
перегородок/колонн и рамка подложки) — заявленный скоуп этой задачи. Этапы
Э2–Э7 — план, не предмет этого ревью. Код не пишу и не правлю.

## Как проверялось

Это первый раунд (r1), «Повторный раунд» и «Унаследовано из r0» не применимы
— прежних документов ревью для #861 не найдено (`docs/reviews/INDEX.md`,
`find docs/reviews -iname "*861*"` — пусто).

Проверка шла по двум осям:

1. **Формальная полнота ТЗ** (PROCESS.md §7.1): все обязательные разделы,
   однозначность и доказуемость AC1–AC10.
2. **Фактическая точность** — ТЗ описывает текущий код с точностью до номеров
   строк, числовых порогов и имён; при таком уровне детализации ошибка в
   фактах — это и есть дефект ТЗ (AC, построенный на неверном факте,
   непроверяем). Выборочно, но широко сверил заявления с кодом:

   - номера строк полей/делегатов `_physicalDrag`, `_physicalRotate`,
     `_physicalLastTap`, `_physicalPickCycle` (card `:1756–1768`, `:2540–2541`,

   - то же для `_bdDrag`/рамки (card `:974`, `:2566`; runtime `_bdApply`
     `:4795`, `_bdStart` далее) — совпадают;

     (runtime `:2784`), двойное нажатие `<= 360` мс (`:2905`), порог поворота
     `>= 0.5°` (`:2951`), шаг поворота `Math.round(raw / 5) * 5` (`:2950`),

     (runtime `:820`) — существует, тот же приём приведения типа;
   - все названные в плане тестов и харнессе файлы существуют:
     `scripts/monolith-metrics.mjs`, `monolith-baseline.json`,
     `mutation-registry.mjs`, `smoke-links.mjs`, `candidate-native.mjs`,

## Находки

Находок, блокирующих вердикт (High) или требующих доработки в скоупе
(Medium), не нашёл. Один пограничный момент — ниже, без влияния на вердикт.

- **Low.** Два из трёх пунктов «Находки вне скоупа» (список «жест идёт» не
  знает лестницы/узла — вероятный лишний полный рендер; расхождение TS/Python
  `wallKey`/`_wall_key` на границе `keyEpsilon`) описаны как вероятные, но не
  измеренные дефекты вне этого Э1. Третий (асимметричный сброс поворота
  колонны) автор перепроверил чтением и не нашёл пользовательского пути — это
  закрыто корректно. Для первых двух процессное соглашение (PROCESS.md,
  «скоуп не расширяется: всё найденное вне ТЗ — новый issue») обычно
  подразумевает отдельную запись, а не сноску в чужом ТЗ; но оба — гипотезы
  без измерения, один уже явно привязан к будущему #845 («в его D1–D6 этого
  нет» — то есть автор зафиксировал, что #845 должен это подобрать), второй
  (лестница) нигде не подхвачен. Снимаю сам, по существу: это не вопрос
  владельцу (чисто техническое наблюдение) и не требование к Э1 (поведение
  лестниц и узлов Э1 не трогает). Рекомендация автору на будущее — заводить
  такие гипотезы отдельной строкой-issue в момент находки, а не только в
  тексте ТЗ соседней задачи, иначе они не попадают в бэклог и теряются при
  слиянии. Не завожу это отдельным issue сам: ни одна из двух гипотез не
  подтверждена исполнением (только чтением кода), п. severity "Medium вне
  скоупа" требует состоявшегося дефекта, а не недоказанной гипотезы — заводить
  issue по непроверенному предположению было бы самому создавать находку без
  доказательства, что это ревью как раз требует избегать.

## Что проверено и корректно

- Все обязательные разделы PROCESS.md §7.1 присутствуют: сценарий · что
  человек увидит до/после · проблема · скоуп/не-скоуп · контракт поведения ·
  UX · модель данных/миграция · i18n · AC1–AC10 с доказательством и
  «чем краснеет» · план автотестов · риски · откат · release-артефакты.
  Автор также указывает это прогоном `specFormatErrors(body, 'ask') → []`.
- Два первых обязательных раздела (сценарий, что видно до/после) — продуктовые,
  называют персону (`docs/SCOPE.md`: администратор дома, desktop) и говорят
  прямо: видимых изменений нет, случайная видимая правка — дефект задачи, а не
  приемлемая цена.
- Каждый AC (AC1–AC10) непустой в столбце «чем краснеет»: для каждого назван
  либо конкретный мутант (порог, геттер-пересылка, снятая заморозка кадра,
  удаление smoke-link), либо конкретное текущее состояние на `dev`
  («модуля нет» / «разница 0»). Для «мягких» мутантов (заморозка кадра, AC5)
  честно указано «проверить вручную при написании» — это нормально для этапа
  ТЗ: колонка заполнена планом доказательства, а не пуста; на этапе код-ревью
  это станет предметом проверки отдельно.
- Технических вопросов владельцу нет; продуктовых открытых вопросов тоже нет
  (видимое поведение не меняется — заявление проверяемо и подтверждено
  контрактом поведения п.1–8). Блок «Принято предположительно — поменять
  свободно» в конце корректно фиксирует все чисто технические решения (имена
  модулей, форма порта, механизм рендера, имена тестов) — ревьюер не
  оспаривает: решения разумны и не влияют на AC.
- Разбиение честного остатка #861 на Э1–Э7 со скоупом только Э1 в этой задаче
  — техническое решение по §7.1, не вопрос владельцу; план Э2–Э7 достаточно
  обоснован порядком связности и зависимостей (ждёт #845/#883/#846–848),
  не выглядит произвольным.
- AC8 (бюджет ядра) и AC9 (ленивый граф) опираются на существующие храповики
  (`test/core-file-budget.test.mjs`, `scripts/bundle-budget.mjs`) и не требуют
  поднятия потолков — согласуется с «Границами объединённой задачи» в теле
  issue («no new mandatory tooling freeze»).
- Риски названы по существу (маршрут обновлений, приведение `as unknown as`
  маскирует тихую потерю поля, харнесс маскирует через expando,
  пересечения диффов с #883/#848/#850, малый запас `hostRefs`/бандла) и у
  каждого — AC, который его ловит. Откат — явный, без миграций.
- Release-артефакты: категория `infra`, `User-Visible: no`, changelog не
  трогается — согласуется с тем, что поведение продукта не меняется;
  `baseStable: v1.80.1` — верный текущий stable.

## Чего не проверял

- **Гейты кода не прогонял** — это ожидаемо на этапе spec: зависимости и
  Chromium не ставились (`node_modules` отсутствует, подтверждено), что
  соответствует #696. Поэтому `npx tsc --noEmit`, `npm test`, `npm run build`,
  `node scripts/monolith-metrics.mjs`, `npm run bundle:budget` не
  запускались — на этом этапе материал ещё не код-диф, а текст ТЗ, и этих
  гейтов это ревью не требует (PROCESS.md §2.4, §8 про гейты относятся к
  код-ревью).
- Числа связности (`hostRefs: 5235`, `portMembers: 357` на `ee6717a8`) не
  пересчитывал исполнением `monolith-metrics.mjs` (нет зависимостей) —
  сверил только базовые/пороговые значения из `scripts/monolith-baseline.json`
  и `wc -l`, которые согласуются с утверждениями ТЗ. Точный пересчёт
  connectivity-метрик по AST — предмет код-ревью, когда вынос уже сделан.
  достаточно для оценки на этапе spec.
- Не проверял содержимое закрытых/смежных issue (#624, #642, #699, #843) по
  существу, кроме текущего статуса/меток зависимостей — доверяю ссылкам ТЗ,
  акцент ревью был на доказуемости AC1–AC10 этой задачи, а не на архивной
  истории.
- Ручное тестирование в браузере не делал — не применимо на этапе ТЗ (нет
  кода) и не требуется им же: отрисовка не меняется, сам документ это прямо
  оговаривает («не проверено: настоящий GPU-браузер; это не нужно»).

## Вердикт

Зелёный. ТЗ полное по §7.1, каждый AC однозначен и имеет названный способ
доказательства и условие красноты, продуктовых открытых вопросов нет,
технические решения зафиксированы явным блоком. Широкая выборочная сверка
фактов (номера строк, пороги, файлы, i18n-ключи, бюджеты, статусы зависимостей)
не нашла ни одного расхождения с текущим кодом. Один found-by-the-way момент
(две недоказанные гипотезы о соседнем поведении) снят ревьюером по существу —
не продуктовый вопрос, не требование к Э1, не состоявшийся Medium-дефект,
чтобы заводить issue без доказательства.
