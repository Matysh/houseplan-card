1. **Выбор модели (b) явно назван и непротиворечив.** П.3 теперь гласит:
   «Модель подтверждения задаётся видом команды, а не стеком» — с тремя
   явными ветками: новые структурные Copy/Delete (`confirmUndo`/`confirmRedo`,
   ожидание до ответа), уже поддержанные Move/Resize/Angle/визуальные/LED
   (текущая оптимистичная модель #843, без ожидания), смешанная цепочка (не
   больше одного исполняемого шага одновременно, следующий шаг — по курсору
   после известного исхода, неуспешный оптимистичный шаг не продвигает курсор
   к структурному). Это снимает саму неоднозначность (a)/(b) без остатка —
   текст прямо называет последствия выбора и описывает совместное поведение
   в смешанной цепочке, которого в r1-материале не было.
2. **Технические имена подтверждены чтением.** `confirmUndo`/`confirmRedo` —
   `src/command-stack.ts:104,107`, существуют и не изобретаются заново (как и
   в r1). `history.device_stale` — существующий плоский i18n-ключ
   (`src/i18n/ru.json:201`, `src/houseplan-card.ts:5609`,
   `src/led-strip-card.ts:95-96`), используемый при полной очистке истории
   устаревшей цели — утверждение «существующие очистки истории ... остаются
   как есть» в п.4 корректно описывает реальный, а не придуманный путь.
3. **Проверяемость новых и уточнённых AC.** AC4 получил однозначную
   формулировку порядка («шаг перемещения применяется сразу, шаги Copy/
   Delete — после подтверждения с видимым ожиданием; нажатие во время
   незавершённого шага не создаёт второго шага; отказ записи оптимистичного
   шага посреди цепочки возвращает курсор к нему же») — проверяемо через
   названный в «Доказательство» unit CommandStack/ownership + backend resource
   pins + smoke. Новый AC11 называет конкретный наблюдаемый результат
   (мгновенное превью без ожидания, прежний откат при отказе записи) и
   конкретное доказательство — существующие `test/device-position-history.
   test.mjs` и `demo/smoke_device_position_history.mjs` (оба файла
   подтверждены как существующие: `Glob` нашёл оба пути) «без ослабления» +
   новый unit выбора модели по типу команды + новый smoke превью на первом
   кадре. Ни один из двух AC не оставляет недоговорённости о том, что именно
   нужно доказать.
4. **Непротиворечивость внутри самого раздела.** UX-строка «Пока Undo/Redo
   структурной команды ждёт подтверждения ... кнопки истории и структурных
   действий неактивны» согласована с контрактным «новые Undo/Redo/Copy/Delete
   не принимаются и не ставятся в очередь» (п.3, смешанная цепочка) — одно и
   то же правило не сформулировано дважды по-разному.
