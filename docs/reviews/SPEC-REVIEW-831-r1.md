# SPEC-REVIEW-831-r1

Issue: #831 «Kiosk: sub-threshold jitter удержания блокирует клики в диалоге размеров»
Этап: spec (ревью ТЗ, PROCESS.md §2.4) · Трек: `track:ask` · Заход r1 · блокирующих циклов 0/4

## Материал ревью

Тело issue #831, раздел `## ТЗ`, и комментарии автора (оценка, передача на S4-spec-review,
запись о локальном черновике по §11.8). ТЗ живёт в теле issue (архив `docs/specs/` не
создаётся, #517). Черновик кода автора ревьюером ТЗ не читается и доводом не считается
(§2.4, §11.8) — не открывался.

Канон: `docs/SCOPE.md`, `AGENTS.md`, `docs/process/REVIEWER.md`, PROCESS.md §2.4/§2.5/§7.1,
`docs/TOUCH-SUPPORT.md` (подсистема touch/kiosk). `docs/USER-GUIDE.ru.md` для этой задачи не
даёт новой терминологии интерфейса — задача не меняет видимые тексты/экраны, но строка
диалога «Размеры на этом экране» сверена с `src/i18n/ru.json` (`kiosk.title`).

## Скоуп

Задача закрывает регресс в поверхности **View/kiosk** (J1/J3, `docs/SCOPE.md`): wall-tablet
kiosk hold открывает диалог per-screen масштаба, но при sub-threshold jitter (5–8 px —
между порогом click-suppression в 4 px и порогом распознанного pan/swipe в 8 px) новый
намеренный клик по Close не проходит. Зафиксированный в `docs/TOUCH-SUPPORT.md` контракт
("A new pointer down after the old contacts have ended starts a deliberate input sequence
immediately") уже обещает это поведение — задача приводит код в соответствие уже
зафиксированному контракту, а не придумывает новый. В скоуп/не-скоуп раздел ТЗ корректно
исключает #832 (Resize), новые gestures/UI, пороги и задержки, чужие находки.

### Проверка ключевых фактических утверждений ТЗ по коду (проверено чтением, не исполнением)

| Утверждение ТЗ («Проблема») | Где в коде | Вывод |
|---|---|---|
| «Stage movement >4 px выставляет `_suppressClick`, хотя pan/swipe распознаётся лишь при >8 px» | `houseplan-card.ts:6922` (`if (Math.abs(ddx) + Math.abs(ddy) > 4) { ...; this._suppressClick = true; ...}`) vs. `:6941` (`> STAGE_TAP_DISTANCE_PX` = 8, `room-fit.ts:108`) | Подтверждено |
| «открытие modal очищает stage pointers, но release может уйти в modal... и не очистить этот флаг» | `_interruptViewGesture` (`:5628-5648`) очищает `_pointers`, `_panStart`, `_panLock`, `_pinchStart`, `_swipeStart`, `_roomPointer`, но **не** `_suppressClick` | Подтверждено — именно эта асимметрия и есть баг |
| «Capture activation guard блокирует и новый Close» | `_guardTouchGesture` (`:7270`) → `TouchGestureClickGuard.handleActivation(ev, this._suppressClick)` (`touch-gesture-click-guard.ts:37`) на `click`; диалог (`_renderKioskDialog`, `:10650-10662`) рендерится внутри того же `<ha-card>`, чей `@click` слушатель — `_touchGestureGuard` (capture:true, `:10903`) | Подтверждено: клик по кнопке Close диалога проходит через тот же capture-guard, что и клики по сцене |
| «Простое снятие защиты при открытии modal небезопасно» | Существующий `TouchGestureClickGuard.pointerDown` уже re-arm'ит **свой** флаг `_postGestureClickBlocked` на новом pointerdown, но `_suppressClick` — отдельное поле card, им не управляемое | Корректное архитектурное наблюдение, а не домысел |

Отдельно подтверждено: существующий смок (`demo/smoke_kiosk_scale_no_editor.mjs`, блок «#813 AC1»)
уже гоняет mouse-hold с jitter, но только в раунде 0 и только `(+2,+1)` px (сумма 3 px) — **ниже**
4-пиксельного порога `_suppressClick`, поэтому существующий смок баг не ловит. Это объясняет,
почему регресс не был пойман раньше, и подтверждает, что AC1 требует именно нового диапазона
(5 px, между 4 и 8) — ТЗ формулирует это явно и корректно.

## AC — однозначность и способ доказательства

| AC | Доказательство | Однозначность |
|---|---|---|
| AC1 | smoke | Конкретный сценарий (mouse down → 5 px jitter → реальные 3 s → modal → release → новый Close click), именованный oracle, явное требование «не выдать timeout setup за RED», ≥3 повторов, инварианты (pointers пусты, frame/scale неизменны). Исполнимо как есть |
| AC2 | unit + smoke | Перечислены конкретные классы событий (release/cancel/lost-capture/delayed click без fresh intent), явное разграничение trusted vs dispatched для capture-теста, защита — negative events/registered mutation |
| AC3 | smoke + unit | Конкретные проверки: touch hold → release безопасен → новый trusted tap работает сразу; keyboard Enter/Space после release; второй/оставшийся contact не re-arm'ит |
| AC4 | existing smokes + unit | Регресс-защита (#813/#825 результаты), явно снята обязанность гонять мутанты в этом цикле, но требует названной мутации в реестре — согласуется с §2.7/track:ask |
| AC5 | smoke + code review | «ревью кода» — разрешённый способ доказательства по DoR (§2.5); конкретный набор инвариантов (cold kiosk, editor chunk refused, no service/write, no new i18n/schema/render/CSS) |

Ни одного AC без названного способа доказательства; ни одной догадки о текущем поведении,
не подтверждённой кодом или `docs/TOUCH-SUPPORT.md`.

не наблюдает, агенты решают сами»).

## Находки

Нет High. Нет Medium (ни в скоупе, ни вне скоупа). Низкая находка ниже — снята ревьюером
как не требующая правки текста ТЗ (решение технической редакции остаётся за автором при
реализации, без влияния на приёмку).

- **Low (снято):** контракт п.3 говорит «новый pointerdown... на диалоге re-arms» — в коде
  (`TouchGestureClickGuard.pointerDown`) re-arm происходит на **любом** pointerdown внутри
  `<ha-card>` (capture-слушатель вешается на карточку целиком, не только на диалог). Разница
  не наблюдаема пользователем, пока диалог модален и ничего другого под ним недоступно, поэтому
  не продуктовый вопрос — формулировка ТЗ достаточно точна для приёмки, уточнение не требуется.
