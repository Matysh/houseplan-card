### Почему r2, а не слияние после зелёного r1

r1 (материал `23447c36`) получил зелёный вердикт без находок, документ и
индекс были опубликованы в ветку (`cafc57fe`, `1a086aa6`) — штатный шаг
конвейера после зелёного вердикта. Дальше `dev` ушёл вперёд несколько раз во
время слияния (гонка #492), ветку трижды ребейзили, автосверка процесса
зафиксировала «Validate on the material is completed but the round was not
resumed» и разбудила `S7-code-review` заново на новом материале. Это ребейз на
ушедший вперёд `dev` — один из случаев, когда разбор остаётся полным, а не
сокращается до дельты (§2.10, конспект «Повторный раунд»), поэтому ниже —
полный разбор, а не только показ закрытия находок r1 (их и не было).

## Как проверялось

1. Сверено, что дерево материала r2 после ребейза не разошлось по содержанию
   с тем, что проверял r1: `git diff 94192889~1 94192889 --stat` даёт ровно
   те же 4 файла / 141 вставку / 3 удаления, что и r1 на `23447c36`; хеш
   текста диффа (`scripts/process-gate.mjs`, `scripts/mutation-registry.mjs`,
   `test/process-gate.test.mjs`, `PROCESS.md`) посчитан и сверен — **содержимое
   патча бит-в-бит то же**, что проверял r1. Старое дерево материала r1
   (`e94227ed9fa2…`) само по себе уже не резолвится — объект собран как
   мусор после ребейза; это не находка (конспект «Повторный раунд»: мёртвый
   SHA — обычное дело, если дерево при публикации существовало, а находка —
   только мёртвый SHA уже в момент публикации отчёта; свежий тег подтверждён
   числом изменённых строк и текстом).
2. Проверено, не задевает ли содержательно новые коммиты `dev` между
   материалом r1 и r2 ту же область кода: `git log 88985d2e..origin/dev --

## Что проверено и корректно

- **AC1** (исключение не для маршрута ТЗ) — без изменений от r1, содержимое
  патча идентично. `specRoute = names ∩ SPEC_ROUTE_STATUS`,
  `optional = statusOptional && specRoute.length === 0`; при непустом
  `specRoute` — отказ с текстом, называющим статус, §11.8 и #562 (`:505-508`
  в текущей нумерации, что совпадает по смыслу с `:496-514` из r1 — смещение
  строк из-за восстановленных комментариев выше по файлу, не из-за правки
  логики). `S1-new`/`S2-analysis` вне `SPEC_ROUTE_STATUS` — соответствует
  ТЗ. Юнит покрывает все случаи таблицы АС, включая два issue в одном
  диапазоне и `blocked` поверх специального статуса. Прогнан заново — зелёный.
- **AC2** (сквозной CLI) — без изменений от r1. `S4-spec-review`/`S3-spec` →
  выход 1, `FAIL п.8`, текст с `#753 в <статус>`; `S1-new` → выход 0 и
  предупреждение #562 без `FAIL`. Прогнан заново — зелёный.
- **AC3** (канон + мутант) — без изменений от r1. PROCESS.md §10.2 содержит
  предложение дословно. Мутант `process-gate-infra-entry-covers-spec-route`
  назначен guard'ом `node --test test/process-gate.test.mjs`; целевой прогон
  мутационного гейта на этом SHA подтверждает `ok` (мутант убит новым тестом).
- **Доказательство «тест умеет падать»**: перепрогнано самостоятельно на
  текущем материале, не принято на слово ни от автора, ни от документа r1:
  `node scripts/mutation-gate.mjs --id=process-gate-infra-entry-covers-spec-route --check`
  → `ok`.
- Сообщение `main()` про предупреждение #562 по-прежнему печатается для
  всего диапазона независимо от отказа по конкретному issue — подтверждено
  тестом AC2 (оба сообщения одновременно).
- Трейлеры: `94192889` несёт `Issue: #753`, `User-Visible: no` — корректно
  (CI-гейт, пользовательского поведения нет, CHANGELOG не тронут и не
  должен быть). `cafc57fe` и `1a086aa6` — документация публикации
  (документ ревью и индекс), тоже с `Issue: #753`, `User-Visible: no`; по
  правилу (PROCESS.md §3 п.10) докс-коммит класса C может не нести трейлеры
  вовсе — здесь они проставлены сверх минимума, это не находка.
- Числовых величин, видимых пользователю дважды, диапазон не вводит —
  не применимо, задача не трогает UI.
- Ребейз не оставил конфликтных маркеров, `.orig`-файлов или следов
