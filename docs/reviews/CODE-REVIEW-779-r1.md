## Скоуп

Баг `scripts/reviews-index.mjs`: раздел «Закрытие раунда r<N−1>» (обязателен
по §2.10 для каждого повторного раунда) пересказывает вердикт **прошлого**
раунда строкой вида `Вердикт r2 — зелёный, … (High: 0, Medium: 0)`. Прежний
`VERDICT_OWN_LINE_RE`/`verdictLine(…, true)` считали «своей» любую строку,
просто **начинающуюся** со слова «Вердикт», и `parseVerdict`/`parseCounts`
брали из неё чужой цвет/счётчики раньше настоящей сводки документа —
конкретно `docs/reviews/SPEC-REVIEW-662-r3.md` индексировался как
`🟢 зелёный 0 0`, хотя документ заканчивается `**Вердикт: жёлтый.**` /
`High: 0 · Medium: 2`.

Правка вводит двухуровневое понятие «своей» строки (`Вердикт:`/`Verdict:` с
двоеточием сразу после слова, плюс машинная `Вердикт конвейера:` — высший
уровень; `Вердикт <цвет>` без двоеточия, но не `Вердикт rN …`, — второй
уровень), запрещает пересказу `Вердикт rN —/: …` засчитываться вообще (ни как
свой, ни как упоминание) и добавляет `summaryParagraph()` — поиск последнего
абзаца, начинающегося с `High: N`, как источник счётчиков между секцией
«## Вердикт» и строкой-упоминанием. Меняется только генератор индекса (класс
C/B), продуктовый код и пользовательское поведение не затронуты —
`User-Visible: no` на коммите корректен, второй changelog не требуется.

Один класс изменений (A/B/C по AGENTS.md): задача инфраструктурная
(`scripts/**`, `test/**`, `docs/reviews/INDEX.md` — генерируемый класс D,
но здесь класс D не расходится с классом B, т.к. регенерация детерминирована
кодом этого же коммита), входит на `S7-code-review` напрямую, без спеки —
соответствует правилу AGENTS.md про инфраструктурные задачи.

## Находки

### Medium (в скоупе) — `summaryParagraph()` выбирает «последний абзац на `High:`», доверяя порядку секций, которого формат документа не гарантирует

**Файл:** `scripts/reviews-index.mjs:138-149` (функция `summaryParagraph`),
используется в `parseCounts` (`scripts/reviews-index.mjs:248`) между
`verdictSection(text)` и упоминанием-пересказом.

Комментарий к функции обосновывает выбор «последнего» абзаца допущением:
«пересказы прошлых раундов стоят в начале документа, вывод — в конце». Это
не гарантия формата, а наблюдение по части корпуса. В самом корпусе
`docs/reviews/*.md` порядок секций не зафиксирован: `SPEC-REVIEW-728-r2.md`
кладёт `## Вердикт` первой строкой (после шапки), раньше `## Унаследовано из
r1`; `SPEC-REVIEW-774-r2.md` и `SPEC-REVIEW-806-r2.md` — наоборот, `##
Вердикт`/`## Вывод` в самом конце, после `## Унаследовано из r1`. Порядок
выбирает автор ревью сессии, инструкция конвейера (промпт ревьюера) его не
диктует.

**Воспроизведение** (не из рабочего дерева — синтетическая фикстура,
построенная на реальных формах корпуса; прогнано здесь локально против
кода этого коммита, `scripts/reviews-index.mjs`):

```js
import { parseVerdict, parseCounts } from './scripts/reviews-index.mjs';

const doc = [
  '## Вывод',
  '',
  'High: 0 · Medium: 0.',
  '',
  '## Унаследовано из r1',
  '',
  'Принято без проверки:',
  '',
  '- High: 2, Medium: 1 (закрыто в r1)',
  '',
  '## Вердикт',
  '',
  'Зелёный.',
].join('\n');

parseVerdict(doc); // 'зелёный' — верно
parseCounts(doc);  // { high: 2, medium: 1 } — НЕВЕРНО, документ заявляет 0/0
```

Условие срабатывания: (1) собственный вердикт документа не несёт счётчики
прямо в своей строке/секции (нужна отдельная сводная строка `High: N ·
Medium: N`, как и в реальном `SPEC-REVIEW-662-r3.md`), и (2) где-то дальше по
тексту документа абзац **начинается** с `High:`/`- High:` — это в точности
то, во что реалистично превращается пересказ «Унаследовано из r<N−1>», если
автор процитирует старый счётчик как отдельный пункт списка, а не как
вставку в предложение (как сделано сейчас в `SPEC-REVIEW-662-r3.md`,
`докс/reviews/SPEC-REVIEW-728-r2.md` и др. — там пересказ всегда вставлен в
прозу, не начинает абзац). Правка защищает ровно одну текстовую форму
пересказа — ту, что начинается со слова «Вердикт» — но не защищает новую
форму `summaryParagraph` сама и вводит: пересказ, начинающийся с «High:».

Это тот же класс дефекта, который issue прямо называет повторяющимся
(«сам приём… стандартный, и будет повторяться», раздел «## Причина»): задача
просила общую устойчивость парсера к разделу «Закрытие/Унаследовано», а не
только к наблюдённой на `SPEC-662-r3` конкретной формулировке. В сегодняшнем
корпусе `docs/reviews/*.md` (проверено `--check` и выборочным чтением
`SPEC-REVIEW-728-r2.md`, `774-r2.md`, `780-r2.md`, `806-r2.md`) такой формы
пересказа ещё нет — поэтому регресс по существующим ~1000 документам
отсутствует и утверждение автора «ровно одна строка изменилась» верно.
Находка — про следующий документ, который этот же механизм неверно
проиндексирует, а не про уже случившееся молчаливое искажение.

**Почему Medium, не Low:** это не бухгалтерия (не пропущенный мутант, не
нечувствительный тест) — это воспроизводимый дефект поведения компонента
(`parseCounts` возвращает числа, прямо противоречащие тексту документа),
причём в той самой функции, которую коммит вводит для решения ровно этой
категории багов. `docs/reviews/INDEX.md` — читаемая владельцем и ревьюерами
база знаний по решениям; неверные High/Medium в ней — именно то, что issue
просит прекратить в принципе, а не один раз.

**Предлагаемое направление (не моя работа — для автора):** не выбирать
«последний» абзац из всего документа, а искать совпадающую собственную
сводку только внутри диапазона [строка своего вердикта/секции «Вердикт» —
конец документа] или сразу **перед** первым найденным заголовком
«Закрытие раунда»/«Унаследовано», аналогично тому, как уже тонко решена
проблема пересказа текста «Вердикт».
