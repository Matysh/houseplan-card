## Контракт и отрицательные свидетели

| Требование | Чем доказано | Чем краснеет |
|---|---|---|
| Прогон, начавшийся за 1 с до повторной метки, не входит в кандидаты нового запроса | Новое `assert.deepEqual(reviewRunsForRequest([ready], f.issue, justReapplied), [])` — прямой вызов фильтра, по которому кандидатов отбирают `decideReconciliation`, `snapshot` (`process-reconcile.mjs`) и `decideResume` (`process-resume.mjs:62`) | Мутант реестра `pending-revives-previous-request`: окно `>= at(request.at) - 120_000` возвращает `[ready]` вместо `[]` |

Без применения мутанта чувствительность проверена входом. Тот же прогон подан с запросом, сдвинутым на 120 с назад, — это ровно окно мутанта, код не правился.

```
boundary (code):                      0   кандидатов
mutant-equivalent window via input:   1   кандидат
```

Утверждение `deepEqual(..., [])` различает эти случаи. Мутант на этом входе даёт `[ready]`, и тест краснеет.

Почему мутант сбежал. В #775 (`09fb02cf`) свидетелем было только утверждение на уровне решения: `decideReconciliation(... now = момент метки ...)` → `wait`. Это `wait` получается при обоих вариантах кода, по разным причинам:

```
decide now=req, correct:                  label event is still within delivery grace
decide now=req, run treated as matching:  completed run is still within label-application grace
```

Ветка «завершённый прогон ещё в grace» существует с #555, поэтому утверждение было нечувствительно к границе с самого появления мутанта. Новая строка прямо закрывает эту причину.

## Что проверено и корректно

1. Исправление попадает в причину, а не в симптом. Граница запроса живёт в одной функции `reviewRunsForRequest`, мутант патчит именно её, и тест теперь судит её результат. Ослаблять реестр или переносить мутант не понадобилось.
2. Импорт `reviewRunsForRequest` берётся из того же модуля, что и `decideReconciliation`, — это не копия логики в тесте. Экспорт в `process-reconcile.mjs` уже существовал, поэтому продуктовый и скриптовый код не тронут, что подтверждает `--stat` (1 файл, только тест).
3. Фикстура — реальная идентичность инцидента #740 (`run 36877086418`, `14:32:05Z`), запрос `14:32:06Z`. Сдвиг в 1 с — самый жёсткий случай границы: он отделяет `>=` от сколько-нибудь широкого окна. Обратный случай «прогон в момент метки входит» уже держат соседние тесты, где `request.at === run.createdAt` и решение `resume`/`retry`.
4. `track:show` обоснован. Меняется один тест, новых поверхностей, миграций, UX, геометрии и perf-касаний нет. Маршрут `fix`, оснований для `reclassify` нет.
5. «Одно число — один источник»: новых чисел дифф не вводит. Литерал `14:32:06Z` был в тесте раньше и связан с фикстурой (+1 с); новая строка переиспользует ту же переменную `justReapplied`.

## Находки

### L1 — утверждение на уровне решения по-прежнему не различает границу

`test/process-pending-round.test.mjs:166–167`: `decideReconciliation({ ..., now: Date.parse(justReapplied.at), runs: [ready] }).action === 'wait'`. Сообщение утверждает «cannot be recovered as the new request», но при `now`, равном моменту метки, оба варианта кода дают `wait` (см. выше). Если сдвинуть `now` за grace, они снова совпадают: `ready` несёт `pending` с завершённым Validate, а это `retry` в обоих случаях. Различает только прогон с `conclusion: 'failure'` после grace: правильный код даёт `retry`, а окно мутанта — `escalate`.

Утверждение безвредно и после этой задачи не является единственным свидетелем. Улучшить его можно двумя способами: сравнивать `reason` или взять failure-прогон после grace. На треке `show` нечувствительный тест на побочный вызов — Low (§10.4). Снимаю с блокировки с записью, цикла не открывает. Код в рамках ревью не правился.
