## Скоуп

Баг: при сохранённом OFF и включённом в черновике тумблере «Показывать связи
Zigbee при наведении на устройство» кнопки запуска скана/чтения остаются
недоступны, пока пользователь не сохранит и не переоткроет настройки. ТЗ вводит
составное действие «Сохранить настройки и обновить карту» / «…и прочитать ZHA»
в общих настройках: сохраняет текущий черновик диалога по существующему
CAS-пути и затем, только после подтверждённого ACK, запускает
загрузку/сканирование для конкретного провайдера/топика. Это J7 (диагностика
Zigbee) и J4 (быстрая настройка без лишних кликов) из `docs/SCOPE.md`; View и
киоск не меняются (`docs/TOUCH-SUPPORT.md`: редакторы — desktop-first, этого
ТЗ правило не нарушает).

## Как проверялось

Ревью ТЗ README-уровня: обязательные разделы §7.1, однозначность и способ
доказательства каждого AC, отсутствие недекларированных допущений,
согласованность с `docs/SCOPE.md`/`docs/USER-GUIDE.ru.md`/`docs/TOUCH-SUPPORT.md`.
Дополнительно — техническая реализуемость контракта сверена чтением (не
исполнением) кода, который ТЗ называет точками изменения, чтобы отличить
«недоказуемое заявление» от «реального поведения, которое ТЗ корректно
описывает»:

- `src/hp-zigbee-topology-settings.ts` — текущий `mayLoad = admin &&
  savedEnabled`, `_observing` требует `savedEnabled`, кнопки `zha_read`/
  `z2m_update` вызывают runtime напрямую без сохранения конфигурации;
  `save_first`-подсказка и disabled-состояние уже существуют для случая без
  сохранённого ON — это ровно то состояние, которое по AC9 должно остаться для
  standalone-использования без owner callback (подтверждено использованием в
  `demo/smoke_zigbee_topology_job.mjs:92`, где компонент создаётся
  `document.createElement` без встраивающего диалога).
- `src/editors/general-settings-dialog.ts` — `hp-zigbee-topology-settings`
  встроен как `embedded`, значение приходит из `d.zigbeeTopology`,
  `savedEnabled` — из `zigbeeTopologySettingsOf(host._settings)`; других мест
  встраивания нет.
- `src/houseplan-editor-runtime.ts:9345` (`_saveSettingsDialog`) — реальный
  save pipeline: `dialogSession`-фенсинг владельца диалога, `beginOptimistic`/
  `_saveConfigNow` (CAS/expected_rev), безусловное закрытие диалога на успехе
  и откат на ошибке. Именно этот путь ТЗ просит переиспользовать «в режиме
  оставить открытым», не создавая второй writer — технически это совпадает с
  тем, что уже есть.
- `src/editors/general-form-state.ts` + `src/editors/dialog-baseline.ts` —
  `generalDirty`/`rememberGeneralBaseline`/`forgetGeneralBaseline`,
  `dialogSession` создаёт новый `{}` при каждом `rememberDialogBaseline`.
  Контракт п.7 («после успешного save без закрытия baseline отражает
  сохранённый снимок») и п.8 («другой settings session… запрещают старому
  callback запускать действие») вместе корректно описывают нужное поведение:
  после keep-open save baseline обязан быть пересчитан (иначе дальнейшее
  закрытие ошибочно спросит про несохранённые изменения), а проверка перед
  запуском скана должна идти по **текущей**, а не по захваченной до сохранения
  сессии. Это нетривиальная техническая ловушка, но ТЗ её не прячет — явно
  требует «повторной проверки действующего диалога» перед стартом скана
  (контракт п.4) и относит выбор механизма к «принято предположительно». Это
  граница между продуктовым и техническим вопросом проведена верно (§7.1):
  как именно фенсить сессию — не продуктовый вопрос, и ТЗ закономерно не
  выносит его владельцу.
- Существующий паттерн generation-guard в том же файле
  (`_ensureRuntime().then(runtime => { if (generation !== this._generation...)
  return; …})`) показывает, что «один pending action на компонент» и защита от
  устаревшего callback — не новая идея для этого компонента, а продолжение уже
  работающего идиоматического решения.
- i18n: `src/i18n/topology/ru.json` подтверждает текущие ключи `save_first`,
  `zha_read`, `z2m_update`, `toggle` — новые ключи ТЗ (`save_and_update`,
  `save_and_read_zha`, `save_and_load_help`) не конфликтуют с существующими и
  используют тот же namespace.
- `docs/USER-GUIDE.ru.md:490-519` — терминология ТЗ («Обновить карту»,
  «Прочитать данные ZHA», «связи Zigbee») совпадает с уже описанным
  пользовательским интерфейсом; ТЗ не придумывает новых терминов для старых
  понятий.

## Проверка обязательных разделов (§7.1)

Присутствуют и заполнены по существу: сценарий · что человек увидит до/после ·
проблема · скоуп и не-скоуп · контракт поведения (9 пунктов) · UX и i18n ·
модель данных и миграция · критерии приёмки AC1…AC8 с графой «способ
доказательства» · план автотестов · риски · откат · release-артефакты.
Раздел «Принято предположительно» присутствует и ограничен техническими

ни один пункт не маскирует продуктовое решение под техническое.

## Находки

Высоких и средних находок нет.

Низкое, не образует находки ревью (снимается самим ревьюером, запись для
памяти по §2.4):
- Контракт п.1 говорит о составном действии «для конкретного
  провайдера/топика», но ни один AC явно не описывает случай нескольких
  Z2M-топиков одновременно (список топиков уже поддерживается компонентом —
  `_topics()`/`_z2mRow` на топик). Это не продуктовая развилка: текущий UI уже
  рендерит кнопку на топик, и естественная реализация — composite-кнопка на
  том же месте для каждого топика, что покрывается AC1 по аналогии. Не
  поднимаю до Medium: AC1 проверяет наблюдаемый результат (кнопка активна,
  один клик — одно сохранение и один scan), а не конкретную топик-раскладку,
  и смок-тест на реальном компоненте неизбежно это зафиксирует.

## Что проверено и корректно

- Каждый AC (AC1…AC8) имеет однозначный наблюдаемый результат и явно названный
  способ доказательства (`smoke`/`unit`), включая отрицательные случаи для
  защитных AC2/AC4/AC6/AC8 — соответствует DoR §2.5.
- Контракт поведения не противоречит текущему коду ни в одном из девяти
  пунктов; наоборот, корректно описывает существующие инварианты (CAS/
  expected_rev, dialogSession-фенсинг, generation-guard, admin-only,
  `save_first`-fallback) и явно формулирует, что меняется, а что — нет.
- Не-скоуп исключает Python/WS API, admin-only политику, background jobs/
  cancel, геометрию плана и LQI (#1029) — все точки сверены по коду, ни одна
  из них не трогается описанным контрактом.
- Модель данных: заявление «новых persistent полей и версии схемы нет»
  подтверждается чтением `writeZigbeeTopologySettings`/`zigbeeTopologySettingsOf`
  — новых полей конфигурации контракт не требует, только transient UI/async
  состояние.
- UX-текст (RU точный, EN точный) и три новых ключа не конфликтуют с
  существующим i18n-namespace `topology`.
- Открытых продуктовых вопросов действительно нет: единственная неочевидная
  область (владение сессией между save и start) корректно классифицирована
  как техническая и оставлена реализации, а не владельцу.
- Трек `ask`, подтверждённый владельцем (новый явный UX-контракт,
  async/CAS-риски, ошибки) — соответствует критериям §5 для `ask` и не
  подлежит ревью на предмет занижения/завышения трека на этапе ТЗ.

- Ручную/GPU-приёмку владельцем — не требуется и не проводилась (добровольна,

- Полноту переводов DE/FR — ТЗ прямо называет точный RU/EN текст и оставляет
