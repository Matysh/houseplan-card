# SPEC-REVIEW-842-r1

Issue: #842 · Этап: spec · Трек: ask · Заход: r1 · блокирующих циклов было
израсходовано 0 из 4 на входе в этот раунд.
Материал: тело issue #842, редакция 2 от 13.10.2026, сверена автором с
`origin/dev 3b3e0826`; сессия ревью работает на рабочей копии на
`3b3e08268bdc1ea1f3065d643295bd44a73e9759` (дерево
`4f547dae04714ef9d082d9160a2b1cba012e19dc`). Хеш тела issue на момент
ревью: `ea529bec00e846c16cfef0d83f3f5a94e5298f758771a40e7a196e5967d22ecf`.
Ревью кода не запускалось — реализация не начата («ревью и реализация не
запускались» в теле issue).

## Скоуп

Один контракт сохранности данных: (а) подготовка candidate для записи
(`_prepareConfigCandidate`/`_dropLegacySegments`) не должна молча терять
`partitions`/`wall_columns`/зависимые `openings`, а при обнаруженном
удалении — отказывать в записи и предлагать явное подтверждение; (б) отказ
немедленной записи, которой предшествовала отмена отложенной записи
независимой правки (маркер, LED-полоса, калибровка пылесоса, запись
жизненного цикла зон, vacuum-maps), должен восстанавливать эту отложенную
запись, а не терять её молча. Закрывает J4/J6 (`docs/SCOPE.md`): создать и
безопасно поддерживать план; safety floor запрещает тихую потерю данных.
Не входит: новый формат хранилища, перепроверка стора при загрузке,
автоматическая очистка, last-writer-wins, `walls`-деградация (остаётся
канонической очисткой без диалога).

  `extra=vol.ALLOW_EXTRA`; строка отказа
  `"partition opening host must exist in the same space"` существует
  буквально (`validation.py:1773, 2107`).
- `rollbackOptimistic` (`config-adoption.ts:254-261`) возвращает `true`
  только когда текущая ревизия и fingerprint ещё совпадают с этой
  попыткой — подтверждает К4/К5 формулировку «если откат вернул состояние
  этой попытки».
- `HpConfirmController` (`danger-confirm.ts:38-75`) — действительно

Гейты кода не прогонялись: этап `spec`, зависимости и Chromium не
ставились (#696), реализации ещё нет. Это ожидаемо для этого этапа, а не
пропуск.

## Находки

### Medium (в скоупе) — AC не покрывают заявленный «обычный» путь записи

Контракт К1–К5 явно заявлен для «всех записей редактора» (раздел «Скоуп и
не-скоуп», «Входит: подготовка candidate для всех записей редактора»), а
«Проблема» открывается фразой «Обычное сохранение посторонней настройки
может отфильтровать перегородки и колонны» — это ровно фоновый,
ничем не инициированный путь: `_saveConfig()` → `_saveConfigDebounced`
(`houseplan-card.ts:7865`) → `_writeConfig()` **без** `attempt` и без
какого-либо открытого диалога операции. `_saveConfig()` вызывается из 17
разных мест в `houseplan-editor-runtime.ts` (перенос декора, resize,
presentation-правки и т.д.) — не только из пяти «именных» операций.

АC1–AC6 тестируют только пять явно названных немедленных операций
(диалог маркера, LED, vacuum, явное удаление перегородки/Optimize) — у
каждой из них есть `attempt` (оптимистичная попытка) и открытый диалог с
черновиком. Ни один AC не нацелен на фоновую запись без `attempt` и без
диалога:

- АС2 прямо требует для своих фикстур «диалог маркера открыт с
  черновиком» — то есть сам сценарий привязан к пути маркера, а не к
  фоновому debounce.
- К2 формулирует откат через «оптимистичное состояние операции
  откатывается её обычным `rollbackOptimistic`» и «открытый диалог
  операции остаётся открытым со своим черновиком» — для фоновой записи
  нет ни `attempt`, ни диалога операции, и ТЗ не говорит явно, что в этом
  случае оба пункта вакуумно истинны (нечего откатывать, нечего держать
  открытым), а что фактически увидит администратор: диалог К3 появляется
  незапрошенным, посреди произвольного взаимодействия (после правки
  декора/resize/настройки, без нажатой кнопки «Сохранить»).
- «План автотестов» называет только «подготовку и R — новый тест рядом
  с существующими тестами записи» (unit, по сути — тест чистой функции)
  и пять unit по именным местам К4; ни unit, ни smoke не нацелены на
  наблюдаемое поведение фонового debounce-пути при непустом R.

**Воспроизведение (по коду, не исполнением):** план с вырожденной
перегородкой (`length ≤ 1e-9`) загружен в редактор; администратор правит
декор/комнату без открытия диалога маркера/LED/vacuum (`_saveConfig()` на
любой из 17 точек); через 500 мс срабатывает `_saveConfigDebounced` →
`_writeConfig()` с `attempt = null`. По К2 `config/set` не должен уйти —
но ТЗ не фиксирует ни `attempt`-независимую семантику отката (при
`attempt === null` `rollbackOptimistic` неприменим, потому что сам
`_writeConfig` мутирует живой `_serverCfg` напрямую — см. «как
проверялось»), ни то, что именно увидит пользователь (всплывающий К3 без
предшествующего намеренного Save), ни доказательство для этого случая.

Это не продуктовый вопрос (режим диалога К3 как компонента уже решён),
а технический пробел полноты AC: раздел «Входит» и «Проблема» уже
утверждают покрытие фонового пути, но ни один AC/тест его не называет.
Устраняется либо явным AC7 (фикстура без открытого диалога: правка декора
+ вырожденная перегородка → К2 блокирует `config/set`, К3 показывается,
«Удалить и сохранить» включает отложенную правку декора, «Отмена» не
меняет живой конфиг и правка декора остаётся локально неотправленной),
либо явным сужением scope-раздела с обоснованием, почему фоновый путь
сводится к уже протестированному.

## Что проверено и корректно

- Обязательные разделы §7.1 (сценарий; что человек увидит до/после;
  проблема; скоуп/не-скоуп; контракт поведения К1–К5; UX; модель
  данных/миграция; i18n; AC1…AC6 с доказательством; план автотестов;
  риски; откат; release-артефакты) присутствуют и заполнены по существу,
  не формально.
- i18n: все четыре зарегистрированных словаря (`ru/en/de/fr`) существуют;
  таблица ключей заполняет `ru`/`en`; `de`/`fr` помечены «переводятся по
  смыслу» — приемлемо для DoR (перевод — не продуктовая неоднозначность).
- Каждый AC1–AC6 — защитный и имеет непустую колонку «чем должен
  краснеть» с названным witness на `dev` или названным мутантом (АС3:
  «R без проёмов на перегородке» — явная мутация).
- Границы К2 (сравнение R с кандидатом **до** подготовки, чтобы не
  принять за R удаление самой операции) и AC6 как её прямая защита —
  логически непротиворечивы и соответствуют реальному коду:
  `_dropLegacySegments` сегодня действительно безусловно выбрасывает
  найденные записи, то есть R, вычисленный после операции Delete, был бы
  уже пуст без явного «снимка до» — корректное основание для AC6.
  Указание «К5» зайцем закрывает обходной путь restored-записи, пишущей
  устаревший кандидат (явно: «нет устаревшего документа с новой
  ревизией»).
- Технические «принято предположительно» решения в конце ТЗ (критерий
  вырожденности 1e-9, R на копии, имя общего хелпера ожидания, имена
  фикстур/модулей, конкретный smoke AC6) — ревьюером не оспариваются:
  решения корректны и явно помечены как «можно менять», не выданы за
  факт.
- Пять мест К4 и их `cancel()`-строки, заявление об общем id-namespace
  partitions+wall_columns, `WALL_COLUMN_SCHEMA extra=ALLOW_EXTRA`, точный
  текст backend-ошибки на проёме удаляемой перегородки, поведение
  `rollbackOptimistic` и `HpConfirmController` — все сверены построчно с
  кодом и соответствуют тексту ТЗ (раздел «Как проверялось»).
- Открытых продуктовых вопросов владельцу действительно нет: оба пункта,
  которые первая редакция оставляла неявными, закрыты решением владельца
  от 2026-10-13 и воспроизведены в теле issue дословно.
- Зависимость и порядок с #843/#845 названы явно, не создают скрытого
  блокера этой задачи.

- Гейты кода (`tsc`, `npm test`, `npm run build`, golden, smoke, pytest,
  invariants, performance) — не прогонялись и не требовались: этап
  `spec`, реализации ещё нет, зависимости/Chromium не установлены (#696).
  Это не находка для spec-этапа.
- Фактическое поведение живой инсталляции (воспроизведение потери данных
  на проде) — не проверялось и не требовалось: сам автор прямо пишет,
  что это подтверждённые по коду опасные пути, а не воспроизведённый
  инцидент; дальнейшая проверка — дело код-ревью и smoke/unit из плана
  автотестов.
- `docs/release-ledger/<previous-stable>/842.json` — не создан до S7 по
  процессу (п. 2.6: классификация — до код-ревью, не до ТЗ); на spec-этапе
  не проверяется.
- Корректность возможной реализации (конкретный способ клонирования
  `_serverCfg` перед подготовкой, конкретное место, где физически будет
  жить флаг pending-debounce) — решение автора реализации, не предмет
  ТЗ-ревью.

## Вердикт

Единственная находка — Medium **в скоупе задачи**: AC1–AC6 и план
автотестов не называют доказательство для фонового (ничем не
инициированного, без `attempt` и без диалога) пути записи, который сам
раздел «Входит» и «Проблема» уже относят к контракту К1–К5. Без
High-находок это жёлтый вердикт: автор добавляет AC (или явно сужает
scope с обоснованием) и проходит повторный цикл.
