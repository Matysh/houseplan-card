# SPEC-REVIEW-875-r1

Issue: #875 «Пустой план: добавить кнопку «Import backup» рядом с «Add space»»
Этап: spec (ревью ТЗ, PROCESS.md §2.4) · Трек: ask · Заход: r1 · блокирующих циклов 0/4
Материал: тело issue #875, раздел `## ТЗ` (редакция 1 от 13.10.2026); анализ в
ТЗ ссылается на dev `c7c81adcd03872276b201defceb13978cc81f07e` — тот же SHA,
на котором стоит рабочая копия.

## Скоуп

Новая точка входа в существующий импорт резервной копии House Plan: кнопка
«Import backup» на пустом экране (`spaces: []`), рядом с «Add space».
Переиспользует штатный importer (`/api/houseplan/import/preview` →
`_renderBackupImportDialog` → `import/apply`); не меняет формат копии, ACL,
схему хранения или сам Add space. Обслуживает J4/J6 `docs/SCOPE.md`
(«с нуля до рабочего плана без Inkscape/YAML» и «держать план достоверным»).
Продуктовый код не менялся — ревью оценивает только ТЗ.

## Как проверялось

1. `docs/SCOPE.md` → `AGENTS.md` → `docs/process/REVIEWER.md` — прочитаны
   целиком перед ревью (порядок из промпта).
2. Тело issue #875 и его ТЗ прочитаны через `gh issue view 875` (MCP
   `github.get_issue`/`get_issue_comments` не выдан сессии разрешением —
   использован `gh` CLI с тем же содержанием).
3. Обязательные разделы ТЗ сверены построчно со списком PROCESS.md §7.1:
   сценарий, что человек увидит до/после, проблема, скоуп/не-скоуп, контракт
   поведения (K1–K7), UX, модель данных и миграция, i18n, AC1–AC7 с
   доказательством и отрицательной пробой, план автотестов, риски, откат,
   release-артефакты — присутствуют все, в этом порядке или эквивалентном.
4. Технические утверждения ТЗ сверены чтением фактического кода на
   `c7c81adc` (не исполнением — на этапе spec это и есть штатный метод):
   - `src/houseplan-card.ts:10755–10784` (пустая ветка `_renderBody`,
     `model.length === 0`): подтверждено — кнопка `create-space` действительно
     одна, гейт `this._serverStorage && this._canManageConfiguration`,
     рендерятся `_spaceDialog` и `_importDialog`, `_backupImportDialog` в этой
     ветке отсутствует.
   - `src/houseplan-card.ts:1020–1024`: `_canManageConfiguration` читает
     `_serverCanWrite`/`hass.user.is_admin`, **не** зависит от `_norm`;
     `_canEdit = _norm && _canManageConfiguration`. Подтверждает ключевое
     техническое основание K1 — нельзя было бы использовать `_canEdit`
     напрямую на пустой установке, так как `_norm` там не определён.
   - `src/houseplan-card.ts:11367`: `_backupImportDialog` в непустой ветке
     рендерится при условии `this._editorRuntime` (тяжёлый чанк), а не
     `_onboardingRuntime` (используется для `_spaceDialog`/`_importDialog` на
     пустом экране) — реальная развилка реализации, которую ТЗ корректно не
     решает как продуктовый вопрос (раздел 14, «способ instance-local request
     ownership» оставлен свободным).
   - `src/houseplan-editor-runtime.ts:9173` `_pickBackupImport(ev: Event)`:
     синхронно читает `ev.target`/`input.files[0]`, сбрасывает `input.value`.
     Подтверждает требование K2 «сохранить File отдельно от живого
     DOM Event до завершения lazy-load; не хранить сырой Event через await» —
     без этого правила повторный выбор того же файла или гонка с async-загрузкой
     рантайма реально ломались бы на этом коде.
   - `src/editors/general-settings-dialog.ts:258–270`: существующая кнопка
     импорта в настройках гейтится `host._canEdit` (значит зависит от
     `_norm`) — подтверждает, почему новую кнопку нельзя получить
     копированием существующего гейта без изменений.
   - `src/i18n/settings/{ru,en,de,fr}.json:111–112` vs `src/i18n/{ru,en,de,fr}.json`:
     подтверждено разделение неймспейсов — `backup.import_open` живёт в
     лениво загружаемом namespace настроек, новый ключ `empty.import_backup`
     ТЗ размещает в основном (core) i18n-файле, который доступен без догрузки
     settings-чанка. ТЗ прямо запрещает трогать `backup.import_open` —
     корректно, иначе получили бы två разных текста от одного ключа.
   - `44px`/`360px`: минимальная touch-цель и ширина узкого viewport в UX/AC6
     совпадают с действующими константами проекта
     (`src/styles/{base,chrome,dialogs,form-kit}.styles.ts` → `44px`;
     `demo/smoke_dialog_polish_60{3,5}.mjs`, `demo/smoke_editor_styles_lazy.mjs`
     → `360`) — не изобретённые числа.
5. Проверены на пересечение заявленные «не блокирующие» соседние задачи:
   `gh issue view 844/853`. #853 — бэкенд-аудит restore/delete/ACL (другой
   слой). #844 — закрытие обходных входов в редактор из View/kiosk через
   *другие* поверхности (кнопка «Изменить» информационной карточки,
   `_clickRoom`, `_ackNewDevice`); не про пустой экран и не про Add
   space/Import backup. Пересечения кода или контракта не найдено;
   K1 нового ТЗ (повторная проверка прав/kiosk после async-загрузки) по духу
   соответствует тому, что #844 требует для других поверхностей — не
   противоречит и не дублирует.
6. `docs/USER-GUIDE.ru.md`/`docs/USER-GUIDE.md` проверены на терминологию
   пустого экрана («Добавить пространство» / «Add space» — секции 298, 311,
   2186) — ТЗ использует те же названия кнопок, не придумывает новые.
7. Релизная классификация раздела 13 (`line-fix`) сверена с
   `docs/release-ledger/`: записи `docs/release-ledger/v1.80.1/875.json` пока
   нет — ожидаемо, ledger заводится на этапе code review, не spec. Сама
   классификация (узкое улучшение доступности существующей функции, не новая
   крупная фича, без version bump модели) обоснована текстом ТЗ и не
   противоречит `v1.80.1` как предыдущему stable.

## Находки

Не найдено. High: 0, Medium: 0.

Отдельно проверено по требованию промпта «не бывает сложной задачи без
единого открытого вопроса»: раздел 14 заявляет отсутствие открытых
продуктовых вопросов. Это утверждение подтверждается, а не просто
принимается на веру — задача имеет узкий, прямо сформулированный запрос
владельца («добавить кнопку Import backup»), контракт поведения (K1–K7)
отвечает на все пограничные случаи, которые обычно уходят владельцу
(видимость при правах/kiosk/read-only, поведение при отмене, поздних
ответах, пустой полной копии), и ни один из них не оставлен как
развилка «что увидит пользователь» — только технические детали реализации
корректно вынесены в «принято предположительно». Открытых *технических*
вопросов, ошибочно адресованных владельцу, в ТЗ тоже нет — раздел 14 прямо
перечисляет технические решения и явно относит их к агентам, не к владельцу,
как требует PROCESS.md §7.1.

## Что проверено и корректно

- Все обязательные разделы §7.1 присутствуют и в правильном порядке;
  сценарий и «что увидит пользователь» сформулированы продуктовым языком,
  без терминов реализации.
- Каждый AC (AC1–AC7) имеет наблюдаемый результат, названный способ
  доказательства (конкретные smoke/тесты) и непустую отрицательную пробу —
  требование «AC · чем доказан · чем краснеет» выполнено по всей таблице,
  пустых третьих столбцов нет.
- Скоуп/не-скоуп чётко режет задачу от #844/#853/#89/#53 и прочих соседних
  тем; явно запрещено молча расширять задачу при обнаружении бэкенд-дефекта.
- Технический анализ (раздел «Что уже проверено по коду» и ссылки по строкам)
  проверен построчно против фактического кода на материале — совпадает без
  расхождений; это необычно высокая точность для ТЗ на этапе spec.
- Модель данных/миграция/i18n корректно утверждают «изменений нет» и это
  подтверждается отсутствием новых serialized полей в контракте задачи.
- UX-числа (44px, 360px) и наименования кнопок/иконок взяты из действующих
  констант и `USER-GUIDE`, не изобретены.
- Раздел 14 корректно разделяет продуктовые и технические открытые вопросы и
  не выносит ни одного технического вопроса владельцу.

## Чего не проверял

- Не прогонялись `npx tsc --noEmit`, `npm test`, `npm run build` — на этом
  SHA продуктовый код задачей не менялся (ТЗ прямо фиксирует: «Реализация
  сейчас не запускается»), прогонять их не против чего. Зелёный Validate на
  `c7c81adc` (https://github.com/Matysh/houseplan-card/actions/runs/38390195514)
  подтверждает дешёвые гейты для текущего состояния `dev`, что не относится
  к ещё не написанному коду этой задачи.
- Не исполнялись browser-smokes/golden/invariants/performance — им нечего
  проверять до реализации; план гейтов (раздел 10 ТЗ) оценён по полноте, а
  не по факту прогона.
- Не проверялся сам backend-эндпоинт `/api/houseplan/import/preview` на
  предмет скрытых дефектов при пустой целевой конфигурации — это явно
  закреплено за #853 и вне скоупа текущего ТЗ; при обнаружении блокирующего
  дефекта ТЗ требует отдельный issue, что и является правильным путём.
- Не проверялась визуальная компоновка пустого экрана в реальном браузере
  (кнопки, перенос строк на 360px) — на этапе spec это не требуется:
  AC6 называет конкретный будущий способ доказательства (native browser
  smoke + unit-проверки локалей).

перепроверены по коду и совпадают, открытых продуктовых и ошибочно
