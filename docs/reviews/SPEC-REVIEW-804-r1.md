# SPEC-REVIEW-804-r1

Issue: #804 — «Создание комнаты из части длинной стены отклоняется из-за
duplicate-id (Garderoba, #801)»
Этап: spec (PROCESS.md §2.4) · Трек: ask (§5) · Заход: r1 · блокирующих
циклов 0/4
Материал: тело issue #804, раздел `## ТЗ` (редакция r1, узкий серверный
rehost-контракт уточнён до начала этого ревью), сверено с рабочей копией на
`370df0708c73beee3240d761094044fa0bdfb2dc` (HEAD; Validate на этом SHA
зелёный — https://github.com/Matysh/houseplan-card/actions/runs/37440031986).
Код продукта в этой задаче ещё не писался — есть только локальный черновик
автора под `track:ask`/§11.8, который ревью ТЗ по правилу не читает и доводом
не считает; судится исключительно текст issue. Route: fix.

## Скоуп

Исправление координации идентичности стен при создании комнаты внутри
замкнутой области, часть границы которой проходит по более длинной
независимой стене: lineage новых стен комнаты должно учитывать результат
`reconcileCoincidentPartitions`, а не только исходный (до reconciliation)
набор независимых стен. Служит J4 (дополнение плана комнатой без
Inkscape/YAML) и J6 (поддержание геометрии плана верной) из `docs/SCOPE.md`.
Не-скоуп по тексту ТЗ: перемещение узлов (#803), новый UX создания комнаты,
изменение правил геометрии/слияния/расположения проёмов, массовая
оптимизация, рендер, отключение проверки ID, права, сетевой протокол,
расширение серверного `allow_optimize_rehost` на обычную запись. Эталонная
поверхность — desktop-first редактор плана; новых touch-обещаний нет, что
соответствует `docs/TOUCH-SUPPORT.md` (редакторы desktop-first, View не
затронут).

## Как проверялось

Ревью ТЗ не включает выполнение гейтов: продуктового кода ещё нет, этап его
не требует. Прочитаны `docs/SCOPE.md` → `AGENTS.md` → `docs/process/REVIEWER.md`
→ применимые PROCESS §2.3–2.5, §7.1, §4; канон подсистемы `docs/WALL-THICKNESS.md`
(модель v10, ADR 282, §11 «Planar wall faces» — ровно тот путь «Room from an
existing face», на который жалуется issue).

ТЗ опирается на построчные ссылки на причинный код — они сверены чтением с
реальным деревом материального SHA, а не приняты на слово автора:

только ссылкой автора. Отдельно проверено: контракт midpoint/tie-break при
разделении каталожного атома (`wall-segment-model.ts:555-570`, сортировка
кандидатов по близости к midpoint старого сегмента) — соответствует
формулировке контракта п.2 ТЗ и описанию в `WALL-THICKNESS.md` («A split keeps
the parent ID on the child containing the old midpoint»).

## Находки

High и Medium нет.

## Что проверено и корректно

- Обязательные разделы §7.1 присутствуют: проблема (в теле issue до `## ТЗ`,
  на который сама ТЗ явно опирается первой фразой «До исправления Save
  отклоняется»), сценарий и видимый результат, скоуп/не-скоуп, контракт
  поведения (6 пунктов), UX/i18n/модель данных/совместимость, критерии
  приёмки AC1–AC6 с доказательством, план реализации и автотестов, риски и
  откат, release-артефакты. Раздел «Принято предположительно» фиксирует
  единственное техническое решение (фильтрация подсказок lineage **после**
  reconciliation) и явно оставляет ревьюеру право оспорить способ — это и
  есть обязательный «открытый вопрос» сложной задачи, закрытый внутри
  команды, а не вынесенный владельцу как продуктовый.
- Каждый AC однозначен и привязан к наблюдаемому результату с конкретным
  способом доказательства: AC1 — production smoke на минимальной
  обезличенной фикстуре Garderoba плюс обязательный отрицательный свидетель
  на базовом коде (падает именно по `duplicate-id`/отсутствию комнаты — не
  общий toast); AC2 — table-driven unit (один/два остатка, полное
  поглощение, обратное направление, смешанные толщины, нулевой носитель) с
  инвариантами уникальности и геометрии; AC3 — реальная очередь из двух
  комнат на одном источнике, положительный и отменённый (`Оставить
  стенами`/Cancel/Esc) варианты, инвариант «один физический атом на общую
  границу»; AC4 — явно разделяет поддержанный (same-ID residual) и
  неподдержанный (новый ID/поглощённая часть) переход, с backend
  positive/negative и атомарным rollback; AC5 — Undo/Redo/reload/настоящий
  конфликт без частичной мутации; AC6 — отсутствие побочных полей/регрессий
  соседних rooms/spaces/markers и приём backend-моделью frontend-кандидатов
  AC1/AC2/AC4.
- Контракт п.4 (проёмы) узко и корректно ограничен действующим backend-кодом:
  ТЗ не обещает расширения `allow_optimize_rehost` на обычную запись и прямо
  фиксирует, что неподдержанный host-переход остаётся отказом — это снято с
  владельца техническим решением автора после отзыва преждевременно широкого
  прогона (видно по истории комментариев issue) и подтверждено чтением
  `validation.py`.
- Технических утверждений, не подкреплённых ни кодом, ни каноном и не
  помеченных как предположение, не найдено — все построчные ссылки на
  причину (lineage/reconciliation/barrier) и на backend-контракт проёмов
  совпали с деревом материального SHA.
- Продуктовых вопросов владельцу в тексте нет, и это обоснованно: контракт
  п.6 («настоящие дубли ID по-прежнему отклоняются») и п.3 («нельзя
  переименовывать все стены/очищать все wall_ids») прямо исключают соблазн
  решить задачу ослаблением барьера, а не координацией lineage — то есть
  граница между «что видит пользователь» и «как устроена идентичность»
  проведена и ничего продуктового не замаскировано техническим решением.
- i18n/миграция/touch/performance закрыты явным «нет» с обоснованием (нет
  новых ключей, нет новых полей/версии, desktop-first без новых жестов,
  проверка ID только на Save без изменений на кадр/сеть) — соответствует
  прецедентам в `CONFIG-COMPATIBILITY.md` и `TOUCH-SUPPORT.md`.
- Release-артефакты названы (changelog RU+EN, уточнение
  WALL-THICKNESS/ARCHITECTURE/STATUS, при необходимости DEVELOPMENT), откат —
  явный revert коммита с читаемостью прежним кодом созданных им планов;
  выпуск беты в задаче не запрошен, что соответствует метке задачи.
- Трек `ask` обоснован: несколько связанных путей (frontend lineage,
  client-side reconciliation, backend barrier, host-guard), риск 7/10 по
  оценке владельца, геометрия и стабильные ссылки — выше порога `show`.

## Чего не проверял

- Исполнение гейтов (`tsc`, `npm test`, `npm run build`, model-invariants,
  backend pytest, golden, production smoke) — кода ещё нет, этап spec их не
  требует; зелёный Validate на материальном SHA `370df070` относится к
  существующему `dev`, а не к ненаписанной реализации этой задачи.
- Содержимое и красноту локального черновика автора (`issue/804-partition-room-lineage`,
  `Spec-Draft sha256:1e789aa35c51`) — по §2.4/§11.8 ревью ТЗ его не читает и
  доводом не считает; оценивался исключительно текст issue.
- Фактическую достижимость конкретной реализации «фильтровать подсказки после
  reconciliation, перед барьером» — раздел «принято предположительно» прямо
  называет это не обязывающим выбором автора, который ревьюер кода вправе
  оспорить на реализации; список файлов (`houseplan-editor-runtime.ts`,
  возможный helper рядом с `coincident-partitions.ts`) правдоподобен по
  найденной причине, но фактический дифф — предмет код-ревью.
- Состояние исходного обращения #801 и дубликата #529 как таковых — не
  материал этого ревью; ссылки ТЗ на них (не смешивать с #803, не закрывать
  #801 до выпуска) проверены по смыслу, не по содержимому тех issue.
- Реальное поведение диагностических скриптов автора вне репозитория
  (`C:/Temp/hp801-*.mjs` и аналоги) — они не часть материала и не
  воспроизводились; их результаты приняты как контекст обнаружения причины,
  не как доказательство AC.

## Вердикт

Зелёный. Документ ТЗ полон по §7.1, причинная цепочка дефекта подтверждена
построчным чтением дерева на материальном SHA (а не принята на слово), каждый
AC однозначен и снабжён названным способом доказательства и отдельным
отрицательным свидетелем, открытых продуктовых вопросов нет, технических
утверждений без основания не найдено. High: 0, Medium: 0.
