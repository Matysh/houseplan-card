## Скоуп

Issue #691, продолжение после жёлтого r1
(`docs/reviews/CODE-REVIEW-691-r1.md`). r1 подтвердил продуктовый код
(`src/logic.ts`, `src/room-fit.ts`, `src/houseplan-card.ts` — контракт §6/§7 ТЗ
реализован верно, все 12 AC доказаны автотестом или чтением) и нашёл два
Medium **в скоупе**, оба документационно-тестовые, без продуктовых изменений:

- Medium-1: `docs/USER-GUIDE.ru.md` не обновлён и описывал старый контракт
  (мгновенный room-fit, double-tap только по фону, свайп «при масштабе 1:1»
  без упоминания края) — канонический источник терминологии для видимого
  поведения расходился с кодом.
- Medium-2: `demo/smoke_pan_any_zoom.mjs` (regression-смок из #531, прямое
  совпадение по `smoke-select`) реально красный на материале r1 —
  `kioskSwipeStillSwitchesFloors`/`kioskHorizontalDragIsNotAPan` ожидали
  `true`, получали `false`, потому что тест стартовал drag из середины
  стейджа, что по новому контракту (§6 п.5 ТЗ) корректно классифицируется как
  pan, а не swipe.

r2 — точечный фикс обоих находок, продуктовый код (`src/**`) не менялся.

## Что проверено и корректно

- `docs/USER-GUIDE.ru.md` строки 474–476 и 1936/1938 переписаны и теперь
  дословно по смыслу совпадают с `docs/USER-GUIDE.md` и контрактом §6/§7 ТЗ:
  350 мс отложенный room-fit, double-tap/double-click по фону, заливке
  комнаты и её пассивной подписи (не только по фону), edge-swipe только из
  48 CSS px у края с доступным соседом, «drag вне этой зоны панорамирует
  план». Клавиатурная активация (`Enter`/`Space`) осталась немедленной, как и
  требует §7 п.9 ТЗ (keyboard activation не ждёт 350 мс).
- `demo/smoke_pan_any_zoom.mjs`: положительный kiosk-swipe теперь стартует из
  фактического правого края стейджа (`rect.right - 20`, вычислено из
  `getBoundingClientRect()`, не хардкод), что попадает в 48 px активную зону
  независимо от размера окна; комментарий файла обновлён и больше не
  утверждает устаревший инвариант «любой горизонтальный kiosk-drag — свайп».
  Остальные проверки того же блока (вертикальный drag — pan; zoom > 1 —
  всегда pan) не менялись и не требовали правки — граница находки была
  локализована в r1 правильно.
- Прогон на точном SHA материала (33ae14a9, а не на рабочей ветке после
  моих локальных операций) даёт 55/55 `true` — совпадает с числом из
  хендоффа автора; проверка не является «Verified» без команды — команда и
  результат приведены в таблице гейтов.
- Никакого продуктового кода (`src/**`) в дельте нет — риск регрессии AC1–AC12
  от этого раунда отсутствует по построению, не только по прогону.
- Рабочая копия после моих локальных `bundle:sync`/`check-docs`/смок-запусков
  возвращена к состоянию материала (`git status --porcelain` пуст, `git
