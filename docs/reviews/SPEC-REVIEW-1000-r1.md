## Скоуп

## Находки

### F1 (Medium) — конкретное визуальное представление уровня `attention` не зафиксировано ни одним артефактом, хотя ТЗ формулирует его как решённый факт

Контракт поведения утверждает как факт: «Уровень по умолчанию при создании — `attention`. `attention` даёт **существующую** пассивную жёлтую индикацию семейства #972 без красной пульсации» — и на этом построен защитный/визуальный AC4 («golden attention/alarm в Flat и 2.5D»).

Но ни один из прочитанных артефактов такую «существующую» индикацию для произвольного пользовательского порога не фиксирует:

1. Единственный утверждённый визуальный пакет (immutable `9db1e66f`) **прямо исключает** этот вопрос: его собственный текст передачи исполнителю гласит «В текущем макете нет выбора «внимание/тревога». Требования к двум уровням и общей модели `threshold/external`… этим согласованием не закрываются» (комментарий 6415792068). Иконки/расположения для уровня «внимание» в утверждённых скриншотах нет вовсе.
2. Единственный существующий в коде механизм «пассивного жёлтого знака» — это maintenance-гаечный ключ `device-issues.ts`/`DEVICE-PRESENTATION.md`, который жёстко привязан к конкретному narrow allowlist («The only maintenance override is an active problem binary from `homeconnect_ws` with `binary_sensor_machinecarereminder`…») и текстуально означает для пользователя «Требуется обслуживание» (`USER-GUIDE.ru.md:721`). `DeviceIssueSignal.severity` в коде сегодня буквально `'alarm' | 'maintenance'` — третьего значения `attention` нет.

Из текста ТЗ нельзя понять, что именно увидит пользователь и как это протестировать детерминированно:
- получит ли произвольный порог CO₂ > 1000 «внимание» буквально тот же гаечный ключ и заголовок «Требуется обслуживание» (семантически неверно — это не обслуживание прибора), или
- вводится новый отдельный глиф/раздел карточки специально для пользовательских порогов «внимание» (тогда это не «существующая», а новая индикация, и у неё нет согласованного эталона).

Это ровно случай §7.1 «утверждение о поведении, которого нет ни в одном документе и которое не помечено как предположение» — ТЗ пишет «существующую… индикацию» как факт, хотя единственный документ, который мог бы это подтвердить, прямо говорит обратное. Раздел «Принято предположительно, поменять свободно» этот пункт не упоминает.

**Последствие:** AC4 (защитный/визуальный AC, доказывается golden-сравнением) не может быть реализован и ревью-проверен как «тест умеет падать на известном эталоне» — эталона для `attention` нет, и неочевидно, в каком разделе карточки причин и под каким заголовком появляется пользовательская причина уровня «внимание».

**Чем закрыть:** в разделе «Уровни, общая модель и поверхности» (или в блоке «принято предположительно») явно зафиксировать, что индикация `attention` — новый отдельный визуальный элемент/раздел карточки (не повторно использующий заголовок/иконку «Требуется обслуживание»), либо явно описать конкретный переиспользуемый глиф; без этого пункт переходит либо к владельцу как продуктовый вопрос («как выглядит пассивное внимание для пользовательского порога»), либо автор фиксирует его сам с пометкой предположения.

### F2 (Medium) — виджет ввода значения для текстового сравнения (`=`/`≠`) не определён; исходная защита от опечаток («выпадающий список состояний») молча заменена свободным текстом без фиксации решения

Исходный разбор задачи прямо предлагал механизм, снимающий главный риск текстового условия — опечатку: «Для binary/enum-сущностей оператор «равно состоянию» (`open`, `on`, `unavailable`): **второй столбец становится выпадающим списком состояний**… закрывает «окно открыто» на датчиках без device_class, дверь холодильника, «устройство недоступно»».

Финальный «Контракт поведения» описывает только формат и длину значения — «Текстовый операнд — 1–255 Unicode code points, без CR/LF; регистр, пробелы и сам текст сохраняются» — и ничего не говорит о способе ввода. Единственное предложение о «текущем доступном значении» относится к выбору **сущности/атрибута** («Выбор состояния/атрибута показывает человеческое имя и текущее доступное значение»), а не к значению сравнения. В UX-разделе конструктор описан как generic «Значение» без ветвления по оператору, и согласованный визуал (который не содержит уровней) тем более не решает этот вопрос для текстового оператора.

Поскольку сравнение текста — точное, с учётом регистра, без нормализации («= и ≠ — точное равенство/неравенство… точное текстовое сравнение»), свободный ввод означает: пользователь, набравший `"Open"` вместо фактического `"open"`, или вставивший значение с незаметным конечным пробелом, получает правило, которое **никогда молча не сработает** — и ТЗ не описывает здесь никакой обратной связи для этого случая (описанные ошибки — «источника/оператора/числа/пустого значения/лимита», но не «введённое значение не совпадает ни с одним наблюдаемым состоянием сущности»). Это прямо бьёт по собственному примеру проблемы из задачи («дверь холодильника открыта», «устройство недоступно»), ради которого изначально и предлагался список состояний.

Это не техническая деталь (имя модуля, место хранения), а то, что видит и делает пользователь — печатает текст вслепую или выбирает из подсказанных вариантов, — то есть ровно тот класс вопросов, которые по PROCESS.md §7.1 либо решаются владельцем, либо фиксируются явным предположением. Раздел «Принято предположительно» этого решения не содержит.

**Последствие:** AC2 («…точный текст сравнения по контракту») проверяем с точки зрения чистой логики компаратора, но не с точки зрения заявленного пользовательского сценария — без решения о подсказке/списке состояний основной пример задачи (двери, недоступность) рискует стать источником молча неработающих правил без диагностики.

**Чем закрыть:** явно зафиксировать в ТЗ (или как ответ владельца, или как «принято предположительно» с обоснованием), остаётся ли значение для `=`/`≠` свободным текстом, и если да — добавить по крайней мере текстовую подсказку с текущим наблюдаемым состоянием сущности рядом с полем, чтобы не терять исходную защиту от опечаток.

## Что проверено и корректно

- Обязательные разделы §7.1 присутствуют полностью, включая блок «принято предположительно» для технических имён/разбиения модулей.
- Каждый AC (AC1–AC8) называет способ доказательства (unit/backend/smoke/golden), без пропусков; критерии не оставляют безымянных АС.
- Числовой парсер (отрицательные значения, 0, точка/запятая, строгий полный разбор без остатка/разделителя тысяч/`NaN`/`Infinity`) описан достаточно однозначно, чтобы написать детерминированный тест и обычный отрицательный случай.
- Контракт трёх секунд (активация/снятие, отмена кандидата до срока, перечитывание на границе, неопределённый результат = снятие) описан пошагово и без внутренних противоречий; соответствует существующему паттерну отложенных дедлайнов (`pulse.short_event/transition`, A03 в DEVICE-PRESENTATION.md) — технически осуществимо без постоянного таймера.
- Решения владельца 6417069616 (независимая реализация #1000, выбор уровня по умолчанию «внимание», до трёх правил, 3 секунды, =/≠ для текста/остальные только числа) перенесены в ТЗ без искажения и без тихой подмены — отличие от прецедента SPEC-REVIEW-1070-r1 (там ТЗ прямо противоречило записанному решению владельца; здесь противоречий такого рода не найдено).
- Модель данных (`alert_sources`, additive optional block, без миграции/version bump, явное удаление пустого блока) согласуется с заявленными в `docs/CONFIG-COMPATIBILITY.md` паттернами additive-полей и allowlist-контрактом transfer API.
- i18n-объём (RU/EN/DE/FR, канонические каталоги) соответствует фактической структуре `src/i18n/`.
- Не-скоуп по #1001 (никаких сервисов/эндпоинтов/TTL/разблокировки) описан явно и последовательно в «Скоуп», «Не-скоуп», AC7 и «Релизные артефакты» — нет расползания в заблокированную задачу.
- Откат и релизные артефакты отвечают на обязательные вопросы (как выключить/вернуть, что идёт в changelog/golden), без обещаний, которые нельзя проверить при реализации.

- Конкретные имена файлов/модулей технической реализации (`alert_sources`, разбиение comparator/runtime owner/адаптера) — раздел «принято предположительно» явно отдаёт это автору, не предмет ревью ТЗ.
- Полный перечень i18n-строк и текст подсказок конструктора — содержание переводов решается при реализации.
