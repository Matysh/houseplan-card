## Скоуп

Задача закрывает SCOPE J6 («Keep the plan true as the home evolves») и частично J4: правка
начального инструмента при обычном входе в редактор Плана — убрать безусловный сброс
`_tool = 'draw'` в `_setMode`, заменить его на вычисление по наличию геометрии текущего
пространства. Явно вне скоупа: геометрия/сохранение/миграции, панели свойств (#931), fit/камера,
touch UX, редакторы устройств/подложки, View/kiosk, смена инструмента при переключении этажей
внутри уже открытого редактора. Границы названы явно и проверяемы.

## Как проверялось

Ревью ТЗ: читалось только тело issue (ревьюер ≠ автор, черновик не читается — §2.4, §11.8).
Для оценки выполнимости и непротиворечивости контракта (не для подмены ревью кода) я прочитал
текущую реализацию `_setMode` и смежные точки `_tool = 'draw'`:

- `src/houseplan-editor-runtime.ts:1087–1280` (`_setMode`) — подтверждён описанный в issue
  безусловный сброс (сейчас строка 1275, ранее №1257 на упомянутом коммите — сдвиг ожидаем,
  не находка); guard-ы «пространство отсутствует» (1102–1107) и kiosk (1108) отрабатывают и
  возвращаются **до** точки сброса инструмента, то есть предложенная точка вставки
  («после существующих разрешающих проверок») действительно существует и не требует
  дополнительной перestройки guard-ов.
- `_tool` — единственное общее поле редактора Плана (`src/houseplan-editor-runtime.ts:783` и
  использования по файлу); редакторы Devices/Decor его не читают, поэтому точечное изменение
  в `_setMode` технически не может задеть «Режим просмотра и начальные инструменты редакторов
  устройств/подложки», как и утверждает ТЗ.
- `src/houseplan-card.ts:7621–7636` (публичная обёртка `_setMode`) и
  `src/warm-mode-adoption.ts` (`resumeWarmMode`) — показывают, что при warm-восстановлении той
  же сессии `_editorRuntime._setMode` чаще всего получает управление при уже совпадающем
  `_mode`, то есть срабатывает ранний `return` на строке 1109 **до** пересчёта инструмента —
  утверждение ТЗ «warm-восстановление сохраняет прежний инструмент» не требует отдельного кода
  и не конфликтует с текущей архитектурой.
- `src/space-copy-runtime.ts:246–247` и `src/houseplan-editor-runtime.ts:8166–8189`
  (onboarding/создание/floors-import) — оба явно переустанавливают `_tool = 'draw'` **после**
  вызова `_setMode('plan')`, то есть переопределяют любое новое вычисление независимо от его
  реализации — контракт п.4 («явные сценарии сохраняют предписанный старт Стены») реализуем без
  специальных исключений внутри самой новой логики.
- `docs/USER-GUIDE.ru.md:736–745` — документированное поведение «Копировать» дословно совпадает
  с описанным в ТЗ («открывает копию в редакторе Плана с инструментом «Стены»», комнаты не
  переносятся, их контурные стены становятся самостоятельными) — ссылка на #885 в ТЗ не
  выдумана.
- `docs/UX-MODES.md:289–291` — «Saving a new space opens this editor with the draw tool armed»
  подтверждает документированный старт Walls для создания пространства, с которым ТЗ не
  спорит, а явно сохраняет.
- Термины «независимая стена» (independent wall) и «контурный wall segment» (contour) —
  существующие понятия кодовой базы (`draft-live-preflight.ts`, `houseplan-editor-runtime.ts`
  комментарии о «room interval or independent masonry», `zeroWalls.contour`), а не изобретённые
  ТЗ категории; формулировка однозначна для реализации.
- Проверил пограничный случай, не упомянутый явно в перечне из шести видов геометрии:
  `open_spans` (виртуальные разрывы стены между комнатами, `src/open-spans.ts`). Это
  производная от уже существующих комнат сущность (`sharedBoundary`/`roomEdges` между
  полигонами комнат) и не может существовать без комнаты-источника при обычном
  пользовательском сценарии; «комната» в списке уже покрывает этот случай. Теоретически
  осиротевшая запись `open_spans` без комнат возможна только как результат повреждённых данных,
  а ТЗ прямо отказывается «исправлять повреждённые данные» и не меняет writers — поэтому это не
  довожу до отдельной находки, фиксирую как учтённое наблюдение.
- `AGENTS.md`, `docs/SCOPE.md`, `docs/process/REVIEWER.md` прочитаны как обязательные источники
  роли ревьюера (packet `files`).

Гейты задачи не прогонялись и не нужны на этом этапе: `changedFiles: []`, продуктовый код не
менялся, тестов/сборки для несуществующего диффа не существует (§2.4 — ревью ТЗ предшествует
коду; зависимости/Chromium на spec не ставятся, #696). Это и есть полный перечень «что не
проверялось» для этого раунда.

## Что проверено и корректно

- Каждый AC однозначен и имеет указанный способ доказательства; защитных
  (валидационных/гардовых) AC в этом ТЗ нет — контракт read-only и не вводит отказов/лимитов,
  отдельной строки «чем краснеет» не требуется.
- Контракт не содержит утверждений о поведении, не подтверждённых ни одним документом:
  специальные сценарии (копирование, создание, warm-восстановление, floors-import) либо прямо
  документированы в USER-GUIDE.ru.md/UX-MODES.md, либо проверены по текущей реализации и
  совместимы с предложенным изменением без дополнительных исключений.
- Технический раздел «Принятые предположения» корректно отделяет техническое решение (место
  helper, имена свидетелей — «поменять свободно») от продуктового («трактовка пустоты
  принимается», «старт Walls для копирования/создания не пересматриваем») — открытых продуктовых
  вопросов владельцу нет, что соответствует низкой сложности задачи (оценка автора 2/10).
- Граничные случаи из «Уточнения для анализа» (только подложка → Walls; одна независимая стена
  без комнаты → Select; только колонна/лестница → Select) покрыты контрактом п.1–2 и планом
  автотестов без противоречий.
- Не-скоуп корректно исключает смену инструмента при переключении этажей внутри уже открытого
  редактора — это не регрессия: текущая реализация (`_slideTo`,
  `src/houseplan-card.ts:1508–1516`, и `_onHashChange`, `src/houseplan-card.ts:2516–2524`) уже
  сбрасывает `_tool` на каждое переключение пространства вне `_setMode`, и issue эту точку не
  трогает — зафиксированное ограничение, а не недосмотр.
