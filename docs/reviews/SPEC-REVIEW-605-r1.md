# SPEC-REVIEW #605 · r1

Этап: ревью ТЗ (PROCESS.md §2.4). Заход r1, первый цикл — раздел «Унаследовано
из r0» не нужен (§2.10 применяется со второго захода).

## Скоуп ревью

ТЗ лежит в теле issue #605 (архивного файла `docs/specs/605-*.md` нет — задача
создана после 2026-09-10, материал — тело issue). Семь пунктов остаточной
полировки диалогов настроек после #600/#602/#603: General settings (плитки
цвета, Wall fill Reset, Data-кнопки), Space/Room settings (единый контрол
цвета), Device on the plan (Icon-поле, подпись Rotation/Drehung). Изменения
только UI (CSS/markup/i18n-текст), без нового продуктового поведения и без
миграции конфига. Владельцем задача отнесена к J4/J6 (`docs/SCOPE.md`) — эти
диалоги обслуживают онбординг и поддержание плана в актуальном состоянии;
чисто визуальная полировка уже принятого редизайна вписывается без вопросов.

## Как проверялось

Читал тело issue #605 и оба комментария (аналитика + передача на ревью),
`docs/SCOPE.md`, релевантные разделы `PROCESS.md` (§2.4, §7.1, §7.2, §4),
эталон `docs/design/600-settings-dialogs/{SPEC.md,ACCEPTANCE.md,OPEN-POINTS.md,
reference/*}`. Сверил каждый из семи пунктов отчёта с реальным кодом на `dev`
(`c2fd3188`, рабочая копия уже на нём) — не поверил формулировкам, а прочитал
строки:

- п.1 (обрезание `%`): `src/styles/form-kit.styles.ts:372` —
  `.hpf-colortile-meta .hpf-unit > input { width: 3.2em; min-width: 3em }`,
  подтверждено дословно.
- п.2 (lowercase hex): `src/editors/form-kit.ts:277,320` — `colorField`/
  `colorTile` печатают `${hex}` без `.toUpperCase()`, подтверждено. Эталон
  печатает `c.toUpperCase()` (`reference/general-settings.js:82,90`).
- п.3 (второй шахматный квадрат): `src/hp-color-opacity.ts:94-129` — `.trigger`
  всегда рисует checkerboard-фон и `padding:3px`, `.swatch` внутри занимает
  100%×100%, оставляя видимую шахматную рамку внутри уже закрашенной плитки.
  Подтверждено.
- п.4 (нет Reset у Wall fill): `src/editors/general-settings-dialog.ts:142-151`
  — `colorRow` для `wall_fill` собран без `resetLabel`/`onReset`, в отличие от
  соседнего `bgColor` (строки 174-175, где `onReset` есть). `DEFAULT_FILL_COLORS.
  wall_fill` = `{ c: '#ffffff', a: 1 }` подтверждено в `src/logic.ts:1446` —
  совпадает с AC4.
- п.5 (Data-кнопки): `src/editors/general-settings-dialog.ts:223-244` —
  Export/Import используют `.btn.ghost` (без рамки), Optimize/Undo — `.btn
  ghost alignall`; `.btn.alignall { width:100%; justify-content:center }`
  подтверждено в `src/styles/dialogs.styles.ts:1044`. Совпадает с описанием.
- п.6 (Icon-поле): `src/editors/marker-dialog.ts:573-604` — подтверждены обе
  ветки (`ha-icon-picker`, если кастомный элемент зарегистрирован, иначе
  текстовый fallback), и отдельный `.hpf-iconpreview` рядом с `iconControl` —
  двойное превью правдоподобно при активной ветке `ha-icon-picker` (у неё
  собственный preview-glyph внутри поля).
- п.7 (Rotate → Rotation): `src/i18n/en.json:259` — `"Rotate"`,
  `src/i18n/de.json:259` — `"Drehen"`; RU `"Поворот"` и FR `"Rotation"` уже
  совпадают с целевой формулировкой AC7. Единственное использование ключа —
  `src/editors/marker-dialog.ts:774,778,779`, коллизий со строкой `"Rotate"` в
  smoke/test-файлах не нашёл (найденные совпадения — идентификаторы
  `_physicalRotate`/`fourCornersAndRotate`, не текст).

Дополнительно проверил, что оба смока, названных в AC8/AC2/AC3,
существуют — `demo/smoke_color_picker_consumers.mjs`,
`demo/smoke_dialog_config_parity.mjs` (`ls demo/smoke_*.mjs` даёт 259 файлов).
Проверил i18n-ключи `gs.wall_fill`, `space.opacity`, `btn.reset` — все три уже
существуют (не новые ключи, как и заявлено в разделе «Данные, совместимость,
i18n»). Проверил `nativeColors()`-контракт: единственный потребитель —
`demo/smoke_color_picker_consumers.mjs`, что подтверждает существование
свидетеля, на который ссылается ТЗ и `ACCEPTANCE.md:113`. Проверил остальных
потребителей `hp-color-opacity` (`decor-image-editor.ts`,
`houseplan-editor-runtime.ts`) — они вне четырёх диалогов, значит предположение
«плоский режим включается явно только у контролов этих диалогов» не требует
трогать эти два файла и не создаёт скрытого охвата.

Смоделировал вопрос «выполнима ли AC1 в процессе проекта» (браузерный smoke на
Windows Chromium/Chrome + ручная сверка Windows Chrome/Yandex): по `AGENTS.md:
414` и `docs/DEVELOPMENT.md` («Local Windows workstation») у владельца есть
постоянное Windows-рабочее место с Playwright/Chromium именно для такого
класса регрессий (шрифт/рендер, специфичный для ОС) — это существующая
практика проекта, а не новое требование к процессу. Ручная сверка с Yandex
Browser — вспомогательное свидетельство поверх автоматического DOM-теста, не
единственное доказательство AC1.

## Что проверено и корректно

- Обязательные разделы §7.1 присутствуют по содержанию (местами объединены под
  меньшим числом заголовков, что не запрещено): сценарий+результат для
  человека (персона, поверхность, до/после одной фразой), проблема+скоуп/не-
  скоуп, контракт поведения+UX, данные/совместимость/i18n, критерии приёмки
  AC1–AC8 с доказательством, план автотестов, риски+производительность+touch+
  откат+release-артефакты, явный раздел «Принятые предположения».
- Каждый AC однозначен и привязан к наблюдаемому результату для человека, а не
  к деталям реализации; способ доказательства назван предметно (конкретный
  smoke-файл, golden-сцена, unit-тест), а не общим словом «проверить».
- Утверждения о текущем поведении (все семь дефектов) — не догадка автора, а
  подтверждённое чтением кода состояние `dev`; ни одно не выдаёт
  предположение за факт без пометки.
- Раздел «Принятые предположения» корректно отделяет технический выбор
  реализации (как убрать шахматку, как стилизовать `ha-icon-picker`, ширина
  поля 3.6em как стартовая) от продуктового контракта; ревьюер вправе
  оспорить, но ни одно из предположений не требует продуктового решения
  владельца — это чисто технические развилки.
- Продуктовых вопросов владельцу в ТЗ нет, и корректно нет: все семь
  результатов уже даны референсом (`docs/design/600-settings-dialogs/
  reference/`), а технический выбор внутри реализации не поднимается до
  владельца, как и требует §7.1.
- Не-скоуп сформулирован явно и по существу (не менять `nativeColors() === 0`,
  не трогать логику сохранения/закрытия, не повторять #602/#603, не менять
  View) — граница задачи не размыта.
- AC2 явно фиксирует «один источник данных»: печатный hex меняется только для
  отображения, сохраняемое значение не нормализуется — специально исключает
  дефект класса «одно число — два источника» (#234/#233 из истории проекта).
- Откат тривиален (revert коммитов, миграции нет) и назван явно.

## Чего не проверял

- Не запускал `npx tsc --noEmit`, `npm test`, `npm run build`, golden — на
  этапе ревью ТЗ кода ещё нет (ветка `issue/605-settings-dialog-polish`
  опубликована от `dev` без продуктового кода, по заявлению автора); гейты
  кода относятся к этапу код-ревью (§2.7), не к этому этапу.
- Не проверял вручную рендер в Windows Chrome/Yandex Browser — у меня нет
  такого окружения в этой сессии; полагаюсь на подтверждённость самого
  дефекта чтением CSS (см. «Как проверялось», п.1) и на то, что способ
  доказательства AC1 не единственно ручной (есть автоматический DOM-geometry
  smoke).
- Не проверял, стилизуется ли конкретная версия `ha-icon-picker` через
  документированные CSS-переменные без разрыва Shadow DOM — это инженерный
  риск реализации AC6, явно признанный самим ТЗ («если конкретная версия HA не
  даёт стилизовать… это отклонение фиксируется в хендоффе, не скрывается»);
  ТЗ уже закладывает контролируемый путь деградации, дополнительной находки
  здесь нет.
- Не проверял содержимое `docs/design/600-settings-dialogs/pairs/*.png` и
  `screenshots/*` попиксельно — доверился текстовому описанию расхождений в
  теле issue, которое само по себе достаточно конкретно и привязано к
  строкам кода.
