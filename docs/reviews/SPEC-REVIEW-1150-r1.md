# SPEC-REVIEW-1150-r1

Issue: #1150 — «UI Kit, пакет 4: редакторы и редкие диалоги на ките, удаление старой системы .btn»
Этап: spec (ревью ТЗ, PROCESS.md §2.4) · Трек: `ask` · Заход: r1 · Блокирующих циклов: 0/4
Материал: тело issue #1150, `bodyDigest: f834f19c9c6498f6df5b347615045ed4f43e46c157cf128678ba9595622e0857`
(SHA/tree контекста: `2718cedab93339dadacccf7fdadf9850c0cb4f5c` / `dc9c07a15e187c402adab778ae888ed36436d530`)

Маршрут вердикта: `fix` (директивно для данного этапа/раунда).

## Скоуп

Финальный пакет серии UI Kit после #1146–#1149: три тулбара редакторов,
editor trays/палитры/выбор, панель свойств, один токен плавающей поверхности,
каталог устройств/правила иконок, редкие backup/help/import диалоги и
окончательное удаление legacy `.btn`. Обслуживает J4 (`docs/SCOPE.md`) —
«from zero to a working plan... editable icon rules», конкретно GUI-only
редактирование плана/устройств без разрастания отдельной параллельной
системы оформления контролов. Геометрия, снаппинг, drag/resize, история,
подбор устройств, форматы backup/import, touch-контракт и бэкенд/схема явно
вне скоупа — согласно `docs/SCOPE.md` редакторы остаются desktop-first/best
effort на touch, что текст ТЗ прямо повторяет.

## Как проверялось

Статус — «Кодовый Validate не требуется» (этап spec). Прочитаны однократно:
`docs/SCOPE.md`, `AGENTS.md`, `docs/process/REVIEWER.md`, тело issue #1150 и
обе страницы `REVIEW_CONTEXT` (включая авторский комментарий-аналитику от
2026-10-30 — оценка ценности/сложности/риска, трек `ask`, проверка
дубликатов, явный порядок пакетов «#1146 → #1147/#1148 → #1149 → #1150»).
Дополнительно прочитаны для проверки терминологии и осуществимости:
`docs/DIALOG-UI-KIT.md`, `docs/UX-MODES.md` (через `TOUCH-SUPPORT.md`),
`docs/TOUCH-SUPPORT.md`, `docs/USER-GUIDE.ru.md`, `docs/reviews/INDEX.md` и
`docs/reviews/SPEC-REVIEW-1148-r1.md` (предыдущий пакет той же серии — для
сверки прецедента по трактовке зависимостей между пакетами).

Адресные проверки осуществимости (чтением репозитория, без исполнения —
негативный тест/мутант здесь неприменим: вопросы касаются существования
файлов/строк и непротиворечивости текста, а не поведения кода):

1. **Вопрос:** существуют ли сейчас файлы и совпадают ли с границами диапазонов
   строк, на которые ссылается раздел «Состав» (`styles/chrome.styles.ts:225-242,454-489`,
   `editors/properties/styles.ts:12-34,61-127,159-163`,
   `styles/editor-dialogs.styles.ts:496-551,552-626,632-778`,
   `styles/settings-dialogs.styles.ts:228-252`, `styles/dialogs.styles.ts:34-65,350-353`)?
   **Результат:** все пять файлов существуют; их текущая длина (611, 779, 168,
   529, 257 строк соответственно) вмещает каждый названный диапазон. Прямым
   чтением подтверждено, что `dialogs.styles.ts:34-65` действительно содержит
   старую систему `.btn` (display/border/padding/hover/on/ghost/disabled), а
   `dialogs.styles.ts:350-353` — `.btn.danger`; `chrome.styles.ts:456-489`
   содержит ровно `.editbar .warn/input/drawwall/wallsgroup`, включая
   layout-only `.wallsgroup` (display/gap, без paint) рядом с кандидатами на
   удаление `.editbar input`/`.drawwall` (имеющими border/background/color) —
   пункт 6 контракта («не удалить используемую layout `.wallsgroup` вместе с
   кандидатами `.editbar input`/`.drawwall`») описывает реальную, а не
   воображаемую границу между правилами. ТЗ не фабрикует артефакты.
2. **Вопрос:** существуют ли уже метрики/реестр, на которые ссылаются
   AC1/AC2/AC6 («`btnRulesOutsideKit` = 0», реестр группы «Редакторы» из
   #1131, «метод #1146»)? **Результат:** `grep` по репозиторию не находит
   `btnRulesOutsideKit` ни в `src/`, ни в `scripts/`, ни в `docs/` (кроме
   самого текста ТЗ и предыдущего ревью #1148) — метод/счётчик ещё не
   реализован, т.к. #1146 («измеримость», пакет 0 серии) сам ещё не в `dev`
   (не найден ни в одном `docs/release-ledger/*/1146.json`, ни в
   `docs/CHANGELOG.md`). Это согласуется с явно описанной в ТЗ
   предпосылкой «Перед кодом — S5 и актуальный dev с принятыми
   зависимостями» и с прецедентом ревью #1148 (где тот же разрыв по
   отношению к #1146 не был находкой, поскольку зависимость прямо
   заявлена). Находкой не считаю сам факт «метрика ещё не существует».
3. **Вопрос:** непротиворечиво ли ТЗ называет полный список пакетов-предшественников?
   **Результат:** нет — см. находку F1 ниже.
4. Числа и ширины в разделе «Визуальная проверка» (1280/1024/390, «дополнительно
   существующие 360/320») сверены с `docs/TOUCH-SUPPORT.md`/`docs/USER-GUIDE.ru.md`
   и реальной терминологией («лоток», «панель свойств», «правила иконок»,
   «панель инструментов» — строки 55, 68, 1684, 1742 `USER-GUIDE.ru.md`):
   расхождений с каноном нет, термины не изобретены.

Полные build/test гейты (`gate:small`, `npm test`, `tsc`, golden) не
запускались — на этапе spec они не требуются, а материал ревью не содержит
кода. Мутанты/негативные прогоны неприменимы — предмета (кода) ещё нет.

## Находки

### F1 — Medium (в скоупе issue #1150): список пакетов-предшественников внутри ТЗ противоречив

Раздел `## Связи` (верхний, «аналитический» уровень issue, до `## ТЗ`) гласит:
«После пакетов 0–2. #1131; #931 (согласованная панель свойств); #1145 (пункты
7, 8 закроются здесь). Итог всех пакетов — ≈ 6 900 строк CSS против 7 635 на
29.10.2026.» Нумерация пакетов серии однозначно восстанавливается из заголовков
и предыдущего ревью: пакет 0 = #1146 («измеримость», подтверждено в
SPEC-REVIEW-1148-r1 — «#1146 ('измеримость') — декларированный предшественник»,
«## Связи»: «После пакета 0»), пакет 2 = #1148 (заголовок issue: «UI Kit,
пакет 2»). Значит «пакеты 0–2» = {#1146, #1147, #1148} — без #1149.

Однако сам раздел `## ТЗ` этой же issue, «Проблема, скоуп и не-скоуп», прямо
утверждает: «Финальный пакет **после #1146–#1149**: три toolbar, editor
trays/палитры/выбор, свойства/плавающие поверхности, каталог/правила иконок,
редкие backup/help/import диалоги и окончательное удаление legacy `.btn`.» Это
диапазон 0–3 (включает #1149), и он согласуется с заголовком самой issue
(«пакет 4» — закономерно идущий после пакета 3), а также с явным порядком
из авторского комментария-аналитики: «Порядок: #1146 → #1147/#1148 → #1149 →
#1150. Перед реализацией каждого пакета — актуальный dev и принятые
зависимости».

Итог: один раздел issue называет предшественниками {0,1,2}, другой — {0,1,2,3},
и обе формулировки принадлежат одной и той же задаче. Это ровно тот класс
разрыва, который уже получил Medium в предыдущем раунде серии
(SPEC-REVIEW-1148-r1, находка F1 — там `## Связи` не называл #1147, хотя
контракт на него ссылался). Здесь технический вопрос не выносится владельцу
(выбор уже сделан владельцем в комментарии-аналитике — верный диапазон 0–3),
поэтому решаю его сам: `## Связи` должен читаться «После пакетов 0–3»
(или явно «#1146–#1149»), а не «0–2». Пока это не исправлено, читатель,
ориентирующийся на `## Связи` как на источник зависимостей (как это и
происходило в разборе #1148), может решить, что #1149 не обязан попасть в
`dev` до начала реализации #1150 — прямое противоречие собственному же
разделу «Проблема, скоуп и не-скоуп» и заявленному автором порядку.

**Чем закрывается:** одна правка в `## Связи» — «После пакетов 0–3» (или
явный список «#1146, #1147, #1148, #1149») — без изменения раздела
«Проблема, скоуп и не-скоуп», который уже корректен.

## Что проверено и корректно

- Обязательные разделы §7.1 присутствуют и наполнены: сценарий; что человек
  увидит до/после; проблема/скоуп/не-скоуп; контракт поведения и UX (6
  пунктов); файлы и границы реализации; критерии приёмки AC1–AC7 с указанием
  способа доказательства для каждого; план автотестов; общие ограничения и
  решения; модель данных и миграция («нет»); i18n («новых ключей не
  ожидается»); производительность и взаимодействие; визуальная проверка и
  release-артефакты; принято предположительно; риски и откат.
- Все 7 AC имеют однозначно названный способ доказательства (ревью кода,
  smoke, golden, capturePlans, readback issue), что удовлетворяет DoR
  (PROCESS.md §2.5).
- AC7 корректно отделяет этот пакет от функционального скоупа #1156
  (копирование пространства): UI-часть уже закрыта в #1148 по решению
  владельца от 2026-10-31, а #1150 не объявляет флажки/семантику копирования
  выполненными — подтверждено авторским комментарием «новые флажки и
  семантика копирования остаются в #1156».
- Пути/диапазоны строк в разделе «Состав» (п. 2–7) проверены прямым чтением
  репозитория и соответствуют реальному коду (см. «Как проверялось», п.1);
  это не фабрикация и не устаревшая ссылка на несуществующий файл.
- Контракт п.6 (защита `.wallsgroup` от случайного удаления вместе с
  кандидатами `.editbar input`/`.drawwall`) точно описывает реальное
  соседство layout-only и paint-правил в `chrome.styles.ts:479` и
  `:459,473` — не абстрактное пожелание, а конкретная техническая граница,
  которую implementor сможет проверить при рефакторинге.
- Touch/desktop-first терминология («редакторы остаются desktop-first/best
  effort на touch», «View/киоск... сохраняют 44px») согласована с
  `docs/TOUCH-SUPPORT.md` (desktop-first administration tools, 44×44 px
  цели для View) и `docs/SCOPE.md` (editor parity on touch is outside the
  product guarantee).
- Пользовательские термины («лоток», «панель свойств», «правила иконок»,
  «панель инструментов») взяты из `docs/USER-GUIDE.ru.md`, не изобретены.
- i18n, модель данных/миграция и compatibility корректно закрыты явным
  «нет» с обоснованием (чисто презентационная CSS-миграция, без изменения
  формата конфигурации/HA-записей) — соответствует требованию DoR не
  создавать новую compatibility-поверхность без необходимости.
- Явный анти-gaming пункт («Сцену нельзя переименовать в Н для улучшения
  счётчика», «локальные радиус/фон/рамка/размеры... выносятся в владельца
  примитива, даже если уже выглядят одинаково») закрывает очевидный риск
  формального прохождения AC2 без реальной миграции.
- AC6 явно не требует совпадения с приблизительными «−270 строк»/«6900
  строк» из раздела «Ожидаемое изменение CSS»/«Связи» — не образует
  двойного источника для одного пользователю видимого числа, несовпадение
  прогноза и факта признано заранее и не является находкой.
- Откат описан предметно: отдельный revert пакета, в обратном порядке при
  наличии зависимых пакетов, без миграции пользовательских данных.

## Чего не проверял

- Содержимое самого реестра #1131 (117/173 ячеек, таблица группы
  «Редакторы», части 2 и 3 по ссылкам из раздела «Состав») — внешний
  материал вне тела issue #1150, не входил в `REVIEW_CONTEXT`; не фетчил по
  static-first и по правилу не запрашивать внешние URL вне программистской
  необходимости. Из-за этого не могу независимо проверить точные числа
  «117 из 173» и состав будущего финального реестра для AC2 — но способ
  доказательства AC2 («ревью кода: финальный реестр и CSS/DOM») не
  опирается только на эти числа и проверяем на этапе код-ревью по
  фактическому CSS/DOM независимо от точной предыстории.
- Код не существует — не проверялись Validate/`gate:small`/golden/
  smoke-select: на этапе spec это не требуется.
- Не выполнял ни одного негативного/мутантного прогона: предмет ревью —
  текст ТЗ, соразмерного исполнимого oracle для текста, отличного от
  чтения, не существует.
- Не проверял содержимое #1146/#1147/#1149 как отдельных задач (их тела
  issue вне материала этого ревью) — оценивал только то, что сам текст
  #1150 заявляет о них и следует ли это непротиворечиво из текста #1150
  (см. F1).
- Фактическое состояние `dev` на момент начала кодирования #1150 (придут ли
  #1147/#1149 раньше) — это проверяется конвейером перед S6, а не на этапе
  spec.
