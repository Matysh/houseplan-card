### Разбор дельты построчно

Сравнил старое тело `_deleteSpace()` (оба рантайма, было до рефакторинга —
воспроизведено по `git show 48a37b89` как diff-минус) с новым
`completeSpaceDeletion` в `src/editors/space-delete.ts:1-79`:

- Проверка входа `!accepted || !currentDialog || currentDialog.mode !== 'edit'
  || currentDialog.busy || currentDialog.spaceId !== spaceId || !currentConfig`
  разделилась на `if (accepted) await completeSpaceDeletion(...)` в вызывающем
  коде и остаток условия внутри функции — логически то же самое, `accepted`
  проверяется ровно один раз перед вызовом.
- `currentConfig.spaces.find(…) ; if (!currentSpace) return` →
  `if (!currentConfig.spaces.some(…)) return` — эквивалент.
- Ветка AC4 (сверка `markerIds`/`count`), ветка busy/запись, тройной путь
  `adopted.status !== 'adopted'`, обработка `catch` (`conflict`/`space_in_use`),
  восстановление `deleteBlockers`/`revealSpaceDeleteBlocker` — скопированы
  побайтово, отличается только `this.host.` → `host.` (параметр вместо
  замыкания) и тип catch (`e: any` в редакторе / `error: unknown` в онбординге
  → везде `error: unknown` в общей функции, строже, не слабее).
- Вызов для онбординга — `completeSpaceDeletion(this.host, spaceId, dependencies)`
  без `removeMarkers` (параметр по умолчанию `false`) — согласуется с тем, что
  AC2-кнопка в онбординге не рендерится (см. «Унаследовано из r1», «Отступления
  от ТЗ»); вызов для редактора передаёт `removeMarkers` явно.

Проверил, что перемещение не разорвало ленивую границу (риск, который сам
рефакторинг и был обязан не нарушить): `src/editors/space-delete.ts` импортирует
`HouseplanEditorHostPort` только как `import type` (стирается на компиляции),
значит онбординговый ленивый чанк по-прежнему не тянет тяжёлый
`houseplan-editor-runtime.ts`. Подтверждено и числом бюджета (`lazy onboarding`
прошло) и тем, что оба рантайма остаются отдельными динамическими импортами
(`src/houseplan-card.ts:583,617` — `await import('./houseplan-editor-runtime')` /
`await import('./houseplan-onboarding-runtime')`, не изменились этим диффом).

`test/config-adoption-ownership.test.mjs` и
`test/version-recovery-card-contract.test.mjs` обновлены синхронно с
перемещением единственного вызова `_adoptAuthoritative`/`_getAuthoritativeConfig`
из `houseplan-onboarding-runtime.ts` в `space-delete.ts` — проверил, что новые
ожидаемые числа (`occurrences(onboarding, …) + occurrences(spaceDelete, …)`)
действительно складываются в прежнюю единицу, а не маскируют пропавший вызов.

### Новый тест `test/space-delete-dialog.test.mjs`

14 сценариев (`node --test` насчитал 15 вместе с родительским раннером)
гоняют `completeSpaceDeletion` напрямую на моках `host`, без браузера:
обычное удаление и усыновление по re-read, а не по ответу `space/delete`
(`_cfgRev`/`_layoutRev` из `configResponse`/`layoutResponse`, не из
`{config_rev: 800, layout_rev: 900}` ответа самого вызова — прямая проверка
инварианта #500, упомянутого в ТЗ «Принято предположительно»), флаг
`remove_markers` только с `removeMarkers=true`, отказ при сдвинутом наборе
маркеров под подтверждением (AC4, клиентская сторона), блокировка активных
устройств и пропуск правила для последнего пространства (AC5), шесть
вариантов отказа входа (закрытый/чужой/занятый/create-диалог, нет
конфига/удалена цель) без единого вызова, flush+await `_writeChain` перед
взятием ревизий, `asset-wait`-ветка оставляет дело перезапланированному
reload, восстановление после `conflict`/`space_in_use`/`invalid_format` без
локального удаления. Это не было доказано прямым юнитом в r1 (только
смоком+pytest+node-паритетом) — усиление доказательной базы AC1–AC5, не
ослабление.

## Разбор по AC

AC1–AC6 не меняются этой дельтой по существу — контракт и поведение
идентичны r1. Перепроверил исполнением (не только чтением) именно то, что
дельта физически переместила:

- **AC1** (прокрутка/фокус) — логика живёт в `space-form.ts`
  (`revealSpaceDeleteBlocker`), эта дельта её не трогает; смок на свежей
  сборке — 31/31, включая `blockScrollsTheWarningIntoView`,
  `blockFocusesTheWarning`, `repeatAfterManualScrollRevealsAgain`.
- **AC2** (кнопка/подтверждение/одна запись) — перемещённый путь;
  подтверждено и смоком (`warningOffersDeleteWithDevices`,
  `oneAtomicWriteWithTheFlag`, `markersBecomeTombstones`,
  `bindingsAvailableAgain`), и новым прямым юнитом, и исполнением мутанта
  `space-delete-with-devices-drops-the-flag` (CAUGHT, 5 проверок).
- **AC3** (отмена) — `if (accepted) await completeSpaceDeletion(...)`:
  необнаруженное `accepted === false` не вызывает функцию вовсе, значит ни
  один побочный эффект внутри неё недостижим без принятия — сильнее, чем
  ветвление внутри одной функции в r1.
- **AC4** (конфликт, клиентская сторона) — перемещённый путь; смок
  `changedPlanUnderConfirmationDeletesNothing` зелёный, мутант
  `space-delete-with-devices-ignores-a-moved-plan` исполнением CAUGHT
  (ровно эта проверка падает). Серверная сторона (ревизии) — Python, этой
  дельтой не тронут, унаследовано из r1.
- **AC5** (последнее пространство/без устройств) — вызов онбординга без
  `removeMarkers` и ветка `!currentlyDeletingLastSpace` скопированы
  неизменными; смок `plainDeleteSendsNoNewKey` зелёный.
- **AC6** (тексты/доки) — i18n/USER-GUIDE/CHANGELOG этой дельтой не
  тронуты; добавлены только внутренние доки (`ARCHITECTURE.md`,
  `DEVELOPMENT.md`, `STATUS.md`) про сам рефакторинг — `User-Visible: no`
  корректен, новых пользовательских строк нет.
