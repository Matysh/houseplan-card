# SPEC-REVIEW-1148-r1

Issue: #1148 — «UI Kit, пакет 2: все диалоги на ките — ui-dialog везде, одна система кнопок»
Этап: spec (ревью ТЗ, PROCESS.md §2.4) · Трек: `ask` · Заход: r1 · Блокирующих циклов: 0/4

(SHA/tree контекста: `ecada723a7853a553ede68edb05c988ef7a652a7` / `21e5a5fb02c7f3c8e77cbf198ab37191c7d1e202`)

Маршрут вердикта: `fix` (директивно для данного этапа/раунда).

## Скоуп

Пакет переводит все вызовы `<hp-dialog>` (37 call sites в 23 файлах) на явный
класс `ui-dialog`, сводит кнопки к единому генератору `settingsActionsCss`,
удаляет старую параллельную систему покраски (`styles/dialogs.styles.ts`),
копию кита в PDF-диалоге и собственную оболочку сводной. В этом же пакете по
решению владельца 2026-10-31 выполняется только UI Kit-часть #1156 для
диалога копирования пространства (shell/footer/buttons/отступы/темы/узкий
экран), без функциональных флажков копирования. Обслуживает J4 (`docs/SCOPE.md`)
— «настройка плана через GUI», конкретно единообразие и доступность формы/кнопок
во всех административных диалогах.

## Как проверялось

Статус — «Кодовый Validate не требуется» (этап spec). Прочитаны однократно:
`docs/SCOPE.md`, `AGENTS.md`, `docs/process/REVIEWER.md`, тело issue #1148 и
обе страницы `REVIEW_CONTEXT` (включая комментарии владельца — аналитика
трека и отклонённый механический PASS предыдущей попытки с тех пор устранён:
`data-migration`, `i18n` и способы доказательства AC1/AC2 присутствуют в
текущем теле). Дополнительно прочитаны для проверки осуществимости и
терминологии: `docs/DIALOG-UI-KIT.md`, `docs/development-notes/dialog-style-migration.md`,
`docs/PDF-EXPORT.md`.

Адресные проверки осуществимости (чтением репозитория, без исполнения кода —
негативный тест/мутант здесь неприменим, т.к. вопросы касаются существования
артефактов и зависимостей, а не поведения кода):

1. **Вопрос:** существуют ли сейчас метрики `hpDialogWithoutKit` /
   `btnRulesOutsideKit` / `cssLines`, на которые ссылаются AC1/AC2/AC7 «по
   неизменённому методу #1146»? **Результат:** `grep` по репозиторию не находит
   ни одного из этих идентификаторов — метод ещё не существует, потому что
   #1146 («измеримость») — декларированный предшественник этого пакета
   (`## Связи`: «После пакета 0»; комментарий владельца: «Порядок: #1146 →
   #1147/#1148 → …»). Это согласованное упреждающее указание на будущую
   зависимость, а не изъян: ТЗ прямо требует «актуальный dev с принятыми
   зависимостями» перед кодом. Находкой не считаю.
2. **Вопрос:** названы ли в плане автотестов реально существующие смоки,
   которые можно переиспользовать (`modal recovery`, `danger confirms`,
   `space-copy/space form`, `settings`, `PDF/SVG`, `summary editor`)?
   **Результат:** `Glob`/`Grep` подтверждают реальное существование
   `demo/smoke_dialog_modal_recovery.mjs`, `demo/smoke_danger_confirm_branches.mjs`,
   `demo/smoke_danger_confirmation.mjs`, `demo/smoke_pdf_export.mjs`,
   `demo/smoke_summary_panel.mjs` и семейства `demo/smoke_summary_*`, а также
   `demo/smoke_space_copy.mjs`/`demo/verify_space_copy.mjs` и
   `docs/release-ledger/v1.82.0/1154.json` для lifecycle копирования (#1154 —
   принятая, не гипотетическая зависимость). План автотестов — реализуем.
3. **Вопрос:** существует ли уже заявленный в контракте источник «общего
   движения» #1147, которое пункт 7 запрещает подменять локальными
   keyframes/transition? **Результат:** `grep -r "1147"` по `src/`, `docs/`,
   `demo/` не находит ни одного следа #1147 в принятом коде — пакет ещё не
   реализован. См. находку F1 ниже: в отличие от #1146, #1147 не перечислен в
   `## Связи` как предшествующий пакет.
4. Числа и ширины в разделе «Визуальная проверка» (1280/1024/390,
   «дополнительно существующие 360/320 там, где уже есть договорённость»)
   сверены с `docs/PDF-EXPORT.md` («usable down to a 320 CSS px-wide View
   area», «compact560px settings shell»): расхождения нет, 320 px для PDF уже
   является зафиксированным в каноне соглашением, на которое ссылается общая
   формулировка ТЗ.

Полные build/test гейты (`gate:small`, `npm test`, `tsc`, golden) не
запускались — на этапе spec они не требуются и материал ревью не содержит
кода для их применения; это явно разрешено для spec-этапа. Мутанты/негативные
прогоны на исполняемом коде неприменимы — предмета (кода) ещё нет.

## Находки

### F1 — Medium (в скоупе issue #1148): зависимость от #1147 не отражена в «Связи»

Пункт 7 контракта («Контракт поведения и UX») гласит: «Движение берётся из
#1147 и общего кита, с reduced-motion; **не добавлять местные
keyframes/transition вместо переноса**». Это делает поставку #1147 жёстким
техническим предусловием: без неё implementor не может взять «общее
движение» и одновременно не вправе добавить локальную замену.

Однако раздел `## Связи` называет предшествующим пакетом **только** #1146
(«После пакета 0. #1131; #1145 …; #1132 …») — #1147 там не упомянут. Это же
подтверждает комментарий владельца от 2026-10-30 «Порядок: #1146 →
#1147/#1148 → #1149 → #1150»: запись через «/» не фиксирует, что #1147 обязан
попасть в `dev` раньше #1148, а просто группирует два пакета одного тира
после #1146. Поиском по репозиторию (`grep -r "1147"` в `src/`, `docs/`,
`demo/`) подтверждено, что #1147 ещё не реализован — «общий кит» движения,
на который ссылается пункт 7, пока не существует.

Итог: если исполнитель пакета #1148 начнёт реализацию раньше, чем #1147
примут в `dev` (а формальный порядок это не запрещает — в `## Связи` блокёром
назван только #1146), пункт 7 станет невыполним без нарушения собственного же
запрета на локальные keyframes. Разрыв — не продуктовый вопрос к владельцу
(выбор уже сделан: движение переиспользуется, а не изобретается заново), а
технический вопрос согласования порядка задач, который я снимаю сам: ТЗ должно
явно внести #1147 в список предшествующих пакетов (аналогично #1146) **или**
явно описать временное состояние (например: «пока #1147 не принят, открытие/
закрытие диалога сохраняет существующую локальную анимацию `hp-dialog`, замена
на общий кит — после слияния #1147, без нового review»). Ни того, ни другого
в тексте нет.

**Чем закрывается:** одна строка в `## Связи` («После пакета 0: #1146, #1147»)
или аналогичное явное указание порядка/запасного состояния в пункте 7
«Контракт поведения и UX».

## Что проверено и корректно

- Обязательные разделы §7.1 присутствуют и наполнены: сценарий; что человек
  увидит до/после; проблема/скоуп/не-скоуп; контракт поведения и UX; файлы и
  границы реализации; критерии приёмки AC1–AC7 с указанием способа
  доказательства; план автотестов; общие ограничения и решения; модель данных
  и миграция («нет»); i18n («новых ключей не ожидается»); производительность и
  взаимодействие; визуальная проверка и release-артефакты; принято
  предположительно; риски и откат. Прежний механический отказ («Missing
  required section: data-migration/i18n», «Name the evidence method» для
  AC1/AC2) в текущем теле устранён: оба раздела на месте, у AC1 и AC2 назван
  способ доказательства («ревью кода + smoke»).
- Все 7 AC имеют однозначно названный способ доказательства (`ревью кода`,
  `smoke`, `unit`, `golden`, `UI Lab`), что удовлетворяет DoR (PROCESS.md
  §2.5). Граница с #1156 для AC5 описана дважды (в «Граница с #1156» и в
  «Проблема, скоуп») одинаково и непротиворечиво — копия диалога пространства
  мигрирует только оболочкой, функциональные флажки прямо исключены из
  скоупа обоими разделами.
- Зависимость на лайфцикл #1154 (копирование пространства) — не гипотетическая:
  issue принят, `docs/release-ledger/v1.82.0/1154.json`,
  `docs/analysis/1154-space-copy-lifecycle.md` и смоки `smoke_space_copy.mjs`/
  `verify_space_copy.mjs` существуют, так что AC5 реализуем и проверяем
  существующими средствами.
- i18n, модель данных/миграция и compatibility корректно закрыты явным «нет»
  со ссылкой на отсутствие изменений формата/HA-записей — соответствует
  `docs/CONFIG-COMPATIBILITY.md`-требованию DoR не создавать новую
  compatibility-поверхность без необходимости.
- Touch-контракт (цели ≥44 px, скролл на узком экране, доступный footer)
  согласован с `docs/DIALOG-UI-KIT.md` (токен `--hpf-action-height: 44px`) и
  не противоречит `docs/SCOPE.md`/`TOUCH-SUPPORT.md` (редакторы — desktop-first,
  но обязаны оставаться функциональными, а не «touch-первыми»).
- Ширины визуальной проверки (390, существующие 360/320) согласованы с
  зафиксированным в `docs/PDF-EXPORT.md` контрактом PDF-диалога — расхождения
  с каноном нет.
- Явный выбор между «ui-dialog на call site» и «включение по умолчанию в
  hp-dialog» (вопрос, прямо поставленный в разделе «Состав» как «выбрать на
  этапе ТЗ») — в контракте сделан однозначно: «Выбран явный ui-dialog на call
  site; не ослаблять счётчик #1146, считая условное включение полным».
  Открытых развилок такого рода в тексте больше не осталось.
- Объём работы (37 call sites `<hp-dialog>`, 23 файла) подтверждён прямым
  поиском по `src/` и соответствует заявленному в «Зачем» масштабу — задача не
  занижает и не завышает физический охват.
- Риск-секция прямо называет каскад CSS/ShadowRoot, фокус/модальный стек,
  телефонную раскладку, reduced motion и ленивые границы как основные риски,
  с привязкой приёмки к их проверке — это соответствует перечисленным в
  контракте проблемным точкам (PDF в своём ShadowRoot, сводная в своей
  оболочке, decor/confirm — условные ветки).
- Откат описан предметно: отдельный revert пакета, в обратном порядке при
  наличии зависимых пакетов, без миграции пользовательских данных — закрывает
  обязательный пункт DoR «откат».

## Чего не проверял

- Содержимое внешних комментариев #1131 (часть 2 и часть 3 по ссылкам в
  разделе «Состав») — они не входили в материал ревью (`sources-1.md`/
  `sources-2.md` содержат только #1148); не фетчил их по правилу «не
  вычислять/не запрашивать внешние URL вне программистской необходимости» и
  по static-first: тело issue #1148 самодостаточно по обязательным разделам.
  Из-за этого не могу независимо проверить точный список «перечисленных
  диалоговых golden» и происхождение числа «23 capturePlans» в AC6 — но само
  AC6 не опирается только на эту цифру: способ доказательства («целевой
  golden/UI Lab/ревью источников») и защитное условие («неизвестные/
  непокрытые состояния не объявлены мёртвым CSS») самодостаточны и
  проверяемы на этапе код-ревью независимо от точного числа.
- Код не существует — не проверялись Validate/`gate:small`/golden/smoke-select:
  на этапе spec это не требуется, а разбор по дельте кода относится к
  код-ревью.
- Не выполнял ни одного негативного/мутантного прогона: предмет ревью —
  текст ТЗ, а не исполняемая реализация; соразмерного исполнимого oracle для
  текстового ТЗ, отличного от чтения, не существует.
- Не проверял содержимое #1146 и #1147 как отдельных задач (их тела issue вне
  материала этого ревью); оценивал только то, что #1148 заявляет о них и
  следует ли это из текста самого #1148 непротиворечиво (см. F1).
