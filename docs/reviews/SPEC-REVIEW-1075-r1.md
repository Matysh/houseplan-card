# SPEC-REVIEW — issue #1075, заход r1

**Вердикт: жёлтый · заход r1 · блокирующих циклов 0/4 · High: 0 · Medium: 1 → в задаче**

Материал: тело issue #1075 (`bodyDigest e02532f0f114fa86a04faa2212c71257e7542ade90bbdc3ccd3b17ba18faad27`,
раздел `## ТЗ`), репозиторий на `0bbf6152a5fe6127ca176dbd5d975d93bea5aaee`. Трек `ask`, этап `spec`.
Маршрут вердикта: `route: fix` (поле фиксировано для этапа spec).

## Скоуп

Задача обслуживает J4/J6 (`docs/SCOPE.md`): администратор поддерживает план —
удаляет промежуточный узел стены правым кликом независимо от инструмента и
размещает/отменяет мебель в редакторе подложки. ТЗ закрывает два связанных,
но разных дефекта: (1) доступность контекстного меню узла ограничена
инструментом «Выбрать»; (2) несоразмерная задержка удаления/Undo узла и Undo
размещения мебели. Автор дополняет аналитику первоначального #1045 (node
delete), #803/#834 (перемещение узлов) и #843 (история узлов), не расширяя их
гарантии.

проверено):

## Находки

### Medium (в скоупе) — классификация release-ledger не учитывает, что мебельный путь не внутри-бетный

**Воспроизведение:** §12 ТЗ фиксирует единую классификацию будущего
`docs/release-ledger/v1.82.0/1075.json`: `line-fix`, обоснование — «node
Delete #1045 и связанные редакторские изменения появились после stable
v1.82.0; согласованное поведение мебели сохраняется, нового формата нет».

`line-fix` в этом проекте зарезервирован за внутри-бетными правками —
исправлением функциональности, которой ещё нет в выпущенном stable
(прецеденты `1071.json`/`1039.json`/`1053.json`: каждый несёт `introducedBy`
на конкретный beta-issue, чьё поведение правится). У `1075` таких два разных
компонента:

1. Доступность меню узла и дорогие проходы `node_delete`/`node_delete_host_baseline` —
   действительно внутри-бетные: #1045 появился только в `v1.83.0-beta.1`
   (после stable `v1.82.0`). `line-fix`, `introducedBy: 1045` для этой части
   корректен.
2. Задержка Undo/Redo размещения мебели — **не** внутри-бетная. Причина —
   безусловный вызов `commitWallSegmentModel()` и сброс физических кэшей в
   `_applyGeometryState()` (`src/houseplan-editor-runtime.ts:2362,2380-2382`),
   который не зависит от `physicalChanged`. Эта ветка существует с коммита
   `fac660980` «fix(editor): a refused ordinary Undo/Redo keeps the rest of
   the history (#883)», датированного **2026-10-14** — на неделю раньше тега
   `v1.82.0` (**2026-10-21**, `git log -1 --format=%ad v1.82.0`). Удаление
   промежуточного узла стены как фича — новое в бете, но сам факт полной
   пересборки стеновой модели при декор-only Undo — уже выпущенное в stable
   поведение. Прецедент `1051.json` формулирует именно этот случай:
   `stable-fix` — «an improvement to stable surfaces rather than an entirely
   new subsystem», а `docs/process/REVIEWER.md` отдельно называет
   пользовательскую производительность основанием для milestone
   (`stable-fix`/`major`, не `line-fix`/`infra`).

**Последствие:** единая `line-fix`-классификация всей задачи выводит
мебельный перф-фикс — уже наблюдаемый на выпущенном stable дефект — из
пользовательского release milestone, хотя он подпадает под «пользовательскую
производительность» из §11.9. Это решение автора, но текущее обоснование в
ТЗ его не рассматривает: оно объясняет только долю #1045 и переносит вывод
«line-fix» на компонент, который fix#1045 не вводил.

**Чем закрыть:** до DoR либо разбить обоснование на два компонента с явным
`introducedBy: 1045` только для доли меню/node-delete и отдельной
аргументацией категории для доли мебельного Undo (вероятно `stable-fix`,
по образцу `1051.json`), либо явно объяснить в §12, почему мебельный
компонент всё равно не входит в milestone несмотря на то, что дефект
существует в уже выпущенном `v1.82.0`. Любой вариант — решение автора по
классификации (REVIEWER.md: «это авторское суждение, не вывод из
User-Visible»), но принятое с учётом даты коммита `fac660980`, а не без неё.

- Обязательные разделы §7.1 присутствуют и в правильном порядке: сценарий,
  «что человек увидит», проблема, скоуп/не-скоуп, контракт меню и ввода,

- Открытых продуктовых вопросов нет (§12 ТЗ это утверждает явно); единственный
  технический вопрос, который у меня возник при чтении (структурная ли это
  переделка `down()`), снят самостоятельно чтением кода — решение по существу
  выше, владельцу не передаётся.
- Каждый AC называет способ доказательства (`unit`/`backend`/`smoke`/
  `golden`), и для защитных AC (AC2, AC3, AC5, AC6, AC8) «чем краснеет» уже
  встроено в текст доказательства (конкретные негативные входы — stale/
  authority/late-callback, concurrent/new-violation, ordinary pre-fix
  избыточные build-счётчики), а не оставлено пустым столбцом.
- Технические утверждения аналитики (разделы 1–4 issue) независимо
  перепроверены чтением текущего кода клиента и backend — все совпали,
  включая номера вызовов `commit_wall_segment_model` и отсутствие
  `baseline_counts` на целевом endpoint.
- Терминология видимого поведения (меню узла, причины отказа, «Удалить
  узел», Ctrl/Cmd+Z/Shift+Z/Ctrl+Y, 50-шаговая история) соответствует
  `docs/USER-GUIDE.ru.md` и `docs/UX-MODES.md`; новых UX-терминов ТЗ не
  изобретает.
- Дизайн разделения доступности меню/правого клика от Select-only
  перетаскивания согласуется с уже существующим прецедентом в том же файле:
  Undo/Redo перемещения узла (#843) уже работает «любым инструментом», тогда
  как capture/handles остаются Select-only (`docs/UX-MODES.md:277-279`) — то
  есть ТЗ продолжает уже принятый паттерн, а не вводит новый.
- Классификация `baseStable: v1.82.0` и `introducedBy: 1045` для доли
  меню/node-delete корректна: #1045 опубликован только в неопубликованном
  `v1.83.0-beta.1`, последний stable — `v1.82.0` (2026-10-21).
- Откат (§9), i18n (§8 — без новых ключей), модель данных (§9 — без миграций)
  описаны однозначно и проверяемы.

## Чего не проверял

- Поиск открытого дубликата через `gh`/GitHub issue search — инструмент не
  был разрешён в этом запуске; принято утверждение автора «Открытого
  дубликата не найдено» без независимой проверки.
- Исполнение кода/тестов — на этапе spec не требуется (нет diff продуктового
  кода; вся «Аналитика» — чтение и диагностика на уже неизменённой
  реализации, подтверждена только для факта несоразмерной задержки на Test
  Plan, прогоны самого автора заново не повторялись, это не требуется для
  spec-гейта).
- Реальная серверная фазовая профилировка (lock/executor/CPU/persist) — ТЗ
  откладывает её на этап реализации (AC9); на spec-этапе это соразмерно.
- Полнота перечня затронутых файлов для `store.py` — ТЗ прямо помечает его
  «при подтверждённой необходимости», то есть решение передвинуто в
  реализацию; это не находка ТЗ.
