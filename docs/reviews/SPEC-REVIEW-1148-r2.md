# SPEC-REVIEW-1148-r2

Issue: #1148 — «UI Kit, пакет 2: все диалоги на ките — ui-dialog везде, одна система кнопок»
Этап: spec (ревью ТЗ, PROCESS.md §2.4) · Трек: `ask` · Заход: r2 · Блокирующих циклов: 1/4
Материал: тело issue #1148, `bodyDigest: 99d7d7d75f33fc0f61fee192e0a20106e602562b05b92aaf6231d7212e5d9f33`
(SHA/tree контекста: `51b69164aead32b2334665b33f5b440206d62a9b` / `1b5ce9a425b41118215df4e3f2808887693bc1de`)

## Скоуп

Без изменений относительно r1: пакет переводит все вызовы `<hp-dialog>`
(37 call sites в 23 файлах) на явный класс `ui-dialog`, сводит кнопки к
единому генератору `settingsActionsCss`, удаляет старую параллельную систему
покраски (`styles/dialogs.styles.ts`), копию кита в PDF-диалоге и собственную
оболочку сводной; в этом же пакете по решению владельца 2026-10-31
выполняется только UI Kit-часть #1156 для диалога копирования пространства
(shell/footer/buttons/отступы/темы/узкий экран), без функциональных флажков
копирования. Обслуживает J4 (`docs/SCOPE.md`) — «настройка плана через GUI»,
конкретно единообразие и доступность формы/кнопок во всех административных
диалогах.

## Как проверялось

Static-first: прочитаны однократно в этом раунде `docs/SCOPE.md`, `AGENTS.md`,
`docs/process/REVIEWER.md` (раздел «Повторный раунд» — предмет round'а есть
дельта, разбор полный только при неуверенности в локальности дельты),
`REVIEW_CONTEXT` целиком (тело issue + все страницы `sources-1.md`/
`sources-2.md`, включая четыре комментария владельца с 2026-10-30 по
2026-10-31) и прежний документ `docs/reviews/SPEC-REVIEW-1148-r1.md` для
определения материала и находки предыдущего раунда.

Дельта раунда — сравнение текущего тела issue с текстом, процитированным в
r1-документе: изменился **только** раздел `## Связи`. Старый текст
(процитирован в F1 r1): «…Ревью ТЗ этих пакетов допустимо параллельно. После
пакета 0. #1131; #1145 …; #1132 …» — предшествующим пакетом был назван только
#1146. Новый текст: «Блокирующие зависимости реализации: пакеты 0 (#1146) и 1
(#1147) должны быть в S8 перед началом кода #1148. Общие токены/примитивы
движения поступают из #1147; запасная локальная система движения не
вводится. Ревью ТЗ этих пакетов допустимо параллельно. Порядок кода серии:
#1146 → #1147 → #1148 → #1149 → #1150. #1131; #1145 (пункты 1, 4, 5, 9
закроются здесь); #1132 (печать на ките)». Все остальные разделы (Зачем,
Состав, Готово когда, Ожидаемое изменение CSS, Риски, Граница с #1156, весь
`## ТЗ` от «Сценарий» до «Риски и откат», включая AC1–AC7 дословно) совпадают
с текстом, зафиксированным в r1, — побайтово сверено построчным сравнением
цитат r1-документа с текущим `sources-1.md`/`sources-2.md`. Сомнений в
локальности дельты нет: правка — одно предложение/абзац в одном
некритическом для остального текста разделе, не меняющая AC, контракт,
файлы/границы или план автотестов; полный повторный разбор всей задачи не
требуется (`docs/process/REVIEWER.md`, «Повторный раунд»).

Адресная проверка дельты (единственный конкретный вопрос этого раунда —
закрыта ли находка F1 r1):

1. **Вопрос:** называет ли новый текст `## Связи` #1147 блокирующим
   предшественником кода #1148 наравне с #1146, как требовала находка F1?
   **Результат:** да, дословно — «пакеты 0 (#1146) и 1 (#1147) должны быть в
   S8 перед началом кода #1148». Это сильнее минимального требования F1
   (которое допускало любую из двух альтернатив — явную зависимость или
   явное запасное состояние): текст одновременно называет #1147 блокирующей
   зависимостью **и** закрывает альтернативную лазейку «временного местного
   аналога», прямо запрещая её («запасная локальная система движения не
   вводится»), что согласуется с пунктом 7 контракта («не добавлять местные
   keyframes/transition вместо переноса») и снимает исходное противоречие
   между пунктом 7 и перечнем предшественников.
2. **Вопрос:** согласуется ли новый текст с комментарием владельца
   6536646494 («M1 из SPEC-REVIEW-1148-r1 исправлена… #1146 и #1147 —
   блокирующие предшественники кода #1148, оба должны быть в S8… Порядок:
   #1146 → #1147 → #1148 → #1149 → #1150»), который для spec-этапа является
   пояснением, а не заменой тела issue? **Результат:** да, формулировка и
   порядок серии в теле issue дословно совпадают с решением владельца в
   комментарии; владелец правил именно тело issue (это и есть материал
   ревью), а не прикладывал отдельный хендофф-план.
3. **Вопрос:** не создаёт ли переформулировка новой проблемы — например,
   противоречия с «Ревью ТЗ этих пакетов допустимо параллельно» (параллельное
   ревью ТЗ #1146/#1147/#1148 остаётся разрешённым, в отличие от кода)?
   **Результат:** противоречия нет — фраза про параллельность ревью ТЗ
   сохранена без изменений и относится к этапу `spec`, а новая фраза про S8
   относится к этапу `code`/реализации; оба утверждения независимы и не
   пересекаются по предмету.

Полные build/test гейты (`gate:small`, `npm test`, `tsc`, golden) не
запускались — на этапе spec они не требуются, а материал ревью (тело issue)
не содержит кода. Негативные/мутантные прогоны неприменимы — предмет ревью
текстовый, исполняемого кода нет.
