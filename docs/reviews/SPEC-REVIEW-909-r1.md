# SPEC-REVIEW-909-r1

Issue: [#909](https://github.com/Matysh/houseplan-card/issues/909) — «Убрать
мёртвую summary attachment-границу и исправить битую ссылку ревью».
Трек: `track:ask` (прямое поручение владельца от 2026-10-15 для группы
batch-findings, не обычная классификация по критериям §5). Заход r1,
блокирующих циклов израсходовано 0 из 4.

Материал: тело issue #909 (ТЗ, раздел `## ТЗ`), снимок на момент комментария
владельца 2026-10-15T11:53:28Z. Код не менялся, ветка под задачу не создана —
это чистое ревью ТЗ, без диапазона коммитов.

## Скоуп

Задача — ограниченный technical cleanup (P3, ценность 1/10, сложность 2/10,
класс A/C): удалить подтверждённо мёртвые `SummaryRuntimeSlot`,
`SummaryRuntimeLike`, `SummaryRuntimeAttachment` и метод
`SummaryRuntimeLoader.attach()` из `src/summary-runtime-loader.ts`, перенести
или убрать только тесты этого API, и исправить одну битую относительную
ссылку в `docs/reviews/SPEC-REVIEW-883-r1.md` (указывает на несуществующий
путь вместо `docs/reviews/SPEC-REVIEW-843-r1.md`). Явно не входит: сам
`summary-runtime-loader` (используемый класс), `ViewRuntimeBoundary`,
factory/pending cache, retries/fingerprints, доступность, размер/настройки
панели, архивация прочих старых отчётов.

Находка явно происходит из принятой `CODE-REVIEW-848-r1.md` (Low, «не
блокирует», с прямым предложением того же удаления) — не новое
предположение, а подтверждённый и задокументированный остаток.

Работа не добавляет функцию и не расширяет поверхность продукта: это
внутренняя гигиена кода и документации, видимое поведение не меняется, что
ТЗ прямо фиксирует («После: … видимое поведение то же»). `docs/SCOPE.md`
гейтит добавление функций; на удаление неиспользуемого внутреннего API и
исправление собственной ссылки ревью-архива этот гейт не ложится никаким
пунктом Core user jobs — возражений по скоупу нет.

## Как проверялось

Ревью ТЗ на этапе `spec`: код не исполнялся (веток/коммитов нет), но каждое
фактическое основание ТЗ сверено чтением текущего дерева на
`1d3ef09dbf5a89726f2c3ea4cb7786b5f3b2f963`, чтобы отличить «похоже на
правду» от «проверено»:

- Прочитан `src/summary-runtime-loader.ts` целиком (116 строк). Диапазон
  29–101, названный в ТЗ, действительно покрывает `SummaryRuntimeAttachment`,
  `SummaryRuntimeLoader.attach()`, `SummaryRuntimeLike`, `SummaryRuntimeSlot`.
- `grep -rn "SummaryRuntimeSlot\|SummaryRuntimeLike\|SummaryRuntimeAttachment"
  src test demo custom_components` — единственные упоминания вне самого
  файла отсутствуют; `SummaryRuntimeSlot` нигде не инстанцируется
  (`new SummaryRuntimeSlot` не встречается). `.attach(` вне файла встречается
  только в `test/summary-runtime-loader.test.mjs`. Утверждение «нет product
  consumer» подтверждено, не принято на слово.
- Прочитан `src/view-runtimes.ts`: продуктовый путь использует
  `summaryRuntimeLoader` только через унаследованные от `ViewRuntimeCode`
  методы `create()`/`ensure()` (вызываются из `ViewRuntimeBoundary`, не
  `SummaryRuntimeLoader.attach()`), а жизненный цикл установленного рантайма
  управляется напрямую — `host._summary.connect()/disconnect()` в
  `ViewRuntimes.connect()/disconnect()` (`src/view-runtimes.ts:68–83`). Это
  закрывает риск из раздела «Риски» ТЗ («мог разделять полезный cache
  cleanup») — активный путь уже делает эквивалентную очистку сам, без
  `SummaryRuntimeSlot.disconnect()`.
- Прочитан `test/view-runtime-boundary.test.mjs` целиком (88 строк): warm
  sync, dedup конкурентного импорта, один explicit retry и «протухание»
  владения (`f.replace()`/`f.disconnect()`) уже покрыты тестами, независимыми
  от `SummaryRuntimeLoader.attach()` (используют `ViewRuntimeCode`/
  `ViewRuntimeBoundary` напрямую). AC1 ссылается на реально существующую,
  уже работающую страховку, а не на тест, который будет удалён вместе с
  API — так что удаление `.attach()`-специфичных тестов не обнуляет эти
  гарантии.
- Прочитан `test/summary-runtime-loader.test.mjs` целиком: бо́льшая часть
  тестов явно вызывает `loader.attach(...)` (мёртвый путь) — именно их и
  предписывает удалить скоуп ТЗ; последний тест («ensure() rejects… и reset
  возвращает в cold») использует только живые унаследованные методы и под
  описание «работающих гарантий cache/loader» из AC2 не подпадает под
  удаление.
- `node scripts/reviews-archive.mjs --check-links` запущен локально:
  ```
  docs/reviews/SPEC-REVIEW-883-r1.md: ../../houseplan-card/docs/reviews/SPEC-REVIEW-843-r1.md
  битых относительных ссылок: 1
  ```
  Подтверждает: (а) ссылка действительно битая, (б) существующий инструмент
  уже умеет её поймать и падает (exit 1) — то есть AC3 ссылается на годный,
  работающий детектор, а не на воображаемый гейт. Проверен и верный таргет:
  `docs/reviews/SPEC-REVIEW-843-r1.md` существует, а конвенция соседних
  ссылок в том же каталоге (`docs/reviews/INDEX.md:113` на `SPEC-REVIEW-843-r1.md`)
  — простое относительное имя файла в той же папке, без `../../` префикса;
  исправление однозначно.
- Сверена ссылка на основание: `docs/reviews/CODE-REVIEW-848-r1.md:74–87`
  действительно описывает тот же Low с теми же символами и тем же
  предложением удаления — источник находки не придуман.
- `docs/release-ledger/` — записи для #909 нет (ожидаемо: код ещё не
  писался, это только спек-этап).

**Чего не проверял.** Гейты кода (`tsc`, `npm test`, `npm run build`,
golden, инварианты) не прогонялись и не требовались: на этапе `spec` нет ни
диффа, ни ветки — проверять нечего, «зелёный Validate на 1d3ef09d» относится
к текущему `dev`, а не к гипотетической реализации #909. Фактическое
удаление кода, перенос тестов и правка ссылки (включая `--apply`
архивации) — задача этапа `code`, не этого ревью.

## Проверка обязательных разделов ТЗ (§7.1)

Все обязательные разделы присутствуют и однозначны: сценарий · что человек
увидит до/после · проблема · скоуп / не-скоуп · контракт поведения · UX и
доступность · модель данных и миграция · i18n · критерии приёмки AC1–AC3 с
именованным способом доказательства каждого · план автотестов · риски ·
откат · release-артефакты. Раздел «Технические предположения» содержит ровно
одно явно помеченное предположение («принято предположительно, поменять
свободно») — открытый технический вопрос для сложной задачи закрыт этим же
способом, а не вынесен владельцу продуктовым вопросом, которым не является.

AC проверены на доказуемость, а не только на наличие слова «доказательство»:

| AC | Доказательство | Проверено ревьюером |
|---|---|---|
| AC1 | ревью кода + полный поиск импортов src/test; существующие loader/ViewBoundary unit | подтверждено: поиск уже выполнен выше, искомые юнит-тесты существуют и реально покрывают заявленные гарантии независимо от удаляемого API |
| AC2 | существующий summary mount/first/warm/reconnect smoke, без ослабления assertions | smoke не запускался (нет диффа), но ссылается на реально существующий именованный smoke, а не на абстрактную проверку |
| AC3 | существующий link checker (`reviews-archive.mjs --check-links`) + архивный dry-run | подтверждено: инструмент существует, запускается, сейчас красный (1 битая ссылка) — именно то «чем краснеет», что требуется для защитного утверждения о ссылках |

Единственное мелкое наблюдение без последствий: раздел «Текущие основания»
говорит «search src/test», тогда как исходная находка `CODE-REVIEW-848-r1`
проверяла `src/ test/ demo/ scripts/`. Разница не меняет результат — я сам
расширил поиск на `demo` и `custom_components` и подтверждений вне
src/test не нашёл, — поэтому это не находка, а замечание в скобках.

## Что проверено и корректно

- Все фактические основания ТЗ (диапазон строк, отсутствие потребителей,
  битая ссылка, происхождение из #848) подтверждены чтением текущего кода и
  документов, а не приняты на веру.
- AC1–AC3 проверяемы, и для каждого уже существует работающий механизм
  доказательства (юнит-тесты, именованный smoke, работающий линк-чекер,
  который прямо сейчас краснеет на целевой ссылке).
- Риск «мог прятать полезный cache cleanup» в разделе «Риски» — не пустая
  осторожность: прочитан `view-runtimes.ts`, подтверждено что эквивалентная
  очистка уже выполняется на активном пути (`host._summary.disconnect()`),
  так что обеспокоенность ТЗ обоснована, но не указывает на реальный дефект.
- Release-артефакты (infra/без milestone, `User-Visible:no`) соответствуют
  прецеденту (#848) и правилу §11.9 — задача не меняет пользовательское
  поведение.
- Не-скоуп корректно исключает соседние системы (ViewRuntimeBoundary,
  factory/pending cache, retries/fingerprints, доступность, размер панели).
