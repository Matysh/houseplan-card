## Находки

### High — отсутствует обязательная классификация релиза `docs/release-ledger/v1.80.1/837.json`

PROCESS.md §2.6 требует классификацию (`major`/`infra`/`stable-fix`/
`line-fix` + обоснование) **до S7**, в
`docs/release-ledger/<previous-stable>/<issue>.json`. Текущий цикл
(`docs/release-ledger/cycle.json`): `baseStable: "v1.80.1"`. Директория
`docs/release-ledger/v1.80.1/` содержит `638.json`, `674.json`, `838.json`,
`839.json` — файла `837.json` в ней нет ни в рабочем дереве, ни в самом
коммите `0c8181cb` (`git ls-tree -r HEAD --name-only | grep release-ledger`).

Это не формальность: `scripts/merge-candidate.mjs` вызывает
`ops.checkReleaseEntry?.(candidate)` (строки 545 и 595) **перед** каждым
push в `dev` — для обоих путей слияния (быстрый fast-forward и путь с
ребейзом), безусловно для любого трека. `checkReleaseEntry` —
`readMergeEntry` (`scripts/release-ledger.mjs:47-58`), которая делает
`git show <candidate>:docs/release-ledger/v1.80.1/837.json` без try/catch:
при отсутствующем пути `git show` возвращает ненулевой код, и
`must(...)` бросает исключение. Верхний уровень `mergeCandidate` эту
категорию ошибок не разбирает как «отказ пуша» (`error.refusal` не
установлен) — исключение долетает до `.then(resolve, reject)` в точке входа
(`scripts/merge-candidate.mjs:703-712`), который ловит *любую* ошибку,
логирует её, публикует в issue комментарий `commentFor('error', …)` с
текстом сырого исключения и выставляет `to=S6-in-progress`.

Итог: даже зелёный вердикт этого раунда не доехал бы до `dev` — конвейер
попытается слить, споткнётся на отсутствующем файле классификации,
откатит задачу в `S6-in-progress` с малопонятным комментарием об ошибке
git, и раунд ревью придётся проходить заново после того, как автор
добавит файл. Это тот же класс находки, что и High в r1 (механический факт,
гарантированно ломающий последующий шаг конвейера), а не стилистическое
замечание.

**Воспроизведение:**
```
cat docs/release-ledger/cycle.json                       # baseStable: v1.80.1
ls docs/release-ledger/v1.80.1/                           # 638.json 674.json 838.json 839.json — без 837.json
git ls-tree -r HEAD --name-only | grep release-ledger     # подтверждает: 837.json нет и в самом коммите
sed -n '45,58p' scripts/release-ledger.mjs                # readMergeEntry: git show без try/catch на путь entry
sed -n '540,600p' scripts/merge-candidate.mjs             # checkReleaseEntry перед каждым pushWithLease(..., 'dev', ...)
```

Сравнение: `docs/release-ledger/v1.80.1/839.json` — соседняя инфраструктурная
задача того же дня — классифицирована (`"category": "infra"`) с обоснованием
«инструменты процесса, поведение карточки и интеграции не меняется».
Аналогичная запись для #837 отсутствует; какая категория подходит —
решение автора (§2.6: «Это учёт поставленной работы» — не вывод из
`User-Visible`), не ревьюера.

Находка в скоупе #837 (создание одного JSON-файла классификации — работа
этой же задачи, не соседняя), поэтому отдельный issue не заводится —
возврат автору.

Нет Medium-находок вне скоупа, требующих отдельного issue.

## Унаследовано из r1

Принято без повторного детального чтения кода (контент файлов побайтно
совпадает — перепроверено сравнением текущего `git diff origin/dev...HEAD`
по каждому из трёх тестовых файлов с описанием в CODE-REVIEW-837-r1.md,

  сохраняет тот же runtime-эффект мутанта, но больше не рушит сужение типов

  в этом раунде перепроверен заново исполнением (таблица выше), не только
  унаследован.

  встроенный отрицательный контроль (`untrimmed` vs `composed`) доказывает

  (`wall-failed-core` остаётся строгим) — анализ r1, содержимое файла не
  изменилось в этом раунде.
- Риски автора, принятые в r1 как документированное ограничение, не
  находка: переименование `_applyGeometryState` сделает подмену в смоке
  немой, но заметной (упадёт `wall-failed-core`); свидетель 3 не проверялся
