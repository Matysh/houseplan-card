# SPEC-REVIEW-891-r1

Issue: [#891](https://github.com/Matysh/houseplan-card/issues/891) — «Undo/Redo:
сохранить независимую историю при отказах записи и корректно различать ошибки
переноса узла». Трек: `track:ask`. Заход r1, блокирующих циклов израсходовано
0 из 4. Материал: тело issue #891 (раздел `## ТЗ`), повторная сверка владельцем
14.10.2026 на `ef1aeaf6cf94f2f692654e975a4ee18c40b143a7` (v1.81.0-beta.2
candidate) — рабочая копия на этом SHA, продуктовый код не менялся.

## Скоуп

`houseplan-editor-runtime` (`_clearGeometryGesture`, `_writeConfig`,
`_rollbackRejectedPhysicalWrites`, chain undo/redo), `wall-node-editor`/
history/write (`src/wall-node-history.ts`), `geometry-history-step`/
`command-stack`, `websocket_api` узел-эндпоинт (`ws_wall_node_move`), i18n,
unit/backend/native smoke. Явный не-скоуп: не расширять допустимую геометрию,
не менять wall identity/schema, не возвращать историю через внешнюю замену
плана; контракты #843/#883 сохраняются (задача прямо называет, какие функции
не переписывать).

Работа закрывает J6 из `docs/SCOPE.md` («Keep the plan true… drag/resize,
merge/split, optimistic locking») через надёжность уже принятого механизма
Undo/Redo. Сценарий и «что человек увидит до/после» — продуктовые, без
терминов реализации, персона — Home admin, поверхность — редактор Plan (Walls,
Select/node move), сервер House Plan. Остатки после #843/#883/#845 заявлены
явно, с указанием, какую функцию каждого не трогать повторно.

## Находки

### M1 (Medium, в скоупе) — release-артефакты не называют обновление канона
подсистемы `docs/UX-MODES.md`

Контракт поведения (п.3, п.5) и i18n-раздел ТЗ меняют ровно ту таксономию
отказов Undo/Redo переноса узла и общую формулировку временного отказа,
которую сейчас документирует `docs/UX-MODES.md:194-222` («Refusals are named
and keep the history: unavailable right now…», «a temporary failure says
“Undo is not available right now. Try again.”» — именно эта фраза один в один
совпадает с дефектом «текст отказа говорит Undo даже для Redo», который ТЗ
обязуется исправить). Оба непосредственных предшественника в этой же
подсистеме обновляли этот файл в том же коммите: #843 (+16 строк в
`docs/UX-MODES.md`, коммит `f26017d2`) и #883 (+13 строк, коммит `fac66098`,
плюс `docs/ARCHITECTURE.md`, `docs/USER-GUIDE.md`, `docs/DEVELOPMENT.md`,
`docs/STATUS.md`). Раздел «Release-артефакты» ТЗ называет только
«RU/EN changelog + ARCHITECTURE/STATUS» — `docs/UX-MODES.md` не упомянут ни
там, ни где-либо ещё в ТЗ.

Это не формальность: `docs/UX-MODES.md` — канонический источник контракта
(AGENTS.md, «canonical document of the subsystem you touch»), и следующий
ревьюер/автор, читающий его как источник истины о текущей таксономии отказов,
получит текст, который #891 прямо обещает заменить. DoR (§2.5) требует явно
назвать «документация… либо явное «нет»» в release-артефактах; сейчас строка
просто не называет единственный файл, который по факту придётся менять.

**Воспроизведение дефекта ТЗ:** взять раздел «Release-артефакты» и задать
вопрос «какой файл документации меняется, если контракт п.5 заменяет общий
текст отказа на различающий направление/причину?» — ответ по тексту ТЗ: ни
один из названных (ARCHITECTURE/STATUS не содержат эту таксономию; она в
UX-MODES.md).

**Требуемая правка (в скоупе #891, тот же issue):** добавить
`docs/UX-MODES.md` (абзац `#843`/`#883`, строки 194-222) в список
release-артефактов наряду с ARCHITECTURE/STATUS.

### M2 (Medium, в скоупе) — классификация release-ledger не разделяет
pre-v1.80.1 дефект и внутрибетную регрессию #843

Раздел «Release-артефакты» заявляет одной строкой: «Ledger: stable-fix
относительно v1.80.1 для истории/node editor, milestone 1.81; отдельно
проверить first-introduced range» — то есть относит **весь** объём задачи
(включая AC3 — клиентский классификатор node-move отказов) к `stable-fix`
против `v1.80.1`, одновременно признавая, что диапазон первого появления
дефекта не проверен.

По факту истории git это разделяется на два разных случая:

- Контракт п.1/2 (`_clearGeometryGesture`/`_wallChainRedo`,
  `_rollbackRejectedPhysicalWrites`) — код существовал уже в теге `v1.80.1`
  (`git show v1.80.1:src/houseplan-editor-runtime.ts` содержит обе функции и
  обнуление `_wallChainRedo`) — это правда `stable-fix` относительно
  `v1.80.1`.
- Контракт п.3/AC3 на стороне клиента (`nodeHistoryRefusal` в
  `src/wall-node-history.ts`) — этот файл **целиком** создан коммитом
  `f26017d2` 2026-10-13 21:19:34, то есть после тега `v1.80.1`
  (2026-10-09 09:41:58) и после `v1.81.0-beta.1` (2026-10-12). До #843 любой
  отказ переноса узла стирал историю целиком без какой-либо классификации по
  коду ошибки; выборочное (и ошибочно широкое) удаление по префиксу
  `node_move_` — это поведение, которого в `v1.80.1` физически не было. Пользователь
  `v1.80.1` никогда не видел именно этот дефект — он появился вместе с
  улучшением #843 внутри текущей беты.

Per `docs/process/REVIEWER.md`/PROCESS §11.9 (#838): «Инфраструктура и
внутри-бетные исправления не входят в пользовательский milestone релиза».
Исправление AC3 чинит регрессию, появившуюся вместе с #843 в этом же цикле
v1.81.0-beta — это `introducedBy: #843`, а не `stable-fix` относительно
`v1.80.1`, и не должно идти в пользовательский milestone/changelog как
«то, что было сломано в v1.80.1». Текущая формулировка ТЗ смешивает оба
случая в одну запись ledger и оставляет разделение как невыполненную
проверку («отдельно проверить first-introduced range»), хотя эта проверка
ровно то, что реализуемо уже сейчас по `git log`/`git show` (см. «Как
проверялось», п.5) — без необходимости ждать код-ревью.

**Воспроизведение дефекта ТЗ:** `git show v1.80.1:src/wall-node-history.ts`
→ файл не существует на этом теге; `git log --follow --oneline --
src/wall-node-history.ts` → единственный коммит `f26017d2` (#843,
2026-10-13), который моложе `v1.80.1` и `v1.81.0-beta.1`. Блок «Release-
артефакты» тем не менее относит сделанное здесь исправление к «stable-fix
относительно v1.80.1», не выделяя эту часть.

**Требуемая правка (в скоупе #891, тот же issue):** разделить запись ledger
(или её обоснование) на две части — `stable-fix` относительно `v1.80.1` для
контракта п.1/2/4/5 (ранее существовавшее поведение) и `introducedBy: #843`
для клиентского классификатора AC3, с соответствующей пометкой в
changelog/milestone-счёте.

High: 0. Medium: 2 (в скоупе). Low: 0.

## Что проверено и корректно

- Обязательные разделы §7.1 присутствуют и в правильном порядке, включая
  оба продуктовых раздела первыми (сценарий, что человек увидит).
- Все построчные технические утверждения «Проблемы» (клиентский и backend
  классификаторы, безусловный `_wallChainRedo = []`, двойной
  `.clear()`-путь, общий текст «Undo» для Redo) подтверждены чтением

  найдено; формулировки ТЗ дословно совпадают с найденным кодом.
- Скоуп и не-скоуп называют конкретные символы кода

- Дубликаты (#883/#843/#845) перечислены с указанием, какую именно их
  функцию не переписывать заново — соответствует правилу «дубликаты

- Продуктовых вопросов, неправомерно адресованных владельцу как технические,

  отказа «нейтрально или по направлению», контракт п.5) корректно оставлен
  на усмотрение реализации, поскольку AC5 фиксирует единственное
  функционально значимое ограничение и не создаёт развилки для владельца.
- Технические решения корректно вынесены в блок «Принято предположительно,

- i18n: новые ключи (`node_move_write_conflict`,

- Touch: «best effort, cancel/multitouch не коммитит» соответствует

- Откат описан предметно (история page-memory без миграции, backend-код
  совместим со старым клиентом) — не общая фраза.
