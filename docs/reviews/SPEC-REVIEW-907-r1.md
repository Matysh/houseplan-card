## Скоуп

ТЗ описывает три небольших presentation-дефекта без изменения поведения записи/
cleanup, объединённые одним batch-источником (F-BATCH-004/005/017):

1. **F004** — форма маркера учитывает `config.language` (`this.host._t` →
   `langOf(this.hass, this._config?.language)`), а дочерний `<hp-device-preview>`
   берёт только язык HA (`langOf(this.hass)` без override) — смешанный язык
   диалога при HA≠card.
2. **F017** — ранний guard смены владения конфигом (`_persistDevicePlacement`)
   бросает `new Error('config authority changed')` без `.code`, и этот
   английский текст утекает как есть в RU/EN toast через `_errText`.
3. **F005** — Optimize (`_optimizeReferenceContext` → `ownerName`) читает
   `roster.names[id]` без проверки собственности ключа; для `id`, совпадающего
   с унаследованным именем (`constructor`, `toString`, `__proto__` и т. п.),
   в название владельца в отчёте попадает строковое представление функции
   прототипа.

Работа из `docs/SCOPE.md` — полировка существующих редакторских поверхностей
J6 («Keep the plan true as the home evolves»: три штатных редактора/
диагностических инструмента — диалог маркера, предпросмотр устройства,
Optimize) и частично J4 (UI на выбранном языке карточки). Новых фич,
полей конфигурации и миграций не вводится; это подтверждено разделом
«Модель данных и миграция» и совпадает с характером правок по коду.

## Находки

### Medium — Release-артефакты: F017 отнесён к stable-fix, хотя introduced в текущей бета-линии

Раздел «Release-артефакты» пишет: «stable-fix для F004/F017, которые есть в
v1.80.1». Для F004 это подтверждается (`hp-device-preview.ts:125-126` — commit
`2a8302f4d`, 2026-08-08, задолго до реза v1.80.1 09.10.2026). Для **F017** это
не так: строка `houseplan-card.ts:5371` (`throw new Error('config authority
changed')` без `.code`) введена коммитом `c4dca1b46` от **2026-10-14**
(`fix: fence layout authority and retain exact canonical attempt ownership`,
issue #890) — спустя пять дней **после** релиза v1.80.1, уже внутри линии
v1.81. `git log --oneline c4dca1b46..HEAD | wc -l` = 139, т. е. коммит прочно
внутри истории, предшествующей текущему тегу v1.81.0-beta.3.

Воспроизведение: `git blame -L 5371,5371 src/houseplan-card.ts` →
`c4dca1b46 (Matysh 2026-10-14 23:22:57 +0300)`; `git log --oneline -3
c4dca1b46` подтверждает issue #890. v1.80.1-пользователь никогда не видел
этот конкретный необработанный `Error` (его просто не существовало в сборке
v1.80.1), поэтому факт «F017 есть в v1.80.1» неверен — это `line-fix`
(регрессия/недоделка текущей бета-линии) с `introducedBy: #890`, а не
`stable-fix`. PROCESS.md §11.9 отдельно требует `introducedBy` именно для
такого случая. Ошибочная классификация рискует попасть в пользовательский
stable-milestone как будто она чинит то, что затрагивало уже выпущенный
v1.80.1, хотя дефект моложе на один цикл.

Это находка о содержимом самой ТЗ (обязательный раздел §7.1), а не о гейтах
кода — автор утверждает факт без сверки с git-историей. В скоупе задачи:
автор правит формулировку раздела (классификация + `introducedBy: #890` для
F017) в этом же issue.

### Medium — Release-артефакты: F005, вероятно, ошибочно исключён из stable-fix

Та же секция относит F005 (Optimize/`ownerName`) к «полировке внутри текущей
линии», противопоставляя её F004/F017 «которые есть в v1.80.1» — то есть
неявно утверждает, что F005 в v1.80.1 нет. Это противоречит фактам: код
`space-reference-repair.ts:336-338` не менялся с коммита `36b5a8c36`
(2026-08-23) — за полтора месяца до реза v1.80.1. `git blame -L 336,338`
подтверждает единственного автора правки этих строк.

Более того, есть прямой прецедент в этом же поддереве: `docs/release-ledger/
v1.80.1/892.json` уже классифицирует другой дефект того же инструмента
(«Optimize and its orphan-position report existed in v1.80.1») как
`stable-fix` именно по основанию «существовал в v1.80.1». По той же логике
F005 — тоже `stable-fix`, а не внутрибетная полировка, которая не входит в
пользовательский milestone (#838 требует обратного: именно
внутри-бетные правки туда не входят, значит формулировка ТЗ рискует
*потерять* пользовательский пункт о реальном дефекте v1.80.1, а не наоборот).

Обе находки — об одном и том же разделе и одной причине (классификация не
сверена с `git blame`/прецедентом); правятся вместе одной правкой раздела
«Release-артефакты» без переоткрытия AC1–AC3, контракта или плана тестов.

Других находок нет. High: 0. Medium: 2 (обе в скоупе задачи).

### Low — «ленивые DE/FR» в разделе i18n не совсем точная формулировка (снято ревьюером)

Раздел i18n пишет про «совместимый fallback для ленивых DE/FR». Фактически
ключи `err.*`/`marker.*`, которые придётся трогать, лежат в корневых
`src/i18n/{en,ru,de,fr}.json` — все четыре файла уже статически полны
(по 1359 строк, без расхождений), это не те ленивые per-namespace чанки
(`settings/support/topology/tools/led`), которые проверяет
`test/i18n-lazy-namespaces.test.mjs`. На выполнимость это не влияет: новый
ключ в любом случае добавляется во все четыре корневых JSON, никакого
отдельного ленивого контракта это не задевает. Снимаю как Low без цикла —
неточная формулировка термина, а не дефект контракта.

### Low — DoR: производительность и touch не названы явно отдельной строкой (снято ревьюером)

§2.5 требует явного «нет» по производительности и по `docs/TOUCH-SUPPORT.md`.
В тексте ТЗ нет буквальной строки на этот счёт; ближайшее — «Locale
loading/fallback остаётся bounded» в «Рисках». Все три затронутые
поверхности (диалог маркера, Optimize) — редакторские, desktop-first по
`docs/TOUCH-SUPPORT.md`, правки чисто текстовые (строка локали, маппинг кода
ошибки, защита чтения свойства) — влияния на touch и на производительность
нет. Снимаю как Low без цикла: содержание очевидно из характера правок,
автор может добавить явную строку «Touch: нет (редактор, desktop-first) ·
Производительность: нет» при реализации.

  предположения» корректно ограничен нерешаемым пользователем деталями

  2026-10-15 (цитата в разделе «Маршрут и граница поручения»), соответствует
  правилу AGENTS.md о расширении маршрута по прямой команде.
