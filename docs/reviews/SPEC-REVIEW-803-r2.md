узла стены (свободный конец, угол цепочки/комнаты, общий узел нескольких

существующим `src/junction-limits.ts` (`MAX_JUNCTION_VALENCE = 6`).

**Проверка полноты новой таблицы §4.** Обозначив P — число проходящих
осей, B — число конечных ответвлений, валентность узла равна `2P + B`
(проходящая ось даёт два противоположных луча, ответвление — один).
Действующий предел `MAX_JUNCTION_VALENCE = 6` (`src/junction-limits.ts:35`)
ограничивает `2P + B ≤ 6`. Перечислены все целые неотрицательные пары
`(P, B)` с `2P + B ≤ 6` и `P ≥ 0`, они же — все физически достижимые формы
узла:

| P | допустимые B при `2P+B≤6` | строка таблицы §4 |
|---|---|---|
| 0 | 1–6 (B=0 — не узел, стен нет) | «0 \| 1–6 \| Обычный конечный узел/угол» |
| 1 | 0 | «1 \| 0 \| Существующая точка прямой стены» |
| 1 | 1 | «1 \| 1 \| T» |
| 1 | 2, 3, 4 | «1 \| 2–4 \| Сложный сквозной стык: не поддерживается» |
| 2 | 0 | «2 \| 0 \| X» |
| 2 | 1, 2 | «2 \| 1–2 \| X с дополнительными ответвлениями: не поддерживается» |
| 3 | 0 | «3 \| 0 \| Пересечение трёх проходящих осей: не поддерживается» |

Каждая достижимая при `2P+B≤6` пара `(P,B)` попадает ровно в одну строку
таблицы §4, пропусков нет. Формы с `2P+B>6` (например, `P=3,B=1`) уже
отклоняются существующим `junction-limits` до входа в эту таблицу — §4
прямо это оговаривает («Формы с более чем шестью физическими лучами
сохраняют действующий отказ junction-limit, а не получают исключение»).
Случай из находки M1 r1 — X-пересечение (`P=2`) с одной дополнительной
независимой стеной, оканчивающейся в той же точке (`B=1`, валентность 5)
— это ровно строка `«2 \| 1–2»`, которая теперь явно требует отказа. Та
же строка покрывает и валентность 6 при `P=2,B=2`. Гэп закрыт
исчерпывающе, не точечной заплаткой под один пример.

Сопутствующая правка §4 («Считаются distinct физические лучи, а не число
владельцев-комнат или записей: совпадающие лучи одного участка с
несколькими владельцами не повышают валентность») отдельно закрывает
смежный риск двойного счёта луча с несколькими комнатами-владельцами,
который иначе мог бы превратить поддержанный стык (например, обычный
общий угол трёх комнат, физически 3 луча) в кажущийся стык более высокой
валентности при подсчёте по записям, а не по физическим лучам.

## Что проверено и корректно

- Дельта закрывает ровно заявленное: новая таблица §4 математически
  исчерпывающа для всех физически достижимых пар «проходящих осей ×
  конечных ответвлений» при действующем пределе валентности 6 (проверка
  выше), а не только для примера, названного в M1.
- §2 и §4 теперь согласованы друг с другом: явно исключённые в §2 формы
  — это ровно отклоняемые строки таблицы §4, нет формы, исключённой в
  одном разделе и допущенной в другом.
- Дедупликация физических лучей («совпадающие лучи одного участка с
  несколькими владельцами не повышают валентность») закрывает соседний
  риск ложного попадания штатного многокомнатного угла в «сложный стык»
  из-за подсчёта по записям вместо физических лучей.
- Отказ для неподдерживаемой формы специфицирован как pre-flight,
  симметрично серверу: «Проверка того же ограничения повторяется в
  серверном node-move пути: обход UI не разрешает эту операцию» — не
  оставляет лазейку клиент-only проверки, которую сам же ТЗ запрещает в
  §8 для других путей.
- AC2/AC4 обновлены фикстурами ровно на новых отказных строках таблицы
  (T+2/4 ответвления, X+1/2 ответвления, три проходящие оси) и явно
  требуют «ровно unsupported-junction, неизменную геометрию и отказ
  серверного пути» — oracle для негативного теста, которого не хватало
  в r1, теперь есть.
- Новый i18n-ключ `node_move_unsupported_junction` присутствует в таблице
  §9 с en/ru парой, согласован с текстом §4 (используется то же имя
  причины).
