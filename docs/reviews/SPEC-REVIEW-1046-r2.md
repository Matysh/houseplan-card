# SPEC-REVIEW-1046-r2

## Скоуп

Issue #1046 — «Рисование линий: два клика и выравнивание по Shift, как у
стен», трек `ask`, этап spec, заход r2 (0/4 блокирующих циклов израсходовано
до этого ревью). Продуктовая строка не изменилась: J4/J6 (`docs/SCOPE.md`),
View и бытовые действия устройств не затрагиваются; Rectangle/Ellipse
остаются drag-инструментами.

Предмет r2 — **не вся спецификация**, а дельта тела issue после r1: хеш
тела изменился (`d99400e70c3b…` → `37f9435bde1d…`, сверено
`sha256` снимка тела через `gh issue view --json body`), что подтверждает
правку, заявленную комментарием автора в 21:05:23Z («Исправлено по SPEC r1:
AC1 доказывает собственный новый smoke_decor_line_click.mjs; AC6 —
существующие smoke_decor.mjs/smoke_decor_order.mjs…»). Кодовых изменений по
прежнему нет: ветка `issue/1046-*` не запушена (`git ls-remote` отдаёт только
служебные `service-delivery/process-1046-*`), `dev`/материал на SHA
`6186cd19e141953ab85e459f06b7745f8f70d5b8`.

## Как проверялось

Static-first (#857), по делте (§2.10): открыт единственный Medium r1
(`docs/reviews/SPEC-REVIEW-1046-r1.md`, раздел «Находки»), сопоставлен текст
AC1/AC6/«Файлы и i18n» r1 (процитирован в находке) с текущим телом issue
построчно:

- AC1: было «…smoke_decor_line_click + smoke_decor_creation_selection» →
  стало «…**smoke_decor_line_click**» (ссылка на чужой файл убрана).
- AC6: было «…smoke_decor_creation_selection и целевые части smoke_decor…» →
  стало «…**smoke_decor.mjs и smoke_decor_order.mjs; текущие unit guards**».
- «Файлы и i18n»: добавлено явное предложение владения и независимости от
  порядка слияния: «Артефакт smoke_decor_creation_selection.mjs создаёт
  соседняя #1047; его наличие не является предусловием или доказательством
  AC текущей задачи. Если к реализации #1046 он уже вошёл в dev, его
  line-жесты также адаптируются к новому контракту, без зависимости приёмки
  от порядка слияния.»

Адресная проверка осуществимости для конкретного непокрытого вопроса,
который создаёт сама правка (§8 — только адресно для названного пробела):
новые названные свидетели AC6 должны реально существовать уже сейчас (а не
только планироваться), иначе правка заменила бы одну несуществующую ссылку
другой. Проверено `ls demo/smoke_decor*.mjs`: `demo/smoke_decor.mjs` и
`demo/smoke_decor_order.mjs` присутствуют в дереве материала;
`demo/smoke_decor_line_click.mjs` отсутствует и корректно не заявлен как уже
существующий (создаётся этой задачей); `demo/smoke_decor_creation_selection.mjs`
по прежнему отсутствует, и текст больше не выдаёт его за существующий файл
этой задачи. Также проверено остаточным `grep` по телу issue: строка
`smoke_decor_creation_selection` встречается ровно один раз — в новом явном
предложении о владении (#1047) — старых необновлённых упоминаний в AC1/AC6
не осталось.

Статус соседней #1047 перепроверен (`gh issue view 1047`): по прежнему
`S6-in-progress`/`track:show`, ветка не запушена — это именно тот риск
«порядок слияния не зафиксирован», который правка снимает явной
независимостью, а не фиксацией порядка.

Код не менялся (его ещё нет), `tsc`/`build`/`npm test`/`gate:small` не
запускались — на этапе spec не требуются (§8), и единственный пробел,
который создаёт сама дельта (существование новых названных файлов-свидетелей),
закрыт перечисленной выше проверкой `ls`/`grep`, без запуска сборки.

## Что проверено и корректно (r2)

- Делта текстуально закрывает ровно находку r1, не расширяя и не сужая
  продуктовый контракт: поведенческие формулировки AC1 («…ровно два
  независимых сохранённых отрезка…», «Line остаётся активным») и AC6
  («Rectangle/Ellipse по-прежнему создаются drag… View/kiosk не рисуют»)
  не изменились — поменялся только названный способ доказательства.
- Оба новых существующих свидетеля AC6 (`demo/smoke_decor.mjs`,
  `demo/smoke_decor_order.mjs`) реально есть в дереве материала.
- Новое предложение владения корректно отвечает на оба вопроса r1: кто
  создаёт чужой файл (#1047) и что происходит при несовпадении порядка
  слияния (приёмка #1046 от него не зависит) — без сторонних договорённостей,
  текст тела issue самодостаточен.
- Статус #1047 (`S6-in-progress`, ветка не запушена) подтверждает, что риск
  был реальным, а не гипотетическим, и что формулировка по прежнему
  актуальна на момент этого раунда.
