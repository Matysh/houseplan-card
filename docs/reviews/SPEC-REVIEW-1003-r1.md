## Скоуп

Контракт прилипания/контакта значков устройств друг к другу и к стенам в Flat:
угловой кандидат по двум граням, единственный фиксированный шаг соединения,
автоматическое производное перестроение группы при изменении размеров
участника (дополнение 23.10), правило скрытия только пристенных участков
обводки, тип контура (пунктир/сплошной) по составу группы, долговечная основа
связей (`contact_basis`) поверх существующего layout-хранилища, безопасное
детерминированное рассоединение при нехватке места, согласование hit-test с
новым контуром, единый effective layout для core/capsule/diagnostics/hit/
overlays, touch/kiosk/static space-card, legacy-совместимость без массовой
перестройки старых планов. Какую строку `docs/SCOPE.md` обслуживает: J1
(предсказуемый обзор плана), J3 (попадание тапа в нужное устройство), J6
(план остаётся верным при редактировании устройств).

## Находки

Блокирующих (High) и находок Medium в скоупе не обнаружено.

Низкая находка (Low, снимается ревьюером без цикла): в разделе «Модель
данных» поле `at:{x,y,s}` объясняет `x,y` («исходная каноническая позиция»),
но не называет назначение `s`. Это не блокирует ревью: весь блок прямо
помечен «Предлагаемое техническое решение для ревью; не утверждённый новый
продуктовый API» и входит в список «принято предположительно, поменять
свободно» («форма `contact_basis`»), то есть именно техническая деталь,
которую реализация вправе уточнить или переименовать без возврата ТЗ.
Оставляю как замечание на будущее, не как основание для жёлтого вердикта.

Побочных находок вне скоупа #1003 не найдено; по политике
`HP_REVIEW_OUTSIDE_FINDINGS_FILE_ISSUES` (`mode=issues`, см. ниже) новых issue
заводить не из чего.

## Что проверено и корректно

- Все обязательные разделы §7.1 присутствуют, в порядке, предписанном каноном
  (сценарий и «что человек увидит» — первыми).
- Каждый из AC1…AC15 однозначен и несёт способ доказательства; дополнительные
  исторические D1…D5 из дополнения владельца явно подчинены верхнему разделу
  «## ТЗ» («при расхождении действует этот раздел») и не создают
  противоречия, а дублируют/детализируют AC5/AC6/AC8/AC9 как трассируемость.
- Скоуп и не-скоуп разделены явно и согласуются с `docs/SCOPE.md` (J1/J3/J6);
  исключены смежные темы (#873 равный интервал, редактор групп, HA-команды,
  2.5D-перенос, PDF-палитра).
- Модель данных не меняет версию модели/store, описывает lossless-чтение
  неизвестных полей, не вводит миграцию при загрузке — соответствует паттерну
  уже принятых совместимых полей в `docs/CONFIG-COMPATIBILITY.md`.
- Транзакционность (atomic/CAS/paired write, revision-guard) ссылается на уже
  существующие механизмы (`layout/set`+`expected_rev`, `acceptPairWrite`),
  не изобретает новый транспорт без основания.
- Touch/View/kiosk описаны в терминах действующего `docs/TOUCH-SUPPORT.md`
  («best effort», «safety floor»), без расширения editor-паритета.
- Защитные сценарии (нехватка места, повреждённые данные, legacy-сцепки)
  прописаны с конкретным ожидаемым откатом/fallback, а не «как-нибудь не
  упасть».
- Откат и release-артефакты названы, включая явный запрет коммитить бандл/
  изображения/golden baseline в ветку задачи.
- Продуктовых вопросов владельцу нет; все прежние развилки закрыты
  датированными решениями владельца, видимыми и в теле issue, и в
  комментариях.

  spec код не менялся (`changedFiles: []`), зависимости/Chromium не
  устанавливались (#696 — это нормально для spec-ревью, не пропуск гейта).
  Эти гейты относятся к код-ревью (§2.7) и будут обязательны на S7.
- Не проверялась классификация релиза в `docs/release-ledger/` — файла для
  #1003 нет и не должно быть на этом этапе (классификация делается до S7,
  §2.6), это не находка.
- Не воспроизводился мобильный «ступенчатый» артефакт и не выполнялась
  браузерная/GPU-приёмка: на этапе spec реализации ещё нет, план
  синтетического browser-свидетеля (старый код FAIL, затем smoke) описан в
  разделе «План автотестов» и подлежит исполнению на этапе реализации/код-
  ревью, а не здесь.
- Не читался весь объём `src/device-contact-*.ts` построчно — только
  адресные места, упомянутые ТЗ и нужные для проверки грунтованности claims
  (geometry join-depth, editor-guide labels, i18n ключи); полный разбор кода —
  предмет будущего код-ревью, не ревью ТЗ.

## Вердикт

Зелёный. ТЗ полно, каждый AC проверяем и однозначен, модель данных и
транзакции опираются на существующие механизмы, продуктовые развилки закрыты
владельцем, скоуп соответствует `docs/SCOPE.md`. Единственное замечание —

утверждённой) схеме `contact_basis` — не блокирует переход в «Готово к
разработке».
