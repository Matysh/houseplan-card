# SPEC-REVIEW-912-r1

Issue: #912 — «Zigbee2MQTT: сохранять связи после перезапуска HA до ручного обновления
или отключения»
Этап: spec (ревью ТЗ, PROCESS.md §2.4) · Трек: ask · Заход: r1 · блокирующих циклов 0/4

dev-SHA ссылок в ТЗ: `f819e489d9394a09588a5db4a93f393a07fd911d` (= материал, на котором

## Скоуп

ТЗ закрывает J7 («Is my Zigbee mesh healthy here?», docs/SCOPE.md) и смежно J1: текущая
реализация (#800/#808) держит полученную Z2M-карту только в памяти интеграции, и
перезапуск/выгрузка HA уничтожают уже оплаченный долгим сканом результат без какого-либо
действия пользователя. Задача меняет срок хранения на явный — переживает рестарт,
обнуляется только по ручному Refresh (сразу) или по выключению функции, — и явно не трогает
ZHA, возобновление незавершённого скана, авто-обновление или #906 (reuse mapping). Это не
новая поверхность, а продление жизни уже принятого J7-результата — попадает в продукт без
отдельной строки в `docs/SCOPE.md`.

## Что проверено и корректно

- Все обязательные разделы ТЗ присутствуют, в правильном порядке; оба продуктовых раздела
  («Сценарий», «Что человек увидит до и после») открывают ТЗ и отвечают на оба обязательных
  вопроса §7.1 без терминов реализации.
- AC1–AC7 пронумерованы, однозначны, и у каждого явно назван способ доказательства
  (`backend` / `backend + unit runtime` / `unit` / `native smoke` / `backend + ревью кода`),
  включая прямой запрет доказывать через mock-call-count вместо содержимого Store (AC4) и
  через приватные ACK/cache-поля вместо публичного feed (AC5) — это заранее закрывает
  соблазн недоказательного свидетеля на этапе реализации.
- Контракт поведения (8 пунктов) целиком покрывает заявленный сценарий: идентичность
  снимка по entry+topic, неизменность `obtained_at`, список событий, не удаляющих снимок
  (чтение/смена этажа/закрытие браузера/старение/разрыв связи/reload/рестарт), поведение
  Refresh (немедленное удаление только запрошенного топика, дедуп повторного клика, честный
  список событий, НЕ возвращающих старую карту), поведение выключения (полная очистка,
  включение не восстанавливает), защита от гонок (детач/reconnect/поздний job/revision
  fence), лимиты и отказ вместо тихого LRU/перезаписи.
- Единственный продуктовый вопрос задачи (1а vs 1б) задан владельцу одним комментарием с
  предложенным вариантом по умолчанию и снят ответом владельца строго по формату §7.1; текст
  «Решение владельца» в ТЗ передаёт этот ответ без искажений (проверено сверкой с исходным
  комментарием).
- Не-скоуп исключает ровно то, что стоило бы исключить (ZHA, возобновление скана, TTL,
  auto-refresh, heuristics, #906) — нет расползания задачи под видом «заодно починим».
- Модель данных: отдельный entry-owned versioned Store, явно не поля плана/layout и не
  localStorage; единственный сериализованный writer и generation fence для исключения гонок;
  явно названо, что CONFIG-COMPATIBILITY и USER-GUIDE должны заменить два конкретных
  устаревших утверждения — и оба эти утверждения подтверждены чтением текущих файлов (раздел
  «Как проверялось», п.4), а не продекларированы вслепую.
- Release-классификация (major относительно v1.80.1, milestone 1.81) согласуется с деревом
  `docs/release-ledger/` и текущей бета-версией; окончательный `912.json` корректно отложен
  до S7, как и для прежних задач этого же пакета (ср. SPEC-REVIEW-911-r1).
- Откат описан предметно: обычный follow-up revert, новый versioned cache не удаляется при
  downgrade, будущая схема не считается валидной — согласовано с «Моделью данных».
- i18n ограничивает себя точечными ключами EN+RU, явно запрещает eager-словари в стартовом
  графе и требует непротиворечивости DE/FR через namespace fallback, а не исправление
  переводов вручную — соответствует существующей архитектуре i18n проекта.
