## Скоуп

ТЗ описывает полировку четырёх редакторских диалогов настроек (Общие/Пространство/
Комната/Устройство) HA-администратора: девять конкретных UI-дефектов (перенос
длинной подписи Zigbee, единообразие hover/focus/tap подсказок, замена select на
кликабельные превью для выбора начала лучей, выравнивание toggle-строк, лишний
разделитель у подсказки луны, урезанное поле прозрачности 0…100, скачки высоты
диалога, обрезанная hover-рамка «Как в теме», единый hover кнопок). Работа
закрывает J4/J6 (настройка/поддержание плана), задевает J5/J7 только
косметически (показания климатики/LQI не меняются). Эталон — замороженные
мокапы `docs/design/settings-dialogs-944/{general-v10,space-v7,room-v4,
device-v6}.html` на `24f7ab2f266eb89f785192eac563915732a081ab`. Модель данных,
миграции, View и алгоритмы освещения прямо исключены из скоупа.

## Находки

### Medium (в скоупе, возвращается автору)

**M1. Не назван эффект на производительность/бюджеты (PROCESS.md §2.5, п. DoR).**
Файл: тело issue #955, разделы «Риски, откат и release-артефакты» и «Общая
реализация, UX, модель данных / миграция и i18n».
В тексте нет ни утверждения о влиянии на производительность, ни явного «нет» —
раздел DoR требует это поле заполненным в любом виде («названо или явно
„нет“»), пропуск не равен отсутствию эффекта. Задача трогает popup подсказок на
каждый hover (пункт2), пересчёт высоты диалога при появлении/исчезновении
внутреннего scroll (пункт7) и анимации hover (пункт9) — эффект предположительно
пренебрежимый, но ТЗ должно сказать это явно, а не оставлять читателя
достраивать вывод. Пока поле пустое, «Готово к разработке» по §2.5 не
выполняется («все пункты обязательны»).
*Чем закрыть:* одна фраза в разделе «Риски…», например «Влияние на
производительность не ожидается: правки ограничены CSS/layout диалогов
настроек вне цикла рендера плана/View» — или иная формулировка автора, если
эффект иной.

## Что проверено и корректно

- Разделы ТЗ по §7.1 закрыты по содержанию (сценарий/проблема/до-после,
  скоуп и не-скоуп, контракт поведения, UX+модель данных+миграция+i18n одним
  сквозным блоком, AC1…AC4 с доказательством, план автотестов, риски, откат,
  release-артефакты) — объединение нескольких канонических разделов в один
  параграф не нарушает требование, содержание присутствует по каждому пункту.
- Миграция данных: явное «не менять модель настроек, defaults, наследование,
  миграции» — DoR-пункт закрыт словом «нет».
- Touch-влияние: явное «редакторы остаются desktop-first… без новой
  touch-модели» — DoR-пункт закрыт.
- Откат: «revert task commits, без миграции данных» — названо.
- Release-артефакты: оба CHANGELOG, обновление пользовательской документации
  при смене выбора лучей, release-ledger, desktop/mobile evidence — названы;
  обновление документации действительно необходимо, т.к. текущий
  `USER-GUIDE.ru.md:2287` описывает старый `select`-интерфейс поля «Лучи
  солнца», который по пункту3 заменяется кликабельными карточками.
- Каждый из девяти пунктов скоупа и контракта поведения (переносы подписи,
  единые hover/focus/tap подсказки, замена select на превью, выравнивание
  toggle-строк, лишний разделитель, поле прозрачности 0…100, стабильная
  высота диалога, hover-рамка «Как в теме», единый hover типовых кнопок)
  сформулирован как конкретный, проверяемый результат, без скрытых домыслов;
  все совпадают с прямыми замечаниями владельца (источник — его комментарий в
  шапке issue, не предположение автора).
- AC1…AC4 называют метод доказательства из разрешённого словаря
  (`smoke`/`golden`/`unit`/`ревью кода`) и требуют воспроизведения симптома на
  старом коде перед правкой (AC2) — это закрывает требование «негативный
  свидетель до фикса» по духу §7.1, хотя формально задача не относится к
  категории «дефект растра/резкости/композитинга».
- AC3 требует сквозную матрицу «9пунктов × 4 формы» с PASS/N/A и явным
  свидетельством по каждой ячейке, Device — с перечисленными конкретными
  типами устройств (датчик/LED/пылесос/радар); пустых клеток без причины не
  допускает.
- Зависимость на недоделанные #945 (S7, не слито)/#946/#947 (S6, в работе)
  зафиксирована явно и без домысла: фиксы не идут в их замороженные ветки,
  бета ждёт принятия всех четырёх задач — продуктовый риск по срокам учтён
  автором, не продуктовый открытый вопрос.
- Открытых продуктовых вопросов владельцу в тексте нет; не найдено ни одного
  утверждения о поведении, которое не подтверждалось бы `USER-GUIDE.ru.md`,
  `SUN.md`, `STYLING-HOOKS.md` или прямым замечанием владельца.

## Чего не проверял

- Гейты `npx tsc --noEmit`, `npm test`, `npm run build` — не прогонялись:
  этап spec, продуктовый код ещё не пишется, зависимости/Chromium не
  установлены (#696); степень применимости — нулевая для этого этапа.
- Смоки/golden/инварианты модели — не прогонялись: нет диффа кода на этом
  этапе, прогон бессмыслен до реализации.
- Полное содержимое мокапов `docs/design/settings-dialogs-944/*.html` построчно
  не сверялось с каждым из девяти пунктов ТЗ — проверены только версии/наличие
  файлов, тема выбора лучей (пункт3) и используемая в них терминология;
  остальное — предмет код-ревью/golden после реализации, когда появится
  фактический рендер для сравнения.
- Формальная проверка "Трек: ask — решение владельца" построчно не велась:
  метка `track:ask` уже стоит на issue и совпадает с треком, названным в
  собственном комментарии-оценке владельца (`authorAssociation: OWNER`); это
  расценено как согласованное владельцем решение, а не как находка.
- Актуальность внешних ссылок на `src/*.ts#Lnn` при `104a63f1e2…` внутри
  JSON-данных мокапов не сверялась с текущим деревом — не является предметом
  ТЗ и не входит в объём ревью спецификации.
