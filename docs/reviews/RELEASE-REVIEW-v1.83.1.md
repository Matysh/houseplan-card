## Что входило в линию

v1.83.1 — срочный патч одной задачи поверх v1.83.0: регрессия создания
комнаты и Optimize, описанная в `docs/CHANGELOG.md`/`docs/RELEASE-NOTES.md`:
«После обновления комнаты создаются сразу внутри существующих замкнутых
контуров с округлёнными Т-стыками, без предварительного Optimize. Optimize
сохраняет примыкания стен и проёмы, существующие физические стены могут
безопасно получить другого владельца комнаты. Реальные зазоры и
некорректная смена привязок проёмов по-прежнему отклоняются». Диапазон
линии (165 файлов) состоит из: 6 изменённых backend-модулей
(`junction_limits.py`, `partition_promotion.py`, `validation.py`,
`wall_segment_model.py`, `const.py`, `manifest.json`), 11 изменённых/новых
frontend-модулей (`align-grid.ts`, новый `align-wall-contacts.ts`, новый
`stored-wall-contact.ts`, новый `wall-incidence.ts`, `wall-face-graph.ts`,
`wall-face-lineage.ts`, `wall-segment-model.ts`, `junction-limits.ts`,
`coincident-partitions.ts`, `houseplan-card.ts`/`houseplan-editor-runtime.ts`
— версия и проводка новых хелперов), остального — сгенерированные
frontend-бандлы, тесты/фикстуры, changelog/release-ledger/STATUS/
DEVELOPMENT-doc и реестр мутантов. Поверхность пользователя — ровно та,
что названа в changelog: **создание комнаты из готового контура стен**
(редактор плана → инструмент «Стены» → клик в замкнутой области) и
**«Общие настройки → Оптимизировать планы»**, обе описаны в разделе
8 USER-GUIDE («Создание комнаты», «Что делает оптимизация»).

### Шесть классов риска (§2.6)

- **Геометрия (главный риск линии).** Проверено исполнением выше: стыки,
  общие стены, округление до storage-границы, Т-узлы, П1-валентность.
  Негативные пробы внутри тестов отличают «тот же проверенный физический
  контакт» от «просто близко» (3e-7 vs 1e-7, независимое соседнее начало,
  реальный зазор 0,0004/0,0000002 — не закрывается).
- **Данные и права.** `validation.py`:`_existing_wall_room_ownership_only`
  разрешает добавление/удаление комнаты на существующих стенах только по
  полному точному кольцу ID и только «добавили ИЛИ удалили», не
  одновременно; покрыто тестами геометрии (unit) и смоком
  `wall_face_room_split`. Backend-pytest для этого модуля в проверке
  исполнением участия не принимал — см. «Чего не проверял».
- **Async/отмена.** Фикс не трогает debounce/очередь записи или сетевые
  гонки; `geometry-history-refusal.test.mjs` прогоняет write→undo→redo и
  проверяет отсутствие стороннего тоста `geometry_unsafe` — применимый
  срез покрыт, более широких гонок (переподключение, параллельный клиент)
  эта задача не касается.
- **Визуал.** Не тронуты правила отрисовки стыков/фасок (WALL-THICKNESS.md
  описывает их отдельно как «исправление отображения»); смоки
  `junction_holes`/`draw_wall_thickness` прошли без регрессии.
  Скриншот-документация в диффе — только обновление отпечатка, кадры
  идентичны (зафиксировано в DEVELOPMENT.md).
- **Объём/perf.** Новый `demo/benchmark_optimize_contacts.mjs` — в
  манифесте проверок нет соответствующего `smoke:`/`perf:` id, не
  прогонялся (performance не названа в пользовательском AC этой линии).
  Бюджет бандла (`core-file-budget`) зелёный; раздел DEVELOPMENT.md честно
  фиксирует новый zip-бюджет чанка (21 494 байт вместо 21 462) как учёт, а
  не незамеченный рост.
- **Host/input.** Смоки кликают по канвасу (мышь) через фикстуру Playwright
  демо-стенда — `free_walls`, `room_contact_grid`, `junction_*`; отдельного
  touch-сценария для этой геометрической линии нет и не требуется
  (создание комнаты — desktop-first редактор по TOUCH-SUPPORT.md).

## Находки

### Low — приватный backend-хелпер пересекает границу модуля без публичного контракта

`custom_components/houseplan/partition_promotion.py` импортирует
символы с ведущим подчёркиванием из другого модуля:
`from .junction_limits import _INCIDENT_EPS, _stored_wall_contact`
(новая строка в этом диффе). На стороне TypeScript для той же задачи
заведён отдельный публичный модуль `src/wall-incidence.ts`
(`WALL_INCIDENT_EPS`) и `src/stored-wall-contact.ts`
(`storedWallContact`, без подчёркивания) — именно чтобы несколько файлов
могли безопасно делиться константой/функцией. На Python-стороне такой
публичной точки нет: `_stored_wall_contact` и `_INCIDENT_EPS` остаются
«приватными» по соглашению об именовании, но уже потребляются другим
модулем.

**Последствие.** Будущее переименование или уточнение сигнатуры
`_stored_wall_contact`/`_INCIDENT_EPS` внутри `junction_limits.py` (как
«приватной» детали) не сигнализирует само по себе, что ломает
`partition_promotion.py` — в Python нет компилятора типов, который поймает
это на месте импорта, а статической проверки такого рода в прогнанных
гейтах (`build:typecheck` — только TS) нет.

**Локальное улучшение.** Вынести `_INCIDENT_EPS`/`_stored_wall_contact` в
отдельный маленький модуль (например, `wall_incidence.py`, по аналогии с
уже существующим `wall-incidence.ts`) и убрать подчёркивание у публично
используемого имени, либо хотя бы оставить явный комментарий-контракт
рядом с определением о том, что имя используется другим модулем.

**Чем краснеет:** нет зарегистрированного мутанта и не требуется для Low —
это находка по читаемости/сопровождению (§2.7), не по защите поведения;
снимается или чинится по усмотрению владельца.

## Что проверено и корректно

- Сборка, синхронизация ассетов и typecheck кандидата — зелёные.
- Пользовательский сценарий из changelog («создать комнату сразу в готовом
  контуре, без предварительного Optimize») воспроизведён и зелёным тестом,
  и браузерным смоком, в обоих направлениях клика и для обоих контуров
  публичной фикстуры `1166-two-contours.json`.
- Optimize над тем же пространством — no-op по хранимым данным
  (`#1166 accepted Optimize is a storage-roundtrip no-op`), сохраняет оба
  контура и не создаёт новый «долг» вне сетки
  (`wallModelOffGridValueCount` не растёт после очередной записи).
- Защитные свойства (угол стыка ≥15°, реальный зазор не закрывается,
  независимое соседнее начало не даёт ложного прохода, полное кольцо ID
  для смены владельца существующей стены) имеют отрицательные случаи
  прямо в тестах, а также пять новых записей в
  `scripts/mutation-registry.mjs` (`stored-t-room-recognition-1166`,
  `optimize-independent-wall-ends-1166`, `shared-ray-angle-proof-1166`,
  `carrier-chain-gap-proof-1166`, `existing-wall-ownership-proof-1166`) —
  «чем краредеет» не пустой столбец ни по одному защитному свойству;
  статическая целостность реестра подтверждена (`static:mutation-registry`).
- Undo/Redo и отсутствие постороннего отказа (`geometry_unsafe`) при
  обычном сценарии создания комнаты — проверены исполнением.
- Соседние геометрические поверхности (свободные стены, островные
  комнаты, общий геометрический корпус, толщина при рисовании, отказ
  истории геометрии) не регрессировали.
- Релизная бухгалтерия (версия 1.83.1 в manifest.json/CARD_VERSION,
  changelog RU+EN, release-notes, release-ledger) присутствует в том же
  диапазоне коммитов и совпадает с объявленным issue.

## Чего не проверял и почему

- **Backend pytest** (`tests_backend/test_wall_contact_storage.py`,
  `tests_backend/test_ha_room_contact_storage.py`) — в манифесте
  доступных `run_check` id нет пункта для запуска pytest/HA-harness;
  единственный доступный путь проверки — чтение, которое не доказывает
  наблюдаемый результат. Два из пяти зарегистрированных мутантов
  (`carrier-chain-gap-proof-1166`, `existing-wall-ownership-proof-1166`)
  используют именно этот guard — их поимка подтверждается только ночным
  прогоном, не этим ревью.
- **`static:smoke-select`** — скрипт требует `--base`/`--head`, которые
  политика инструмента не даёт передать модели; вместо него смоки выбраны
  вручную по изменённым файлам (см. таблицу выше) — это не формальная
  замена инструмента, а осознанное ручное покрытие.
- **`demo/benchmark_optimize_contacts.mjs`** (новый бенчмарк) — не
  прогонялся: он не числится проверкой в манифесте и пользовательский AC
  линии не называет производительность.
- **Ручная dev/GPU-приёмка владельцем** и интерактивный клик мышью вне
  зафиксированных Playwright-смоков — не выполнялась; по правилам §11.5 и
  REVIEWER.md её отсутствие не является находкой, доступный исполнимый
  oracle (headless-смоки) использован полностью.
- **Полный `npm test`/`gate:small`** — не гейт этого ревью (§8: полные
  наборы — предрелизный гейт); прогнаны только адресные unit/smoke для
  изменённой геометрии.
- Диалоговые UI-сценарии с фикстурой `ha-dialog` (#505) не применимы: эта
  линия не трогает HA-диалоги (привязка устройства/зоны), а работает в
  плоскости геометрии стен/комнат без таких диалогов.

Документ не блокирует выпуск; решение по находке Low — за владельцем.
