## Аудит r1 (почему пришлось выйти за рамки одного JSON-файла)

Дельта `7fd0ae4b` существует только потому, что `0b782ee7` (фикс каскада: «host-gated groups belong to their owner surface») изменил `src/**` уже ПОСЛЕ того, как звучали числа в переписке по #266. Чтобы понять, корректно ли отражён этот фикс в принятом (уже смердженном) коде, я сверил конкретные числа из `CODE-REVIEW-266-r1.md` (документ смерджен в `dev` коммитом `fd4bf0e9`, идёт сразу после `0b782ee7`) с фактическим деревом на HEAD.

**Результат: 4 из 4 проверенных точных чисел в CODE-REVIEW-266-r1.md не совпадают с HEAD.**

| Факт | Заявлено в r1 | Факт на HEAD | Воспроизведение |
|---|---|---|---|
| `@media (prefers-reduced-motion: reduce)` блоков | «10 блоков в сумме по пяти файлам. Совпадает… с origin/dev» | **12** | `grep -c "@media (prefers-reduced-motion: reduce)" src/styles/*.styles.ts` → сумма 12; `test/styles-split.test.mjs:73` явно `assert.equal(…, 12)` |
| Исключение юнита непересечения (AC4) | «единственное исключение (`.dev:focus-visible` base∩devices) обосновано» | **исключений нет** | `test/styles-split.test.mjs:62` → `assert.deepEqual(clashes, [])`, комментарий строки 59–61: «the exception list is empty» |
| Дельта размера бандла (AC7) | «origin/dev = 1 291 440, HEAD = 1 291 458 → +18 байт» | **1 291 440 → 1 291 562, +122 байта** | `git show 0b782ee7:dist/houseplan-card.js \| wc -c` → 1291562 (совпадает с текущим HEAD, `git diff 0b782ee7..HEAD -- dist/` пуст) |
| Мутантные якоря `mutation-gate.mjs` | «2 → base.styles.ts…; 3 → devices.styles.ts» | **все 5 → devices.styles.ts, 0 → base** | `grep -n "file: 'src/styles" scripts/mutation-gate.mjs` |

Разгадка нашлась сразу: все четыре «заявленных» числа **точно совпадают** с состоянием на `0d62a48b` — коммите, который r1 сам назвал в строке «Материал» («…на SHA `0d62a48b`»). Но `0d62a48b` идёт **до** `0b782ee7` в истории ветки — то есть r1 не проверял именно тот код, который реально ушёл в `dev`, хотя его текст обсуждает контекст фикса (мотивацию, факт «якоря переадресованы») так, будто проверял. Пруф:

```
git show 0d62a48b:src/styles/base.styles.ts | wc -l                 # 248 — совпадает с r1
git show 0d62a48b:dist/houseplan-card.js | wc -c                     # 1291458 — совпадает с r1
git show 0d62a48b:scripts/mutation-gate.mjs | grep -c "base.styles"  # 2 — совпадает с r1
```

**Важно: это не означает, что смердженный код неверен.** Я независимо перепроверил итоговое (HEAD) состояние отдельно от заявлений r1 — `styles-diff.mjs` пуст, `golden:verify` 129/129 без переприёмки, `smoke_device_icon_design`/`smoke_plan_snap_overlay`/`smoke_preloader` зелёные, `npm test` 1318/0 — и оно действительно корректно. Фикс `0b782ee7` устранил реальный визуальный баг (пойманный CI-смоком до этого ревью), и после него код и тесты согласованы между собой. Но то, что «зелёный» вердикт r1 был подписан по числам чужого, более раннего SHA, а не по факту смердженного кода — это ровно случай, о котором предупреждает эта задача («Verified без названной команды и её результата доказательством не является»): команды были названы, но выполнены не на том дереве.

Заведён отдельный процессный issue **#312** («Код-ревью #266/r1 подтвердил числа SHA до правки, а не смердженный код») — по аналогии с #311 из SPEC-REVIEW-266-r3. Это не Medium-находка «вне скоупа продукта» в смысле §12 (не дефект соседнего пользовательского поведения), а наблюдение о процессе ревью; тем не менее решил зафиксировать его отдельным issue, а не только в тексте, чтобы не повторить ошибку #171/#207 («оставили в тексте — не считается закрытием»). `docs/reviews/CODE-REVIEW-266-r1.md` не редактирую — исторический артефакт, уже смерджен.

## Находки текущего раунда (r2)

**Medium (в скоупе #266).** AC6a ТЗ (`docs/specs/266-split-styles.md:82`) требует буквально: «все **10** блоков `@media (prefers-reduced-motion: reduce)` присутствуют в итоговой склейке». Фактически в смердженном коде их **12** — `0b782ee7` разрезал 2 из 10 исходных обёрток, ранее ошибочно смешивавших зоны, на по-зонные копии (это и есть содержание фикса каскада). Автор явно обозначил это как открытый вопрос в хендоффе issue («микро-отступление от буквы AC6a «10» … на решение ревью»), но ни r1, ни спецификация это решение не зафиксировали — r1 просто (ошибочно) заявил, что число совпадает с ТЗ.

Сам факт корректен и я его подтверждаю как ревьюер: 12 физических обёрток над теми же 10 «исходными» блоками правил — законный результат обязательного фикса, доказанный пустым `styles-diff.mjs` (ни одно правило не потеряло обёртку) и зелёными смоками `forced-colors`/`reduced-motion`. Но текст AC6a должен отражать факт, а не противоречить принятому коду. Дёшево чинится: заменить «10» на «12 (10 исходных обёрток, 2 из которых были смешанными по зонам и разрезаны на по-зонные копии при фиксе каскада `0b782ee7`; `styles-diff.mjs` подтверждает сохранность содержимого)» — формулировка по образцу того, как уже исправлен комментарий в `test/styles-split.test.mjs:69-72`.

Других находок Medium/High в дельте r2 нет.

**Low, не блокирует.** AC2 (`docs/specs/266-split-styles.md:77`) приводит «фактический замер»: base 248/chrome 381/devices 540/dialogs 1180/plan 1359. После `0b782ee7` реальные числа другие (base 165, chrome 391, devices 559, dialogs 1201, plan 1396 — те же файлы, но 2 группы правил уехали из `base` туда, где им и место). Порог AC2 (`каждый ≤1650, сумма ≤3874`) как ограничение **по-прежнему выполняется** (сумма 3731 ≤ 3874, максимум 1396 ≤ 1650) — это не нарушение критерия, только устаревшая иллюстрация. Не требую отдельной правки как блокирующей, но раз AC6a всё равно правится в этом раунде, разумно поправить и эту строку заодно (тот же абзац).
