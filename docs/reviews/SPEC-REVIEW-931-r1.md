## Скоуп

Задача закрывает J4/J6 из `docs/SCOPE.md`: единая оболочка панели свойств объекта
в трёх существующих редакторах (План/Устройства/Подложка), без слияния
редакторов, без нового общего входа, без новых геометрических операций или
полей модели данных. Явный не-скоуп (единый редактор, общая история Undo,
массовое изменение, новые координаты/биндинги, миграция/backend) описан в §2
тела ТЗ и согласован с границами из `docs/UX-MODES.md`/`docs/TOUCH-SUPPORT.md`
(touch — best effort/intentionally degraded).

## Как проверялось

1. Прочитаны `docs/SCOPE.md`, `AGENTS.md`, `docs/process/REVIEWER.md`,
   `PROCESS.md` §2.3–2.10, §7.1 (обязательные разделы ТЗ, правило вопросов
   владельцу).
2. Прочитано тело issue #931 целиком (раздел `## ТЗ`, 13 подпунктов, 12 AC) и
   все комментарии — включая механический preflight r1, нашедший 5
   отсутствующих секций по заголовкам (`before-after`, `problem`,
   `non-scope`, `contract`, `tests`), и последующую правку автора, после
   которой заголовки появились. Формальный PASS (errors=[]) — это проверка
   формата, не вердикт (сам автор это отметил в хендоффе); содержание
   проверено заново по существу, а не по факту наличия заголовков.
3. Сверены точечные фактические утверждения ТЗ о текущем поведении с кодом,
   поскольку неверная предпосылка об «уже существующем» поведении могла бы
   сделать AC непроверяемым или дать автору реализации неверную базу для
   сравнения:
   - `settings.decor_default_style` — существует (`src/houseplan-editor-runtime.ts`,
     `src/editors/decor/geometry.ts`, backend validation/schema).
   - `LED_DEFAULT_RADIUS_CM = 30` — существует (`src/led-strip-geometry.ts:29`,
     комментарий «Default linear field radius (#784): 30 cm»), совпадает с
     заявленным в §7 «существующий LED fallback 30 см».
   - Текущее поведение «двойной клик всегда означает edit this object» в
     Select — подтверждено `docs/UX-MODES.md:396`; заявленное в ТЗ новое
     поведение (одиночный клик для комнаты/контурной стены) корректно
     помечено как **новое поведение #931**, а не выдано за уже существующее.
   - Термин «Свойства» как подпись пункта меню уже используется в
     `docs/USER-GUIDE.ru.md:2065` — заголовок панели не вводит разъезжающуюся
     терминологию.
   - Существующий смок на живую проверку прав `demo/smoke_view_edit_permissions.mjs`
     подтверждает, что заявление §5 «снятие прав немедленно блокирует запись
     и возвращает View» опирается на реально существующий механизм, а не на
     придуманный.
   - Ссылки раздела 13 на конкретные файлы/строки (`room-settings-dialog.ts#L127`,
     `draft-actions.ts#L20`, `led-strip-editor.ts#L555`, `radar-section.ts#L271`
     и др.) по именам файлов соответствуют текущему дереву `src/`.
4. Проверены обязательные разделы ТЗ по списку PROCESS.md §7.1 (сценарий,
   до/после, проблема, скоуп/не-скоуп, контракт поведения, UX, модель данных и
   миграция, i18n, AC1…ACn с доказательством, план автотестов, риски, откат,
   release-артефакты) — построчно сверено с текстом разделов 1–13, все
   присутствуют по существу, не только по ключевому слову в заголовке.
5. Прогон гейтов: не выполнялся. На этапе spec зависимости и Chromium не
   устанавливаются (`AGENTS.md`, #696) — проверено: `node_modules` в рабочей
   копии отсутствует, `npx tsc --noEmit` падает из-за отсутствия TypeScript в
   окружении. Код в этой задаче не менялся (подтверждено хендоффом автора:
   «исходники не изменялись»), поэтому typecheck/test/build не относятся к
   предмету ревью — гонять их по неизменному `dev` не добавляет доказательств
   по этому ТЗ. Это зафиксировано как «не проверялось» ниже, а не скрыто.

## Находки

Находок уровня High или Medium нет.

Рассмотренные и отклонённые кандидаты (зафиксировано, чтобы не создавать
видимость, будто сложный текст проверен поверхностно):

- **Выбор целевой комнаты для «Применить ко всей комнате» при общей стене**
  (§6, §4) описан через «явный выбор одной из прилегающих комнат» и «список»,
  без детализации виджета. Это не продуктовая неоднозначность (пользователь
  явно выбирает из названных комнат, случайный resolver по индексу массива
  прямо запрещён), а техническая деталь представления — попадает под «всё,
  чего пользователь не наблюдает, агенты решают сами» (PROCESS.md §7.1).
  Не нахожу.
- **«Шесть клеток» допуска старого поиска толщины** (§4) — не нашёл точного
  соответствия в коде/`docs/WALL-THICKNESS.md`. Утверждение используется
  только как контраст («не переносится в Select»), не как часть нового
  контракта и не входит ни в один AC; ошибка в этой исторической детали (если
  она есть) не делает новое поведение (±4 CSS px экранная зона для нулевой
  стены в Select) неоднозначным или непроверяемым. Low, не блокирует; при
  желании автор может уточнить формулировку, решение оставляю ему.
- **Единственный открытый технический вопрос, который ТЗ закрывает само** —
  раздел 12 прямо фиксирует блок «Принято предположительно, поменять
  свободно» (имена/разбиение модулей, внутреннее представление session
  target/dirty baseline, размещение fixtures) — это правильное место для
  технических решений по §7.1, не площадка для находки.

Не найдено ни одного продуктового вопроса, вынесенного на усмотрение
владельца явно или неявно (задачу не пришлось бы снимать и решать самому) —
автор решил все развилки сам и аргументированно, включая самую рискованную
(порядок применения «ко всей комнате» при общей стене, идентичность LED,
разделение local commit / server ACK по writer’ам).

## Что проверено и корректно

- Обязательные разделы ТЗ присутствуют и содержательны (не только формально
  по ключевым словам preflight).
- Каждый AC1–AC12 называет конкретный проверяемый результат и способ
  доказательства (`browser smoke`/`unit`/`visual snapshot`/`fault-injection
  smoke`/`code review`) — ни один не оставлен с одним словом «Verified» без
  названного способа.
- Защитные по характеру положения (dirty-guard §5, идентичность объекта §5–6,
  граница local commit/server ACK §5, запрет на запись при снятых правах)
  имеют явный пользовательски наблюдаемый oracle (какой диалог появляется,
  какая кнопка недоступна, что показывает панель) — не сведены к «работает
  как должно».
- Не-скоуп прямо исключает слияние редакторов, новую общую историю, новые
  геометрические операции, backend/миграцию — соответствует заголовку issue
  и `docs/SCOPE.md` (J4/J6, не выходит в CAD/историю/реестр).
- i18n: таблица новых RU/EN строк в namespace `editor.properties.*` присутствует
  (§10); существующие подписи не дублируются новыми синонимами.
- Touch/degradation — явно по `docs/TOUCH-SUPPORT.md`: desktop — полная
  поддержка независимо от ширины контейнера, touch — best effort с
  сохранностью данных и безопасным выходом (AC11).
- DoR (PROCESS.md §2.5) по пунктам: AC с доказательствами — есть; файлы/модули
  — перечислены (§10); i18n — есть; миграция/совместимость — явное «нет»
  (§10); performance — назван через AC12 и риск «eager рост View»; touch —
  назван; release-артефакты — перечислены (§12); откат — описан (§12, простой
  revert без миграции данных); открытых продуктовых вопросов нет; риски
  перечислены (§12).
- Базовый коммит сверки (`e9ce1963`) не «протух»: между ним и материалом
  ревью (`dcf9b5a0`) лежат только документационные коммиты, то есть описанное
  в ТЗ «существующее» поведение не разошлось с фактическим деревом за время
  подготовки ТЗ.

## Чего не проверял

- `npx tsc --noEmit`, `npm test`, `npm run build` — не выполнялись: код не
  менялся, `node_modules` не установлен (этап spec, #696), прогон по
  неизменному `dev` не доказывает и не опровергает ничего в этом ТЗ.
- Golden/visual snapshots, HA-гармонический бэкенд-тест, performance-замеры —
  неприменимо: нет реализации, план проверки (не исполнение) зафиксирован в
  §12 ТЗ как будущая работа.
- Не вычитывал построчно весь объём `src/houseplan-editor-runtime.ts` и
  остальных перечисленных в §10 файлов — только точечно проверил
  фактологические утверждения ТЗ о «существующем» поведении, которые
  используются как опорная точка AC (список выше). Полная ревизия текущей
  реализации — не задача ревью ТЗ.
- Не проверял каждую из ~90 ссылок на CSS-переменные/токены form-kit на
  фактическое существование в стилях — ТЗ явно декларирует переиспользование
  существующего набора, а не вводит новый дизайн-токен; при ошибке в имени
  токена находка относится к ревью кода, а не ТЗ.
