# SPEC-REVIEW-903-r1

Issue: [#903](https://github.com/Matysh/houseplan-card/issues/903) — «Не считать
публикацию принятого ТЗ реализацией при сборке release catalogue». Этап: spec
(ревью ТЗ, PROCESS.md §2.4). Трек: `track:ask`. Заход r1, блокирующих циклов
израсходовано 0 из 4. Материал: тело issue #903 (единственная редакция,
15.10.2026, группа batch-findings-20261015/03) и единственный комментарий
автора (аналитика с «Трек: ask», claim занятия).
Рабочая копия на момент ревью — `1d3ef09dbf5a89726f2c3ea4cb7786b5f3b2f963`
(`v1.81.0-beta.3`), совпадает с заявленным в задаче материалом; Validate на
этом SHA зелёный (ссылка в задаче ревью).

## Скоуп

ТЗ описывает узкий producer/consumer контракт вокруг
`docs/release-ledger/<baseStable>/<NN>.json`: конвейер ревью ТЗ публикует
документ `SPEC-REVIEW-NN-rN.md` и `INDEX.md` прямо в `dev` коммитом с
трейлерами `Issue: #NN` / `User-Visible: no` (C-only, класс документации), а
`readCatalogue` (`scripts/release-ledger.mjs`) требует файл классификации для
**любого** issue-трейлера в диапазоне `baseStable..candidate` без различения
фазы — иначе бросает `Missing classification for #NN` и ломает сборку каталога
для **всей** беты, не только для этого issue. Задача вводит явный способ
отличить «ТЗ принято, реализации ещё нет» от «реализация поставлена без
актуальной классификации», не трогая продуктовый код, UX, touch, миграции
runtime-конфига или права владельца. Инфраструктура, `User-Visible: no`,
пользовательского job из `docs/SCOPE.md` не закрывает напрямую — обслуживает
надёжность конвейера, которым поставляется продуктовая работа (аналогично
прецедентам #897, #896, #855).

## Находки

Находок нет. High: 0. Medium: 0. Low: 0.

Разобрал потенциальные точки сомнения отдельно, ни одна не подтвердилась как
дефект:

- **Персона сценария — «автор»/«релиз-менеджер», не из `docs/SCOPE.md`.** Это
  соответствует установленной практике для чисто инфраструктурных ТЗ, которые
  не меняют поведение ни одной персоны out of `docs/SCOPE.md` (ср.
  `SPEC-REVIEW-897-r1.md`: «Задача не меняет видимое поведение ни для одной
  персоны `docs/SCOPE.md`… обслуживает надёжность самого конвейера»). Не
  замечание.
- **Механизм различения фазы (readMergeEntry vs readCatalogue vs
  release-membership) не специфицирован на уровне схемы.** Технический вопрос:
  ТЗ прямо описывает наблюдаемое поведение (AC1–AC3), отделяя его от
  реализационного решения («фазовый entry…» помечено предположением). Решать
  такой вопрос — дело автора и ревьюера кода, не владельца; эскалации нет,
  замечания не образует.
- **AC2 («старый doc-only placeholder сам по себе не даёт PASS») требует
  детектировать, что классификация устарела относительно факта появления
  A/B-коммитов под тем же issue в том же `baseStable`.** Технически
  реализуемо без новых внешних данных: `readCatalogue`/`candidateInputs` уже
  проходят полный диапазон коммитов `baseStable..candidate`, то есть могут
  сверить набор классов файлов коммитов issue с содержимым/маркером записи
  классификации. ТЗ не обязано фиксировать этот алгоритм на этапе spec — это
  соответствует «список файлов и модулей» и «план автотестов», где
  негативная матрица (AC3) явно требует кейс «A/B под видом spec». Не
  замечание.
- **Дедупликация.** Проверил #838 и #855 (единственные два релевантных
  соседних issue, названных автором) построчно — оба решают другую задачу
  (авторский changelog-категории и мех. preflight до модели соответственно),
  открытого точного дубля нет.

## Что проверено и корректно

- Все обязательные разделы §7.1 присутствуют по существу; механическая
  проверка `specFormatErrors` подтверждает формат независимо от ручного
  чтения.
- Каждый AC (AC1–AC4) однозначен и имеет явный способ доказательства: AC1 —
  unit/integration на фикстуре git-истории; AC2 — unit на той же фикстуре;
  AC3 — unit negative matrix по пяти названным классам (forged phase, unknown
  phase, A/B под видом spec, malformed record, неподтверждённый C path); AC4 —
  ревью кода и process-digest tests, с явной оговоркой, что точечная правка
  одного файла (как 900.json) не закрывает задачу.
- Технические утверждения о текущем поведении кода («Проблема», «Текущие
  основания и дедупликация») сверены построчно с деревом на `1d3ef09d` —
  совпадают без расхождений, включая номера строк `.github/workflows/_process.yml`,
  `scripts/release-ledger.mjs`, `scripts/candidate-readiness.mjs`.
- Скоуп/не-скоуп чётко разграничены: явно исключены категории changelog,
  права/трейлер Issue, условия закрытия/S8, promotion-only, owner release
  authority, verdict/budget, автоматическая продуктовая классификация и
  автоматическое назначение milestone.
- Единственное техническое предположение («фазовый entry…») корректно
  помечено как предположение и не вынесено владельцу; открытых продуктовых
  вопросов действительно нет при повторном прочтении — выносить на самом деле
  нечего, весь объём решения не наблюдаем пользователем.
- План автотестов называет существующие, не вымышленные файлы
  (`test/release-ledger.test.mjs`, фикстуры `candidate-readiness`/`candidate-858`
  используют синтетические git-истории, а не реальные теги) и явно исключает
  дорогие гейты (full browser/performance/мутанты) — соразмерно
  инфраструктурной задаче на `track:ask`.
- Release-артефакты корректно классифицированы предварительно как
  `infrastructure`/`User-Visible: no`/без milestone, с явным требованием
  актуальной ledger-записи для будущей реализации до S7 — соответствует
  §2.6 и прецеденту 900.json.
- Откат описан и не предполагает исключений из общих правил (без force-push,
  без переписывания принятых вердиктов/raw, без ослабления гейтов при смене
  формата).

## Чего не проверял

- Не выполнял код реализации и не гонял `npx tsc --noEmit` / `npm test` /
  `npm run build` — на этапе `S4-spec-review` реализации не существует,
  Validate на материальном SHA (`1d3ef09d`) уже зелёный (см. задачу ревью), и
  эти гейты не относятся к проверке текста ТЗ (#696).
- Не проверял `scripts/release-contract.mjs`, `scripts/release-notes.mjs`,
  `scripts/merge-candidate.mjs`, `scripts/review-preflight.mjs` построчно
  целиком — только точечно, чтобы подтвердить полноту списка затронутых
  потребителей (`readCatalogue` напрямую: `release-ledger.mjs`,
  `candidate-readiness.mjs`, `release-contract.mjs`, `release-notes.mjs`;
  `readMergeEntry` отдельно и, по доступному чтению, не относится к этому
  классу дефекта, так как читает ровно один issue в момент слияния его же
  ветки, а не весь диапазон чужих issue). Детальная сверка каждого потребителя
  — задача код-ревью, не ревью ТЗ.
- Не проверял реальный прогон `test/release-ledger.test.mjs` /
  `test/candidate-858.test.mjs` (они и так зелёные на материальном SHA по
  Validate) — цель чтения была подтвердить пригодность паттерна фикстур для
  плана автотестов, а не повторно гонять гейт.
- Не искал исторические закрытые issue на предмет похожей идеи за пределами
  явно названных автором #838/#855 — объём, соразмерный ревью ТЗ, не аудиту
  всего трекера.
- Не оценивал корректность будущей реализации (её не существует) — только
  проверяемость и однозначность AC как контракта для будущего код-ревью.
