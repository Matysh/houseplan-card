# SPEC-REVIEW-905-r1

Материал: тело issue #905 на момент ревью (SHA дерева репозитория
`1d3ef09dbf5a89726f2c3ea4cb7786b5f3b2f963`, v1.81.0-beta.3). ТЗ — раздел
`## ТЗ` в теле issue (решение владельца 2026-09-10, #517); `docs/specs/`
не содержит файла для #905 — архив не создавался, корректно.
Этап: spec (`S4-spec-review`). Трек: `track:ask`. Заход r1, блокирующих
циклов израсходовано 0 из 4.

## Скоуп

Процессная/инфраструктурная задача (классы B/C: `.github/workflows/_process.yml`,
`docs/TESTING.md`, `docs/process/REVIEWER.md`, `PROCESS.md`,
`test/process-digests.test.mjs`) — без файлов класса A. По `docs/SCOPE.md`
задача не закрывает ни один Core user job (J1–J7): это не продуктовая
фича, а правка собственно ревью-конвейера, на что у владельца есть прямое
поручение, зафиксированное в разделе «Маршрут и граница поручения» самого
ТЗ («track:ask предложен агентом по прямому поручению владельца... Это
явное расширение маршрута... для B/C-only задач»). Инфраструктурные
задачи по умолчанию идут сразу в `S7-code-review`
(`AGENTS.md`, PROCESS.md §1); то, что эта идёт полным `ask`-маршрутом со
спек-ревью, — осознанное исключение владельца, а не нарушение процесса.
Я не оспариваю это решение: оно явно названо и не подменяет метку
владельца собственным суждением.

Предмет ТЗ: устранить реальное противоречие между (а) `docs/process/REVIEWER.md`,
который формулирует запрет ручного/временного прогона мутанта «ни на каком
треке» — но внутри раздела `## Трек show`, что читается как относящееся
только к этому треку; (б) `docs/TESTING.md`, правило 4 (строки 74–79),
которое для «чистых юнитов» прямо разрешает «прогон со снятой защитой,
приведённый в документе ревью» — то есть исполнение временной мутации
исполнителем/ревьюером; (в) фактический текст промпта `_process.yml`
(строки ~1401–1404, 1701–1720), который не просто упоминает, а
документирует как рутину: «ревьюер работает с Bash и в ходе проверки
«умеет ли тест падать» вполне может сделать `git add`» — то есть
рассматривает ручную мутацию продуктового кода ревьюером как ожидаемую
практику, объясняя через неё выбор `git reset --hard` вместо
`checkout`+`clean`.

## Как проверялось

Статический разбор текста, без изменения рабочей копии (запрещено по
условиям прогона). Прочитаны целиком: `docs/SCOPE.md`, `AGENTS.md`,
`docs/process/REVIEWER.md`, `PROCESS.md` §1–§2.7, §7.1; тело issue #905 и
единственный комментарий владельца; `docs/TESTING.md` (правила для новых
тестов, строки 1–110); `.github/workflows/_process.yml` (строки
1230–1270, 1340–1410, 1690–1725); `test/process-digests.test.mjs`
(структура, существующие ассерты на текст `_process.yml`, в т.ч. прецедент
#750 AC1/AC2 — те же инструменты уже используются для похожей правки).
Проверены дубликаты независимо от утверждения автора:
`gh issue list --search "мутант"` / `"mutant restore prompt"` — открытых
совпадений, кроме самого #905, нет; #900 нерелевантен.

Каждое фактическое утверждение проблемы ТЗ проверено чтением
соответствующего файла, а не принято на слово автора — см. цитаты выше;
все три подтвердились.

## Находки

Блокирующих (High) и находок Medium в скоупе не обнаружено.

Рассмотренный и снятый технический вопрос (не продуктовый, решаю сам,
по правилу §7.1 «технический спор решается вердиктом»): при удалении
из `_process.yml` рамки «ревьюер мутирует и затем восстанавливает» как
легитимной практики нужно сохранить сам факт инженерной защиты
(`git reset --hard` вместо `checkout`+`clean`, #365) — просто без
характеристики ручной мутации как ожидаемой/разрешённой; это страховка
на случай произвольных операций Bash-сессии, а не санкция на конкретно
мутационный прогон. Решение попадает под собственный блок ТЗ
«Технические предположения» («принято предположительно, поменять
свободно») и не требует отдельного AC — то, что скоуп уже называет
«не необходимую изоляцию обычных generated outputs» не трогать,
покрывает этот случай.

Low (не блокирует, не открывает цикл, фиксирую для разработчика):
ни один AC не промаркирован явным тегом `unit`/`ревью кода`
(`PROCESS.md §2.5` перечисляет именно эти пять слов), хотя метод
доказательства недвусмысленно следует из формулировки каждого AC
(AC1 — «ревью кода сравнивает…», AC2 — «Unit process-digests/
prompt-contract tests…», AC3 — обычные тесты + список команд в хендоффе).
Снимаю сам: неоднозначности в методе доказательства это не создаёт.

## Что проверено и корректно

- Обязательные разделы ТЗ присутствуют все: сценарий, что человек увидит
  до/после, проблема, скоуп/не-скоуп, контракт поведения, UX, модель
  данных и миграция, i18n, AC1–AC3 с указанием способа доказательства,
  план автотестов, риски, откат, release-артефакты, явный блок
  «Технические предположения» (§7.1).
- Технический факт, положенный в основание ТЗ (противоречие
  REVIEWER/TESTING/промпт), подтверждён независимо построчным чтением
  всех трёх источников — это не недоказанное утверждение.
- Структурная правка, предложенная в «Скоуп» («поместить общую политику
  до трековых разделов»), напрямую снимает замеченную мной же
  неоднозначность места текущего правила REVIEWER.md внутри `## Трек
  show` — то есть автор уже учёл эту проблему, отдельной находки не
  завожу.
- Не-скоуп исключает verdict schema, стоимость/модель, CI-права, ночной
  график, mutant registry implementation, исторические verdict/S8 —
  согласуется с «граница поручения» и не расширяет задачу скрыто.
- План автотестов называет существующий инструмент
  (`test/process-digests.test.mjs`), который уже умеет проверять текст
  `_process.yml` на конкретные паттерны (прецедент #750 AC1/AC2) —
  план реалистичен, не бланкетная отсылка.
- Release-артефакты корректно классифицированы предположительно как
  infra/process, `User-Visible:no`, без релизного milestone — совпадает
  с §11.9 (внутрипроцессные правки не входят в пользовательский
  milestone).
- Дубликаты перепроверены самостоятельно, не только со слов автора.

## Чего не проверял

- Исполняемые гейты (`typecheck`/`npm test`/`npm run build`) не
  прогонялись: этап — ревью ТЗ, продуктовый/тестовый код не менялся,
  зависимости и Chromium на spec-этапе не ставились (#696) — требование
  не распространяется на этот этап.
- Будущий текст самих документов (PROCESS.md/TESTING.md/REVIEWER.md/
  `_process.yml`) не писал и не проверял — это материал кода, а не ТЗ;
  AC1 явно называет способом доказательства «ревью кода» на следующем
  этапе.
- Не проверял содержимое `scripts/mutation-registry.mjs` и ночного
  воркфлоу `mutation-gate.yml` — они прямо в «Не-скоуп» ТЗ.
