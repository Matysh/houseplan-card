## Находки

### Medium (в скоупе) — не определена судьба существующего диалога «двойной клик → полные свойства» для объектов Плана/Подложки, которые теперь получают панель

**Где:** тело issue #931, §6 «Контракт поведения: выбор и жизненный цикл»,
пункты 2–3 (Plan/Подложка), и §8 «Действия» (где конфликт панель↔диалог
решён только для устройств).

**В чём проблема.** Для декора (прямоугольник/овал, линия, текст, мебель,
изображение) и для независимых стен/колонн действует **документированное и
действующее сегодня** поведение: один клик выбирает объект, **двойной клик
открывает полный диалог со всеми редактируемыми свойствами** —
`docs/DECOR-EDITOR.md:21` («double click opens all editable properties»),
`:33` («double click opens geometry, angle, contour/fill colour and
opacity»), `:34,88` (подложка плана — «double click opens width, height and
angle»); для физических объектов Плана то же самое фиксирует
`docs/UX-MODES.md:448` («double-click/tap properties» для независимых стен
и колонн). В коде это не историческая запись: `_decorShapeDbl` в
`src/houseplan-card.ts:8330` вызывает `_openDecorProperties` —
«One properties entry point shared by double click and the context tray»
(комментарий в коде, `src/houseplan-card.ts:8336`) — то есть диалог со
всеми теми же геометрией/цветом/opacity, которые теперь редактируются прямо
в новой панели, остаётся живым и достижимым.

Редакция 2 описывает контракт выбора для Плана и Подложки (§6.2–6.3) так,
будто единственный эффект клика — выделение объекта для панели; про
двойной клик в этих двух редакторах ТЗ не говорит ни слова (в отличие от
Устройств, §6.4, где одиночный/двойной клик расписаны явно: «одиночный клик
выбирает устройство, двойной открывает его полные настройки»). При этом
именно для Устройств ТЗ отдельно и осознанно решает конфликт двух
одновременно живых поверхностей редактирования одного объекта (§8, последний
абзац): «Полные настройки устройства строятся заново из актуальной модели
после завершения/подтверждения pending-правки панели. Пока модальный диалог
открыт, панель inert, скрытый blur не пишет». Для декора/независимых стен/
колонн — ровно та же структурная ситуация (два живых UI с одинаковыми
полями одного и того же объекта), но соответствующего решения нет вовсе.

Это оставляет для автора реализации (и для AC2/AC4/AC5/AC9) неразрешённый
развилок с видимым пользователю поведением:
- Если старый диалог остаётся достижимым по двойному клику — продукт
  получает **две параллельные, не согласованные между собой поверхности**
  редактирования одних и тех же полей (цвет+alpha, W/H/угол, непрозрачность)
  для прямоугольников/линий/мебели/изображений/стен/колонн, что прямо
  противоречит заявленной в §3 цели («нужна **единая** предсказуемая
  поверхность визуального редактирования») и не упомянуто нигде как
  сознательно сохранённое поведение.
- Если старый диалог предполагается закрыть/вывести из употребления для этих
  типов объектов — это значимое изменение видимого поведения, которое не
  зафиксировано ни в §3 «Не входит», ни как AC, ни в §16 release-артефактах
  как подлежащее changelog-записи, и `docs/DECOR-EDITOR.md`/`docs/UX-MODES.md`
  не отмечены как документы, где это поведение меняется (только «обновить
  по факту», без объявления факта).

Это не техническая деталь представления (решается не «как угодно, лишь бы
работало») — это ровно тот класс продуктового вопроса «что человек видит и
делает», который по PROCESS.md §7.1 должен быть решён в самом ТЗ. Пока это
не решено, AC5 («Esc/no-op/invalid — ноль [history steps]... ошибка не
меняет геометрию») и AC9/AC11 (история Undo, «не теряются» завершённые
команды) не полны: они не покрывают случай «старый диалог открыт поверх
панели с её pending-вводом» — ровно симметричный кейс, для которого в §8 уже
есть формулировка для устройств, но не для декора/плана.

**Как закрыть.** Добавить в §6 (или в начало §8) одно явное предложение по
образцу уже существующего для устройств: что происходит с двойным кликом на
декоре/независимой стене/колонне/лестнице при видимой панели — диалог
сохраняется с тем же guard («панель inert, пока диалог открыт, актуальная
модель строится заново после коммита панели») либо явно выводится из
употребления для перечисленных типов с соответствующей правкой
`docs/DECOR-EDITOR.md`/`docs/UX-MODES.md` и записью в §16/changelog.

## Рассмотренные и отклонённые кандидаты

- **Выбор целевой комнаты для толщины общей стены контура** (§7, строка
  «Стена контура») — как и в r1, виджет выбора одной из прилегающих комнат
  не детализирован, но это техническая деталь представления, а не
  продуктовая неоднозначность (случайный resolver по индексу явно запрещён
  общими формулировками §9/§10 о сохранении siblings). Не нахожу.
- **«Шесть клеток» допуска старого поиска толщины»** — эта историческая
  деталь (упомянутая как контраст в r1) из текста редакции 2 исчезла вместе
  со старой формулировкой; повторной проверки не требует.
- Открытых вопросов, адресованных владельцу явно или неявно, в самом тексте
  не нашёл — автор решил спорные развилки сам (контур read-only, отказ от
  Apply-all комнаты, last-writer-wins для позиции маркера). Единственный
  найденный пробел (выше) — не вопрос, вынесенный на усмотрение владельца, а
  пропущенный случай, симметричный уже решённому в этом же ТЗ для устройств;
  решается автором по аналогии, без обращения к владельцу.
