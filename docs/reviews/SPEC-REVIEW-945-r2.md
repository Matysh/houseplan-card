## Находки

### Medium (в скоупе) — новое/переименованное поле локального режима заряда устройств пространства нигде не называется по имени, хотя ТЗ (включая новый backend-раздел этого же раунда) требует синхронного обновления трёх backend-контрактов и frontend по этому полю

**Где в ТЗ:** раздел «Показатели устройств и наследование заряда» вводит
поведение `s-battery-mode: inherit/all/low/off` и цепочку наследования; раздел
«Модель данных, миграция и обязательные различия» перечисляет это поле как
«необходимое расширение модели» наравне с `card_name_scale`/`card_label_scale`;
новый (этого раунда) раздел «Уточнение backend-контрактов по ревью r1»
требует обновить `_SPACE_DISPLAY_FIELDS`, `_space_settings()` и
`SPACE_SETTINGS` «вместе с frontend» и доказывать AC3/AC4 backend
unit-тестами, которые явно проверяют «все режимы заряда».

**Суть:** для двух новых полей размера ТЗ прямо называет имя хранения —
«Новые поля хранения: `card_name_scale` и `card_label_scale`» — и этим именем
оперируют все остальные упоминания (включая новый backend-раздел). Для
нового поля локального режима заряда такого предложения нет нигде в тексте
ни разу: везде фигурирует либо описание по смыслу («новое поле локального
режима заряда устройств пространства», «локальный режим заряда пространства»),
либо макетный layout-id `s-battery-mode` (тот же стиль id, что `s-name-font`/
`s-caption-font`, которые НЕ являются именами хранения — ТЗ отдельно поясняет
их реальное маппинг на `card_name_scale`/`card_label_scale`). Для заряда такого
маппинга нет. Проверено построчным поиском «заряд» по всему телу issue —
совпадений с именем нового storage-поля нет (см. «Как проверялось»).

Проект уже имеет прецедент именно такого поля: `space.settings.show_lqi_mode`
(`inherit/on/off`) зарегистрирован явным именем в `scripts/
config-field-registry.mjs` при введении (#876) — ровно та же форма
(наследование от общей настройки на уровне пространства), и реестр — штатное
место, где такие решения фиксируются. Новое поле заряда того же класса
(`inherit/all/low/off`), но имени не имеет нигде, включая раздел, который сам
же ссылается на обязанность трёх backend-контрактов его хранить.

**Чем краснеет:** доказывается чтением, не исполнением — кода реализации не
существует (этап spec), мутировать нечего. Логический риск детерминирован
структурой задачи, а не домыслом: три backend-контракта
(`import_export.py::_SPACE_DISPLAY_FIELDS`, `support_package.py::
_space_settings()`, `support_wire_schema.py::SPACE_SETTINGS`) — explicit
allow-list/closed-schema (подтверждено повторным чтением кода в этом раунде,
см. «Как проверялось»), и frontend — отдельная кодовая база. Если ТЗ не
фиксирует единое имя поля, вероятность того, что эти явные allow-list будут
обновлены с другим именем, чем использует frontend (или друг с другом) —
структурный риск именно того типа, который сам раздел «Уточнение
backend-контрактов» и был написан предотвратить для `card_name_scale`/
`card_label_scale`, но не распространил на третье поле той же модели.

**Эффект на пользователя, если не исправить до реализации:** пользователь
задаёт пространству собственный режим заряда устройств (например, «Все» при
общем «Нет») → при расхождении имени поля между frontend и одним из трёх
backend-контрактов (или общей записью настроек) это значение либо не
сохранится, либо не попадёт в экспорт/пакет поддержки, либо будет отклонено
wire-валидацией как «незнакомый ключ» — тот же класс тихой потери данных или
отказа диагностики, который и был предметом находки r1, только для третьего
поля, которое новый backend-раздел прямо обязался защитить, но не смог
однозначно назвать.

**Почему это находка ТЗ, а не мелочь реализации:** ТЗ уже демонстрирует
правильный паттерн для двух других новых полей (явное «Новые поля хранения:
…») и для аналогичного прежнего поля `show_lqi_mode` в практике проекта
(зарегистрировано по имени при введении). Третье поле той же модели,
введённое тем же абзацем и защищаемое тем же backend-разделом, пропущено —
это несогласованность внутри собственного текста ТЗ, а не вопрос, который
можно оставить исполнителю: имя обязано совпасть одновременно во frontend и
в трёх независимых backend-контрактах, то есть это ровно модельное решение,
а не внутренняя структура модуля.

**Предлагаемое исправление ТЗ:** одним предложением в «Модель данных,
миграция и обязательные различия» (рядом с «Новые поля хранения:
`card_name_scale` и `card_label_scale`») — назвать явное имя нового поля
локального режима заряда устройств пространства (например, по аналогии с
`space.settings.show_lqi_mode` — `space.settings.show_device_battery_mode`
или любое другое явно выбранное имя), и той же фразой включить его в список
полей, которые раздел «Уточнение backend-контрактов по ревью r1» обязывает
добавить в `_SPACE_DISPLAY_FIELDS`/`_space_settings()`/`SPACE_SETTINGS`.

Это единственная находка раунда; High-находок нет. Находка целиком в скоупе
задачи — это тот же backend-раздел, который сам же появился в этом раунде
для закрытия r1, и та же модель данных пространства, которую ТЗ и так вводит.
