## Скоуп

Баг-репорт + ТЗ владельца: составное замыкание комнаты (новая стена +
существующая перегородка + существующие стены) ошибочно классифицируется как
полностью новая вложенная грань вместо составного Split родительской комнаты,
из-за чего общая стена с соседней комнатой получает третьего владельца
(`third-owner`), запись отказывает, а диалог создания остаётся с нерабочим
активным Save. ТЗ переносит действующий wall-to-wall Split contract на
составной контур и добавляет точечную очистку формы после отказа, не ослабляя
`third-owner`/physical/junction guards. Явно не-в-скоупе: общий redesign
диалога, Split/Merge/Optimize, миграция модели, HA-зоны, View/Glow — см. §3 ТЗ.
Соответствует J4/J6 `docs/SCOPE.md`.

## Находки

Находок не обнаружено — ни High, ни Medium, ни Low.

Проверены потенциально спорные места отдельно и сняты без замечаний:
- **Детерминированный выбор стороны при точном равенстве площадей** (§4.3,
  «канонический ключ») — не новый продуктовый вопрос: уже существующий простой
  Split (`_offerWallFaces:2521`, `polygonArea(p1) >= polygonArea(p2) ? p1 : p2`)
  решает тот же пограничный случай тем же способом («p1» побеждает на ничьей);
  составной Split продолжает тот же прецедент, не вводит новое видимое
  поведение.
- **Классификация ledger (`stable-fix`/`line-fix`)** — ТЗ откладывает её до
  проверки фактической предыдущей stable (§10); это зона код-ревью
  (`docs/release-ledger/<previous-stable>/874.json`), не обязанность спеки.
- **Запрещённый backend host-transition при поглощённой partition с проёмом**
  (§4 п.9) — явно назван риск и явно исключён из скоупа (не расширяем host
  transitions), с AC5, проверяющим именно отказ-с-сохранением-проёма.

## Что проверено и корректно

- Все обязательные разделы §7.1 на месте, в ожидаемом порядке смысла.
- AC1–AC6 пронумерованы, однозначны, у каждого — доказательство и (для
  защитных) способ покраснения.
- Технические утверждения о текущем поведении (`_offerWallFaces`,
  `splitRoomPath`, `_clearGeometryGesture`, `_commitRoom`, rollback-контракт,
  зависимости, i18n-ключи, смоки) перепроверены чтением исходников и канона —
  совпадают дословно, догадок не найдено.
- Скоуп/не-скоуп чётко очерчен и не пересекается с #804/#845/#851 (разные
  причины отказа, явно разведены в аналитике и §3 ТЗ).
- Контракт геометрии (§4) формализован достаточно для unit-теста без
  дополнительных уточнений у владельца.
- Открытых продуктовых вопросов, спрятанных как технические, не найдено;
  единственный пограничный случай (ничья по площади) — не новый, а
  унаследованный прецедент.
- Release-артефакты, откат, i18n, performance/touch названы явно (включая
  явное «нет» там, где уместно).
