## Скоуп

Новый серверный адаптер для штатной интеграции Ecovacs (`image.*`, SVG-карта
X1 Omni / deebot-client 18.7.0 / HA 2026.10.2): нормализация позиции робота,
базы и векторного пути из SVG, безопасный растровый фон для существующей
ручной подгонки, интеграция с действующими контрактами карт/маршрутов/путей
(#162, #872, #918, #940). Автопостроение геометрии дома из растровой карты
исключено явно. Это расширение существующего семейства поддерживаемых
источников пылесоса (XCME / Dreame / Valetudo), а не новая продуктовая
способность — относится к J1 («что происходит сейчас») и J6 («план остаётся
верным»).

## Находки

Находок нет — ни High, ни Medium, ни Low.

Проверка намеренно была придирчивой (в т.ч. на предмет «не бывает сложной
задачи без единого открытого вопроса»); ниже — то, что было отдельно
проверено и признано корректным, а не упущением:

- Два отдельных числовых лимита фона (`≤4096 на сторону` и `≤16 млн пикселей`)
  не противоречат друг другу: это два независимых AND-ограничения (квадрат
  4096×4096 = 16 777 216 px не проходит через более строгий лимит пикселей) —
  поведение однозначно, воспроизводимо и не требует выбора «какое побеждает».
- Отключение автокалибровки для Ecovacs (`vacuum.rooms` — только имя/ID, без
  координат) не конфликтует с общим механизмом автокалибровки в `VACUUM.md`:
  спецификация явно запрещает использовать словарь имён как геометрию и
  направляет на ручную подгонку, вместо того чтобы молча давать автоматике
  провалиться на фиктичных нулевых якорях.
- Новая метка «Все камеры и карты» (расширение существующего `All cameras` на
  `image.*`-кандидаты) описана как обычный выбор вручную, не как источник
  неявной автопривязки — сохраняет инвариант `VACUUM.md` («The collapsed All
  cameras section… is never used for automatic binding»).
- Отличие в частоте чтения (ивент-драйвенный coalescing 2 с + резерв 10 с при
  движении, а не периодический поллинг 30/10 с, как у Dreame) оправдано иной
  природой источника (`image.*` обновляет своё состояние по событию, а не
  требует активного опроса MJPEG-потока) и не противоречит ничему в
  `VACUUM.md`.
- Исключение автопостроения стен/комнат из растровой карты (прямой запрос
  пользователя в теле issue) верно отведено ссылкой на существующую границу
  `docs/SCOPE.md` («General CAD… → specialised applications»), а не придумано
  задачей заново.
- Все шесть AC называют конкретный способ доказательства (категории тестов +
  конкретные пути файлов из «Плана реализации и автотестов»), AC3 честно
  называет ограничение headless, AC5 — мутационный реестр без локального
  прогона мутантов (соответствует общей политике, запрещающей исполнение
  мутанта вне ночного workflow).
- Раздел «Принято предположительно» корректно разделяет техническое (имена
  модулей, кэш, выбор API) от уже решённого продуктового (автопостроение дома
  исключено); оставшиеся технические детали (например, какой именно набор SVG
  `transform` считается «явно поддержанным») не являются продуктовым вопросом
  и не требуют отдельной эскалации — это решает автор/ревьюер кода при
  реализации.

## Что проверено и корректно

- Согласованность с `docs/VACUUM.md` по всем числовым контрактам, которые
  задача переиспользует (лимиты пути 100000/1024, квота рендера 20000,
  17.5 см/2 см сглаживания, `map_id`-цепочка, статусы источника, модель
  `map_routes`/легаси `calibration`, source-first #940) — ни один инвариант не
  переопределяется молча.
- Ссылки на контракты #162/#872/#918/#940 и их формулировки соответствуют
  `VACUUM.md`.
- Терминология UI («Пылесос», «Живая позиция», «Источник и показ пути», «Карты
  и этажи», «Все камеры») взята из `docs/USER-GUIDE.ru.md`, а не изобретена;
  единственное новое название («Все камеры и карты») — явное, обоснованное
  расширение существующего пункта, не скрытая подмена.
- Безопасность источника (XXE/DTD/entities/scripts/внешние ссылки/
  неподдержанные transform отклоняются, SVG не вставляется в DOM, токен и
  исходник не достигают клиента) описана как явные негативные случаи с
  однозначным результатом (ошибка/диагностика, не угаданное поведение).
- Жизненный цикл чтения (lease переживает timeout/reload, generation fence,
  backoff, поздний ответ не публикуется) и запись пути (source-first,
  sample-fallback только до первого нативного канала, explicit empty ≠ error)
  описаны без противоречий и совместимы с уже принятым #940.
- Откат описан явно: отключение адаптера не повреждает существующие
  source/route/calibration/путь; release-ledger классификация (`major`,
  относительно последнего stable) обоснована (новое поддерживаемое семейство
  устройств), а не выведена механически из `User-Visible`.
- Владельческий вопрос не оставлен открытым: запрос пользователя на
  автопостроение дома разобран по существу и закрыт ссылкой на
  `docs/SCOPE.md`, а не передан дальше как вопрос.

## Чего не проверял

- Исполняемых гейтов (`tsc`, `npm test`, `npm run build`, golden, demo smoke,
  `pytest tests_backend`, invariants) — неприменимо: продуктового кода в этой
  задаче нет, ветка указывает на тот же `dev`-коммит, диффа не существует.
- Реальную доступность `homeassistant.components.image.async_get_image` как
  публичного API именно в версии 2026.10.2 — не верифицировалось исполнением
  (в этом окружении HA venv не установлен, что ожидаемо на этапе spec, #696);
  это оставлено как техническое решение реализации, не продуктовый вопрос,
  и будет видно на код-ревью по факту использования.
- Фактическую частоту обновлений `image.*`-сущности у реального устройства за
  пределами двух предоставленных пользователем снимков — задача сама
  признаёт это ограничение полевых материалов в разделе «Риски» и не выдаёт
  его за доказанный факт.
- release-ledger JSON файл для #939 — не применимо на этапе spec (вносится
  автором при коде/релизе, проверяется на код-ревью).
