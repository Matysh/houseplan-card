история API использует кеширование; один ответ без submit_review получает одно содержательное напоминание.
Резерв CI умеет забирать применимые успешные результаты предыдущего прогона, а не обязательно выполнять всё заново.

## Что не объявляем исправленным запуском этих тестов

- Настоящие права GitHub, платный вызов Opus, публикация и HACS проверяются при подключении на отдельном маршруте.
- Полный HA E2E и backend coverage 87,2% ещё не выполнены. Шесть внешних converter-контрактов требуют проверки влияния на coverage.
- 490 browser-файлов stable оставлены консервативно; содержательная ревизия каждого из них не завершена.
- Из 75 новых выбранных кадров прошлый прогон дал 5 совпадений, 15 различий и 55 отсутствующих эталонов.
  Это не зелёный визуальный набор. Сначала обсуждение изображений, затем адресное принятие/исправление.
- Внешний converter E2E остаётся отдельной задачей #1179 и диагностикой, не блокирующей основной продукт.
- Если хранилище артефактов окончательно не сохранило результат API перед потерей ephemeral runner,
  восстановить отсутствующие байты нельзя. Второе дублирующее хранилище ради этого не вводилось.

Ревью до очереди и замена JSON-хранилища очереди метками — альтернативные архитектуры, а не исправления утверждённого маршрута.
Они не внедрены. Сохранение диагностического замера каждого stable принято владельцем отдельно.

## Последующее решение владельца: контекст исполнителя

Владелец утвердил форму «постоянные правила ревью + контекст конкретной задачи от исполнителя».
Она реализована через раздел issue по `templates/review-context.md`, существующий пакет S4/S7 и поле `authorContext`.
Постоянный промпт не формируется автором заново. Авторские цель, подход, альтернативы, риски и ограничения
передаются как сведения; ревьюер самостоятельно проверяет их полноту по исходникам и фактическим результатам.
Нового вызова модели, гейта или обязательной анкеты нет. Снимок авторского контекста сохранён отдельно от выводов
ревью и не подменяется позднейшей редакцией при повторе публикации.

## Второе ревью — исправления

Основание: `review-1105-round-2.md`, проверявший `97cfd359e`. Все девять замечаний исправлены в подготовленных механизмах;
это не подтверждение работы ещё не подключённых GitHub workflow, Opus, публикации и HACS.

Итог: **191/191 тест обвязки, 0 пропусков, 6,09 секунды в Ubuntu WSL**.
Отчёт: [evidence/round2-wrapper-tests-wsl.tap](evidence/round2-wrapper-tests-wsl.tap).
Неактивные YAML-шаблоны разобраны; `git diff --check` без ошибок. Рабочие workflows/hooks не менялись.

| № | Проблема | Исправление и проверка |
|---|---|---|
| 1 | Незавершённое платное ревью повторяется бесконечно | Один автоматический повтор на запрос, сохранённый до вызова API; затем видимая причина и освобождение слота. Повтор действительно получает новый ответ вместо копирования incomplete. Окончательный отчёт переиспользуется. Устаревший комментарий заменяется. |
| 2 | Пропавший исполнитель снова занимает очередь | Истечение допуска sync/testing оставляет задачу на S6 вне очереди; повторный вход — только ready/finish. Результат уже идущего удалённого ревью сохраняется. |
| 3 | Постоянная служебная ошибка бесконечно держит слот | 30 минут на одну причину; heartbeat этот срок не сбрасывает. У HTTP есть timeout 60 секунд. Тесты воспроизводят ошибку merge и отсутствующий исполнитель. |
| 4 | Опрос создаёт лишнюю нагрузку GitHub | finish ждёт по минуте, ожидающие агенты не обслуживают чужие задачи, heartbeat отдельный. Предыдущий отчёт выбирается по issue/виду до загрузки артефактов. Проверены ожидание без записей и один нужный артефакт среди посторонних. |
| 5 | Stable не видит кеш/отчёты беты в другом worktree | Общий каталог Git worktree по умолчанию. В существующем кеше сохраняются только явно разрешённые отчёты coverage/golden; проверяются входы и хеши, повреждение ведёт к исполнению. Два настоящих worktree: смена версии засчитывает проверки, изменение кода отменяет зачёт. |
| 6 | Комментарий перезапускает S4 | Идентичность ТЗ зависит от тела issue; комментарии остаются контекстом. Show/ship вообще не запускают индивидуальное ревью ТЗ. |
| 7 | Ship требует лишнего доказательства владельца | По последнему решению владельца установленная метка обязательна. Агент только добавляет отсутствующую; источник чата необязателен. Принятие превышений метрик отдельно требует явного текста/источника, одного actor недостаточно. |
| 8 | CI-резерв не связан с finish | `finish --s6 github`: допущенный SHA, общий профиль, фактический отчёт, без локального запуска. Есть предел ожидания и один повтор сбоя подготовки; FAIL тестов не повторяется как ошибка транспорта. Неоднозначный dispatch не размножает запуски. |
| 9 | Возврат выпущенного кода требует ещё одного платного ревью | Для точного опубликованного тега и чистого автоматического merge засчитывается прежнее ревью, выполняется S6 результата слияния. Ручной конфликт/новый код не получают такого зачёта. Проверено на настоящем временном remote и через маршрут очереди. |

Исправления не добавляют обязательных проверок каждой задачи. Адресные регрессии входят в тесты изменённых механизмов.
Предложения убрать учёт dev-build, заменить хранилище очереди или перенести ревью до допуска не приняты автоматически.
Оставшиеся внешние проверки и работа с 70 непринятыми/различающимися кадрами перечислены выше; этот раунд их не выполнял.

## Третье ревью — исправления

Основание: `review-1105-round-3.md`, проверявший `079590caa`. Все изменения остаются в подготовленной обвязке.
Самостоятельный выбор ship отдельно согласован владельцем: четыре условия в `PROCESS.md`, без запрета по подсистемам.

Итог: **202/202 теста обвязки, 0 пропусков, 6,84 секунды в Ubuntu WSL**.

Разбор изменённого YAML-шаблона и `git diff --check` без ошибок. Рабочие workflows/hooks не менялись.

| № | Проблема | Исправление и проверка |
|---|---|---|
| 1 | После исчерпанного повтора тот же код нельзя снова отправить на ревью | Новый явный ready/finish после выхода получает новый номер входа и запрос, сбрасывает использованный повтор при отсутствии принятого ревью. Дубликаты, ожидание очереди, автоматическое продолжение и чистый rebase сохраняют запрос. Интеграционный тест проходит старый exhausted → ready с тем же кодом → новый dispatch → accepted → merge. |
| 2 | Координатор выбирает show и пропускает S4 | Событие label только читает существующий трек; отсутствующую метку инициализирует исполнитель через ready/finish. S4 без метки идёт на ревью как ask, независимо от старой записи ownerDecision. Проверены отсутствие записи меток на S4/S8 и явный выбор ship исполнителем. |
| 3 | Вся история прогонов перегружает/ломает чтение ревью | Поиск ограничен 60 днями, срок хранения артефакта указан явно — 60 дней. Плотный диапазон делится по датам, чтобы прочитать больше 1000 результатов без потери; ровно полная страница завершается по total_count. Известный runId читается напрямую, включая старые запуски. Проверены 2050 старых + свежие, ровно 100 свежих, 1100 внутри окна и старый известный повтор. |
| 4 | Старый Git блокирует возврат релиза | Любой отказ optional merge-tree отменяет только зачёт ревью; обычный маршрут по треку продолжается. Ошибки обязательных Git-операций остаются видимыми. Проверены код 128 старой опции, конфликт и обычная ошибка; отдельный старый бинарник Git не запускался. |

Для поиска использованы поддерживаемые [параметры GitHub REST](https://docs.github.com/en/rest/actions/workflow-runs#list-workflow-runs-for-a-workflow),
а срок артефакта указан через [retention-days](https://github.com/actions/upload-artifact#retention-period).
Это изменения существующих механизмов, без новых этапов, гейтов и хранилищ. Необязательная перестройка очереди и доставки dev-build не выполнялась.
Реальные Actions/Opus/публикация/HACS, полные продуктовые наборы и принятие визуальных эталонов остаются за границей этого исправления.
