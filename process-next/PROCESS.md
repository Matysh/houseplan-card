# Процесс Houseplan: новая обвязка

Это короткая инструкция для владельца и агентов по решениям [#1105](https://github.com/Matysh/houseplan-card/issues/1105).
Снимок решений: [decisions/1105.json](decisions/1105.json). При расхождении уточнять по решениям владельца.
**Состояние: подготовлено рядом; действующий процесс не переключён.**
Новые команды не подключены к старым workflow/hooks. Подключение обсуждается после независимого обзорного ревью.

## Как дорабатывать обвязку

**Сбой исправляем в самом механизме, а не обстраиваем новыми гейтами.**
Если нужен регрессионный тест, он проверяет конкретный дефект и запускается при изменении этого механизма.
Он не становится обязательным прогоном каждой продуктовой задачи. Баг сам по себе не основание для нового этапа,
сертификата, повторного Validate или ещё одного слоя проверок результатов предыдущих проверок.
При доработке сначала ищем упрощение: убрать лишнее состояние, объединить дублирующие действия, сократить передачу данных.
Эта инструкция — принцип проектирования; отдельной джобы для проверки соблюдения инструкции нет.

## Задача и трек

Задача живёт в GitHub issue; восемь статусов сохраняются:
S1 — новая → S2 — анализ → S3 — ТЗ → S4 — ревью ТЗ → S5 — готова → S6 — реализация и проверки → S7 — ревью кода → S8 — завершена.
Трек определяет нужные шаги; пропущенный шаг не изображаем выполненным.
`blocked` дополняет текущий статус, не заменяет его.

Трек `ship/show/ask`, прямо назначенный владельцем меткой или в чате, окончателен.
Агент и автоматизация не повышают его и не требуют повторного подтверждения.
Owner ship: короткое описание → реализация → очередь → короткие проверки S6 → merge → S8.
У него нет индивидуального ревью ТЗ/кода, нового формального ТЗ или лишних гейтов из-за старого WIP.
Для show достаточно конкретного ожидаемого результата; для ask автор готовит ТЗ по существующему шаблону.
Ревью ТЗ — для ask; обычное код-ревью — для задач, не освобождённых owner ship.

Цель от взятия до merge: ship около 10 минут, show 20–30 минут, ask около часа.
Сложная задача может занять до пары часов. Реальную ошибку не игнорируем ради срока.
Ожидание очереди видно отдельно; нулевое ожидание не обещаем.

## Где выполнять проверки

Основное место — подготовленный Ubuntu WSL, агент запускает обычную общую команду.
GitHub хранит задачу/очередь/ревью, выполняет merge и служит резервом исполнения при недоступности WSL.
В резерве те же определения наборов, версии и команды. Постоянный self-hosted runner не требуется.
Успех не повторяется только из-за перехода этапа, другого оформления отчёта или смены среды.
Реальный FAIL сначала разбирается; запуск в другом месте не способ скрыть его.
Временный понятный сбой допускает один адресный повтор. Поломка обвязки — прямой запуск или резерв с результатом.
Отсутствующее окружение, прерванный/неполный запуск и неожиданно пустая обязательная выборка не PASS.
«Проверки не требуются» — нормальный результат для чистой документации.

| Событие | Что выполняем | Что не добавляется автоматически |
|---|---|---|
| Продуктовая задача, S6 | Сборка с типами, критичные данные/права, один стартовый View smoke, малая выборка изменённой области | Полный product/tooling, бюджеты, golden, HA E2E, Validate |
| Инфраструктурная задача, S6 | Синтаксис/типы изменённых инструментов, поведенческие тесты затронутого механизма | Продуктовые тесты без объяснённого влияния, полный tooling |
| Чистая документация | Чтение/правка; для show/ask ревью текста | Любые тесты, build, lint, ссылки, Validate, включая косвенные hooks |
| S4 | Содержательное ревью ТЗ | Продуктовые проверки и механическая приёмка оформления |
| S7 | Ожидание ревьюера, затем содержательное ревью кода | Сборки, тесты, Validate, установка зависимостей, проверки реестров |
| Бета | Все быстрые поведенческие проверки продукта; фиксированные browser/golden/HA E2E; размеры и время | Повтор успешного набора без изменения входов; квота «30%» |
| Stable | Весь оставленный после ревизии набор; зачёт применимых результатов беты; backend coverage | Обязательный полный повтор уже проверенного кандидата |
| Hotfix | Короткий набор по дефекту и ревью; адресный HA E2E при необходимости | Обязательная бета или полный stable-набор |
| Фон | Мутации ночью, JS/TS coverage как диагностика | Блокирование обычной задачи этими результатами |

Сборка уже включает проверку типов. Подготовка `test-build` не требует второй продуктовой сборки.
Критичное ядро защищает сохранение/конфликты/устаревшие ответы, связи данных, права и безопасные действия.
Стартовый smoke проверяет готовый View непустого сохранённого дома, read-only и отсутствие необработанных ошибок.
Синтетический HA не подменяет серверные ACL/хранение; изменённому backend нужны соответствующие реальные проверки.
Один кейс выполняется один раз; цель продуктового минимума вместе с выборкой — до пяти минут в подготовленном WSL.
Это целевой бюджет, а не выдуманный замер всей новой обвязки.

## Очередь и завершение

Подготовка параллельна в отдельных ветках/worktrees. В очередь входим **до** финального rebase и проверок S6.
Среди ожидающих готовые ship первые; внутри ship и остальных — порядок готовности.
Новый ship не прерывает допущенную задачу. Другие задачи не пишут в dev, пока слот занят.
В слоте: актуализировать dev при необходимости → свои проверки S6 → ревью, если требуется → merge → удалить рабочую ветку → S8.
Для owner ship после успеха S6 сразу merge; для чистой документации проверок нет.
S7 может ждать ревьюера; это видно как «ожидает ревьюера», затем «идёт код-ревью».
Отказ, конфликт или возврат ревью освобождает слот: правки параллельно, затем новый вход с сохранением применимых результатов.
Повтор события не повторяет merge; сбой комментария не отменяет успешный merge; зависший обработчик не держит вечный lock.
Все записи в dev идут через один механизм. Сам выпуск очередь задачи не держит.
`dev` — интеграция, `dev-build` — быстрый стенд, `main` — стабильная линия.

## ТЗ и ревью

Автор до S4 проверяет существующий шаблон ТЗ: разделы, заполнение, поведение до/после, нумерованные AC.
`checkSpecFormat` проверяет форму, а не качество требований. Это не проверка каждой документационной задачи.
Независимая новая сессия ревью получает требования/решения владельца, base/head, связанные исходники/тесты,
результаты S6 и прошлый раунд. История доступна через diff/show/log/blame, определения и вызовы — через поиск.
Ревьюер разбирает логику и окружение, риски ошибок, читаемость, сложность, сопровождение и разумные альтернативы.
Замечание содержит условие, последствие, место и направление исправления; улучшения отделены от блокеров.
Полезные комментарии объясняют неочевидную причину/контракт. Нет квоты замечаний, обязательного рефакторинга или сокращения строк.
Отчёт коротко описывает понимание решения, реальные блокеры, полезные улучшения и границы анализа.
Недостаточность проверки возвращается исполнителю на S6; ревьюер не запускает её и не исправляет продукт сам.

Для новой обвязки закреплён **Claude Opus 5.5, `claude-opus-5-5`**, без автоматического перехода на Sonnet.
[Модель](https://platform.claude.com/docs/en/models/opus-5-5/overview) и [фиксированность ID](https://platform.claude.com/docs/en/about-claude/models/model-ids-and-versions) проверены 01.11.2026.
Подготовленный адаптер использует Anthropic Messages API и требует отдельный `ANTHROPIC_API_KEY`.
Существующий `CLAUDE_CODE_OAUTH_TOKEN` автоматически не подходит; настройка секрета потребуется при подключении.
Предпросмотр контекста работает без ключа и сети. Живой платный вызов при подготовке не выполнялся.
Модель получает только ограниченные функции чтения Git и отправку отчёта в заданный хостом каталог.
Это ограничение инструментов приложения, **не OS sandbox**. Права проверяются при изменении механизма, а не отдельным этапом каждого ревью.
Старые seals, сертификаты, аудит каждого чтения и таблицы доказательств ради формы не переносятся.

## Бета, stable, hotfix

Бета берёт фиксированный SHA dev в отдельную ветку/каталог; dev продолжает жить.
До следующей успешной беты сохраняется ветка последней опубликованной; неудачный кандидат её не удаляет.
Во время прогона материал не меняется. Независимые группы завершаются даже после первого отказа.
После сводки: разбор → исправление → новый кандидат → упавшие и связанные проверки.
Продуктовый фикс проходит короткое независимое ревью; новые задачи dev не подмешиваются в кандидат.
Исправления выпуска возвращаются в dev. Stable строится из выбранной беты, а не свежего dev.
Успехи применимы при неизменных значимых входах; недостающие/затронутые проверки дополняются.
Backend coverage собирается в том же запланированном запуске беты, порог проверяется только на stable.
JS/TS coverage диагностический, без порога. Отсутствующий замер не изображаем отчётом.
Hotfix начинается от stable; при уже готовящемся выпуске владелец останавливает его и включает исправление в новый кандидат.
После beta/stable коротко подтверждаем доступность через настоящий HACS и правильный скачиваемый артефакт.
Для беты учитывается prerelease. GitHub API сам по себе не доказывает видимость обновления в HACS.
Сбой сети/кеша повторяет доставку или её проверку, а не продуктовые тесты.

## E2E, визуальные проверки и конвертеры

После задачи автор сохраняет «надо/не надо» с причиной в `Matysh/houseplan-e2e`, с поиском по исходной issue.
Если надо — сценарий/ожидаемое изменение и ссылка; для состава беты собирается список, правки отмечаются выполненными.
Реальные HA E2E дорабатываются перед бетой, быстрые unit/fake-hass smoke — в самой задаче.
Для hotfix короткий воспроизводящий случай сразу; остальное записывается на следующую бету.
Не менять ожидания просто ради зелёного: намеренное изменение связывается с требованиями, необъяснённый отказ разбирается.
Фиксированная бета: **13 HA E2E случаев в 7 группах, 23 golden сцены в 8 группах, 13 browser файлов в 9 группах**.
Точные селекторы и назначения лежат в общем определении наборов; отдельной копии списка команд здесь нет.
Golden на задаче адресный; на stable весь осмысленный оставленный набор с зачётом беты, без массового принятия эталонов.
Внешние конвертеры — отдельный продукт. Перед stable их проверка обязательна, но диагностическая и не блокирует Houseplan.
Их отказ оформляется отдельно. Защита собственного импорта Houseplan от повреждённых данных остаётся продуктовой.

## Размеры и производительность

На обычной задаче обязательного бюджетного замера нет; оптимизация измеряет свою область по необходимости.
Перед бетой сравниваем с последним stable, а фиксированный v1.83.1 показываем только для накопленной диагностики.
Пауза публикации только при подтверждённом `delta > max(reference × fraction, absolute)`:

| Метрика | Процент | Абсолютный допуск |
|---|---:|---:|
| Готовый ZIP | 5% | 32 КиБ |
| Весь frontend, gzip | 5% | 16 КиБ |
| Начальная загрузка View, gzip | 5% | 8 КиБ |
| Первый устойчивый кадр | 10% | 50 мс |
| Смена этажа | 10% | 75 мс |
| Один wheel-шаг масштаба (`panZoomMs`) | 10% | 5 мс |
| Обновление состояния | 10% | 15 мс |

Для времени сравниваются медианы сопоставимых серий. Один шаг масштаба не означает FPS или всю серию перемещений.
Модули, прочие микрозамеры и накопление относительно v1.83.1 не блокируют. Нет данных — явно «нет данных».
Сначала полный отчёт, затем владелец принимает превышение, требует оптимизацию или принимает с задачей.
Повторно разрешать тот же кандидат не требуется; dev продолжает работу, оптимизация повторяет затронутое.

## Команды и результаты

Общая точка входа: `node process-next/cli.mjs --help`. Примеры из подготовленного WSL:

```sh
node process-next/cli.mjs plan --event task --issue 1105 --track show --layer infra --changed-file process-next/lib/e2e.mjs --area-test process-next/test/e2e.test.mjs
node process-next/cli.mjs run --event task --issue 1105 --track show --layer infra --changed-file process-next/lib/e2e.mjs --area-test process-next/test/e2e.test.mjs
node process-next/cli.mjs run --event task --issue 1234 --track ship --layer product --area-test test/config-write-conflict.test.mjs
node process-next/cli.mjs plan --event beta --request release.json
node process-next/cli.mjs run --event beta --request release.json
node process-next/cli.mjs run --event mutation --mutation-shard 1/5
node process-next/cli.mjs review preview --base BASE_SHA --head HEAD_SHA --issue 1234 --task-file task.md
```

`release.json`: версия/название выпуска, `e2eRoot`, `workRoot`, точный `upgradeFrom`, закреплённый `haVersion`; для беты также `metricsRequest`.
Кандидат по умолчанию упаковывается из готовой сборки в `artifacts/process-next/candidate`; tracked frontend не переписывается.
При внешнем готовом кандидате указываются `candidateRoot` и `expectedVersion`; названием выпуска нельзя подменять его байты.
В `metricsRequest` — путь к измерению последнего stable и наблюдённые условия питания/машины; секреты в JSON не хранятся.
Мутации запускаются отдельной фоновой командой с явно выбранным шардом `i/n`, например `1/5`; обязательной 20-дневной ротации нет, расписание ещё не подключено.
Предпросмотр ничего не выполняет. Платное ревью вызывается только явным `review run`; `spec-check --file ТЗ.md` выполняет автор до S4.
Для видимого окна из PowerShell: `.\process-next\open-wsl.ps1 -Repo /home/matysh/houseplan -Request C:\work\request.json`.
Окно открывает Ubuntu, запускает тот же CLI и оставляет итог до Enter.

Результаты Node-групп переиспользуются по зависимостям; браузерный набор зависит от всей карточки, поэтому его reuse пока консервативный.
Изменение продуктовых исходников может повторить браузерные кейсы; это ограничение подготовки, а не обещанная точность по каждой функции.
Проверки самой новой обвязки не доказывают прохождение целого продуктового, beta или stable набора.
Реальный HA E2E и платный Opus при подготовке не запускались. Идентификатор Opus отдельно проверен по официальной документации выше.
HA-адаптер требует подготовленные зависимости E2E/Chromium, Docker и отдельный каталог лабораторий; пользовательский `HA_URL` не принимается.
Он копирует нужные E2E-файлы, сверяет точные сценарии через `--list`, создаёт собственный seed/контейнер и удаляет только свой контейнер.
Три HA-среды последовательны, но отказ одной не отменяет независимые остальные; пустой остаток stable явно «не требуется».
Отчёты и собственные каталоги лабораторий сохраняются для разбора; старый E2E checkout и пользовательский HA не очищаются.

CI-резерв подготовлен в `templates/fallback.yml`, вне действующих workflows; он не активирован и не запускался.
Для beta/stable запрос дополнительно содержит `e2eCommit` — полный SHA `Matysh/houseplan-e2e`; зависимости ставятся без hooks.
`metricsRequest` и указанный в нём `latestStable` — относительные файлы кандидата; необязательный `measurementsCommit` берёт оба из отдельного закреплённого SHA `Matysh/houseplan-card`.
Замеры обязательны перед бетой; stable не добавляет их автоматически, явно переданный `metricsRequest` на stable диагностический.
Подготовитель заменяет WSL-пути на каталоги CI и записывает фактические CPU/kernel. JSON не вставляется в shell-код.
Для времени нужен замер последнего stable в сопоставимом CI-окружении; WSL-замер его не заменяет. Фиксированный v1.83.1 остаётся только диагностикой.
В артефакты CI попадают отчёты E2E, но не каталоги HA с авторизацией; платное API-ревью и его отдельный ключ подключаются позже.

Новая обвязка не вызывает старый полный Validate по умолчанию и не меняет labels/dev от одного предпросмотра.
В видимом окне Ubuntu показываются название стадии и фактически выполненные элементы/общее число.
Проценты вычисляются из реальной завершённости; очередь, загрузка, установка и работа модели не получают выдуманного процента.
Сводка различает успех, отказ, прерывание, отсутствие данных и «не требуются»; хранит команды и ссылки на результаты.
Конкретные файлы ревизии и технические проверки новой обвязки — работа реализации, не новая процедура одобрения владельцем.
