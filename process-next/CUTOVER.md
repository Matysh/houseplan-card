# Подключение процесса #1105

После выпуска `v1.84.0-beta.1` владелец поручил полностью заменить старую
обвязку. Подготовительный запрет на активацию снят. Это описание устройства
переключения и восстановления; фактические refs, настройки и результаты
проверки находятся в [evidence/cutover-status.md](evidence/cutover-status.md).
Правила разработки описаны только в [PROCESS.md](../PROCESS.md).

## Что становится действующим

| Назначение | Единственный рабочий маршрут |
|---|---|
| Задачи, очередь, метки, восстановление оформления | `.github/workflows/process-next-coordinator.yml`, `cli.mjs finish`, `lib/coordinator.mjs` |
| Ревью ТЗ и кода | `.github/workflows/process-next-review.yml`, Opus и постоянные правила `prompts/review.md` |
| Локальные наборы | `cli.mjs plan/run`, общий каталог `lib/catalog.mjs` |
| Резерв тех же наборов в GitHub | `.github/workflows/process-next-fallback.yml`, `finish --s6 github` |
| Фоновые мутации и диагностическое JS/TS coverage | `.github/workflows/process-next-background.yml` |
| Подготовка, публикация и завершение выпуска | `cli.mjs release prepare/publish/complete` |
| Завершение уже опубликованного выпуска с GitHub-секретами Telegram | Ручной `.github/workflows/process-next-release-complete.yml`, тот же `complete-release` |
| Снимки и адресное принятие эталонов | `catalog/golden-runner.mjs`, `cli.mjs golden-accept` |

`process-next/config.json` хранит настройки без секретов. GitHub хранит очередь
в `process-state`, выпуски — в `process-release-state`. Состояние последней
опубликованной беты и stable переносится по их фактическим тегам. Последняя
beta-ветка сохраняется для подготовки stable; релизные теги не перемещаются.

GitHub доставляет события через default branch `main`; обработчики используют
согласованную версию исполняемой обвязки. Workflow-входы должны присутствовать
на ветке доставки событий и на `dev`. Продуктовая stable-линия `main` не
обновляется до нового релиза только ради установки workflow.
Отдельный служебный коммит `main` включается в историю `dev`, чтобы будущий
stable сохранял общую историю.

Первый stable/hotfix, начатый от опубликованного до переключения тега, ещё не
содержит новой обвязки. До фиксации кандидата и его проверок включить в
release-ветку служебный коммит подключения из `main`, указанный в отчёте
переключения. Это перенос только инфраструктурного изменения; опубликованный
тег не меняется и свежие продуктовые задачи из `dev` не подмешиваются.
Следующие выпуски уже наследуют эту историю.

## Что остаётся в архиве

Старые workflow-семейства Process/Validate/release/nightly, их hooks,
генераторы доказательств и собственные устаревшие тесты переносятся в
`legacy/process-v1/` с сохранением относительных путей. GitHub не исполняет
workflow из этого каталога; npm не устанавливает старые hooks.
Архив нужен для истории и адресного восстановления, а не для запуска рядом
с новым процессом. Исходный план сохранён в
[архиве CUTOVER](../legacy/process-v1/process-next/CUTOVER.md).
Миграционная инвентаризация — [catalog/cutover.json](catalog/cutover.json)
и [catalog/inventory.json](catalog/inventory.json); это не дополнительные гейты.

Сохраняются продуктовая сборка и её используемые зависимости, backend,
браузерные fixtures, эталоны, полезные адресные тесты, `dev-build` и доставка
на стенд. Независимая ручная съёмка документации `docs-screenshots.yml`
остаётся доступна. Внешние конвертеры и support relay не архивируются вместе
с процессом. Полезные действия сопоставлены в
[AUTOMATION-PARITY.md](AUTOMATION-PARITY.md).

Старое локальное `core.hooksPath=.githooks` снимается только там, где оно
указывает на hooks этого репозитория. Пользовательские и глобальные hooks
не заменяются. Старый `prepare` не должен возвращать их при `npm ci`.

## Проверка подключения

Перед включением новых обработчиков старые выключаются; одновременно двух
координаторов не бывает. Проверяется адресный набор самой обвязки и пустой
живой запуск координатора. Продуктовый beta/stable-набор ради переключения
не добавляется. Первую настоящую задачу выбирает владелец.

OAuth-доступ Claude Code и Telegram проверяются отдельно от автономных
тестов; секреты не записываются в Git или отчёты. Для обычного подтверждения
доставки сохраняется прежняя проверка публичного release feed и ZIP;
доступ к пользовательскому HA не нужен. Anthropic API для ревью не
используется. Переключение не является командой выпустить версию, послать
анонс или принять визуальные расхождения. Непринятые панельные эталоны
остаются видимым незавершённым результатом.

## Восстановление после сбоя

Сначала остановить новые обработчики через `PROCESS_NEXT_ENABLED=false`
и сохранить фактическое состояние очереди/выпусков. Уже слитые задачи и
опубликованные версии не откатывать вместе с процессом.

Исправить конкретный механизм или вернуть нужные файлы обычным коммитом из
зафиксированного исходного состояния. Старые обработчики можно включать
только после остановки новых и сверки незавершённых действий. Не применять
force push, не перемещать теги и не восстанавливать старые гейты как
обязательное дополнение к новой обвязке.
