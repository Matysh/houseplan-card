| Установочный frontend и ZIP | bundle:release / release-prerelease | `lib/package.mjs` собирает готовый dist и backend в отдельный кандидат. Отслеживаемый frontend обычной задачей не переписывается. |
| Все публичные файлы | Старые release-assets / release workflows | `preparePublicationArtifacts`: `houseplan.zip`, `houseplan-card.js`, `RELEASE-MEMBERSHIP.json`, `SHA256SUMS`. Для stable отдельно сохраняется диагностический `measurement.json`. |
| Точный annotated tag и main при stable/hotfix | Старые release scripts | `lib/github.mjs: publishCandidateRefs` сохраняет annotated tag, точный source, атомарность ref-записи и FF main. Теги не передвигаются при повторе. |
| Тело GitHub release из авторских текстов | release-notes / user-stable-changelog | Подготовка читает тексты из точного кандидата; publisher получает уже готовое тело. Пустая строка или текст соседнего checkout не подменяют выпуск. |

| «Выпущено в…», ссылки и очистка статусных меток | release-bookkeeping | Комментарий с маркером тега, release и RU/EN changelog; затем снятие S-меток и закрытие. Повтор не дублирует комментарий. Ссылка на старый exact-SHA Validate не требуется. |
| Вернуть выпущенную историю и исправления в dev | Новое требование отдельных release-веток | `lib/return-worker.mjs`: отдельный worktree/служебная issue, обычная очередь и `finish`, подготовка зависимостей на S6, проверка фактического включения опубликованного тега. Чистый merge использует ранее принятое ревью; конфликт/дефект остаётся видимым, не переписывается автоматически. |
| Сохранить последнюю beta-ветку и убрать предыдущую | Новое согласованное требование | После новой успешной беты удаляется только прежний ref с прежним точным SHA. Если он изменился, ветка сохраняется и показывается pending. Последняя опубликованная бета остаётся доступной для stable. |
| Telegram stable/hotfix | release.yml → announce.yml | `lib/notifications.mjs` вызывается завершением выпуска и передаёт авторский RU пользовательский changelog. Beta молчит. Receipt отправки хранится в существующем release state. |
| Довести публикацию до результата | Старые связанные release jobs | `publish-prepared` вызывает общий `completePublishedRelease`: публичная доставка → issue bookkeeping → stable Telegram → прежняя beta-ветка → возврат в dev. Повтор `complete-release` продолжает только незавершённые действия. Если Telegram-секреты доступны только в Actions, ручной `process-next-release-complete.yml` продолжает тот же кандидат через эту же функцию. Один выпуск ведёт один вызывающий агент; повтор запускается после завершения предыдущего вызова. |

Сбой вспомогательной операции не делает состоявшуюся публикацию «неопубликованной».
Итог показывает конкретное pending-действие. Для Telegram сохранённый `sent`
не отправляется второй раз; известный отказ повторяется отдельно. Если ответ на POST
потерян, результат помечается `uncertain`: сначала выяснить, появилось ли сообщение,
а не слепо размножать его. Это честная граница транспорта, не обещание exactly-once.

Авторские тексты не генерируются из названий коммитов и не пишутся дополнительной
модельной джобой. Скрипты подготавливают/переносят уже написанный агентом результат.
Запись необходимости обновления E2E также остаётся обязанностью исполнителя.

## Уведомления, фон и отдельные инструменты

| Действие | Подготовленный маршрут | Граница |
|---|---|---|
| Ночные мутации частями | `templates/background.yml` → `background-job.mjs` → общий mutation-профиль | Ротация по UTC-дате, по умолчанию 5 частей; размер настраивается `PROCESS_NEXT_MUTATION_SHARDS`. Это фон, не проверка задачи/beta/stable. |
| Issue об отказе ночных мутаций | `lib/background.mjs` и существующий formatter mutation-gate-report | Открытая issue дополняется, повтор того же запуска не создаёт дубль. Ручной диагностический dispatch не спамит issue. Инфраструктурные отказы не отправляются в пользовательский Telegram. |
| JS/TS coverage | Независимая background job вызывает `coverage-diagnostic.mjs`, сохраняет и частичные отчёты | Без порога и влияния на выпуск; это не backend coverage, порог которого остаётся перед stable. |
| Скриншоты документации | Сохраняются отдельный ручной `docs-screenshots.yml` и адресное принятие | Не запускаются от обычной правки документации; картинки не принимаются ботом автоматически. |
| Контекст/история результатов | Полный issue-отчёт, runner artifacts и существующее состояние | Наличие текста или артефакта не выдаётся за живую проверку API и не создаёт второй процесс принятия задачи. |

Перед удалением старой обвязки из мутационного реестра и diagnostic coverage
убираются retired инфраструктурные тесты и ссылки на удаляемые механизмы.
Содержательные продуктовые проверки в смешанных файлах сохраняются.
Новый фон не должен незаметно восстановить полный старый tooling.

## Что намеренно не переносится

- Старые Validate-круги, полные проверки на каждом push/rebase и CI-дубликаты
  принятого локального результата.
- Ночной полный Validate, его night-red предупреждения и отдельное пакетное
  ревью ship: исходные механизмы согласованно удаляются.
- Еженедельный сбор старой процессной статистики и full-performance на push.
  Замеры размеров/времени выполняются в согласованном выпускном профиле.
- Старые обязательные ratchet/budget потолки на каждой задаче, сертификаты,
  seals и метапроверки результатов ревью.
- Обязательное сохранение каждого ревью в Git/индекс. Постоянный отчёт остаётся
  в issue; 60-дневный artifact не является единственной копией текста.
- Автоматическое принятие golden/производных файлов без просмотра.

## Что проверено и что ещё требует подключения

Сопоставление старых и новых действий выполнено по исходникам. Реализация
проверяется автономными тестами обработчиков, подставными GitHub/HACS/Telegram
и временными Git-репозиториями: повтор после сбоя, фактический состав,
переходы меток, сохранение цикла milestone, транспортный receipt и возврат истории.

Живые GitHub Actions, права/секреты, HACS, Telegram, Opus, расписание и выпуск
настоящего продукта **не проверялись** этим автономным прогоном. Эти границы
не меняют факта отсутствия активации. Полные продуктовые beta/stable наборы
и принятие визуальных эталонов также не объявляются выполненными.

Следующий этап — отдельная команда владельца на подключение по [CUTOVER.md](CUTOVER.md).
Этот список не вводит новые тесты каждой задачи и не даёт разрешения публиковать
релиз или отправлять сообщения сейчас.
