## Находки

### Medium (в скоупе) — пропорция core/shell в контракте п.4 не согласована с действующей

**Файл:** тело issue #866, раздел «Контракт поведения — форма и общая
обводка», пункт 4.

**Формулировка ТЗ:** «Контрольные пропорции Flat берутся из исходного круга:
core `80/103 × s`... В production `s` определяется существующими effective
size/iconUnit/marker.size, а не новой пиксельной настройкой.»

**Факт в коде:** `src/styles/devices.styles.ts:114-116`:

```css
--dev-size: calc(var(--device-base-size, 2.25cqw) * var(--dev-scale, 1));
/* 101.5/80 is the package shell/core ratio, including its stroke. */
--device-shell-size: calc(var(--dev-size) * 1.26875);
```

`--dev-size` — это ровно то, что ТЗ называет «effective size/iconUnit/
marker.size» (производная от `device-base-size`/`dev-scale`), и это уже
сегодняшний диаметр core-иконки: core = `s` один-в-один, а не `80/103 × s`.
Существующее соотношение shell/core, задокументированное дважды (комментарий в
коде и `docs/DEVICE-PRESENTATION.md`, раздел «Face geometry»: «The 101.5/80
shell/core ratio»), даёт core = `80/101.5 × shell` ≈ 0.7882, а не `80/103`
≈ 0.7767 — разница **≈ 1.47 %**.

**Чем краснеет (конкретика):** контракт п.1 того же раздела прямо запрещает
менять core одиночного маркера: «Свободный одиночный маркер сохраняет нынешний
круглый core». Если реализация буквально возьмёт `s` = текущий core-диаметр и
применит `core = 80/103 × s`, одиночные маркеры **визуально сожмутся примерно
на 22 %** — прямое нарушение п.1 тем же коммитом, что обязан его соблюдать.
Если же `s` трактовать иначе (как некий независимый «эталонный» юнит дизайн-
референса, не совпадающий с production-переменной), то контракт этого нигде не
говорит, а AC1 требует geometry-assertion с допуском **≤ 1 CSS px** на
контрольных сценах 32/56/96 px: на 96 px расхождение 1.47 % — это ≈ 1.4 px,
то есть **больше заявленного допуска**, и тест, построенный по буквальному
п.4, не сможет одновременно пройти и совпасть с текущим, неизменным рендером
core. Значение «103» не входит ни в один из существующих канонов (значение в
коде — 101.5) и не перечислено в финальном блоке «принято предположительно,
поменять свободно» — то есть не помечено как допущение, а заявлено как факт
контрольной пропорции.

**Почему это находка, а не придирка:** AC1 и AC2 — главные критерии приёмки
задачи (геометрическое соответствие макетам, допуск в пикселях); если число,
на котором построена их арифметика, расходится с уже закреплённым production-
значением и контракт не объясняет, как это согласовать с запретом трогать
core, автор реализации и автор геометрических unit-тестов неизбежно выберут
разные интерпретации независимо друг от друга.

**Что нужно для зелёного:** один из двух вариантов явно записать в тексте
ТЗ — (a) «103» — это внутренняя единица измерения макета дизайнера,
не совпадающая с production-переменной `--device-shell-size` (1.26875×);
geometry-assertion AC1/AC2 сравнивает нормализованные контуры **между собой**
(референс↔референс, production↔production), а не смешивает две системы
единиц; core production-рендера по-прежнему равен `s` без изменений — либо
(b) число исправлено на `80/101.5`, чтобы совпасть с уже закреплённым
соотношением. Либо третий вариант — явно перенести решение в блок «принято
предположительно».

### Medium (в скоупе) — два новых i18n-ключа без описанной точки размещения

**Файл:** тело issue #866, раздел «i18n».

Объявлены четыре ключа: `editor.device_magnets` / `..._help`,
`editor.device_snap_wall` («К стене» / “Snap to wall”),
`editor.device_snap_join` («Общая обводка» / “Join outlines”). Раздел «UX и
доступность» и «Представления плана» описывают **только один** видимый
элемент управления — переключатель «Магниты» (`editor.device_magnets`) с
подсказкой (`editor.device_magnets_help`) в «существующей стабильной панели
Devices». Нигде в ТЗ не сказано, где на экране появляются тексты «К стене» и
«Общая обводка»: не tooltip, не aria-label, не отдельный переключатель (отдельные
переключатели explicitly отвергнуты решением владельца M — «Переключатель и
Alt только для стен и соседей» говорит об одном переключателе, не о двух).

**Чем краснеет:** AC10 требует «EN/RU новые тексты соответствуют согласованному
охвату» и проверяется `unit/i18n`-тестом, но без названной точки размещения
такой unit-тест может только проверить наличие строки в словаре, а не то, что
она действительно показывается человеку в предсказанном месте — то есть сам
критерий AC10 для этих двух ключей не формулирует наблюдаемый результат
(нарушение требования §7.1 "что человек увидит" для **новых** строк).

**Что нужно для зелёного:** добавить одно предложение, где именно появляются
`device_snap_wall`/`device_snap_join` (например: aria-label на painted-контуре
во время direction-specific preview, или диагностическая подпись в превью
диалога устройства), либо удалить ключи из ТЗ, если они не нужны для
заявленного единственного переключателя.

## Что проверено и корректно

- Обязательные разделы §7.1 присутствуют и в нужном порядке: сценарий → что
  человек увидит → проблема/основание → скоуп/не-скоуп → контракт поведения
  (форма+обводка, стены+наклон) → UX и доступность → представления плана →
  перемещение/отмена/Undo → модель данных/миграция → i18n → AC1…AC10 с методом
  доказательства у каждого → план автотестов/гейтов → производительность/touch
  → файлы и модули → риски → откат → release-артефакты → явный блок решений
  владельца и технических допущений.
- Продуктовые развилки (форма, перемещение связки целиком, наклонные стены,
  область действия переключателя «Магниты», поведение 2.5D) отвечены владельцем
  буквальными цитатами в теле issue и в комментариях `6217465451`,
  `6217946233` — старые Q1–Q3 из черновика 12.10 явно объявлены неактуальными,
  претензий к процессу эскалации нет.
- AC1 прямо требует production-renderer, а не demo-renderer дизайнера, явно
  запрещает «похоже на глаз» и смену golden baseline как доказательство —
  закрывает типичный обходной путь для этой категории задач (сравнение с
  визуальным референсом).
- Защитные случаи (скрытая/короткая стена, проём, диагональная близость без
  контакта, конфликт spacing/grid, NaN/Infinity/чужой space/ACL/rev-конфликт,
  late ACK после release) перечислены как часть соответствующих AC (AC2, AC3,
  AC4, AC7), с указанием ожидаемого отрицательного исхода, а не абстрактным
  «валидация сохраняется».
- Контракт корректно ссылается на существующие контракты вместо изобретения
  новых: 44×44 px floor и painted-ownership (`DEVICE-PRESENTATION.md`),
  6/10 px у #873 (`device-spacing.ts`, `SPACING_R_IN/OUT`), touch-контракт
  View/kiosk vs best-effort editor (`TOUCH-SUPPORT.md`), сохранение плиток
  #649 и их 1.12×/lift/edge/shadow в 2.5D (`ISOMETRIC.md`, Stage 6) — числа и
  формулировки совпадают с канонами дословно.
- Перечисленные файлы класса A существуют в дереве репозитория на материальном
  SHA `e9ce1963`.
- Пороговые значения захвата/отпускания в CSS px (6/9 wall, 14/22 device) —
  не нашёл прямого источника в дизайнерском архиве (архив вне ревью, ссылка
  внешняя), но это согласуется с установленной в проекте практикой: подобные
  пороги (6/10 у #873, 8/12 у node-move #803/#885) неизменно задаются автором
  ТЗ технически, без отдельного продуктового вопроса владельцу — не нахожу
  оснований требовать здесь иное.
- Откат описан предметно (обратный коммит, без миграции, старое представление
  восстанавливается из тех же координат) — не формальная отписка.
- Release-артефакты корректно отделяют текущее поручение (ТЗ + ревью,
  остановиться на S5) от будущей реализации (ledger `866.json`, changelog,
  milestone 1.82) — не предвосхищает release-ledger решение, которое
  принимается на code-review этапе.
- Ни одного открытого продуктового вопроса к владельцу в тексте не осталось;
  оба оставшихся на 16.10 вопроса (объём переключателя, поведение 2.5D)
  отвечены и зафиксированы с явным указанием, какой вариант **не** принят.

## Чего не проверял

- Не прогонял `npx tsc --noEmit` / `npm test` / `npm run build` — на этапе spec
  нет кода, нет диапазона `git diff`, реализация не поручена; эти гейты
  относятся к code-review (§2.7), не к ревью ТЗ (§2.4).
- Не открывал архив дизайнера (zip, внешняя ссылка user-attachments) — ТЗ
  явно трактует его как не-нормативный для реализации артефакт («дизайн-
  референс, не готовый production-патч»); ревью ТЗ по §2.4 проверяет текст
  issue, а не сторонний файл, который к тому же недоступен инструментам
  ревью без скачивания стороннего URL.
- Не воспроизводил скриншоты/golden — на этапе spec зависимости и Chromium не
  устанавливались (явно оговорено в задании), а AC1/AC8 с golden проверяются
  при реализации, не сейчас.
- Не проверял сам факт прогона `spec-format-check.mjs`, упомянутого автором —
  это процессное самозаявление автора, не предмет содержательного ревью ТЗ.
- Не оценивал производительность (AC9) и выбор конкретных структур данных для
  spatial-индекса — это инженерная реализация, вне объёма ревью ТЗ; сам текст
  формулирует наблюдаемый бюджетный критерий («раньше/после на сопоставимом
  материале», «не заново по каждому pointermove»), чего достаточно для DoR.

## Итог

Структура ТЗ полная, обе продуктовые развилки отвечены владельцем, AC
пронумерованы и у каждого указан способ доказательства — формально документ
готов к «Готово к разработке». Но два пункта контракта содержат либо числовое
рассогласование с уже закреплённым production-значением (п.4, угрожает самому
AC1/AC2), либо необъяснённое назначение новых строк (i18n-ключи
`device_snap_wall`/`device_snap_join`) — оба в скоупе этой же задачи и
устранимы правкой текста ТЗ без нового обсуждения с владельцем (это
технические уточнения, не продуктовые вопросы). High-находок нет.

**Вердикт: жёлтый.**
