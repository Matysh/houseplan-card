# SPEC-REVIEW-918-r1

Issue: #918 «Пылесос движется на плане без следа: сохранённые точки не доходят до отображения»
Этап: spec (ревью ТЗ, PROCESS.md §2.4) · Трек: `track:ask` · Заход: r1 · блокирующих циклов израсходовано 0 из 4
Материал: тело issue #918, раздел `## ТЗ`, редакция «после механической проверки, 17.10.2026»,
сверено против принятого `dev@104a63f1e218eede610dd621a62346ceb3eab2e6` (текущий HEAD рабочей копии).
Вердикт: **зелёный**.

## Скоуп

Дефект: при явном `map_routes` (root-камера и отдельная route-камера на другой карте)
новые валидные точки пути пылесоса сохраняются, но не считаются принадлежащими текущему
`run` и не отображаются («9/9/0»); диагностика не называет причину. ТЗ фиксирует контракт
«один владелец записи», безопасный переход orphan→identified run, согласованное отображение
значка/пути/подсказки и понятную причину отказа в диагностике. Работа закрывает J1/J6 из
`docs/SCOPE.md` (достоверный живой обзор дома и устойчивость уже настроенного плана).

Это первый содержательный раунд: до него была только механическая (форматная) проверка
заголовков разделов, не вызывавшая модель и не тратившая цикл (сама же issue это явно
фиксирует: «Механическая подготовка ревью не пройдена… цикл не израсходован» →
«исправлены все пять замечаний… Первая попытка не вызывала модель»). Раздел «Повторный
раунд» (PROCESS.md §2.10) здесь неприменим — предыдущего содержательного вердикта нет.

## Как проверялось

1. Прочитан канон в предписанном порядке: `docs/SCOPE.md`, `AGENTS.md`,
   `docs/process/REVIEWER.md`, тело issue #918 целиком (включая аналитику 16.10 и
   уточнение 17.10, предшествующие разделу `## ТЗ`), `docs/VACUUM.md` (канонический
   документ подсистемы), выборочно `docs/USER-GUIDE.ru.md` (раздел «Позиция и путь»,
   «Диагностика», термины «путь»/«след»/«получено/сохранено/нарисовано»),
   `docs/CONFIG-COMPATIBILITY.md` (общий принцип реестра полей и read-policy).
2. Сверены обязательные разделы ТЗ (PROCESS.md §7.1) построчно с телом issue.
3. Каждый AC1…AC8 разобран на однозначность критерия, названный способ доказательства
   и отрицательный соседний случай (таблица ТЗ уже содержит третью колонку
   «Доказательство и отрицательный соседний случай» для каждого AC — это превышает
   минимум §2.5, где обязателен только способ доказательства).
4. Сверен пункт DoR-чеклиста (§2.5): файлы/модули, i18n ключи en+ru, миграция/
   совместимость по `CONFIG-COMPATIBILITY.md`, performance, touch (`TOUCH-SUPPORT.md`),
   release-артефакты, откат, открытые продуктовые вопросы — против текста ТЗ.
5. Отдельно проверено на внутреннее противоречие: соотношение между новым правилом
   «точная пара source+map_id» (пункт 1 контракта) для identified-run-ownership и уже
   задокументированным в `docs/VACUUM.md` read-time усыновлением доread-#162 orphan-ранов
   по `map_id`, суженному по `vacuum.source` маркера («it is adopted at read time by the
   routes of the same marker whose map_id matches, narrowed by the marker's root
   vacuum.source»). Вывод: конфликта нет — это разные механизмы. VACUUM.md описывает
   одноразовый grandfather-путь для ранов, записанных до появления `map_routes`;
   контракт ТЗ (пункт 3) правит текущую recorder-логику (`trails.py`
   `same_run_identity`/`ensure_run`), которая у репортёра продолжает orphan-ran *сейчас*,
   уже в эпоху `map_routes`, что и является багом. AC1 явно проверяет, что старые orphan-
   точки НЕ подхватываются задним числом новым identified run — значит переход
   согласован и не переписывает grandfather-сценарий для настоящего legacy-only случая.
6. Код не менялся (этап spec), поэтому `tsc`/`npm test`/`npm run build` не гоняются —
   они не относятся к материалу ревью этого этапа (тело issue, не диапазон коммитов).
   Инструмент предреализационных гейтов (`npm run gate:small`, pytest, invariants,
   golden) к спецификации неприменим: класса A/B диффа нет, Chromium/зависимости на
   этапе spec не ставились (#696). Сверено, что это предусмотрено и прямым текстом
   задания на этот прогон.
7. `REVIEW_FINDINGS_POLICY` сверен с доверенным снимком из промпта — совпадает дословно
   (`mode=issues`, issue 918, stage spec, round 1); расхождений нет, маршрут не менялся.

- Все обязательные разделы ТЗ присутствуют и отвечают на два продуктовых вопроса первыми
  (сценарий, что видно до/после), без терминологии реализации.
- Каждый AC однозначен, проверяем и указывает способ доказательства плюс отрицательный
  соседний случай — требование §2.5 выполнено с запасом.
- Контракт поведения (8 пунктов) непротиворечив внутри себя и согласован с
  `docs/VACUUM.md` (route identity, fail-closed статусы `ambiguous`/`unmapped`/
  `missing_space`, политика current/previous, teardown/generation, лимиты и смягчение).
- UX-формулировки и предложенные i18n-строки согласуются с терминологией
  `docs/USER-GUIDE.ru.md` (раздел «Позиция и путь», «Диагностика»: «путь», «след»,
  «получено/сохранено/нарисовано» уже используются в этом же смысле).
- Технические допущения вынесены отдельным блоком «принято предположительно, менять
  свободно на техническом ревью» — ревьюер кода вправе их оспорить без возврата к
  владельцу.
- Release-категория названа («stable-fix относительно v1.81.0»), является авторским
  суждением (не выводом из `User-Visible`), согласуется с характером правки
  (внутрибетный баг-фикс одной уже выпущенной функции, не инфраструктура и не новая фича).
- Отрицательных примеров достаточно у каждого защитного пункта контракта (6 из 8 пунктов
  контракта — защитные/fail-closed; для всех назван соответствующий AC с отрицательным
  случаем).

## Чего не проверял и почему

- **Не исполнялся код.** Этап — ревью ТЗ; реализация не начата, диапазон коммитов для
  код-ревью отсутствует. `typecheck`/`npm test`/`npm run build`/`gate:small` не относятся
  к материалу этого ревью (материал — текст issue, не git-диапазон) и не запускались.
- **Не проверялась работоспособность предложенного исправления** — она не существует;
  AC1–AC8 будут перепроверены исполнением на этапе код-ревью (§2.7), включая обязанность
  убедиться, что тесты умеют падать на названных отрицательных свидетелях.
- **Не запрашивались и не оценивались дополнительные данные от репортёра** — владелец
  прямо закрыл это направление 17.10.2026; синтетических сценариев и уже выполненных
  аналитических проб (16.10, зафиксированы в комментарии) достаточно для DoR.
- **Golden/скриншоты и performance** не прогонялись — на этом этапе нет диффа, который
  можно было бы прогнать; ТЗ корректно называет `ci:golden` как будущее требование
  реализации, а не как гейт этого ревью.
- **Ручная dev/GPU-приёмка** не запрашивалась и не требуется (решение владельца 2026-10-16,
  #929) — отсутствие её не является находкой.
