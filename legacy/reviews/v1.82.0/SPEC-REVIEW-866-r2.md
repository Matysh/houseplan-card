## Закрытие раунда r1

| Находка r1 | Чем закрыта | Где это видно |
|---|---|---|
| **M1** — пропорция core/shell в п.4 (103 vs 101.5) конфликтовала с production и грозила AC1/AC2 (п.1 запрещает менять core, допуск ≤1 px на 96 px сцене) | Текст п.4 переписан: `Sref`/`Dref` прямо объявлены единицами прототипа дизайн-референса, не совпадающими с production-переменной; production `D = --dev-size` остаётся без умножения на 80/103 («без умножения на 80/103 и без нового уменьшения»); существующий `Sprod = 101.5/80 × D` (=1.26875×D, тот же коэффициент, что в коде) сохранён буквально. Калибровка `D = 80/103 × Sref` ограничена ролью синтетической capture-сцены для сопоставления с 32/56/96-px референсом, а не правилом рендера. Известное расхождение явно посчитано: на `Sref=96` `Sprod=94.602`, то есть **0.699 px на сторону** относительно общего core-центра — меньше заявленного допуска ≤1 CSS px; на 32/56 абсолютная величина меньше пропорционально. AC1 прямо запрещает накопление ошибки по длине ряда и отдельную подгонку каждого участника, фиксирует отдельный regression-oracle свободного одиночного маркера на `Sprod=1.26875×D` | Тело issue, раздел «Контракт поведения — форма и общая обводка» п.4 (оба абзаца); AC1 (абзацы 1–2). Проверка арифметики: `101.5 × 96 / 103 = 94.6019…`, `(96 − 94.6019) / 2 = 0.69903` — совпадает с числом в тексте и с заявленным в комментарии автора |
| **M2** — `editor.device_snap_wall`/`device_snap_join` объявлены без описанной точки показа, AC10 проверял только наличие ключа | В «UX и доступность» добавлено предложение: подпись появляется в **guides-слое**, только во время выбранного wall/device snap, у соответствующей направляющей, «вне полной оболочки с бейджем», не закрывает core/значение, не перехватывает указатель; явно описаны появление/снятие (вместе с направляющей, по release/cancel/bypass/отсутствию contact proposal) и взаимодействие с #873 (при spacing proposal новые тексты не рисуются, остаются старые подписи). AC10 дополнен видимым oracle: «Для обоих языков smoke реально показывает «К стене»/«Общая обводка» либо их EN-эквиваленты у contact guide во время соответствующего snap … Наличие ключа в словаре не заменяет этот видимый oracle» | Тело issue, раздел «UX и доступность», абзац 2 («На время drag…»); AC10, предложения 3–4 |

Обе правки — текстовые уточнения в скоупе прежней задачи, без нового
продуктового вопроса и без отката уже данных владельцем ответов — ревью не
требовало эскалации к владельцу ни по одной из них.

## Что проверено и корректно

- Арифметика новой калибровки п.4 самосогласована и действительно укладывается
  в заявленный допуск ≤1 CSS px на всех трёх контрольных сценах (32/56/96),
  а не только на той, что фигурировала в примере r1.
- Новый коэффициент `Sprod = 101.5/80 × D` дословно совпадает с константой
  `1.26875` в `src/styles/devices.styles.ts:116`, то есть п.4 больше не
  противоречит коду, который должен остаться неизменным по его же п.1.
- Размещение i18n-строк теперь описывает наблюдаемое поведение (где, когда
  появляется/исчезает, в каких случаях не рисуется вместе с чем), что делает
  AC10 проверяемым native-смоком, а не только словарным тестом.
- Автор не расширил скоуп и не тронул решения владельца M/V при исправлении —
  проверено текстовым сравнением соответствующих абзацев с цитатами r1.

## Чего не проверял

- Не прогонял `npx tsc --noEmit` / `npm test` / `npm run build` — на этапе spec
  нет кода и диапазона `git diff`; эти гейты относятся к code-review (§2.7), не
  к ревью ТЗ (§2.4), и этот раунд правок не меняет это основание.
- Не открывал архив дизайнера — так же, как в r1, это внешний не загруженный
  инструментами ревью файл; формульная калибровка в п.4 проверена арифметически
  по числам, явно приведённым в самом тексте issue, без обращения к архиву.
- Не воспроизводил golden/скриншоты для AC1/AC8 — зависимости и Chromium на
  этапе spec не ставились, а это не меняющийся с r1 факт.
- Не проверял фактический визуальный вид новой guide-подписи (AC10) — это
  поведение будущей реализации, доказывается native smoke на code-review, а не
  текстом ТЗ.
