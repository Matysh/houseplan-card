## Находки

### Medium (в скоупе) — «Затронутые модули»/модель данных не называют три
бэкенд-контракта, которые молча потеряют новые поля пространства

**Раздел ТЗ:** «Модель данных, миграция и обязательные различия», «Данные
сравнения и намеренные различия», AC3/AC4 — нигде не упомянуты backend-файлы,
хотя раздел прямо вводит новые/переименованные поля хранения пространства:
`card_name_scale`, `card_label_scale` (взамен единого `card_font_scale`) и
новое поле локального режима заряда устройств пространства (`s-battery-mode`,
цепочка «общие → пространство → устройство»).

**Суть:** у House Plan есть три независимых backend-поверхности, каждая со
своим явным allow-list полей пространства, и ни одна не содержит новых/
переименованных имён:

1. `custom_components/houseplan/import_export.py:93-99` —
   `_SPACE_DISPLAY_FIELDS = ("show_borders", …, "card_font_scale", "north_deg",
   "sun_rays")`. Это ручной тuple, используемый экспортом/импортом конфигурации
   пространства (сам ТЗ ссылается на #439/#442 — «достоверность сохранения» —
   как на связанные задачи). `card_name_scale`/`card_label_scale`/новое поле
   заряда в этот tuple не попадают ни явно, ни по старому имени.
2. `custom_components/houseplan/support_package.py:200-227` —
   `_space_settings()` вручную копирует фиксированный список ключей
   (`_copy_keys(value, ("show_borders", …, "card_font_scale", …))`) в пакет
   поддержки; те же три поля в список не входят.
3. `custom_components/houseplan/support_wire_schema.py:307-322` —
   `SPACE_SETTINGS = Object({...})`, закрытая схема диагностического снимка
   (`validate()` в строках 1050-1056: `set(value) - rule.fields.keys()` →
   `raise WireRejected`, если в объекте есть незнакомый ключ). Текущий список
   содержит `card_font_scale`, но не содержит новые поля.

**Чем краснеет:** это доказывается чтением, не исполнением — окружения для
`pytest tests_backend` на этапе spec нет (см. «Чего не проверял»), а кода
реализации ещё не существует, выполнять мутацию не на чем. Логический вывод
из самого кода детерминирован: `_SPACE_DISPLAY_FIELDS` и `_space_settings()`
— explicit allow-list copy (`_copy_keys`/кортеж полей), поэтому любое поле вне
списка проходит через них молча отброшенным, без исключения — это вытекает из
самой структуры функции (`_copy_keys` копирует только перечисленные ключи), а
не из домысла о поведении. Для `SPACE_SETTINGS`/`validate()` поведение на
лишнем ключе — `WireRejected`, что прямо следует из `set(value) -
rule.fields.keys()` на строке 1053. Ни один из этих трёх путей сейчас не
покрыт тестом, завязанным на набор полей пространства (в отличие от
прецедента #943, где `tests_backend/test_support_package.py` подобный дрейф
хотя бы ловил для `fill_colors`) — `grep -rln card_font_scale tests_backend/`
не находит ни одного файла.

**Эффект на пользователя, если не исправить до реализации:** пользователь
меняет независимые размеры названия/показателей или собственный режим заряда
устройств пространства → экспортирует конфигурацию пространства (функция,
про достоверность которой уже есть отдельные задачи #439/#442) → при импорте
назад эти два-три значения не восстановятся (тихая потеря данных, прямое
нарушение духа `docs/SCOPE.md` «никогда не терять данные пользователя по
умолчанию», хоть это не про файлы) **или** формирует пакет поддержки для
диагностики проблемы с размером/зарядом → в пакете этих полей не будет, и
отчёт о проблеме окажется неполным именно там, где нужен. Валидация записи
(`validation.py`, `extra=vol.ALLOW_EXTRA`) не пострадает — обычное сохранение
не ломается, поломка исключительно в двух производных контурах (экспорт/
импорт и пакет поддержки).

**Почему это находка ТЗ, а не мелочь реализации:** PROCESS.md §2.5 (DoR)
требует «перечислены затронутые файлы и модули» как самостоятельный
обязательный пункт, отдельно от §7.1 секций. Раздел «Решения по
совместимости для реализации» детально разбирает миграцию `show_borders`/
`hide_openings` и фон/glow-совместимость, но не упоминает ни один из трёх
файлов выше ни разу во всём теле issue (проверено `grep` по полному тексту).
Ровно такой же класс пробела уже был найден ревью #943-r1 (см.
`docs/reviews/SPEC-REVIEW-943-r1.md`, находка про `support_package.py`/
`support_wire_schema.py`) и признан Medium в скоупе — это не новый прецедент,
а повторяющийся класс риска для задач, переименовывающих/добавляющих поля
пространства.

**Предлагаемое исправление ТЗ:** одним абзацем в «Модель данных, миграция и
обязательные различия» и ссылкой в AC3/AC4 — назвать
`import_export.py::_SPACE_DISPLAY_FIELDS`,
`support_package.py::_space_settings()` и
`support_wire_schema.py::SPACE_SETTINGS` как затронутые модули, требующие
добавления `card_name_scale`/`card_label_scale`/нового поля заряда (с
сохранением обратной совместимости по `card_font_scale` там же, где она уже
описана для рендера), и явно включить backend-тест экспорта/импорта и/или
пакета поддержки пространства с новыми полями в доказательства AC3/AC4.
Заодно стоит одной строкой упомянуть `scripts/config-field-registry.mjs`
(`docs/CONFIG-COMPATIBILITY.md`) — три новых/переименованных поля являются
ровно тем видом compatibility-дебта, который реестр должен покрывать, хотя
отсутствие записи там не ломает рантайм.

Это единственная находка цикла; High-находок нет. Находка целиком лежит в
скоупе задачи — это та же модель данных пространства, которую ТЗ и так
переопределяет, а не чужая задача.
