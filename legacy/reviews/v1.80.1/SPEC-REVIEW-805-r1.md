## Скоуп

Чистая оптимизация стартового графа View без изменения видимого поведения:
перенос CSS-правил, которые использует **только** ленивый editor runtime, из
`src/styles/dialogs.styles.ts` и `editorSecondaryStyles` (сейчас в `static
styles` карточки) в новый ленивый лист, вносимый конструктором
`HouseplanEditorRuntime` через существующий `EditorRuntimeLoader`. Служит
J1/J3 (`docs/SCOPE.md`, View — продукт для двух персон из трёх) через
снижение байт/CSS-правил, которые холодный View загружает и сопоставляет, не
применяя. Четыре кандидата исследованы и измерены на `origin/dev`
`7fbc97a2`; выбран кандидат «стили редактора» (−4 524 Б initial, +5 732 Б
lazy editor) вместо более крупного по байтам, но рискованного для живого
first-frame пылесоса. Не-скоуп по тексту ТЗ: стили редактора в
`plan.styles.ts`/`chrome.styles.ts`, мёртвые правила, живой пылесос, плоские
солнечные лучи, live radar, EN/RU словари, Glow, `polyclip-ts`/`bignumber.js`,
#763 (ошибочная загрузка редактора в киоске) — явно каждый пункт обоснован
отдельным измерением или ссылкой на смежную задачу.

## Находки

### High

Нет.

### Medium (в скоупе)

**M1. Открытый продуктовый вопрос без `blocked` и без батч-комментария
владельцу (§7.1, §2.5).** «Вопрос 1. Обмен байтами» в разделе «Вопросы
владельцу» — по тексту ТЗ прямо продуктовый («какая персона важнее при
конфликте»: домочадец на холодном View выигрывает на каждой загрузке, админ
при первом открытии редактора проигрывает один раз за загрузку страницы) и
при этом **существенный**: сама ТЗ говорит «при «нет» кандидат теряет смысл,
потому что любой вынос CSS редактора переносит его в граф редактора» — то
есть отрицательный ответ владельца обесценивает весь выбранный кандидат, а
не одну деталь. §7.1 требует, чтобы, пока ответа нет, issue оставался в
текущем статусе с меткой `blocked` («статус не подменяется, `blocked` его
дополняет»); §2.5 (DoR) отдельным обязательным пунктом требует «открытых
продуктовых вопросов нет» до перехода к реализации. Ни то, ни другое не
выполнено: issue #805 уже на `S4-spec-review`, без `blocked`, и ни в одном
комментарии вопрос не задан владельцу отдельной пачкой — он есть только
внутри текста ТЗ с пометкой «по умолчанию: принять» и фразой в
занятии-комментарии «работа идёт по ним, пока владелец не скажет иное».
  - **Чем воспроизводится:** в тот же день, в том же репозитории, issue #792
    демонстрирует корректный паттерн для ровно такого случая — три цикла
    `labeled blocked` / `unlabeled blocked` (05:43–11:37 UTC, 2026-10-06),
    каждый раз с явным «До ответа — `S3-spec`/`S6-in-progress` + `blocked`;
    реализация и ревью не запускаются» и последующей фиксацией фактического
    ответа владельца в теле issue. #805 этот паттерн не повторяет: вопрос
    эквивалентной весовой категории (инвалидирует выбор кандидата целиком)
    идёт без `blocked`, без отдельного комментария, с пометкой «работа идёт
    по дефолту».
  - **Фикс:** один комментарий-пачка владельцу с Вопросом 1 (готовый текст
    уже есть в разделе ТЗ, можно скопировать), метка `blocked` поверх
    `S4-spec-review` (или возврат на `S3-spec` на время ожидания) до
    фактического ответа владельца; содержимое самого ТЗ менять не требуется.
  - Возврат автору, жёлтый вердикт — правка организационная, не меняет ни
    один AC и не требует повторного вычитывания ТЗ целиком.

### Low (снято ревьюером)

**L1. Вопрос 2 («Пересчёт потолка lazy editor») — технический вопрос,
ошибочно вынесенный владельцу (§7.1: «всё, чего пользователь не наблюдает,
агенты решают сами»).** Пересчёт `LAZY_EDITOR_GZIP_CEILING` не виден
пользователю ни в каком виде — это внутренний порог гейта сборки. Решение:
снимаю вопрос и отвечаю по существу сам, без обращения к владельцу.
Обоснование — десять предыдущих задач, трогавших этот же потолок (#600,
#608, #614, #642, #627, #618, #645, #663, #676, #798; все найдены в
комментариях-истории `scripts/bundle-budget.mjs` рядом с
`LAZY_EDITOR_GZIP_CEILING`), пересчитывали его той же формулой «факт +
≈1000 Б», полоса 2000 Б без изменений — ни разу не видно обращения к
владельцу или метки `blocked` ради этого шага; это рутинная, уже устоявшаяся
практика, а не решение с продуктовыми последствиями. Предложенный в ТЗ
default («разрешить», жёсткая граница +6 000 Б, формула без изменений)
совпадает с этой практикой один-в-один — **разрешаю**, никакого действия от
автора не требуется, кроме переноса записи из «Вопросы владельцу» в «Принято
предположительно» при следующей правке текста (не обязательно отдельным
циклом ради одного этого).
