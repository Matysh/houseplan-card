## Скоуп

Три остаточных дефекта lifecycle полной карточки и read-only space-card после
релиза v1.80.0-beta.8, источник — находки F37 (P1)/F38/F49 (P2) из
`findings-2026-10-06.md`, явно не дублирующие уже выпущенные #813 (первый
кадр нового проёма)/#814 (кэши)/#756/#762 (отложенный редактор):

- F37: `space-card.connectedCallback()` переподписывается на `onConfigChange`,
  но `willUpdate()` загружает конфиг только при `!this._snap ||
  !this._loadedOnce` — изменение конфигурации, случившееся во время detach,
  при attach не перепроверяется.
- F38: таймаут paint-barrier может подставить под новую геометрию снимок
  устройств старой геометрии (ложная «открытая» новая дверь).
- F49: поздний resume полной карточки может дёрнуть `_loadFromServer()` до
  появления `hass`, рискуя необработанной ошибкой.

Все три — прямое обслуживание J1 («живой» план), J2 («покажи, где не так» —
ложное состояние двери) и J6 («держать план актуальным», multi-client live
sync) из `docs/SCOPE.md`; конфликта со SCOPE нет. Поверхности — full card и
read-only space-card (которая по контракту п.6 ТЗ остаётся read-only — лок на
HA-запись не трогается, согласовано с «View mode is the product» и «lock
invariant» из SCOPE.md). Канон — `docs/WARM-REMOUNT.md` (§2.1, §5) и
`ARCHITECTURE.md` › Client side/Second card; touch View/kiosk заявлен
блокирующим по `docs/TOUCH-SUPPORT.md` корректно (View — гарантированная
touch-поверхность).

## Как проверялось

Ревью ТЗ на этапе `spec` не запускает гейты: зависимости и Chromium не
ставились (#696), продуктовый код для задачи не существует. Прочитаны
`docs/SCOPE.md` → `AGENTS.md` → `docs/process/REVIEWER.md` →
`docs/WARM-REMOUNT.md` целиком → PROCESS.md §2.3–2.5, §7.1, §4, §7.2.

Вместо исполнения — построчная сверка каждого фактического утверждения ТЗ о
текущем коде против рабочей копии на точном SHA, который сам ТЗ называет
базой анализа (`f623903e4037bc21897c2dc16d2cebe4b02a7eaa`, совпадает с
`git rev-parse HEAD`):

- **F37** — `src/space-card.ts:328-350` (`connectedCallback`): переподписка
  `onConfigChange` подтверждена построчно. `src/space-card.ts:399-409`
  (`willUpdate`): `if (this.hass && !this._loading && (!this._snap ||
  changed.has('hass'))) { if (!this._snap || !this._loadedOnce)
  this._load(); }` — при живом `_snap` и `_loadedOnce === true` условие
  `_load()` ложно даже когда `changed.has('hass')` истинно: пропущенное во
  время detach событие конфигурации на attach не перезапрашивается. Ровно то
  утверждение, которое несёт AC1 — подтверждено чтением, не домыслено.
- **F49** — `src/houseplan-card.ts:2662` (`connectedCallback`) и `:3211`
  (`setConfig`) зовут `_beginResumeSettle()` без проверки `this.hass`.
  `_beginResumeSettle()` (`:6522-6534`) при `!this._loading` зовёт `void
  this._loadFromServer()` тоже без проверки `hass`. `_loadFromServer()`
  (`:4248` далее) на первой же строке тела делает `this.hass.callWS(...)` —
  без optional chaining. Если `hass` ещё не передан (поздний resume), это
  `TypeError` внутри `async`-функции, вызванной через `void` без `.catch` —
  непойманный reject, ровно «необработанная ошибка» из текста ТЗ.
  Контрастная проверка: `src/space-card.ts:726` (`_load`) САМ начинается с
  `if (!this.hass) return;` — у space-card эта дыра уже закрыта, у полной
  карточки — нет. Подтверждает точность диагноза и его границы.
- **F38** — `src/houseplan-card.ts:3706-3753` и `src/space-card.ts:628-672`
  (`_settleContinuityFrame`, два независимых места, как и написано в ТЗ —
  «обе»): в ветке `!committed` обе версии делают `this._candidateDeviceSnapshot
  = null;` без отката уже принятой геометрии. `src/render-device-snapshot.ts:
  49-59` (`selectRenderDeviceSnapshot`): при `staged=false` и `candidate=null`
  `preferred = visible`; если `visible.geometry !== geometry`, `other =
  candidate` (`null`) — функция возвращает `preferred`, то есть старый
  snapshot под новой геометрией. Вручную прогнал эту чистую логику по тексту
  функции для входа `(visible-old, null, false, geometry-new)` — результат
  `visible-old`, совпадает с «pure probe» из текста issue дословно. Контракт
  п.3 ТЗ («неудачный paint не возвращает старый snapshot под новую
  геометрию») адресует именно эту ветку, не придуманную проблему.
- Файлы и смоки, перечисленные в скоупе (§4), существуют: `src/space-card.ts`,

### Low

**L1 (снято ревьюером).** AC2 («cold/short/long return, hass до/после
attach… detach до позднего hass») не называет прямым текстом, что это
сценарий именно **полной карточки** (`houseplan-card.ts`), в отличие от AC1,
которое явно пишет «space-card». Формально это можно прочитать как
применимое к обеим карточкам. Проверкой кода установлено: `_warmLongReturn`/
`_beginResumeSettle`/«cold/short/long return» — словарь `WARM-REMOUNT.md`
§2.1, принадлежащий исключительно `src/houseplan-card.ts`
(`grep` по `src/space-card.ts` не находит ни одного вхождения); у space-card
аналогичный путь (`_load()`) уже защищён собственной проверкой `!this.hass`.
Терминология однозначно идентифицирует поверхность для читателя, знакомого с
каноном (а ревьюер кода обязан его прочитать по `AGENTS.md`), поэтому это не
расходится на два разумных прочтения и не поднимается до Medium — снимаю с
записью, без действия для автора.
