неоднозначности или противоречия (не только «слово присутствует»):

- «Модули, модель данных и совместимость»: подтверждает п.58 ТЗ «новый
  изолированный модуль `previous_data.py`», уточняет источник чтения summary
  (`data.config.spaces` из HA Store-конверта, не `Store.async_load`, чтобы не
  спровоцировать миграцию) — техническая деталь, корректно не вынесенная
  владельцу (§7.1: «всё, чего пользователь не наблюдает, агенты решают сами»),
  согласуется с контрактом п.1 («чтение — без записи и без миграций»).
  `docs/CONFIG-COMPATIBILITY.md` подтверждает: новых полей схемы нет, «нет»
  — законное закрытие DoR-пункта о миграции/compatibility-полях.
- «План автотестов и защитные сценарии»: три пункта (unit, HA backend,
  отрицательные пробы) теперь покрывают сам мастер (меню → restore/fresh →
  user → CREATE_ENTRY, отмена на каждом шаге, i18n-покрытие), а не только
  функцию подсчёта N/M/даты, как было в r1 — это ровно предмет находки M1.2.
  Пункт 5 корректно откладывает таблицу «AC / чем доказан / чем краснеет» до
  хендоффа реализации (это требование код-ревью §2.7, не DoR этапа spec).
- «Риски»: перечисляет ровно те кандидаты, которых не хватало в r1 (`EXDEV`
  при разных точках монтирования, свободное место на диске, неатомарность
  нескольких `rename` при аварийном выключении, коллизия имени каталога,
  симлинки/выход за границы) и для каждого называет наблюдаемое поведение
  (откат уже перенесённого, abort без entry, ничего не удаляется, путь
  частичного архива в логе). Согласуется с «Принято предположительно»
  (которое в r1 уже описывало откат на середине) — не противоречит, а
  детализирует.
- «Производительность и touch»: явное «нет» для runtime View/FPS/WebSocket/
  bundle, порядок работы инвентаризации (`O(число файлов)` stat, JSON только
  для N, rename без побайтовой копии, executor а не event loop) и явное «не
  применимо» для touch/kiosk со ссылкой на `TOUCH-SUPPORT.md`. Закрывает ровно
  два пункта DoR (производительность, touch), оба явно.
- «Откат и release-артефакты»: «откат функции» (revert коммита/HACS) отделён
  от «возврата данных» (ручной перенос из архива с пошаговой инструкцией) —
  два разных смысла слова «откат» в этой задаче не спутаны. Release-артефакты
  перечислены с явным «нет» для golden/performance/security-бюджетов.

Рассмотрел отдельно (не входит в находки, см. «Что проверено»): ни один из
численных риск-сценариев в «Риски»/«План автотестов, п.3» (например, «ошибка
второго переноса → обратные rename») не получил собственного номера AC —
только текстовое описание в «Риски» и тестовый сценарий в «План автотестов».
Счёл это допустимым: DoR §2.5 требует, чтобы существовали пронумерованные AC
с доказательством, не чтобы каждый защитный сценарий риска стал отдельным AC;
«план автотестов» и «риски» — отдельные обязательные разделы §7.1 именно для
такого материала, и поведение в них описано однозначно (кто/что/как), не
расплывчато.
