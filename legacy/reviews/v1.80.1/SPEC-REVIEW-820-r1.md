## Скоуп

Новый шаг-меню в мастере добавления интеграции House Plan (`custom_components/
houseplan/config_flow.py`), решающий проблему: при повторной установке после
полного удаления записи интеграции и пакета HACS данные на диске остаются, и
старый план подхватывается без вопроса. Поверхность — исключительно
HA-мастер интеграции (`strings.json`/`translations/*.json`,
`docs/USER-GUIDE.ru.md`); карточка (`src/**`) не меняется — подтверждено
собственной аналитикой автора («поверхности — мастер интеграции HA,
`strings.json`/`translations`, USER-GUIDE; фронт карточки не меняется») и
перечнем «Где сейчас» в ТЗ, который называет только Python-модули бэкенда.

Первый вопрос по `docs/SCOPE.md`: задача не закрывает буквально одну из
J1–J7, но прямо обслуживает «Standing rule: never delete a user's file on an
inference» (SCOPE.md) — заменяет текущее implicit-поведение (старые данные
просто переиспользуются без вопроса, а ручная альтернатива — вручную стереть
файлы в `.storage`/`config/houseplan`, то есть без подтверждения и без
возможности передумать) на явный выбор администратора с обратимым архивом
вместо стирания. Это также прямо обслуживает J6 («держать план актуальным»
для персоны «домашний админ», которая переустанавливает интеграцию как часть
жизненного цикла дома) и даёт чистую точку входа в онбординг J4 («Начать с
чистого листа» → «онбординг первого пространства»). Конфликта со SCOPE нет;
вне-скоуп явно и верно исключает интерфейс удаления/восстановления из
`docs/SCOPE.md`'s «Out of scope» (регистронные UI, которые мы не строим) —
автор сам отметил это строкой «Вне скоупа».

## Находки

### High

Нет.

### Medium

**M1 (в скоупе).** ТЗ не закрывает несколько обязательных пунктов DoR §2.5 /
обязательных разделов §7.1 — не как расплывчатую формулировку, а буквально:
соответствующий текст отсутствует, в том числе в форме явного «нет».

1. **Способ доказательства назван не для каждого AC.** §2.5 требует: «у
   каждого [AC] указано, чем он доказывается: unit / backend / smoke / golden
   / «ревью кода»». В тексте issue это сделано только для AC1 («pytest config
   flow проверяет тип шага, порядок пунктов и плейсхолдеры») и AC5
   («существующий `test_ha_config_flow.py` зелёный»). AC2, AC3, AC4, AC6 и
   AC7 описывают проверяемое поведение (это не претензия к однозначности
   самого контракта — он последователен и фактически точен, см. «Как
   проверялось» и «Что проверено»), но ни один не называет, какой тест или
   какая команда его доказывает: неясно, один ли новый pytest-файл/класс
   покроет AC2–AC4/AC6 (restore/start_fresh/abort/corrupted — естественно,
   что это один набор сценариев config flow), или разработчик и ревьюер кода
   должны будут заново придумывать это распределение без опоры на ТЗ.
2. **Раздел «план автотестов» фактически не существует.** Единственный
   кусок плана — «юнит-тесты на пустой, обычный, повреждённый набор и набор
   «только архив»» в «Принято предположительно», и тот — только для функции
   подсчёта N/M/даты, не для самого мастера (меню, архивирование, откат на
   середине, abort). Для AC2–AC4/AC6 (ровно тех, что без метода доказательства
   в п.1) нет ни одного слова о тестовом покрытии.
3. **«Риски» не названы.** Ни общей фразой, ни перечнем. Кандидаты, которые
   ТЗ не рассматривает явно: перенос файлов между разными точками монтирования
   (`os.rename` между разными файловыми системами падает с `EXDEV` — контракт
   п. «Принято предположительно» говорит «rename, без копирования», но не
   говорит, что будет, если `config/houseplan/archive/` окажется на другом
   mount, чем `.storage/`/`config/houseplan/{plans,files,assets}` — для
   большинства инсталляций HA это один и тот же `config/`-том, но ТЗ этого не
   утверждает и не исключает); свободное место на диске при архивировании
   большого набора планов.
4. **«Откат» (DoR: «как выключить или вернуть назад») не назван.** Это не
   новый персистентный формат и не флаг Labs — вероятный ответ «откат = откат
   коммита/понижение версии HACS, на диске уже существующие файлы это
   поведение не меняет» тривиален, но в тексте ТЗ его нет в любой форме,
   включая явное «нет».
5. **Влияние на производительность не названо** — даже как «нет» (типовое
   закрытие для разовой операции при установке; без слова в тексте DoR-пункт
   формально не закрыт). Прямой прецедент того же вывода в этом проекте:
   `docs/reviews/SPEC-REVIEW-806-r1.md` вернул жёлтый вердикт ровно за один
   пропущенный DoR-пункт «влияние на производительность» при полностью
   однозначном во всём остальном ТЗ — этот ревью применяет тот же стандарт.

**Чем это плохо:** §2.5 говорит буквально «Если хоть один пункт не выполнен —
статус не «Готово к разработке», как бы ни хотелось начать» — перечисленные
пункты (1)–(5) не выполнены, не один, а несколько сразу; без способа
доказательства по AC2–AC4/AC6 код-ревью не сможет свериться с ТЗ, какой
именно тест обязан был появиться и мог бы «упасть» при регрессии (условие
код-ревью «ревьюер убедился, что тест умеет падать» требует названного
теста, которого сейчас не на что указать).

**Предлагаемый вариант по умолчанию** (техническое дополнение текста, не
продуктовый вопрос владельцу): дописать к каждому AC2–AC4/AC6/AC7 конкретный
метод (например, «backend: новый сценарий `test_ha_config_flow.py`» для
AC2–AC4/AC6, «ревью кода» для AC7 — docs/changelog), добавить короткий пункт
«план автотестов» (какие файлы/новые сценарии появятся), и закрыть
«риски»/«откат»/«производительность» явными короткими фразами (при
необходимости — явным «нет» с одной причиной, как это уже сделано в
`SPEC-REVIEW-804-r1`/`802-r1` для похожих по размеру задач).

Находка **в скоупе задачи** (правит тот же текст ТЗ, не чужой скоуп) → не
заводится отдельным issue, возвращается автору жёлтым вердиктом.
