## Скоуп ревью

Задача — продолжение серии геометрической перф-гигиены (#769 закрыт, #789 закрыт,
#778 закрыт, #805 открыт параллельно по соседнему скоупу lazy CSS). Скоуп этой
задачи — три независимых правки:

1. **Opening/sun инвалидация** (`_openingWallIndexFor`, `_renderSunRays`) — убрать
   `_cfgEpoch` из ключа и заменить на полный отпечаток фактических входов
   (комнаты/стены/cuts/масштаб для opening; геометрия/окна/occluders/north/
   azimuth/elevation/origin/нулевые стены/Iso-параметры для sun), чтобы правка на
   чужом этаже и HA-only update не инвалидировали кэш.
2. **Межэтажный пул тел/туннелей** (`_physicalBodiesCache`, `_openingTunnelCache`) —
   сейчас односоточные (один `{key, ...}` объект на карточку), заменить на LRU-пул
   по восемь записей, как уже сделано для `_openingWallIndexCache` (Map, лимит 4) и
   для `WALL_UNION_POOL_LIMIT` в `floor-geometry-key.ts`.
3. **Переиспользование union в resize** (`floorMinusBodies` →
   `unionBodies(bodies)` в `physical-geometry.ts:405`) — сейчас объединение тел
   пересчитывается на каждый вызов `floorMinusBodies`, то есть на каждую комнату
   внутри одного шага resize (`houseplan-editor-runtime.ts:3480`); закэшировать
   один union на неизменный набор тел на весь жест/шаг.

Видимая пользователю часть — J1 (переключение этажей на настенном планшете/
киоске без лишней повторной работы) и J6 (resize двух комнат с общей стеной,
живые площади). Обе работы уже закрыты продуктом; это оптимизация существующего
поведения, а не новая фича — соответствует «Partially covered»/tech-debt
трактовке `docs/SCOPE.md`, отдельной строки SCOPE для перф-гигиены не требуется,
конфликта со SCOPE нет. F19 (bignumber.js) и F27 (bundle ratchet) — audit-only,
не продуктовое поведение, не меняют видимую часть.

   editors — reference environment) не затрагивает touch-гарантии View.
   Отдельного вопроса владельцу не требуется — ТЗ верно трактует это как «нет
   нового touch-поведения».

   мемо экземпляра карточки, не персистентные данные.
7. **Открытых продуктовых вопросов.** Специально искал повод для хотя бы

   «принято предположительно, поменять свободно»); отсутствие численного
   порога ускорения в AC5 (сознательное решение — деterministic win доказан

   процента, последовательно с прошлой практикой проекта на perf-тасках).
   Оба решения не меняют то, что видит пользователь, и корректно остаются в
   компетенции агентов по §7.1.

## Находки

Нет High и Medium находок.

**Low (снято ревьюером, не блокирует).** AC1, первое предложение: «Для
opening/sun чужой этаж, общие метки вне записи текущего этажа и HA-only
update дают ноль построений» — синтаксически плотная формулировка, термин
«общие метки» нигде в кодовой базе не определён дословно (в отличие от
«запись» / floor record, который — установленный термин `floor-geometry-
key.ts`). Из контекста (контракт п.1 и параллельная структура AC2) смысл
восстанавливается однозначно: правка на другом этаже или объекте, не входящем
в отпечаток записи текущего этажа, не должна бампать счётчик построений
текущего этажа. Не поднимаю до Medium, так как (а) формулировка не меняет ни
один из семи перечисленных входов контракта, которые и определяют фактическую
проверку; (б) у AC1 уже есть точный список отрицательных свидетелей (возврат
эпохи в ключ, удаление значимого входа), которые однозначно проверяемы без
участия этой фразы. Исполнитель может читать «общие метки» как любой
общий/внешний относительно записи текущего этажа объект — трактовка не
сужает и не расширяет фактический контракт.
