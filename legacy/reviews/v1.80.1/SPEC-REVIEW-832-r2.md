## Скоуп

Без изменений к r1: фронтенд-баг в Resize (`src/resize.ts`,
`src/houseplan-editor-runtime.ts`) — рассинхронизация coalesced user-contour и
persisted `wall_ids` после первого коммита. Задача обслуживает J6 SCOPE.md.
r1 был зелёным (0 находок); r2 — не ответ на находку ревью, а авторский
self-audit **до пуша**: после r1-GREEN автор нашёл, что strict physical
preview PASS для independently rehydrated +2 не гарантирует прохождение
final-materialization/junction proof, потому что соседняя комната с общим
wall_ids содержит derived collinear seam vertex, который при материализации
может снова породить старый короткий atom. ТЗ уточнён до того, как что-либо
было запушено или код начал писаться по старой версии — пересмотр честный,
не постфактум-подгонка под уже написанный код.

## Как проверялось

Ревью по дельте (PROCESS.md §2.10): предмет раунда — именно изменение текста
issue между r1 и r2, а не повторная проверка задачи целиком.

Технической возможности получить точный `git diff` тела issue нет — GitHub
REST/events API не отдаёт предыдущую ревизию тела (`events --jq
'select(.event=="edited")'` вернул пусто), а `docs/specs/` для этой задачи не
применяется (ТЗ 2026-10-08, архив только до 2026-09-10). Дельта установлена
тремя независимыми способами, которые сошлись:

1. Текущий текст сам маркирует добавленное предложение тегом `(r2)` в AC1 —
   самоописывающаяся правка, не требующая внешнего диффа.
2. Авторские комментарии `2026-10-08T12:26:38Z` и `12:26:43Z` называют именно
   то, что изменено: новый п. §3a, уточнение AC1 (full final-materialization
   proof вместо одного physical preview) и AC3 (явное разделение физической
   геометрии соседней комнаты и derived compatibility atom по §3a).
3. Сверка с дословными цитатами r1-ревью (`SPEC-REVIEW-832-r1.md`, «Как
   проверялось») — там нет п. §3a и нет упоминания «final materialization/
   junction proof с baseline» в AC1; но оракулы, которые r1 цитирует дословно
   («actual second commit вместо fake private commit», «full structural
   snapshot сравнение, не history.size», «таблица доказан/чем краснеет для
   AC4») присутствуют в текущем тексте без изменений — значит AC2, AC4, AC5 и
   большая часть AC1/AC3 дельту не затронула.

Проверил именно задетое дельтой:

- **§3a** (новый пункт) сверен с `docs/WALL-THICKNESS.md` (раздел «Stable
  stored identity», строки 56-165, особенно 135-137: «When a maximal wall run
  crosses a collinear vertex belonging to another room, its exact endpoints
  cover that room's shorter child side too» и 139-151 про Resize/коллинеарные
  overlap boundaries). §3a не вводит новое поведение модели — он описывает
  уже задокументированный инвариант (derived collinear точка соседней
  комнаты — не независимый authored corner) на уровне ТЗ конкретной задачи.
  Противоречий канону нет.
- **Граница «bounded ID-owner closure»** читается однозначно: только прямые
  потребители изменённых catalog IDs; явный запрет третьей комнате/переносу
  её стены («Это не присоединение третьей комнаты к solver и не перенос её
  стены») закрывает цепную эскалацию на несвязанные комнаты. Терминология
  («compatibility poly», «ordered wall_ids», «derived») согласована с
  `rooms[].wall_ids[]`/`space.walls[]` из `WALL-THICKNESS.md:56-59`.
- **AC1** (правка): новое предложение требует от independently rehydrated
  кандидата пройти full strict physical proof **и** final
  materialization/junction proof с baseline, а не только physical preview —
  именно это закрывает сам дефект self-audit (PASS физики ≠ PASS после
  материализации с соседней комнатой). Способ доказательства (smoke+unit) и
  наблюдаемый oracle не изменились, добавлено только условие полноты
  доказательства.
- **AC3** (правка): «меняется только обоснованный derived collinear seam
  vertex по §3a, ни один authored corner/field не меняется» плюс negative
  witness («попытка сдвинуть настоящий соседний corner либо contradictory
  incident IDs отказывается») — однозначно и проверяемо: способ (smoke+units)
  назван, есть и позитивный, и негативный критерий.
- **«Принято предположительно»**: добавлена строка «исходная обещанная
  byte-equivalence уточнена, поскольку catalogue authoritative» — это
  техническое уточнение той же гарантии (абсолютная byte-equivalence
  распространялась и на derived compatibility atoms; теперь явно — только на
  комнаты вне owner closure, а внутри closure byte-equivalent остаётся
  физическая форма/углы/поля, кроме derived seam). Видимого пользователю
  поведения это не меняет (контур/форма комнаты те же), раздел UX не
  противоречит.
- Не нашёл скрытого продуктового вопроса в правке: граница «что считается
  authored corner vs derived seam» — техническое решение о внутреннем
  представлении каталога, не продуктовый выбор, и ТЗ фиксирует его явно и
  проверяемо (AC3 negative witness), а не оставляет на усмотрение реализации.
