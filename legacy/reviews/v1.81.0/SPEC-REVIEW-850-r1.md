## Разбор ТЗ

Обязательные разделы §7.1 присутствуют: Сценарий, Что человек увидит до и
после, Проблема и основание, Скоуп и не-скоуп, Контракт поведения, UX, Модель
данных/миграция/совместимость, i18n, Критерии приёмки (AC1–AC6, у каждого
назван способ доказательства и столбец «чем краснеет»), План автотестов и
гейтов, Производительность и touch, Файлы и модули, Риски и откат,
Release-артефакты, Зависимости и порядок, Решения и открытые вопросы (с
явным блоком «принято предположительно — поменять свободно»). Два первых
раздела отвечают на продуктовые вопросы §7.1 («какая персона, на какой
поверхности» и «что человек увидит одной фразой, без терминов реализации»),
а не только описывают работу.

Задача закрывает строки J1/J2/J3/J7 `docs/SCOPE.md` (отзывчивый живой план,
точные и видимые сразу состояния) — ТЗ называет их явно и не расширяет
скоуп сверх измеренного горячего пути; раздел «Не входит» корректно выносит
смежные находки (сужение рендера до показанного этажа при S1b, работа
`updated` после рендера, наведение/подсказка) за пределы задачи с объяснением
почему каждая из них не входит — это техническое решение автора (§7.1:
«всё, чего пользователь не наблюдает, агенты решают сами»), не продуктовая
неопределённость, и не требует отдельного issue на этом ревью: ни одна из них
не является известным пользователю дефектом, скрытым от владельца, — все три
прямо названы в тексте ТЗ как «находка, не эта задача».

Каждый AC численно и однозначно задан:

- **AC1** — отчёт по контракту п.1 плюс починка слепого счётчика
  `led-strips-v1`; «чем краснеет» называет конкретные текущие числа на `dev`
  (400 презентаций, 1 LED-кадр, 50 трубок на тик S1; `recomputesOnHaTicks` = 0
  при 100 из 100 фактических сборок кадра) — проверяемо и фальсифицируемо.
- **AC2** — по каждому входу ключа LED-кадра (п.4 контракта) отдельный пункт,
  мутанты явно названы (убрать `icon_size` из ключа → толщина устаревает;
  вернуть `_renderPlanHass` в ключ → счётчик красный) — оба мутанта
  действительно ловят регресс именно этого AC.
- **AC3** — дифференциальный оракул на ≥200 тиках `large-house` с
  перечисленным набором классов изменений (значения, свет, связи `marker:*`,
  заряд, LQI, контакт двери, `unavailable`, реестр, настройки, виртуальный
  свет, активность) — оракул сравнивается с полной пересборкой, это сильная и
  однозначная защита от главного названного риска (пропущенный вход).
- **AC5/AC6** — «свежесть»/«без регрессий» явно отмечены как уже выполняющиеся
  на `dev`, с перечисленными golden-эталонами и существующими бенчмарками —
  не путают «новое требование» с «не регрессировать».

Контракт п.2 («вход вычисления», fail-open по образцу
`classifyHassRenderChange`) и п.5 (барьерный кэш) не противоречат уже
зафиксированному в `docs/LIGHT.md` устройству барьерного кэша (ключ —
геометрический отпечаток + подпись проёмов, не `_cfgEpoch`): ТЗ чинит частоту
вычисления отпечатка на проход рендера, а не схему ключевания кэша, которая
уже корректна по канону. Противоречия с каноном нет.

## Находки

### Medium (в скоупе задачи) — AC4(а) не называет способ доказательства для заявки «0 пересчётов … на камере»

**Где.** Тело issue #850, раздел «Критерии приёмки», строка AC4, пункт (а):
«Геометрический отпечаток преград: 0 пересчётов на S1, S1b, S2, **наведении и
камере**.» Столбец «Чем доказан» для AC4 — «unit (`test/glow-scene.test.mjs`,
`test/devices.test.mjs`) + benchmark counter», без указания, какой именно
бенчмарк и сценарий покрывает долю «камера» (pan/zoom).

**Почему это находка, а не придирка.** Часть «наведении» этого же пункта
доказывается без нового кода: измерение в разделе «Проблема и основание»
(«Наведение (H1/H2): 0 полных рендеров и 0 снимков…») уже установлено как
проходящий существующий гейт `large-house-interaction-v1`, а геометрический
отпечаток вычисляется только внутри прохода рендера — 0 рендеров на наведении
автоматически даёт 0 пересчётов отпечатка, доказательство наследуется.
Камера — другой случай: pan/zoom вызывает реальные проходы рендера (ровно
поэтому у LED есть отдельная политика качества #789 и счётчики
`recomputesOnCamera` в `demo/benchmark_led_strips.mjs`), то есть при
неисправленном коде отпечаток преград сейчас пересчитывается и на
камера-вызванных проходах («`contentFingerprint` … на каждый проход
рендера», раздел «Проблема и основание»). Я проверил код существующих
бенчмарков: `recomputesOnHaTicks` / `recomputesOnCamera` /
`recomputesOnColour` в `demo/benchmark_led_strips.mjs:326–328` считают только
промахи кэша геометрии LED-поля (это прямо следует и из текста самого ТЗ:
«Его счётчик `recomputesOnHaTicks` … считает только промахи кэша геометрии
поля»), а в `demo/benchmark_large_house.mjs` счётчика отпечатка преград нет
вовсе (поиск по `barrier|glowClipCache|geometryFingerprint` не дал
совпадений). Раздел «План автотестов и гейтов» называет, куда добавляются
новые точные счётчики, только применительно к `demo/benchmark_led_strips.mjs`
и `demo/performance/budgets-led-strips.json` (сценарии S1/S1b/S2 — тики HA);
`large-house-interaction-v1` / `benchmark_large_house.mjs`, где единственно
воспроизводится камера (pan/zoom), в плане новых счётчиков не упомянут вовсе
— только как участник существующего гейта «Full Performance» без изменений.
Мутанты, названные для AC4 («кэш отпечатка по id этажа», «исключить строку
контроллера из состояния света»), проверяют функциональную корректность
кэша, а не частоту его вычисления при камере — ни один из них не покраснеет,
если реализация будет пересчитывать отпечаток на каждом camera-тике вместо
переиспользования. Это ровно случай из инструкции ревью: защитная часть AC
есть, а строка «чем краснеет» для неё не покрывает один из перечисленных в
самом AC сценариев.

**Как закрыть.** В контракте плана автотестов (раздел «Benchmark») назвать,
где именно появляется счётчик «отпечаток преград пересчитан» для
camera-сценария — либо расширить `large-house-interaction-v1`
(`benchmark_large_house.mjs`) новым точным счётчиком и завести его в бюджет,
либо явно обосновать, почему unit-теста «вызов дважды с неизменным сырым
конфигом этажа → второй вызов не пересчитывает» достаточно для camera-случая
без отдельного browser-сценария (то есть доказать по коду, что camera-проход
рендера вызывает ту же функцию с тем же инвариантом входов, что и HA-тик, и
явно зафиксировать это в ТЗ, а не оставлять читателю выводить самому). Любой
из двух вариантов закрывает находку без изменения ни одного числа в самих
AC и без расширения скоупа — чисто уточнение способа доказательства уже
заявленного утверждения.

## Вердикт

Жёлтый. Один Medium в скоупе задачи — защитная часть AC4(а) про «камеру» не
имеет названного способа доказательства (ни бенчмарк-сценария, ни unit-теста,
ни обоснования, почему достаточно существующего плана), хотя сама заявка
(«0 пересчётов») есть в тексте AC. High-находок нет: обязательные разделы на
месте, остальные AC1–AC6 однозначны и выполнимы заявленными способами,
контракт согласован с уже задокументированным устройством барьерного кэша
(`docs/LIGHT.md`), скоуп обоснован строками `docs/SCOPE.md`, риски и откат
разобраны, touch-гарантии явно сохранены.
