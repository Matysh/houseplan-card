## Скоуп

Объединённая задача из аудита (A2-9, A2-11, A2-12, A2-13, A2-15; U11, U13): два независимых,
но смежных дефекта редакторов плана —

1. создание marker/room (в отличие от edit) закрывается по Esc/крестику/Cancel/backdrop без
   вопроса о несохранённом вводе, а обычный Save комнаты сбрасывает форму раньше проверки
   результата commit;
2. отказ `_finishWallChain()` блокирует смену инструмента/режима/пространства без объяснения и
   безопасного выхода.

Правило первой строки SCOPE.md: обслуживает J4/J6 («GUI-онбординг без потери ввода», «держать
план достоверным по мере работы с ним») — обе точки входа найдены в этих строках, расширения
продукта вне мандата нет.

### Проверка на скрытый продуктовый вопрос

Задача помечена «Новых открытых продуктовых вопросов нет». Поскольку скоуп собран из семи пунктов аудита
и затрагивает несколько диалогов и жизненный цикл цепочки стен, эта строка проверена отдельно, а не принята
на слово:

- Возможная продуктовая развилка «предупреждать ли о закрытии вкладки/уходе с route с несохранённым
  черновиком» явно решена ссылкой на существующий контракт View/session-reset и явно вынесена в
  «не-скоуп» (reload/route departure recovery). Это не технический вопрос, спрятанный как решённый:
  граница совпадает с уже принятым продуктовым решением (unload-перехват не делается нигде в продукте),
  а не с новым умолчанием автора.
- Граница «что считается значимым вводом» (раскрытие списка/поиск/busy — не правка) — техническое
  уточнение уже существующих `markerDirty`/`roomDirty` хелперов, не новое пользовательское поведение;
  корректно отнесено к зоне авторского решения (§7.1 «Всё, чего пользователь не наблюдает»).
- Текст двух новых UI-сообщений (failed-chain) зафиксирован дословно RU/EN в самом ТЗ — не оставлен
  на усмотрение реализации, вопрос не возникает.

Скрытого продуктового вопроса, достойного эскалации владельцу или трактовки как замечание, не найдено;
все развилки либо дедуцируемы из существующих контрактов (#874, #842/#843, SCOPE.md), либо прямо
зафиксированы текстом ТЗ.

## Что проверено и корректно

- Все 10 технических утверждений раздела «Что проверено» ТЗ подтверждены чтением кода на точном SHA
  материала (таблица выше) — спецификация не опирается на устаревший или неточный диагноз.
- Каждый AC (AC1–AC5) однозначен, имеет план доказательства и явный красный случай (колонка «чем должен
  краснеть»); для AC5 (низкоприоритетные гипотезы) явно требуется наблюдаемый свидетель либо снятие —
  не допускает бездоказательного исправления.
- Не-скоуп корректно исключает #842/#843 (rollback/history authority), stylus parity, reload/route-recovery,
  автосохранение, общий рефакторинг диалогов — не позволяет задаче расползтись.
- i18n: переиспользование существующих `dialog.discard_*` без правки остальных форм; новые ключи заданы
  сразу RU+EN, коллизий имён нет.
- Release-артефакты корректно отделяют инфраструктурную подготовку (`release-ledger` JSON, Issue/User-Visible
  трейлеры) от публикации — ничего не запрошено раньше владельца.
- Ссылки на смежные issue (#842, #843, #874, #861, #803, #832) использованы по существу, не как повод
  расширить или сузить эту задачу без оснований.

- Гейты `npx tsc --noEmit` / `npm test` / `npm run build` + `bundle-policy --verify` не запускались: на
  этом SHA нет продуктового diff (ветка `issue/851-editor-dirty-exit` чистая, автор это подтвердил в
  комментарии и `git status` в рабочей копии ревью пуст); зависимости и Chromium на этапе spec не
  ставились (#696, подтверждено отсутствием `node_modules`). Это ревью ТЗ, а не кода — указанные гейты
  относятся к S7.
- Смоки/unit/golden/invariants/performance не запускались по той же причине (нет реализации для прогона).
- Содержимое будущего `docs/release-ledger/1.80.1/851.json` (классификация major/infra/stable-fix/line-fix)
  не проверялось — файл по плану ТЗ появляется до S7, не сейчас.
- Фактическая проверка low-гипотез (initial validation, empty bounds, diagonal resize handles, pen parity)
  не проводилась — ТЗ прямо откладывает её до стадии реализации с witness-требованием (AC5); на этапе
  spec оценивается только формулировка требования, а не факт бага.
