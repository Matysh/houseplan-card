сохранить независимую историю при отказах записи и корректно различать ошибки
переноса узла». Трек: `track:ask`. Заход r2, блокирующих циклов израсходовано
1 из 4. Материал: тело issue #891 после правки владельца 2026-10-14T17:43:32Z
(GitHub `userContentEdits`, последняя запись); продуктовый код не менялся —

материал кода (`ef1aeaf6cf94f2f692654e975a4ee18c40b143a7`) остаётся вершиной
`dev`, между ними только коммиты `docs: review document for #...` (`git log
ef1aeaf6cf94..HEAD` — проверено, `src/**`/`custom_components/**` без диффа).

   - заменён абзац «Release-артефакты» (старый текст, процитированный самим
     r1 в находках M1/M2: «RU/EN changelog + ARCHITECTURE/STATUS» и «Ledger:

   UX, модель данных, i18n, план автотестов и откат — побайтово идентичны

   эти факты не передоказываю (static-first, «пригодный неизменившийся check
   не повторять»).
3. **M1 (закрытие).** Новый текст: «RU/EN changelog + ARCHITECTURE/STATUS и
   **docs/UX-MODES.md** (таксономия отказов/нейтральный Undo/Redo текст в
   блоках #843/#883)». Файл и абзац названы точно теми же словами, что
   требовала находка r1 («абзац #843/#883, строки 194-222»). Закрыто
   дословно.
4. **M2 (закрытие).** Новый текст явно разделяет происхождение: «категория
   stable-fix обоснована самостоятельной pre-v1.80.1 частью… (пункты 1/2/4/5)»
   против «selective nodeHistoryRefusal клиентской части AC3 создан #843
   после stable, это внутрибетная line-fix introducedBy #843, не
   самостоятельная починка v1.80.1» — ровно то разделение, которое
   «Воспроизведение дефекта» и «Требуемая правка» r1 называли по номеру
   пункта и по файлу (`src/wall-node-history.ts`, коммит `f26017d2` после
   `v1.80.1`/`v1.81.0-beta.1`).
   Проверена реализуемость этого плана по факту схемы, а не только по
   тексту ТЗ: `scripts/release-ledger.mjs` — `CATEGORIES` только
   `['major','infra','stable-fix','line-fix']`, `validateEntry` требует
   ровно одно поле `category` на issue, "mixed"-примитива в схеме нет;
   `isUserReleaseEntry` берёт `entry.summary.ru/en` для пользовательского
   текста (`scripts/release-narrative.mjs:41`, фильтр `category ===
   'stable-fix'`). План ТЗ («одна запись остаётся `stable-fix`, в `reason`
   отдельно разделить происхождение, пользовательский stable
   changelog/анонс не перечисляет AC3 как старый баг, технический beta
   changelog остаётся полным, отдельный milestone/issue для line-fix-доли не
   создаётся») механически реализуем этой схемой без противоречия: единственное
   поле `category` действительно должно быть одно на issue («mixed issue» в
   тексте ТЗ — не предлагаемое значение схемы, а описание самого issue,
   формулировка это не маскирует); разделение, которого требовал PROCESS
   §11.9/#838 (не выдавать внутрибетную регрессию за старый stable-баг),
   выполняется на уровне свободного текста `rationale`/`summary`, который
   пишет агент, а не скрипт — это ровно тот способ, который допускала сама
   находка r1 («разделить запись ledger **или её обоснование**»). Сверено с
   реальными образцами той же подсистемы (`docs/release-ledger/v1.80.1/843.json`,
   `883.json` — оба: единственный `category: "stable-fix"`, обоснование —
   длинный свободный текст с точными номерами строк кода на теге) — формат
   ТЗ-плана не расходится с прецедентом.
5. Проверено, что «Дельта r2» корректно называет только эти два пункта и
   явно фиксирует неизменность контракта/AC1–AC6 — совпадает с
   фактическим диффом (п.2).
6. Гейты кода — без изменений относительно r1: этап `spec`, диапазон
   `ef1aeaf6..HEAD` не содержит правок `src/**`/`custom_components/**`
   (проверено `git log`/`git diff --stat`, пусто) — `npx tsc --noEmit`,
   `npm test`, `npm run build` неприменимы, Validate на материале кода уже
   зелёный тем же SHA, что видел r1.
