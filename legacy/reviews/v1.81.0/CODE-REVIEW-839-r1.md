## Находки

### Medium — в `docs/release-ledger/v1.80.1/839.json` протащена часть
скоупа #838, явно объявленного вне скоупа этой задачи

`docs/release-ledger/` — новый каталог, впервые появляющийся в дереве именно
этим коммитом (`git log --all -- docs/release-ledger` не находит более
ранних коммитов). Файл `839.json` содержит
`{"schema": 1, "issue": 839, "baseStable": "v1.80.1", "category": "infra",
"rationale": "… Запись подготовлена для единого учёта, вводимого #838."}`.

Сам issue #839 заявляет ровно три AC (две проверки unit-гейта + «без
runtime/performance/release-изменений») и в последней строке прямо пишет:
«Вне скоупа #838: исправлять отдельной инфраструктурной задачей». При этом
коммит добавляет артефакт, который — по собственному тексту rationale —
подготовлен именно для механизма #838 (единая классификация
feature/infra/fix при формировании changelog стабильного релиза, описанная
в теле #838: `schema`, `category` и 4-категорийная авторская классификация
оттуда совпадают почти дословно).

Ни один скрипт, workflow или канонический документ не читает и не
валидирует `docs/release-ledger/**`: `grep -rln "release-ledger"` по
`scripts/*.mjs`, `*.md`, `.github/workflows/*.yml` не находит ничего, кроме
самого нового файла. Схема (`schema: 1`, перечень полей, допустимые
значения `category`) нигде не зафиксирована — ни в `docs/DEVELOPMENT.md`
(дифф этого коммита туда её не вносит), ни в `PROCESS.md`, ни в открытом
#838 (там описаны только требования к будущему механизму, не формат файла).

**Почему это находка, а не безобидная подготовка:** пока #838 не слит,
формат файла — ничем не закреплённая догадка самого исполнителя. Если #838
определит иную структуру (другие имена полей, другой набор категорий, иное
место хранения — например, запись внутри changelog-бюллетеня, а не
отдельным JSON на issue), этот файл придётся переписывать или удалять —
чистый churn без пользы, а до тех пор это мёртвый, нигде не проверяемый
артефакт в каталоге стабильной линии v1.80.1. Это также незаявленная вторая
поверхность изменения (инфраструктура ревью-гейта vs. инфраструктура учёта
релизов) в задаче, которая по треку `show` рассчитана на одну.

**Воспроизведение:** `ls docs/release-ledger/v1.80.1/` → только `839.json`;
`git log --all --oneline -- 'docs/release-ledger/*'` → один коммит, этот же;
`grep -rln "release-ledger" --include="*.mjs" --include="*.md"
--include="*.yml" --include="*.json" .` → ничего, кроме самого файла.

**Это Medium в скоупе ревью этого коммита** (файл лежит в проверяемом
диапазоне, а не в соседнем неизменённом коде) — не заводится отдельным
issue, возвращается автору. Приемлемые способы закрыть: убрать файл из
этого коммита (перенести в #838, когда там появится механизм и схема), либо
прямо расширить AC/тело issue #839 записью о том, что эта подготовка
согласована владельцем и описать схему (хотя бы кратко, в `docs/DEVELOPMENT.md`
рядом с уже добавленным абзацем про #839).

## Проверено и корректно

- **`renderedMarkdown` (scripts/md-anchors.mjs)** — fenced-блоки (`` ``` ``/`~~~`,
  ≥3 символа, закрытие требует ≥ той же длины и того же символа; backtick-забор
  с backtick в info-строке фенсом не считается — правило CommonMark о
  неоднозначности с инлайн-кодом) и inline code spans (пары одинаковой длины
  backtick-рядов, без пересечения «пустой строки»-разрыва абзаца) заменяются
  пробелами с сохранением переводов строк — офсеты совпадают с исходным
  текстом посимвольно, что критично: оба вызывающих места (`repairLinks`,
  `brokenLinks`) используют смещения (`match.index`) и регэксп на замаскированном
  тексте, адресуясь в исходный `text`. Прочитано и прогнано на реальном
  документе, из-за которого завели #839 (`legacy/reviews/v1.78.0/CODE-REVIEW-682-r1.md`,
  содержит ровно сочетание inline-примеров и fenced bash/python-блока) —
  все 5 «ложных» ссылок из тела issue подтверждённо исчезают из
  `brokenLinks()` (прогон `--check-links` на всём дереве → 0).
- **`repairLinks`** — новый `Set` смещений реальных (не замаскированных)
  `](target)` ограничивает замену только настоящими ссылками; код внутри
  code span остаётся побайтно неизменным (тест
  «repair preserves examples verbatim» прогнан, зелёный; мутация подтвердила
  падение без защиты).
- **`indexEntry` / ship-итог (scripts/reviews-index.mjs)** — `shipSummary`
  вычисляется из `ownText(renderedMarkdown(text))`, то есть после снятия
  цитат/пересказов чужого раунда И fenced/inline-примеров; `High > 0`
  перекрывает любую попутную цветную строку («красный» всегда побеждает),
  отсутствие канонической строки оставляет вердикт «—», не повышает его до
  зелёного. Обычные `CODE/SPEC-REVIEW` документы правило не трогает
  (`meta.stage === 'ship'` — единственная ветка, где `body` вообще
  маскируется). Прогон на двух реальных документах `docs/reviews/` —
  `SHIP-REVIEW-v1.80.0-beta.{1,7}.md` — подтверждает ожидаемый зелёный с
  `High 0 · Medium 0` (регрессионный тест держит это как фикстуру по живым
  файлам, не только inline-строкам).
- **Трейлеры и changelog** — коммит несёт `Issue: #839` и
  `User-Visible: no`; изменения не затрагивают видимое пользователю
  поведение карточки/интеграции, поэтому отсутствие правок в
  `docs/changelog/*` и `custom_components/.../changelog/*` корректно.
- **Числа `docs/STATUS.md`** — `Node unit 4073 → 4077` совпадает с `+4`
  новыми тестами в диффе и с фактическим `npm run inventory` на этом SHA.
- **`test/merge-candidate.test.mjs`** — добавление `md-anchors.mjs` в список
  файлов, копируемых в фикстуру `seedReviewedIndexGenerator`, — техническая
  необходимость: `reviews-index.mjs` теперь импортирует этот модуль, без
  копии фикстура упала бы при импорте в изолированной временной директории;
  сам тест это и проверяет (прогнан в составе общего прогона, зелёный).
- **`docs/reviews/INDEX.md` «устарел» при локальном `--check`** — не
  находка: по `.github/workflows/validate.yml` (строки 105–117, комментарий
  к шагу не менялся этим диффом) этот гейт исполняется только на `push` в
  `refs/heads/dev` и помечен `continue-on-error: true`; на ветке issue он не
  запускается вовсе, свежесть индекса после мёрджа восстанавливает сам
  конвейер (`commitIfStale`/`candidate-reviews-index.mjs`). Расхождение,
  которое я вижу локально (`SHIP-REVIEW-v1.80.0-beta.{1,7}` всё ещё
  показаны «⚪ —» в закоммиченном `docs/reviews/INDEX.md`, тогда как новый
  код уже даёт «🟢 зелёный»), ожидаемо и самоизлечится при следующем проходе
  конвейера по dev — это и есть задокументированная архитектура, не дефект
  этого коммита.
- **AC3 (класс B/C, без runtime/performance)** — дифф не касается `src/`,
  `www/`, порогов производительности, опубликованного релиза/changelog;
  единственный спорный элемент по границе скоупа — ledger-запись — разобран
  отдельной находкой выше, но сам по себе он тоже не трогает runtime.
