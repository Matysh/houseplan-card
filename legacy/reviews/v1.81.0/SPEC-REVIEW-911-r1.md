# SPEC-REVIEW-911-r1

Issue: #911 — «Толщина стены: сохранять выделение редактируемой стены при открытом диалоге»
Этап: spec (ревью ТЗ, PROCESS.md §2.4) · Трек: ask · Заход: r1 · блокирующих циклов 0/4
Материал: тело issue #911, bodyDigest `2f014da48c75534c8413406bbc346cd2f1b2d2ae016e3d0cdff4b809d33c63c9`,
dev-SHA ссылок в ТЗ: `f819e489d9394a09588a5db4a93f393a07fd911d` (= материал этого прогона).

## Скоуп

ТЗ закрывает узкий разрыв в J6 («Keep the plan true as the home evolves», docs/SCOPE.md):
инструмент «Толщина» существует и обслуживает этот job, но при открытом диалоге подсветка
редактируемой стены пропадает, и после панорамирования/перемещения диалога (#900) непонятно,
какая стена сейчас меняется. Чисто презентационная правка lifecycle существующего hover/selected
состояния, без нового UX, палитры, config/schema или прав доступа. В рамки продукта попадает,
отдельной строки не требует — это полировка уже принятого инструмента.

## Что проверено и корректно

- Все обязательные разделы ТЗ присутствуют, в правильном порядке, два продуктовых раздела
  («Сценарий», «Что человек увидит до и после») открывают документ.
- AC1–AC4 однозначны и у каждого указан способ доказательства (ordinary native smoke для
  AC1/AC2/AC4, unit + ревью кода для AC3), включая прямой запрет доказывать через приватное
  поле (`_wallDialog`) вместо публичного UI — это заранее закрывает соблазн недоказательного
  "unit-only" свидетеля.
- Контракт поведения (5 пунктов) покрывает заявленный сценарий целиком: единственный источник
  цели по identity диалога, а не по курсору; соответствие реальной (не черновой) толщине;
  устойчивость к pan/zoom/resize/перемещению диалога без второй копии; корректный teardown и
  fail-closed при недостоверной цели; отсутствие регрессий без диалога и отсутствие новых
  config/history записей от одной лишь навигации/выделения.
- Не-скоуп исключает ровно то, что стоило бы исключить: hit testing, геометрию/толщину стен,
  Apply/Undo, камеру и жесты (принадлежат #900), палитру, 2.5D/PDF/Z2M/прочие инструменты —
  нет расползания задачи под видом «заодно починим».
- Модель данных: явно «только session/runtime presentation», никаких schema/version/migration
  полей — согласуется с характером правки (чистый презентационный lifecycle).
- Release-артефакты корректно классифицированы и доказаны чтением тега, а не продекларированы;
  `introducedBy` не требуется, так как это не `line-fix`, а `stable-fix`.
- Порядок работ («финальная реализация после S8 #900, ТЗ/ревью ТЗ можно закрыть раньше») не
  создаёт зависимости для этого ревью: #900 действительно ещё не влит (`S6-in-progress`), и
  ТЗ явно не утверждает иного.
- Кросс-ссылки на #900/#303/#313 проверены чтением и фактически точны.

## Чего не проверял

- Не прогонял `npm test` / `npm run build` / `bundle-policy --verify` — зависимости (в т.ч.
  `typescript`, тестовый раннер) не установлены на этапе spec (#696), а `changedFiles: []`:
  в этом диффе нет кода, который эти гейты оценивали бы. Это не относится к полноте ТЗ.
- Не выполнял native/browser-проверку (golden, smoke, ручной клик) — на этапе spec реализации
  не существует; AC1/AC2/AC4 сами требуют native-смока только после кода (S6/S7).
- Не проверял реализацию #900 по существу (её код/тесты) — только раздел «Не-скоуп» её ТЗ,
  нужный исключительно для проверки кросс-ссылки #911 на #900.
- Не оценивал трудоёмкость/способ реализации (выбор имени helper'а, расположение теста) —
  это явно отнесено ТЗ к решениям исполнителя и не входит в обязанности ревью ТЗ.
- Не проверял `docs/release-ledger/` — ТЗ само откладывает создание `911.json` до S7 (до кода),
  что соответствует процессу; на этапе spec файла нет и не должно быть.
