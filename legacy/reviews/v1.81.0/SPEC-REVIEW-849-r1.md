# SPEC-REVIEW-849-r1

## Материал раунда

- Issue: [#849](https://github.com/Matysh/houseplan-card/issues/849), тело на момент ревью (редакция «Дельта перед S4 — 14.10.2026», ответы владельца 1а/2а/3а учтены, `blocked` снят).
- Трек: `ask`. Заход: r1. Блокирующих циклов израсходовано 0 из 4.
- Исходный контекст кода, на который ссылается ТЗ: `origin/dev 6c2a433891fb` / `ee6717a8` (анализ и формулировка AC), рабочая копия ревью сверялась с текущим деревом репозитория (та же ветка `dev`, тот же код `_cardToggle`/`.oplock`/`marker-dialog.ts`).
- Маршрут вердикта зафиксирован конвейером: `route: fix`.

## Скоуп задачи

J3 (`docs/SCOPE.md`): «осознанное безопасное действие на плане» — согласованность
подтверждения между маркером плана и кнопками внутри информационной карточки
устройства, плюс keyboard/ARIA доступ к сведениям о замке (без нового пути
активации). Явно не входит: новая группа `controls` при клике по entity-row,
смена `tap_action` по умолчанию, actuation lock/alarm с плана/бейджа, общая
keyboard-навигация редакторов. Пересечения с открытыми #846 (active-space guard
при смене этажа) и #847 (отменённое удержание) разведены явно: #849 оставляет
себе только row-specific revalidation и semantic-control контракт, не
дублируя закрытие диалогов по смене пространства.

## Как проверялось

Прочитаны по порядку: `docs/SCOPE.md`, `AGENTS.md`, `docs/process/REVIEWER.md`,
тело issue #849 и все 4 комментария (аналитика 10.10, вопросы владельца
14.10, ответы «1а 2а 3а», закрывающий комментарий автора ТЗ), `docs/UX-MODES.md`
(раздел View — lock-badge, feedback dispatch 95%/200ms), фрагменты
`docs/USER-GUIDE.ru.md` (разделы «Замок», «Действия», «Жесты маркера»,
«Основные настройки маркера» — терминология «Переключить состояние»,
«Спрашивать подтверждение», «Информация»).

Поскольку ТЗ опирается на утверждения о текущем поведении кода, они
сверены с деревом репозитория, а не приняты на слово:

- `src/houseplan-card.ts:12704` — `_cardToggle(eid)` действительно вызывает
  `homeassistant.toggle` напрямую, проверяя только secure-домен (`lock`,
  `alarm_control_panel`) и доступность сущности; `marker.tap_confirm` не
  читается. Подтверждает проблему из ТЗ дословно.
- `src/houseplan-card.ts:12493–12511` — `.oplock` — кликабельный `<div>` без
  `tabindex`/`role`/`aria-label`, внутренняя иконка помечена
  `aria-hidden="true"`; клик обрабатывается, keyboard-путь отсутствует.
  Подтверждает owner-находку «60 нажатий Tab, нет focus/role/aria-label».
- `src/editors/marker-dialog.ts:421–429` — чекбокс `marker.tap_confirm`
  рендерится только при `effectiveTapAction === 'run' || 'toggle'` — точное
  соответствие решению владельца 1а и формулировке AC1 («видимо и включено»).
- `src/device-toggle.ts` — `resolveToggleIntent`, `toggleOperation`,
  `toggleIntentName`, `isControllable` существуют с этими именами; контракт
  п.2–3 ссылается на реальные функции, а не на вымышленные.
- `src/houseplan-card.ts:2041–2044,5654–5665` — `_tapConfirm` — существующий
  guard уровня маркера; `exec` уже пересчитывает `current` на момент
  подтверждения. ТЗ корректно описывает его как переиспользуемый механизм,
  а не предлагает писать заново.
- `#846` (open, `S5-ready`) — тело подтверждает заявленный скоуп («смена
  пространства не оставляет активных действий/подтверждений старого
  этажа», active-space guard) — ссылка в ТЗ на этот issue как на владельца
  закрытия диалогов по смене этажа корректна, пересечения нет.
- `#844` (closed) и `#847` (open, `S4-spec-review`) — названы ТЗ только как
  зависимости по порядку проверки, не как предмет этой задачи; корректно.

Гейты (`typecheck`/`npm test`/`npm run build`, смоки, golden, инварианты) на
этом этапе **не запускались и не требовались**: ТЗ не код-правка, продуктовый
код не менялся, диффа нет — раздел «Чего не проверял» ниже перечисляет это
явно вместо того, чтобы прогонять их вхолостую.

## Обязательные разделы (§7.1 / DoR §2.5)

Все обязательные разделы присутствуют и в правильном порядке: сценарий → что
человек увидит до/после → проблема и основание → скоуп/не-скоуп → контракт
поведения (5 пунктов) → UX → модель данных и миграция → i18n → критерии
приёмки AC1–AC5 с доказательством → план автотестов → производительность и
touch → файлы и модули → риски и откат → release-артефакты → зависимости и
порядок → решения и открытые вопросы.

Продуктовые вопросы отсутствуют — три вопроса владельцу были заданы на этапе
аналитики (видимость чекбокса, объём защищённых кнопок, размер hit-зоны
замка) и получили ответы 1а/2а/3а до публикации этой редакции; ревью не
видит ни одного вынесенного владельцу вопроса, который следовало бы снять
самостоятельно. Технические решения (размещение helpers, механизм
scoped cache/queue, имена тестовых fixtures) явно помечены как «принято
предположительно, поменять свободно» — соответствует §7.1.

## Критерии приёмки — построчно

| AC | Однозначность | Доказательство названо | Защитный AC: «чем краснеет» заполнено |
|---|---|---|---|
| AC1 | Да — условие «видимо и включено» точно соответствует `effectiveTapAction` в коде; «confirm off/скрытый true» явно сохраняет старое поведение | unit + smoke | Да: прямой вызов `_cardToggle`, bypass подтвердившегося маркера |
| AC2 | Да — ревалидация availability/secure domain/identity/context привязана к существующему toggle-контракту | unit + smoke | Да: закэшированная цель + повторный dispatch на double click |
| AC3 | Да — explicit no-op для lock/alarm/secure, keyboard badge только открывает карточку | smoke | Да: generic toggle на Enter бейджа — секьюр-сервис не должен появиться |
| AC4 | Да — focus/name/Enter/Space + неизменный размер hit-зоны + подавление feedback на cancel/no-op объединены в один наблюдаемый набор по одной UI-поверхности | native smoke | Да: clickable div без keyboard handler или анимация до согласия |
| AC5 | Да — регрессия на подтверждённый владельцем `TypeError` (`_tapConfirm!`), single-use guard, нет повторного вызова сервиса | native smoke + unit | Да (вынесено отдельным абзацем, не строкой таблицы — содержательно полно: проверяемый negative case назван) |

Формальное отступление: AC5 оформлен отдельным абзацем, а не строкой общей
таблицы AC1–AC4. Содержание требования (доказательство + негативный пример)
присутствует полностью, поэтому это не находка — не тот случай, когда третья
колонка пуста (§2.7 про пустой столбец «чем краснеет» здесь неприменим: он
заполнен текстом, просто не в табличной ячейке).

## Находки

Находок уровня High или Medium нет.

Low (снято ревьюером, запись только для прозрачности): AC5 можно было
оформить шестой строкой таблицы AC1–AC4 для единообразия формата — не влияет
на проверяемость и не возвращается автору.

## Что проверено и корректно

- Лок/аварийный инвариант не ослабляется: `_cardToggle` уже отказывает
  `lock`/`alarm_control_panel`, контракт п.4 и AC3 явно запрещают новый путь
  активации через клавиатуру/карточку, что совпадает с инвариантом
  `docs/SCOPE.md` («No lock or alarm panel is ever actuated by a tap on the
  plan») и `docs/UX-MODES.md` («plan-icon taps never toggle locks»).
- Решение 3а (hit-зона замка не расширяется до 44 px) зафиксировано и в
  контракте, и в UX-разделе, и в AC4 — три точки не расходятся.
- i18n-ключ `opening.lock_info_label` назван на оба языка (ru/en), новых
  config-полей или миграции нет — соответствует
  `docs/CONFIG-COMPATIBILITY.md`-классу «без миграции».
- Touch/View-гарантии (`docs/TOUCH-SUPPORT.md`) не ослабляются: правка
  целится в View/kiosk-доступность без изменения desktop-first статуса
  редакторов.
- Зависимости по порядку (#844 закрыт, #846 `S5-ready`, #847 `S4-spec-review`)
  описаны верно и не создают скрытого блокера текущего ТЗ.
- Release-артефакты: предварительная классификация `stable-fix` обоснованно
  отложена до факта диффа на S7, `User-Visible: yes` с обоими changelog
  зафиксирован как требование будущих коммитов — корректно для этого этапа.

## Чего не проверял

- **Код не написан** — это ревью ТЗ, не код-ревью; `npx tsc --noEmit`,
  `npm test`, `npm run build`, смоки, golden, инварианты модели, pytest —
  неприменимы и не запускались, диффа нет.
- Не проверялось фактическое исполнение будущих тестов (`demo/smoke_
  household_journeys.mjs`, планируемый info-card/lock a11y smoke) — они
  пока не существуют, план перечисляет намерение, а не исполненную
  проверку, что ТЗ прямо и указывает.
- Не перечитывались тела #844/#846/#847/#565/#813 целиком — только
  заголовки, состояния меток и (для #846) фрагмент ТЗ, нужный для проверки
  заявленного разведения скоупа; остальное к предмету этого ревью не
  относится.
- Мутанты в реестре не проверялись и не ожидались — на этапе ТЗ и в
  разработке они не запускаются (#709), ловит ночной прогон.

## Вывод

ТЗ полное, однозначное, каждый AC имеет названный способ доказательства и
наблюдаемый негативный пример, продуктовых вопросов не осталось, контракт
поведения проверяемо соответствует существующему коду и канону (`SCOPE.md`,
`UX-MODES.md`, `USER-GUIDE.ru.md`). Возврата на доработку не требуется.
