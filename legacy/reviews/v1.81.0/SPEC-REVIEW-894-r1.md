## Скоуп

Пять независимых поверхностей View/kiosk, объединённых владельцем в одну
задачу `track:ask` (комментарий-оценка подтверждает решение явно):

1. Карточка проёма — идентификация (имя вместо родового «Дверь») и
   актуальность после config change (AC1).
2. Warm View marker draft — lazy-load editor runtime при восстановлении
   диалога после HA remount (AC2).
3. Клавиатурная доступность значка HA Area у подписи комнаты (AC3).
4. Единая иконка `mdi:lightbulb-group` для `device:`-привязок Z2M Group,
   не только `entity:` (AC4).
5. Автообновление увеличенного (`zoom>1`) киоска с `cycle:0` после паузы
   взаимодействия, со снятием единственного гейта `baseZoom` (AC5—AC7 —
   защитные гарантии и golden).

Относится к `docs/SCOPE.md`: J1 (узнаваемость объекта/состояния), J2
(актуальность происходящего «где»), J6 (план остаётся верным — не терять
результат работы при remount), вспомогательно J4/accessibility backlog.
Все пять пунктов укладываются в уже существующие job-строки, новых
продуктовых сущностей не вводится.

## Как проверялось

Ревью ТЗ — не код-ревью: реализация не начата («Реализация не начата» —
слова автора, подтверждено отсутствием веток/коммитов с `Issue: #894`).
Поэтому гейты сборки/типов/тестов неприменимы и не запускались — проверялась
не работа кода, а проверяемость и выполнимость написанного контракта.
Проверено исполнением (поиск по исходникам и выполнение существующего
скрипта), а не только чтением:　

- `node scripts/review-preflight.mjs` → `specFormatErrors(body, 'ask', false)`
  выполнен напрямую на теле issue: возвращает `[]` (PASS), подтверждает
  заявление автора «структура → PASS». Эта проверка — только заголовки
  разделов, не их содержание (см. ниже находку по производительности).
- Все ключевые технические утверждения контракта сверены с текущим кодом
  на `ef1aeaf6` (не риск-ориентированная выборка, а проверка, что контракт
  вообще выполним):
  - `_openingInfo` действительно хранит объект по ссылке и не переустанавливается
    при config change (`src/houseplan-card.ts:1924,3635,12504`) — баг из
    «Проблема» реален, предложенный признак красноты (`retained _openingInfo
    object`) — реальное поле.
  - `OpeningCfg.id` — стабильное строковое поле (`src/types.ts:291`), контракт
    «re-resolves по stable opening id» выполним.
  - Значок HA Area сегодня — `<ha-icon>` с голым `@click`, вложенный в
    `<div role="button" tabindex="0">` подписи комнаты
    (`src/houseplan-card.ts:12141-12161`) — ровно nested-interactive дефект,
    который ТЗ называет явно («без nested-button нарушения»); устранимо
    перестройкой DOM без изменения видимого поведения — техническое решение,
    не продуктовый вопрос.
  - `isVersionReloadSafe` сегодня требует `snapshot.baseZoom` наряду с семью
    другими предикатами (`src/version-recovery.ts:147-158`) — контракт п.7
    («все прочие predicates сохранены») перечисляет именно эти семь по
    смыслу by-name, лишнего/недостающего предиката нет.
  - `_cyclePausedUntil = Date.now() + 60000` существует дважды
    (`src/houseplan-card.ts:5497,6667`) — «существующая 60-секундная pause»
    не придумана.
  - `docs/DEVICE-PRESENTATION.md:28-33` уже описывает `mdi:lightbulb-group`
    для `light.*`-групп и устройств модели `Group`, но код закрыл только
    `entity:`-путь (#878) — расхождение документа с кодом по `device:`-пути
    подтверждает, что AC4 закрывает реальный, а не придуманный разрыв.
  - Ключи i18n `opening.info_named`, `opening.lock_named`,
    `room.open_area_named` не существуют (проверено в `src/i18n/ru.json`) —
    коллизий имён нет.
- Дубликаты — см. таблицу выше, каждый проверен `gh issue view`, не только
  по тексту ТЗ.
- Классификация `docs/release-ledger/v1.80.1/894.json` — файла ещё нет
  (ожидаемо, создаётся до S7, §2.6); сверил текст плана в разделе
  «Release-артефакты» с историей: `docs/DEVICE-PRESENTATION.md:28-33`,
  описывающий `device:`-охват, добавлен коммитом `1baec4c1` (#878) уже
  **после** `v1.80.1` (`v1.80.1` — предок HEAD), а сама поддержка
  `device:`-привязок как таковая — с `v1.6`/`v1.10` (задолго до v1.80.1).
  См. находку Low ниже.

## Находки

### Medium (в скоупе) — отсутствует обязательный пункт DoR «влияние на производительность»

**Файл:** тело issue #894, раздел `## ТЗ`.

**Суть:** §2.5 PROCESS.md требует в числе обязательных пунктов DoR: «влияние
на производительность и бюджеты названо (или явно «нет»)». В тексте ТЗ
(весь раздел `## ТЗ`) нет ни одного упоминания производительности —
проверка `произв`/`perf` по полному телу `## ТЗ` даёт ноль совпадений.
Это не формальность: задача трогает lazy-load editor runtime при warm
restore (AC2), добавляет периодический auto-reload в кiosk (AC5) и меняет
путь построения иконок на нескольких поверхностях (AC4) — для каждого из
них правдоподобен быстрый ответ «нет» (переиспользуется существующий
lazy-loader, предикат reload не чаще раза в N секунд, иконка — одна
дополнительная проверка при построении), но ТЗ обязано назвать это явно,
а не оставлять вывод ревьюеру.

**Почему это находка, а не придирка:** автоматическая проверка структуры
(`specFormatErrors`) проверяет только заголовки разделов, а не их
содержание, и не ловит отсутствие конкретного обязательного утверждения
внутри раздела — поэтому «PASS» со стороны автора не покрывает этот пункт
DoR, и он не может считаться устным упущением без записи.

**Воспроизведение:** `grep -i "произв\|perf" <тело ## ТЗ>` → 0 совпадений.

**Что изменить:** одна строка в конце ТЗ (например, рядом с «Принято
предположительно») — «Производительность: нет / <явная оценка>» с кратким
обоснованием по каждой из трёх затрагиваемых поверхностей (lazy-load,
kiosk-reload-период, icon-resolve).

Без High-находок это — жёлтый вердикт: автор правит ТЗ, фикс проходит
повторный цикл (§2.4).

### Low (снято ревьюером, не блокирует)

**Файл:** тело issue #894, раздел «Release-артефакты».

**Суть:** фраза «#878 device-group дополнение учитывать как line-fix
внутри итогового общего описания» классифицирует часть изменения (AC4 для
`device:`-привязок) как `line-fix` без обоснования относительно
предыдущего stable, как того требует §11.9 («каждая задача... получает
авторскую классификацию с обоснованием»). По определению таблицы §11.9
`line-fix` — это правка функции, которой **не было** в предыдущем stable
(`v1.80.1`). Проверка историей показала обратное: поддержка `device:`-
привязок существует с `v1.6`/`v1.10` (намного раньше `v1.80.1`), то есть
сама функция, которую чинит `device:`-часть AC4, в `v1.80.1` уже была —
формально это ближе к `stable-fix` (как и классифицирован сам #878
относительно entity:-пути, `docs/release-ledger/v1.80.1/878.json`).
Контраргумент тоже существует: текст `docs/DEVICE-PRESENTATION.md:28-33`,
декларирующий `device:`-охват как часть определения, добавлен только
коммитом #878 — **после** `v1.80.1`, так что можно читать расширение как
«достройку функции, впервые заявленной в этой бете». Вопрос нетривиален и
по существу решается на S6 отдельным файлом
`docs/release-ledger/v1.80.1/894.json` со своим обоснованием и своей
проверкой код-ревьюером (§11.9) — блокировать спек-ревью из-за этого не
вижу оснований.

Снимаю как Low с записью: автору — при заполнении ledger на S6 явно
аргументировать выбор между `stable-fix` и `line-fix` для #878-доли,
опираясь на историю `device:`-привязок, а не только на дату документации.

## Что проверено и корректно

- Все 7 обязательных разделов §7.1 присутствуют и их содержание отвечает
  на поставленный в них вопрос (сценарий и «что человек увидит» — в
  продуктовых терминах, без терминов реализации).
- Каждый AC1…AC7 имеет однозначный способ доказательства (`smoke`/
  `unit + smoke`/`golden`) и явный признак красноты либо сценарий,
  различающий «было»/«стало».
- Защитный AC5 (единственный снимаемый гейт) описан так, что не оставляет
  простора для случайной деградации остальных safety-предикатов — текст
  ТЗ по смыслу перечисляет все семь непеределываемых предикатов
  `isVersionReloadSafe`, кроме самого `baseZoom`.
- Открытых продуктовых вопросов к владельцу не осталось: все развилки
  (lightbulb-group для `device:`, обновление увеличенного киоска) закрыты
  решением владельца от 14.10.2026, зафиксированным в теле ТЗ текстом, а
  не ссылкой на устный разговор.
- Блок «Принято предположительно, поменять свободно» корректно отделяет
  техническое (формат memo, модуль resolver) от продуктового.
- Терминология (`комната`, `HA-зона`, `Открыть зону в HA`) берётся из
  существующих ключей `src/i18n/ru.json` и `docs/USER-GUIDE.ru.md`, не
  изобретается.
- Границы с #846/#844/#878/#462 — проверены по факту (см. таблицу выше),
  ни одного неточного утверждения о чужом скоупе не найдено.
