## Скоуп задачи

Инфраструктура/инструментарий для личной инсталляции владельца, которая
отслеживает голову `dev` (#835): маркировка dev-сборки (`BUILD.json`,
суффикс версии манифеста), отпечаток фронтенда как идентичность сборки
(вместо номера версии) для URL регистрации ресурсов и для сверки версий
(#462), отображение метки в консоли/«О программе»/окне сверки, прокидка
метки в отчёт поддержки, экспорт и relay.

Первый вопрос по `docs/SCOPE.md`: прямой строки Core user jobs у задачи нет —
это не новая функция для персон из таблицы, а усиление уже существующей
диагностической возможности (сверка версий фронтенда/бэкенда, #462,
обслуживающей J6 «Keep the plan true as the home evolves») для случая, когда
тот же механизм слеп на dev-канале. На релизе и бете (то, что видят реальные
персоны из `docs/SCOPE.md`) контракт не меняется ни на один байт видимого
текста — задача расширяет уже принятую инфраструктуру (#462, #657, #835), а
не добавляет новую продуктовую поверхность. Это не нарушение `docs/SCOPE.md` и
не попытка протащить фичу в обход — задача корректно классифицирована как
`ask`-маршрут из-за изменения публичного контракта сверки (#462) и URL
регистрации ресурсов, а не из-за новой пользовательской ценности.

## Как проверялось

Это ревью ТЗ: гейты (`tsc`, `npm test`, `npm run build`) не прогонялись и не
нужны — кода задачи ещё нет, черновик автора не является материалом (§2.4,
§11.8), зависимости и Chromium на этапе spec не ставятся (#696). Весь объём
проверки — чтение текста ТЗ против обязательных разделов §7.1 и DoR §2.5, и
сверка каждого фактического технического утверждения ТЗ с текущим состоянием
кода в дереве (а не с догадкой):

- `scripts/source-fingerprint.mjs` — прочитан целиком: `sourceFingerprint`
  строго детерминирован (sha256 по содержимому файлов корпуса, без меток
  времени и случайности), поэтому обобщение сверки «для любого канала» не
  грозит ложными «версии разошлись» на двух сборках одного и того же коммита
  релиза/беты.
- `custom_components/houseplan/frontend_registration.py:586`,
  `panel_registration.py:168` — подтверждён заявленный baseline: сегодня URL
  модулей — ровно `?v=<VERSION>`, без иных параметров.
- `custom_components/houseplan/import_export.py:661` (`parse_document`) —
  прочитан: валидация идёт через `document.get(...)` по конкретным ключам,
  непредусмотренные top-level ключи не отклоняются → утверждение ТЗ «прежний
  импортёр неизвестное поле конверта игнорирует» подтверждено.
- `scripts/support-relay/hp_relay/validate.py` — `PACKAGE_ALLOWED_TOP_LEVEL` и
  путь `support_rejected` при `unknown request fields` существуют →
  подтверждена предпосылка «relay сегодня отклоняет новое поле `build`» и,
  значит, необходимость явной правки relay в скоупе задачи.
- `scripts/bundle-manifest.mjs:446` (`entryFallbackPlugin`),
  `rollup.config.mjs:51`, `src/i18n/registry.ts:9`
  (`ENTRY_BUILD_FINGERPRINT`) — подтверждено, что механизм entry-обёртки и
  паттерн «плейсхолдер-отпечаток в юнит-тестах» уже существуют в кодовой базе
  (используется для `ONBOARDING_RUNTIME_FINGERPRINT`), К5 не изобретает новый
  примитив, а переиспользует имеющийся.
- `custom_components/houseplan/websocket_api.py:1435,1492` —
  `houseplan/config/get` и поле `integration_version` существуют как описано

- `src/i18n/en.json`/`ru.json` (`gs.about_version`, `version_mismatch.*`) и
  `src/version-recovery-card.ts:226-227` — подтверждено, что добавление

## Находки

Нет ни одной High- или Medium-находки.

Единственное замечание уровня Low, снятое ревьюером без возврата автору
(§2.4): пункт «принято предположительно» №2 («“О программе” и консоль
показывают метку **работающего** фронтенда (К5), а не `build` из
`config/get`») — не чисто техническое решение, а меняет то, что увидит
пользователь в конкретном сценарии (открытая до обновления вкладка): при
исходном предложении владельца («О программе»: при `build.channel == 'dev'`
… из `config/get`) в этом сценарии диалог показывал бы метку **бэкенда**,
который уже обновился, а не то, что реально выполняется в вкладке; решение
автора показывает метку **фактически загруженного** кода. Формально это
продуктовый вопрос («что видит пользователь»), который по букве §7.1 мог
уйти владельцу, а не лечь в категорию «меняется свободно». По существу
решение верное и единственно согласованное: оно явно описано, снабжено
примером («что человек увидит до и после», сценарий со вкладкой до
перезапуска) и однозначно проверяется (AC6, К5, К7) — отдельное окно сверки
уже информирует о расхождении с бэкендом, так что дублирование той же
функции в «О программе» было бы избыточным и вводящим в заблуждение. Технический
спор решается вердиктом, а не владельцем (§7.1): ревьюер принимает решение
автора, фиксирует несоответствие категоризации как Low и не возвращает
задачу на этот пункт.

## Что проверено и корректно

- Обязательные разделы §7.1 присутствуют и в правильном порядке: сценарий →
  что человек увидит до/после → проблема → скоуп/не-скоуп → контракт
  поведения → UX → модель данных и миграция → i18n → критерии приёмки →
  план автотестов → риски → откат → release-артефакты.
- DoR §2.5 выполнен пункт за пунктом: AC1–AC7 пронумерованы, у каждого назван
  способ доказательства (unit/backend/smoke, с указанием конкретного файла
  теста); затронутые файлы и модули перечислены («поверхности» + «План
  автотестов»); i18n — явное «новых ключей нет» (и это подтверждено чтением
  кода, см. выше); миграция/compatibility — явное «нет», совместимо с
  `docs/CONFIG-COMPATIBILITY.md`; производительность и touch названы явно
  («нет»/«чтение двух файлов при настройке»); release-артефакты перечислены
  построчно (changelog RU+EN, DEVELOPMENT.md, ARCHITECTURE.md, support-relay
  README, явное «golden — нет»); откат описан конкретно (revert коммитов,
  `dev-build` без метки, URL возвращается обновлением на месте); открытых
  продуктовых вопросов не осталось — единственный пункт «что решить при
  разборе» был заранее закрыт владельцем дефолтом прямо в теле issue, и автор
  явно это зафиксировал.
- Каждый AC однозначен и имеет названный способ падения на старом коде там,
  где это применимо («Свидетели красные на `dev`» — AC1, AC5), либо явно
  описывает новое поведение, которого в принципе не существовало (AC2–AC4,
  AC6–AC7 — не регрессионные тесты, а тесты новой функциональности, что
  корректно не требует «red on dev»).
- Защитные случаи (невалидный `BUILD.json`, отсутствующий отпечаток, битая
  схема, неизвестное поле relay) перечислены исчерпывающе в К2, К4, К6, К8 и
  продублированы отдельным списком мутантов (4 штуки) — это покрытие,
  адекватное объёму задачи на этапе spec (мутанты в разработке не гоняются,
  ревьюер лишь проверяет, что защита названа, §2.7 / трек show-раздел по
  аналогии).
- Технические утверждения, проверяемые по коду, оказались точными (см. «Как
  проверялось») — ни одного случая «утверждение о поведении без пометки
  „предположение“, которого нет ни в одном документе» не найдено.
- Риски (отказ загрузчика HA на суффиксе версии, relay переразвёртывание,
  окно между установкой и рестартом HA, HACS-сравнение версий, YAML-режим,
  ручной URL ресурса) перечислены с последствиями и соответствующими AC/
  фолбэками — ни один не оставлен без ответа.
- Трек `ask` обоснован верно: меняется публичный контракт сверки версий
  (#462) и формат регистрации ресурсов — это не вопрос соответствия критерию
  §5 для понижения, вопроса на reclassify нет.

## Чего не проверял

- Не прогонялись `npx tsc --noEmit`, `npm test`, `npm run build` — на этапе
  spec кода задачи ещё нет, гейты неприменимы (#696, §2.4/§11.8: черновик
  автора — не материал).
- Не читался возможный черновик кода на ветке `issue/836-dev-build-identity`
  — ревью ТЗ по правилам судит только тело issue.
- Не проверялось соответствие `docs/release-ledger/<previous-stable>/836.json`
  — классификация релиза относится к этапу реализации/код-ревью (ТЗ сама
  называет её как TODO в «Release-артефактах», это корректно для spec-этапа).
- Не проверялась работа реального HA-загрузчика на версии с суффиксом
  `+dev.<sha8>` (AC4) — это именно то, что ТЗ правильно выносит в risk +
  AC, подлежащий доказательству на этапе реализации, а не на этапе
  спецификации.
- Фактическая детерминированность бандла при пересборке в CI (а не только
  детерминированность хеш-функции на уровне исходников) напрямую не
  тестировалась — проверка ограничена чтением `source-fingerprint.mjs`;
  остаточный риск недетерминированной сборки (например, из-за порядка
  обхода файловой системы или внешних входов рантайма сборки) не исключён
  полностью, но ТЗ уже полагается на этот же механизм, используемый сегодня
  для `bundle-policy.mjs`/`assertCommittedBundleFresh` — то есть это не новый
  риск, вводимый задачей, а существующее свойство инфраструктуры.

## Вердикт

Зелёный. ТЗ полное, однозначное, каждый AC проверяем и привязан к способу
доказательства, технические предпосылки подтверждены чтением кода, открытых
продуктовых вопросов не осталось. Единственное замечание — Low по
категоризации одного пункта «принято предположительно» — снято ревьюером и
не требует возврата автору.
