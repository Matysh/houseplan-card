## Скоуп

Расширение существующего PDF-диалога печати/экспорта (`docs/PDF-EXPORT.md`,
`src/pdf/`) вторым форматом — SVG-снимком текущего вида активного пространства.
PDF обслуживает узкое исключение SCOPE.md для #53 (чертёж для установщика/
страховщика). Новый SVG формат заявлен как «для сохранения внешнего вида плана
и дальнейшего использования в документах и графических редакторах» — то есть
решает другую задачу, чем #53. См. находку Medium-2 ниже: это не покрыто ни
Core user jobs J1–J7, ни текущим текстом исключения #53 в SCOPE.md.

## Находки

### Medium-1 — «предложение перейти в просмотр» при вызове из редактора не имеет AC и не описано как взаимодействие

Место: тело issue #1036, раздел «Контракт результата и поведения», предложение
«Вызов экспорта из редактора предлагает перейти в просмотр: нельзя выдавать
редакторский кадр за View.»

Это не декоративная деталь: кнопка печати в `.header-actions`
(`src/houseplan-card.ts:10979`) рендерится при `_canEdit` вне зависимости от
`_mode` — то есть реально доступна, когда открыт редактор `plan`/`devices`/
`decor`. Для PDF это было безопасно, потому что PDF строится из модели, а не из
DOM (`pdf-scene.ts`/`pdf-writer.ts`), и режим редактора не просачивался в
результат. SVG, по контракту этого ТЗ, захватывает **живой DOM View**
(«иконки разворачиваются из shadow DOM», «снимок фиксируется... до первого
асинхронного чтения ресурсов») — то есть именно в режиме редактора в DOM не
View, а редакторский кадр с панелями/инструментами. Это прямое столкновение с
инвариантом `docs/SCOPE.md`: «Editors are writer-only tools and must never leak
interactions into View.»

Однако единственное предложение контракта:
- не привязано ни к одному из AC1–AC9 и не имеет собственного способа
  доказательства (ни unit, ни smoke, ни «ревью кода» не названы для именно этого
  поведения — AC7 говорит про исключение chrome/handles из уже снятого кадра
  View, а не про сам факт вызова из редактора);
- не описывает механику: «предлагает перейти» — это блокирующий confirm-диалог
  с кнопками, неактивная опция SVG с подсказкой, автоматическое переключение
  режима с последующим тостом, или что-то ещё; не назван и момент триггера —
  при открытии диалога печати, при выборе формата SVG в уже открытом диалоге,
  или только при нажатии «Скачать».

Чем это красит: реализация может молча захватить DOM редактора (оба прочтения
единственного предложения ему не противоречат), и код-ревью не сможет отклонить
такой вариант как дефект, потому что проверяемого критерия нет — AC на эту
ветку не существует, и в плане автотестов (`demo/smoke_svg_export.mjs`) такой
сценарий не перечислен.

Предлагаемый дефолт: добавить отдельный AC (например AC10) с конкретной формой
— «диалог печати, открытый в любом режиме редактора, при выборе/использовании
SVG показывает блокирующий экран/подсказку "Переключитесь в просмотр, чтобы
скачать SVG" вместо захвата DOM; PDF из редактора работает как сейчас» — и
способом проверки: smoke, вызывающий печать из `plan`/`devices`/`decor` и
проверяющий, что вместо скачивания показан переход-в-просмотр, а не кадр
редактора.

Медиум **в скоупе** задачи: правится в этом же ТЗ одним абзацем и одним AC, не
требует отдельного issue.

### Medium-2 — новая возможность не отражена в `docs/SCOPE.md`, текст исключения #53 не покрывает SVG

`docs/SCOPE.md` (строки ~131–138) формулирует единственное относящееся сюда
узкое исключение: «A narrow read-only exception approved … for #53 exports the
current canonical space as a single print-ready PDF… its purpose is to hand the
already maintained House Plan geometry to an installer, insurer or renovation
contractor.» Это текст про чертёж для профессионала, с явной целью.

Новый SVG-формат по тексту самого issue решает другую задачу: «SVG — для
сохранения внешнего вида плана и дальнейшего использования в документах и
графических редакторах» — визуальный снимок текущего вида, а не архитектурный
чертёж. Ни один из Core user jobs J1–J7 (`docs/SCOPE.md` «Core user jobs») не
формулирует «сохранить визуальный снимок плана для внешнего использования»;
ближе всего J1 («show the whole home… live spatial overview»), но J1 — про
экран, не про файл для графических редакторов.

Раздел «Артефакты, безопасность, откат, release» ТЗ перечисляет
release-артефакты: «RU/EN changelog и user guide, PDF-EXPORT, ARCHITECTURE,
DEVELOPMENT/STATUS» — `docs/SCOPE.md` в этом списке не назван.

Чем это красит: SCOPE.md — объявленный владельцем ограничитель («features are
built, improved and accepted only if they serve a job listed here»), и он же
единственное место, по которому следующий автор/ревьюер судит, разрешено ли,
например, добавить PNG-экспорт или SVG всех этажей «по аналогии с уже принятым
#1036». Без собственной строки/поправки SCOPE.md эта проверка не пройдёт для
новых похожих запросов, потому что текст и так уже написан для другого случая
(единственный PDF-чертёж для контрактора) — и это именно то расхождение между
документом и фактическим решением владельца, которое ревью спецификации обязано
ловить.

Предлагаемый дефолт: расширить формулировку исключения #53 в SCOPE.md (или
добавить отдельную строку со ссылкой на #1036) теми же ограничивающими словами,
что уже в самом ТЗ — один файл текущего пространства, геометрия остаётся
векторной, не экспортирует другие этажи/пространства, не вводит новую модель
оформления, — и добавить `docs/SCOPE.md` в список release-артефактов задачи.

Медиум **в скоупе**: это редакторская правка в том же ТЗ/в том же issue, не
отдельная задача.

Больше находок уровня High/Medium не обнаружено. Побочных находок вне скоупа
этой задачи нет — новый issue по доверенному снимку
`HP_REVIEW_OUTSIDE_FINDINGS_FILE_ISSUES` (`mode=issues`) не создаётся, маршрут
не задействован.

## Что проверено и корректно

- Все обязательные разделы §7.1 присутствуют и заполнены по существу, не
  шаблонно.
- Таблица AC1–AC9 — каждый пункт имеет указанный способ доказательства (unit/
  smoke/код-ревью), ни один столбец доказательства не пуст.
- «Принято предположительно» корректно ограничивает техническими решениями
  (имена модулей, техника snapshot, разбиение тестов) — продуктовые дефолты
  (устройства off, фон «Прозрачный», свой цвет белый/alpha 1) заданы прямо, а не
  вынесены туда же.
- Терминология сверена с кодом и канонами и оказалась не изобретённой:
  - «фон режима просмотра» = существующий контракт `bg_color`/day-cycle из
    `docs/SUN.md` («The scene background never bleeds through the plan», фон
    независим от `north_deg`) — совпадает с описанием «Как сейчас на плане»;
  - «device shadows» = существующий 2.5D floor-shadow слой (`src/device-face.ts`
    `GEOMETRY-ONLY TWIN… common 2.5D floor-shadow layer`);
  - «LED-представления» отделены от Glow — подтверждено разграничением в
    `docs/LIGHT.md` («Top-level LED-strip source data is excluded from this
    architectural fingerprint» vs. «Glow off for the space… still computed»);
    формулировка ТЗ «освещение комнат/окон/солнца остаётся… независимо от
    иконок» этому разграничению не противоречит;
  - «общий компонент UI-kit» для крестика закрытия — реальный существующий
    `<hp-dialog>`/`.close` с `cursor:pointer` и hover-transform по умолчанию
    (`src/hp-dialog.ts:314-339`); PDF-диалог сейчас переопределяет
    `--hp-dialog-icon-size` до 40.48px на уровне своего `:host`, что через
    наследование custom properties увеличивает в том числе крестик относительно
    дефолта 24px — пункт требования #7 ссылается на реальное визуальное
    расхождение, а не на уже решённую задачу;
  - 120 мс fade для первого чекбокса — согласуется с существующими короткими
    transition в `chrome-tooltip.ts`/`hp-help.ts`/`hp-color-opacity.ts`
    (везде 120 мс), не произвольное новое число.
- Сценарий и «до/после» — продуктовые, названа персона (администратор, View) и
  поверхность, как требует §7.1.
- Открытых продуктовых вопросов, вынесенных владельцу, в тексте нет — и это
  корректно: оба найденных замечания технические/процедурные (отсутствие AC,
  отсутствие правки SCOPE.md), ревьюер решает их сам предложенными дефолтами, а
  не передаёт владельцу.
- Не найдено ни одного места, где поведение, которого нет ни в одном документе,
  подаётся как факт без пометки предположения — кроме двух находок выше, которые
  именно про отсутствие/нечёткость, а не про скрытое домысливание.
