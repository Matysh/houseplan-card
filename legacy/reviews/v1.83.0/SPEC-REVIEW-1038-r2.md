множественное выделение, совместное перемещение и групповые свойства».
Этап: spec (ревью ТЗ, PROCESS.md §2.4). Заход r2, блокирующих циклов
израсходовано 1/4. Трек: `track:ask`.

Материал: тело issue #1038, раздел `## ТЗ`, зафиксированное в
`REVIEW_CONTEXT.material` — `sha=8fb6b6838816d95a229d52c9e566e01b23a7320c`,
`tree=7db43bf1bec244300696c3f46804abc11bed31df`,
`bodyDigest=9a35afa1e36910604ad7382f0a83dd58c38a54bea1518eebc3d8e2b55189bded`.
Тело issue сверено напрямую (`gh issue view 1038 --json body`) — содержимое
совпадает с `REVIEW_CONTEXT.body` байт в байт (отличие SHA-256 — другой
алгоритм/нормализация на стороне подготовки снимка, не расхождение
содержимого). Маршрут вердикта предопределён промптом: `route: fix`.

## Скоуп

Тот же, что в r1: фича закрывает J4/J6 (`docs/SCOPE.md`) — мультиселект
декора, совместное перемещение, групповые цветовые поля в существующей
Properties, два новых сочетания клавиш и две новые подсказки в редакторе
«Подложка». Этот раунд — ревью делом по дельте (PROCESS.md §2.10): единственное
изменение тела issue — переформулировка п.2 раздела «Ctrl+A, Ctrl+M и границы
перехвата» в ответ на единственную Medium-находку SPEC r1.

## Как проверялось

Кодовый Validate на этапе spec не требуется (PROCESS.md §8,
`docs/process/REVIEWER.md` «Ревью ТЗ»); `tsc`/`npm run build`/`npm test`/
`gate:small` не запускались — не гейт этого этапа, это не упущение, а
корректный объём.

1. Прочитаны статические обязательные источники раунда: `docs/SCOPE.md`,
   `AGENTS.md`, `docs/process/REVIEWER.md` (сверены с `REVIEW_CONTEXT.files`).
2. Прочитано полностью тело issue #1038 на материале `8fb6b6838` и все
   текущие комментарии GitHub (аналитика, вопрос A/B, решение владельца,
   два авторских комментария о фиксации и правке ТЗ, вердикт пайплайна r1).
3. Найден и прочитан документ предыдущего раунда,
   `docs/reviews/SPEC-REVIEW-1038-r1.md`, и его материал (`sha=0e59b41b3573`,
   `bodyDigest=f7e9043792fac6…`).
4. Дельта выделена сравнением дословной цитаты п.2 в SPEC-REVIEW-1038-r1.md
   («При idle-инструменте Background сочетание переводит в Select и выбирает
   набор; незаконченный рисунок/цепочка Line и активный pointer-жест не
   завершаются и не сохраняются сочетанием.») с текущим текстом п.2 в теле
   issue. Запрошена также история редактирования тела через GraphQL
   `userContentEdits` — GitHub вернул только последнюю редакцию, и её поле
   `diff` оказалось идентично текущему телу (не содержит маркеров удаления),
   то есть не дало отдельно старую версию; дословная цитата из
   SPEC-REVIEW-1038-r1.md остаётся опорной точкой дельты и достаточна —
   автор сам описал суть правки тем же комментарием (6379531633), и обе
   формулировки сверены построчно.
5. Проверена однозначность и осуществимость новой формулировки п.2 (ниже) и
   её согласованность с AC1/AC5, которые единственные ссылались на этот
   сценарий как на предмет негативного browser-свидетеля. Для этого
   перечитаны относящиеся места `docs/DECOR-EDITOR.md`: состояние
   `idle → draft/move/scale/rotate → release → named history command →
   debounced save` и его `Esc`-откат, «Drawing tools stay armed», модель
   Line click-chain с накоплением anchor по каждой принятой точке, отмена по
   `Esc`/`pointercancel`/потере pointer capture. Это тот же канонический
   документ подсистемы, который r1 уже читал целиком (его статус не
   изменился — непройденная повторно часть не содержит новых фактов,
   затронутых дельтой).
6. Остальные разделы ТЗ (матрица полей, модель перемещения, история/
   сохранение, i18n, risks/release-артефакты) не менялись и не задеты
   дельтой — не перепроверялись заново (см. «Унаследовано из r1»).
7. Конкретных непокрытых вопросов, требующих отдельного исполняемого probe
   (сборка/негативный кейс на текущей реализации), не возникло: продуктовая
   реализация #1038 не начата (подтверждено последним авторским
   комментарием — ветка #1045 не переключалась), поэтому исполняемого
   мутанта/negative-input case в этом ревью не требуется и не проводился.

## Закрытие раунда r1

| Находка | Чем закрыта | Где это видно |
|---|---|---|
| Medium (в скоупе): п.2 не определял поведение Ctrl+A/Ctrl+M, когда Background-инструмент не idle (активная цепочка Line, вооружённый, но не нажатый Rectangle/Ellipse/Furniture, живой pointer-жест) — AC1/AC5 ссылались на этот сценарий без детерминированного oracle. | Текст п.2 раздела «Ctrl+A, Ctrl+M и границы перехвата» переписан: явно определено «idle» (отсутствие начатого draft, активной цепочки Line, удерживаемого контакта, live drag/resize/rotate/draw-жеста); вооружённые Rectangle/Ellipse/Furniture без begin/contact/draft (включая пассивный furniture hover-preview) отнесены к idle и переводятся в Select без создания объекта; явно выбран единственный вариант для не-idle случая — сочетание **целиком поглощается**: инструмент, точный состав выделения, anchor/draft/preview и захваченный pointer не меняются, новых Save/команд истории нет, следующий endpoint Line использует прежний anchor, pointerup/Esc обрабатывается прежним владельцем жеста. | Тело issue #1038, раздел «Контракт выбора и UX», п.2 (материал `sha=8fb6b6838816d95a229d52c9e566e01b23a7320c`, `bodyDigest=9a35afa1e36910604ad7382f0a83dd58c38a54bea1518eebc3d8e2b55189bded`); авторский комментарий 2026-10-24T03:56:43Z, id 6379531633 (упомянут как исправляющий именно эту находку). |

Выбранный вариант (полное поглощение, без изменения tool/selection/anchor/
preview/capture) соответствует существующей модели `docs/DECOR-EDITOR.md`:
drawing-инструменты остаются «armed» между действиями, активная Line-сессия
накапливает anchor по принятым точкам и переживает Undo/Redo операции над
уже принятыми сегментами, а отмена определена только через `Esc`/
`pointercancel`/потерю pointer capture — не через постороннее сочетание
клавиш. Теперь из текста п.2 однозначно выводится единственное ожидаемое
конечное состояние для `smoke_decor_multiselect.mjs` и негативной матрицы
AC5 в сценарии «активный Line-жест + Ctrl+A»: ничего не меняется, кроме
отсутствия побочного создания/сохранения. AC1 («вооружённые idle Rect/
Ellipse/Furniture переходят Select без объекта») и AC5 («при активной
Line/draft/contact/drag полностью сохраняют tool/selection/anchor/preview/
capture и число Save/history; после клавиши продолжается прежний жест»)
теперь дословно отражают именно этот выбор — расхождения между контрактом
и таблицей AC не найдено.

Находка закрыта полностью, новых формулировок, оставляющих тот же вопрос
открытым, не найдено.

## Что проверено и является корректным

- Новая формулировка п.2 однозначна: для каждого из двух состояний
  Background-инструмента (idle / не-idle) указан ровно один исход, без
  развилки «на усмотрение реализации», которая была находкой r1.
- Формулировка согласована терминологически с `docs/DECOR-EDITOR.md`
  (idle/armed/anchor/draft/pointercancel/Line chain используются в том же
  смысле, что и в каноне подсистемы) — осуществима без противоречий с
  существующей архитектурой.
- AC1 и AC5 теперь дословно соответствуют обновлённому п.2: оба свидетеля
  (`smoke_decor_multiselect.mjs` и native browser negative matrix) получили
  детерминированный oracle для сценария «активный жест/draft + Ctrl+A/
  Ctrl+M», которого не хватало в r1.
- Порядок проверки guard'ов явно зафиксирован («исключения полей/диалогов
  из п.3 проверяются прежде поглощения сочетания») — не осталось вопроса,
  какая проверка идёт первой при одновременном попадании в поле и в
  активный жест (гипотетически невозможная комбинация, но текст её не
  оставляет недосказанной).
- Остальной текст ТЗ (см. «Унаследовано из r1») не изменился, внутренних
  противоречий с обновлённым п.2 не внесено.
