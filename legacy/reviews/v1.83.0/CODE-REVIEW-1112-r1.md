## Что проверено и корректно

- **AC1 (rev-фильтр + 200мс коалесценция, defensive).** Код: `invalidate(kind, event)` в `src/config-store.ts:120-141` — `knownRev = max(cache.rev|layoutRev, pendingRev)`; `rev <= knownRev` → `return` без побочных эффектов (ни `configInvalid/layoutInvalid`, ни `fetchGeneration++`, ни таймера). Событие без числового `rev` (legacy) проходит мимо этой проверки и инвалидирует безусловно — соответствует «событие без rev по-прежнему сбрасывает кэш» (AC2).
  **Чем доказано · чем краснеет:** `test/config-store-events.test.mjs`, тест «stale revisions do not wake cards…» — свежий прогон на материале (`unit:test/config-store-events.test.mjs`, receipt `0393985e…`) → PASS 6/6. Независимо прочитана базовая (pre-fix) версия файла через `read:base:src/config-store.ts`/`read:diff`: там единый `invalidate()` безусловно обнуляет `cache` и синхронно будит всех слушателей на **любое** событие без проверки `rev` и без debounce — на этой версии тот же тест упал бы на первой же паре `assert.equal(wakes,0)` после `s.event('config',5)`/`{4}`, потому что `wakes` стало бы `1` уже на первом событии. Это подтверждает, что тест — не тавтология, а разрешённый негативный свидетель (чтение base, без исполнения мутанта).
  Десятикратный `layout` burst за 50мс (rev 7..16) даёт один `houseplan/layout/get` и одно пробуждение на подписчика — проверено тем же прогоном (тест «a layout burst reads only layout once…»).
- **AC2 (регрессия #437/HP-1454-08/виртуальные лампы, без правок ожиданий).** Свежие прогоны на материале: `unit:test/config-store.test.mjs` (`summary_panel_api`, decor API v1) → PASS 2/2; `unit:test/space-card-audit-lows.test.mjs`, `space-card-fit.test.mjs`, `space-card-led-disconnect.test.mjs`, `space-card-signal.test.mjs` → все PASS, без изменения ожиданий (сверено: диапазон диффа не касается `space-card.ts` и его тестов). Виртуальные лампы сохраняют немедленный путь — отдельный unit-кейс «virtual-light events retain their immediate path…» (PASS), сам код не подписывает `houseplan_virtual_light_updated` на `invalidate`/окно — ветка осталась буквально нетронутой (diff не задевает этот блок, кроме форматирования соседних строк).
- **Generation-fence / race-корпус (не входил в явные AC, но прямой риск диффа).** Два отдельных сценария гонки трассированы вручную построчно и подтверждены свежим unit-прогоном: (а) событие, пришедшее во время held-ответа, не даёт устаревшему ответу перезаписать общий кэш (`generation === fetchGeneration` guard), но сохраняет значение для исходного вызывающего; (б) `force` во время смены соединения — устаревшее событие от старого соединения временно продвигает `fetchGeneration`, более новый fetch не коммитится в общий кэш для *этого* ответа, но переключение на новое соединение сбрасывает `pendingConfigRev/pendingLayoutRev`, и следующее штатное событие нового соединения корректно будит слушателей и даёт верный `rev`/`config` в кэше — именно это чинит коммит `43ee3364e` поверх `cb62d8897` (comment 6465588301/6466064924). Оба сценария — regression-тесты в файле, PASS.
- **AC3 (native smoke, двусторонняя — не только читается, но и выполнена заново на самом материале).** `smoke:demo/smoke_static_config_events.mjs` выполнен заново на точном SHA `43ee3364e` после `build:build` + `build:bundle:sync` (все три — свежие прогоны этой сессии, не унаследованы): PASS, все 7 проверок `true`, включая `sharedOneLayoutRead` (суммарно 1 `layout/get` на обе static-карты), `eachStaticAtMostOneRead`, `staticConfigNotReloaded` (0 `config/get`), `bothStaticMarkersPaintLatestPosition` и `lastAckIsServerRevision`. ## Риск по изменённым участкам (#707)

Авто-классификатор пометил `src/config-store.ts:38-42` (и ещё 44 строки) как участок с риском класса `migration`. По факту это объявления модуль-локальных `let`-переменных рантайм-состояния (`configInvalid`, `layoutInvalid`, `eventTimer`, `pendingConfigRev`, `pendingLayoutRev`) и логика внутри `fetchFresh`/`getConfig`/`invalidate` — ни одна из них не персистится, не входит в сохраняемый конфиг, не меняет формат `houseplan_card_cfg_v1` и не добавляет новое поле в `HpConfigSnapshot` (сверено построчно с `read:diff`: интерфейс и `cachedSnapshot()` не тронуты). Ожидаемое поведение зафиксировано дважды: (1) в самом ТЗ issue #1112 («Протокол, события и серверная сторона не трогаются»; «config-store.ts помнит rev/layoutRev… как снимок... Событие layout_updated сбрасывает только layout-половину»), и (2) как уже принятый паттерн в `houseplan-card.ts` (`_onLayoutEvent`, rev-фильтр + 200мс окно), на который issue прямо ссылается как на образец для переноса в общий модуль. Критерий `migration` §5 («нет миграции конфига и новых compatibility-полей») выполнен буквально — реальной миграции конфигурации нет. Остальные классы §5 тоже не нарушены: один модуль/одна поверхность (`surfaces`), конечный видимый пользователем эффект не меняется, только исчезает избыточность запросов (`ux-contract`), чистая оптимизация чтений без новых touch-зависимостей (`perf-touch`), поведение документировано в теле issue и зеркалит уже принятый соседний контракт (`undocumented`). Сложность диффа (генерация/forced-refresh/connection-race) нетривиальна, но целиком покрыта регрессионными unit-тестами, которые я независимо прогнал и дополнительно сверил логикой на базовой версии — открытых вопросов не осталось.
