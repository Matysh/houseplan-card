## Находки

### Medium (в скоупе) — M1: «Контракт поведения» противоречит сам себе насчёт элемента `type: image` без `entity`, и это не закрытый владельцем вопрос, а новый открытый того же рода, что уже вернул предыдущий раунд

Абзац «Контракт поведения», посвящённый виртуальным маркерам, начинается однозначно: «**service-button и icon без entity** сохраняются как virtual markers на исходной позиции, с доступными name/mdi icon» — `image` в этом определяющем предложении не назван. Но тот же абзац двумя предложениями ниже, перечисляя случаи, которые не создают новых команд, пишет: «Неточное/multi-target, area/device targeting, template, произвольный service/data, navigate/url, **icon/image без поддерживаемого действия** не создают новых команд: explicit none для virtual, безопасный info для entity marker + отдельный action_skipped/fallback report» — здесь `icon/image` снова стоят парой, как в исходной (досоглашательной) таблице сопоставления раздела «Что переносится»: «`service-button`, `icon`/`image` без `entity` → виртуальное устройство с действием / декор-картинка ссылкой».

Из текста ТЗ нельзя однозначно установить:

1. становится ли `type: image` элемент без `entity` виртуальным маркером (как подразумевает фраза «icon/image без поддерживаемого действия», которая явно оперирует понятием `virtual` для `image`), или
2. элементы `image` вообще не входят в контракт этой задачи и продолжают безусловно пропускаться с кодом (как действующая реализация делает сегодня, `scripts/sh3d-convert/picture.mjs:156`, `element_image_skipped`) — тогда первое упомянутое выше предложение о «icon/image» касается не элементов-картинок, а чего-то иного, и само ТЗ не объясняет, чего именно.

Ни AC4 («service-button/icon без entity становятся virtual…»), ни AC3, ни любой другой AC не называют `image` вовсе — значит нет и способа доказательства того или иного выбора. Это не редакционная мелочь: `type: image` — такой же штатный тип элемента HA picture-elements, как `icon`, и ровно того же рода декоративный элемент без сущности (силуэт мебели, лестница, логотип), который мотивировал решение владельца №2 «создавать виртуальные маркеры» для `icon`/`service-button` — то есть продуктовый довод («получает подложку и устройства на местах, дальше обводит комнаты») одинаково применим и к `image`. При этом вопрос владельцу (комментарий 6374260123, пункт 2) был сформулирован только про «`service-button` и `icon` без сущности» — без `image` — и ответ владельца (6394496141) отвечает буквально на заданный вопрос, то есть **владелец не решал судьбу `image`-элементов**; раздел «Что разобрать на аналитике» исходного тела issue тоже не называет `image` отдельно, хотя предшествующая таблица сопоставления явно группирует его с `icon`/`service-button`.

Это ровно тот класс дефекта, по которому вернулся предыдущий код-ревью (`ux-contract`, §5): «размытое место не додумывается, а выносится владельцу» (PROCESS.md §7.1), а здесь размытое место осталось внутри уже «починенного» текста — конкретный разработчик на код-ревью снова окажется перед выбором, решать ли за владельца эту же категорию вопроса, просто для соседнего типа элемента.

**Воспроизведение:** issue #1022, раздел `## ТЗ` → «Контракт поведения», абзац 5 (первое предложение против предложения с «icon/image без поддерживаемого действия»); сверка с «Что переносится» (досоглашательная таблица, строка `service-button, icon/image без entity`) и с «Что разобрать на аналитике» (вопрос 2, только `service-button`/`icon`) и ответами владельца 6374260123/6394496141, ни один из которых `image` не называет. Дополнительно — действующая реализация `scripts/sh3d-convert/picture.mjs:156` (`element_image_skipped`), показывающая, что вопрос уже решался молча один раз.

**Что нужно для зелёного:** явно решить в тексте `## ТЗ`, становится ли `type: image` без `entity` виртуальным маркером наравне с `icon`/`service-button`, либо остаётся всегда пропускаемым с отчётным кодом — и привести оба предложения абзаца «Контракт поведения» к одной формулировке; добавить `image` в соответствующий AC (AC4 либо отдельная строка) со способом доказательства. Если это продуктовый выбор, а не очевидное технически, — вынести отдельным пунктом владельцу по образцу уже заданных вопросов 1/2, а не решать его автором ТЗ единолично (тот же §7.1, на который уже сослался предыдущий раунд).

Других Medium/High находок к тексту ТЗ в этом раунде нет.

## Вердикт
