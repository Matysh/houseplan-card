## Находки

### Medium-1 (в скоупе). К6 защищает только «проём без носителя», но тот же код
допускает тихую посадку на занятый участок и для проёма, потерявшего
действующий носитель — заявленное поведение не соответствует коду

**Файл/раздел:** тело issue #1033, «Контракт поведения» → К6; опора —
`custom_components/houseplan/wall_segment_model.py:684-765` (`_host_openings`)
и `src/wall-segment-model.ts:686-708` (`hostRoomOpenings`).

**Что заявлено.** К6 ограничивает новую защиту двумя случаями: «проём без
`host` при записи модели 10» и «любой проём в начальной миграции». Дальше: «Действующий носитель не перепроверяется. Запись модели 10,
потерявшая носитель, по-прежнему отказывает `opening-host`.» Раздел «Риски»
вторит: «Затронуто только присоединение проёма без действующего носителя».

**Что в коде.** `_host_openings` не различает «проём изначально без носителя»
и «проём, чей текущий носитель только что стал непригодным» — оба случая
проходят один и тот же путь:
- `current` (текущий носитель по `host.id`) вычисляется; если он всё ещё
  `eligible`, короткое замыкание — носитель не меняется (это и есть «действующий
  носитель не перепроверяется», тут текст ТЗ точен).
- Если `current` отсутствует или стал непригоден (стена сдвинута, утончена до
  0, удалена и т.п.), `candidates` пересчитывается заново по **всем**
  сегментам — независимо от того, был ли `host` изначально `None` или был
  словарём.
- `if len(candidates) == 1: materialize(candidates[0]); continue` — это
  **безусловная тихая посадка**, без проверки занятости участка, и она
  выполняется для обеих веток одинаково: что для изначально бесхостового
  проёма, что для проёма, только что потерявшего носитель.
- Отказ `opening-host` происходит только тогда, когда `len(candidates) != 1`
  **и** `host is not None` **и** не `initial_migration` (строки 737-740) — то
  есть только при 0 или ≥2 новых кандидатах. При ровно одном новом кандидате
  отказа нет никогда.

Зеркало TS даёт тот же результат: `resolveRoomOpeningHost` — это и есть общая
функция «найти единственного подходящего носителя», и она вызывается
одинаково что в ветке `!opening.host && !initialMigration` (строка 696), что в
общей ветке для хостованного проёма (строка 700) — `throw` происходит только
когда `resolveRoomOpeningHost` вернул `null` и `migrateRoomOpeningHost` тоже
`null` (не initial migration).

**Почему это находка, а не придирка к формулировке.** К6 введён именно затем,
чтобы не повторился сценарий из «Риски»: «Раньше такой исход давал отказ схемы
на каждой записи» (проём садится поверх соседа → схема отказывает каждую
следующую запись). Но сценарий «проём потерял действующий носитель, нашёлся
ровно один новый кандидат, этот кандидат занят соседним проёмом» —
реализуем на обычной правке плана (пользователь подвинул/утончил стену в
редакторе — к импорту отношения не имеет) и проходит **тот же код**, что и
защищённый К6 случай, но без проверки занятости участка, потому что К6
описан как применимый только к «без host». Результат: проём садится на
занятый участок, следующая же запись плана отказывает по схеме (`wall openings
must not overlap`) — то есть тот самый баг, который К6 должен закрыть,
остаётся достижимым через соседнюю, текстуально исключённую ветку того же
алгоритма. Заодно фраза «запись модели 10, потерявшая носитель, по-прежнему
отказывает `opening-host`» — неточна как общее утверждение: она верна только
при 0 или ≥2 кандидатах, а при ровно одном (как раз том случае, где нужна
защита) запись не отказывает, а молча переносит носитель.

**Чем краснеет (защитный пункт контракта, таблица «AC · доказано · краснеет»
обязательна по правилам код-ревью, но и на этапе ТЗ пустая связка
«заявление/код» без закрывающего AC — тот же дефект специфичности, только на
уровне спецификации):** AC12 — единственный защитный AC для К6 — явно
ограничен «проём **без носителя** на занятом участке» (цитата AC12:
«самовосстановление модели 10: проём без носителя на занятом участке…»). Нет
ни одного AC на «проём, потерявший носитель при записи, с ровно одним занятым
кандидатом» — сценарий не описан, не протестирован и, по тексту К6, прямо
выведен за рамки защиты, хотя код не даёт для этого основания.

**Как закрыть (техническое решение, не продуктовый вопрос — ревьюер решает
сам, владельцу эскалировать нечего):**
- либо расширить К6: защита «не занимать занятый участок» должна стоять в
  общей точке `materialize()`/`resolveRoomOpeningHost` независимо от того, был
  ли исходный `host` пуст — тогда переформулировать «действующий носитель не
  перепроверяется» (оставить как есть — это про сохранение текущего,
  валидного носителя) и убрать неверное «по-прежнему отказывает
  `opening-host`» в пользу точного описания нового поведения, плюс новый AC на
  этот сценарий (можно в составе AC12 через второй фикстурный случай);
  либо
- явно вынести этот сценарий в «Не-скоуп» с честной формулировкой («проём,
  потерявший действующий носитель вне импорта, по-прежнему может занять
  место соседа при ровно одном новом кандидате — существующее поведение
  `#316`/`#478`, этим issue не меняется») — тогда К6 и «Риски» нужно
  переписать так, чтобы не утверждать «отказывает» там, где код молча
  успешно пересаживает.

И то и другое — правка текста ТЗ (и, может быть, объёма К6), не вопрос
владельцу: продуктового поведения снаружи это не меняет ни в одном из двух
вариантов, выбор целиком технический.
