## Скоуп

Инфраструктурная задача (P2/infra, #1067): после частичного GitHub rerun
`Full Validate 40163270549` producer паспорта сохранил успешный `tooling`-job
из попытки 1, а потребители (`release:check`/`release:prepare`) корректно
отказали с `tooling: foreign direct task receipt`, потому что
`scripts/ci-proof.mjs` для `mode=executed` требовал точного совпадения
`attempt`. CODE r1 (жёлтый, High0/Medium0) нашёл код корректным, но вернул
задачу с `route: reclassify/undocumented`: новый доверительный контракт паспорта
(`claim.retained`, межпопыточная аутентификация job/шагов) не был зафиксирован
заранее ни в одном каноне — решать было что, а не «решать нечего» (§5). Эта
задача — ревью того ТЗ, написанного постфактум по уже существующему B/C-коду
(`issue/1067-retained-job-proof`, source `4a3d233c4`). Обслуживаемая работа —
не строка `docs/SCOPE.md` (продуктовый J1–J7): это инфраструктурная задача
(§1 PROCESS.md/AGENTS.md), скоуп явно `Только B/C`, без класса A, без UI,
геометрии, устройств или release membership — её цель держать доверенным
единственный канал приёмки кандидата, через который проходят все продуктовые
job'ы, а не обслуживать конкретную строку таблицы Core user jobs.

## Находки

Находок нет: ни High, ни Medium (в скоупе и вне скоупа), ни Low.

Контракт поведения (10 пунктов) внутренне непротиворечив: п.4 явно снимает
кажущееся противоречие «нужно совпадение SHA/run/workflow, но клонированный
job получает новый ID» («Равенство job ID не требуется: GitHub действительно
создаёт новый объект клона»); п.7 разводит «unrelated failure исходного
attempt» и «completed/success конкретного source-job», не ослабляя
п.4 («каждый completed/success»); п.8 явно запрещает любое смешение нового
retained-пути со старым cross-run reuse («исходное исполнение direct, не
reused… между разными run прежний запрет full/fresh reuse остаётся») — то
есть нельзя образовать цепочку retained → reused → retained через несколько
релизов. «Текущая попытка строго новее исходной» (а не «ровно на единицу
больше») корректно покрывает реальный инцидент из комментариев issue, где
итоговая успешная попытка оказалась 4-й при retained-источнике из 1-й/2-й —
контракт не завязан на соседние номера попыток.

AC3 перечисляет около 15 разных отклоняемых случаев одним пунктом; это
компактная, но не двусмысленная формулировка (каждый случай назван явно,
проверяемость не зависит от числа перечисленных сценариев в одном AC) —
такой же паттерн уже принимался в SPEC-REVIEW-1071-r1 для AC3 (аудит по
шести `kind`) без находки.
