# SPEC-REVIEW — issue #1078, заход r1

Вердикт: зелёный · заход r1 · блокирующих циклов 0/4 · High: 0 · Medium: 0 · Документ: docs/reviews/SPEC-REVIEW-1078-r1.md

Материал: тело issue #1078 (раздел `## ТЗ`, редакция r1 от 25.10.2026 · `track:ask`),
аналитика основана на принятом dev `f4f689127f0e7bec9dd872f102d635bc15cf1065`. Открытый
продуктовый вопрос закрыт решением владельца 1б (передавать солнечный доступ по
цепочке отмеченных комнат); других вопросов к владельцу в ТЗ нет.

## Скоуп

Задача обслуживает core job J1 `docs/SCOPE.md` («Show the whole home… room fills…»,
точнее её солнечное под-направление, уже закреплённое `docs/SUN.md`): точность
визуального представления того, куда на самом деле доходит солнце. Опция живёт в
обычных настройках комнаты (писательская поверхность), а эффект виден в View/kiosk —
двум из трёх персон `docs/SCOPE.md`. Не расширяет границы продукта: не создаёт новый
тип комнаты, не трогает искусственный свет (явно разведено с #1079), не меняет
геометрию/площадь/прозрачность пола. Терминология «наружное/внутреннее окно» и
структура карточки настроек — те же, что уже используются для солнца в
`docs/USER-GUIDE.ru.md` и `SUN.md`, не изобретены заново.

## Как проверялось

Ревью этапа spec: кодовый Validate не запускался (не требуется, #696 /
REVIEWER.md «Ревью ТЗ»). Проверка — независимое чтение существующей солнечной
подсистемы и сопоставление с каждым утверждением «Контракта поведения» и каждым
AC, а не принятие формулировок на слово:

- `src/sun.ts` (`isExteriorWall`, `windowWallInfo`, `computeSunRays`) — подтверждает,
  что экстерьерная классификация окна/стены уже построена на точечном пробинге по
  ПОЛНОМУ списку комнат (не требует предварительной фильтрации), что ровно
  соответствует контракту п.3/п.6 («по исходной полной геометрии, до исключения
  комнат»; «нельзя просто отфильтровать до проверки наружности»). `computeSunRays`
  уже возвращает `{openingId, roomId}` на луч — именно тот oracle, который требует
  AC3/AC7, а не выдуманный формат.
- `src/floor-geometry-key.ts` (`openingWallIndexKey`, `sunGeometryKey`) —
  подтверждает действующий паттерн «ключ строится из состава комнат/стен/окон
  конкретного этажа, а не из глобальной ревизии/`_cfgEpoch`» (DEV-B701-01), на
  который ссылается раздел «Геометрия, кеш»: добавление `sun_transparent` и его
  геометрических зависимостей в этот же ключ — локальное расширение существующего
  механизма, а не новая подсистема инвалидации.
- `src/editors/room-save.ts` (строки 26-49, #581 «preserve unknown/future
  settings») — подтверждает, что произвольные ключи `room.settings` уже сохраняются
  через copy/merge без выборочной эрозии, что делает реалистичным заявление AC1 про
  Undo/Optimize/клонирование, сохраняющие соседние настройки.
- `test/space-copy.test.mjs` (строка 92, `assert.deepEqual(copy.rooms, [])`) —
  подтверждает буквально процитированное в ТЗ поведение «Копии пространства»
  (геометрия без комнат/настроек): технический факт, а не домысел автора.
- `docs/CONFIG-COMPATIBILITY.md` (записи #920 Room CO₂, #1037 Independent room
  appearance, #977 Marker state source) — подтверждает, что аддитивное
  `rooms[].settings.sun_transparent?: boolean` без миграции/version bump, с
  известным поведением plan-only/full/support-проекций, — ровно тот же проверенный
  паттерн, что уже принят для похожих room-level полей; это не новый прецедент,
  требующий отдельного обоснования.
- `docs/SUN.md` целиком — контракт «Window light wedges» (геометрия клина,
  `windowLit`, 3°-порог, память на `sunGeometryKey`) не меняется ТЗ и не
  переопределяется задачей дважды: ТЗ явно оставляет общий код
  `src/sun.ts`/`src/iso-sun.ts` источником правды для обеих веток (Flat/2.5D).
- `docs/TOUCH-SUPPORT.md`/`docs/SCOPE.md` — подтверждают, что формулировка
  «Touch editor: best effort, View/kiosk — гарантии» и выбор персоны/поверхности
  соответствуют их закреплённым определениям, а не придуманы автором заново.
- Геометрический разбор AC7 «вручную»: пересчитана эталонная фикстура
  (R [0,0]-[100,100], T2 [-40,0]-[0,100], T1 [-80,0]-[-40,100], N [-80,-40]-[100,0],
  S [-80,100]-[100,140], окно W на x=0,y=50,angle=90°,length=30) — геометрия
  непротиворечива: T1 действительно имеет ровно один наружный участок (запад,
  x=-80), T2 действительно полностью закрыта R/T1/N/S и не имеет собственной
  наружной стены, добавление W0 действительно отрезает T1 от улицы. Автор не
  описал внутренне противоречивый эталон.
- Манифест `run_check` (REVIEW_CHECKS) просмотрен для состава `gate:small`
  (`static:bundle-budget` в его составе) — подтверждает, что заявленный в «Плане
  автотестов» прогон `gate:small` перед S7 уже покрывает бюджет бандла, отдельного
  упоминания не требуется.

Адресных проверок осуществимости/negative-input не потребовалось: ни одно
утверждение ТЗ не разошлось с прочитанным кодом/документами/тестовой фикстурой,
поэтому не возник конкретный непокрытый вопрос, оправдывающий исполнение
(обычный собственный разбор геометрии по чтению заменяет его здесь честно).

## Разделы ТЗ (§7.1)

Все обязательные разделы на месте: сценарий, что человек увидит до/после, проблема,
скоуп и не-скоуп, контракт поведения (11 пунктов), UX, модель данных и
совместимость, i18n, критерии приёмки AC1-AC7 с указанным способом доказательства
для каждого, план автотестов (с перечисленными конкретными тестовыми файлами),
риски (включая геометрические классы §2.6: ложная наружность вложенных комнат,
двойное принятие окна, тени оставшихся физических тел, расхождение Flat/2.5D,
устаревший кеш, потеря sparse-поля), откат, release-артефакты. Два продуктовых
раздела («Сценарий и результат до/после») отвечают на требуемые вопросы персоны/
поверхности/момента одной фразой, без терминов реализации.

## Находки

Нет High. Нет Medium. Нет Low.

По каждому AC — однозначность и способ доказательства:

- **AC1** (настройка и данные) — защитное по характеру (sparse-поле не должно
  пропадать/портиться), но при этом не про геометрический гард: proof явно назван
  (backend+unit+smoke) и привязан к конкретным существующим и новым тестовым
  файлам (`test/room-save-946.test.mjs`, `test_ha_import_export.py`,
  `test_support_package.py`, relay wire-schema, unit на Optimize/Undo/Копию
  пространства) — достаточно для DoR §2.5, таблица «чем краснеет» (§2.7) здесь не
  требование этапа spec.
- **AC2** (положительный наружный сценарий) — однозначный до/после сценарий,
  включая вложенный/охватывающий вариант, proof unit+smoke/visual.
- **AC3** (защита от ложной внутренней улицы) — ключевой защитный AC: ТЗ сам
  требует «разрешённые openingId/roomId и непустой/пустой результат, а не только
  строки исходника» — именно то честное требование к oracle, которое иначе стало
  бы находкой; `computeSunRays` уже возвращает такой формат, значит это не
  невыполнимое пожелание.
- **AC4** (солнце и принимающая комната) — перечисляет все существующие
  ограничения (азимут/ночь/север/inner-outer/косое окно/толщина стены) и явно
  разводит «между двумя отмеченными — лучей нет» от полной проверки цепочки,
  которая вынесена в AC7 — не оставляет такого же утверждения недоказанным дважды.
- **AC5** (общие поверхности, отсутствие побочных эффектов) — явно требует golden
  только с заранее объяснёнными отличиями (не допускает «тихого» визуального
  дрейфа), proof smoke+golden.
- **AC6** (обновление и стоимость) — явно разводит, что инвалидирует кеш
  (сохранение флага/геометрии), а что нет (обычный HA-тик, другое пространство),
  используя уже существующий паттерн `floor-geometry-key.ts`.
- **AC7** (цепочка и наружность группы) — самый сложный AC, но задан числовым
  эталоном с точными координатами и углами, а не словесно: пересчитан и признан
  непротиворечивым (см. «Как проверялось»); тестирует и позитивный, и все
  уместные негативные случаи (цикл без наружной стены, касание углом, цепь через
  обычную комнату, добавление блокирующей комнаты W0, третья отмеченная комната
  транзитивно) одним согласованным планом, с общим oracle для Flat и 2.5D.

Технических вопросов, вынесенных владельцу, в ТЗ нет; владельцу задан и решён
только один продуктовый вопрос (1б, цепочки) — ровно по правилу «владельцу только
продуктовые вопросы».

## Что проверено и корректно

- Соответствие «Проблемы» и контракта реальному коду солнечной подсистемы
  (`isExteriorWall`, `windowWallInfo`, `computeSunRays`, `sunGeometryKey`) — точное,
  переиспользование существующего пробинг-механизма для классификации вместо новой
  геометрической модели архитектурно обосновано.
- Явное разведение с #1079 (искусственный свет) — непротиворечиво, скоуп не
  пересекается, зависимость явно запрещена в обе стороны.
- Модель данных — аддитивное `rooms[].settings.sun_transparent?: boolean`, default
  false, без миграции/version bump — совпадает с уже принятыми прецедентами
  `docs/CONFIG-COMPATIBILITY.md` (Room CO₂, name_color/wall_fill, marker state
  source) по форме и по заявленному поведению экспортных/support-проекций.
  Утверждение про «Копию пространства» (геометрия без комнат) проверено построчно
  по `test/space-copy.test.mjs`, а не принято на веру.
- i18n-ключи (`room.sun_section`, `room.sun_transparent`,
  `room.sun_transparent_help`, `room.sun_transparent_help_aria`) не пересекаются ни
  с одним существующим ключом — свежая проверка по исходникам.
- Кеширование и инвалидация описаны через уже существующий контент-ключ
  (`floor-geometry-key.ts`), а не через новую или глобальную ревизию — соответствует
  явному запрету «не использовать глобальную ревизию» и действующему DEV-B701-01.
- Откат предметный (выключить опцию в комнате; отдельно — технический revert) и
  явно запрещает автоматическое включение при чтении/миграции старых планов.
- Release-классификация (`major`) названа предварительно с оговоркой «окончательно
  до S7» — соответствует тому, что реальный `release-ledger/<NN>.json` создаётся
  до код-ревью, а не на этапе spec.

## Чего не проверял

- Кодовый Validate (tsc/build/`gate:small`/`npm test`) — не требуется на этапе
  spec (REVIEWER.md «Ревью ТЗ», #696); продуктовый код ещё не написан.
- Реальное исполнение unit/smoke/golden-сценариев из «Плана автотестов» — их ещё
  нет, это предмет код-ревью на S7.
- Техническое решение «как именно» вычислять связность отмеченных комнат
  (структура резолвера, точное имя внутренних функций) — ТЗ сознательно оставляет
  это в «Принято предположительно, поменять свободно»; не предмет ревью ТЗ, пока
  не меняет утверждённый контракт 1б.
- Фактический бюджет бандла/производительности для нового резолвера связности —
  покрывается существующим `gate:small` (включает `bundle:budget`), отдельного
  измерения на этапе spec не делал.
