# SPEC-REVIEW-1045-r1

## Скоуп

Issue #1045 — «Редактор плана: безопасное удаление узла через контекстное
меню», трек `ask`, заход r1 (0/4 блокирующих циклов до этого вердикта).
Запрос владельца: в редакторе Плана (Select) по правому клику на структурном
узле B между двумя стенами A–B/B–C добавить пункт контекстного меню «Удалить
узел», который заменяет две стены одной A–C, сохраняя A/C на месте. Операция
разрешена только когда в узле сходятся ровно две физические стены и итоговая
геометрия проходит действующие проверки безопасности (вырождение,
пересечения, толщина, проёмы, room rings) — иначе пункт недоступен и план не
меняется.

Продуктовая строка — J4/J6 (`docs/SCOPE.md`): «от нуля до рабочего плана без
Inkscape/YAML» и «держать план достоверным по мере жизни дома» — точечное
улучшение существующего редактора стен, без нового UX-режима, без View/kiosk
действий. Задача прямо строится «по образцу wall-node-move» (#803, уже
реализован и закрыт) и переиспользует его модель структурного графа,
server-proved local delta и 50-шаговую историю, а не вводит новую механику.

Кодовых изменений на этом этапе нет: материал ревью — ровно тело issue
(`material.sha` в REVIEW_CONTEXT = `6186cd19e141953ab85e459f06b7745f8f70d5b8`,
`bodyDigest` сверен и совпадает с телом, полученным отдельно через
`gh issue view 1045 --json body`). Механическая подготовка ревью уже один раз
возвращалась автору (комментарий 21:04: у AC3 не был назван способ
доказательства) и была исправлена автором (комментарий 21:05) без траты
цикла — это не раунд ревью, а преflight.

## Находки

### Medium (в скоупе) — не названы итоговые строки для write_conflict/write_unavailable/update_required

Раздел «Файлы и i18n» перечисляет шесть новых ключей (`node_delete`,
`node_delete_history`, `node_delete_degree`, `node_delete_unsafe`,
`node_delete_opening`) и далее говорит: «update/conflict/unavailable
используют существующие согласованные общие сообщения либо прямые localized
аналоги» — то есть оставляет выбор между двумя вариантами открытым.

Проверка показала, что «существующих согласованных общих сообщений» для
этого класса ошибок не существует: каждая смежная фича (`wall-node-move`,
`support`, Zigbee-топология) хранит собственный специфичный по тексту ключ,
а не общий (`node_move_write_conflict`: «The plan changed while **moving**
the node…», `node_move_write_unavailable`: «The node **move** could not be
saved…», `node_move_update_required`: «…to **move** wall nodes»,
`support.update_required`, `scan_backend_required` — ни один из них не
нейтрален к операции). `grep` по `src/i18n/*/en.json` на
`write_conflict|write_unavailable|update_required|conflict` общего
операции-независимого сообщения не находит.

Это значит, что буквальное «использование существующих» для node_delete —
это дословный текст про перемещение узла («Перемещение отменено», «Update…
to move wall nodes»), показанный пользователю в момент, когда он нажал
«Удалить узел» и ничего не двигал. Это конкретный и наблюдаемый дефект
текста (AC4 — транспортный отказ/CAS-конфликт, AC6 — «старый backend даёт
update-required»): без фиксации в ТЗ разработчик либо скопирует
move-формулировку (неверный текст для пользователя), либо придумает новую
формулировку сам — а статья §7.1 явно требует, что «что человек видит»
решает ТЗ (или автор, или владелец), а не остаётся «принято предположительно,
поменять свободно» (эта корзина — только для технических, не наблюдаемых
пользователем решений). Раздел «Принято предположительно» в конце ТЗ этот
выбор не перечисляет — то есть он не признан техническим допущением, а
просто не решён.

**Чем краснеет:** обычный negative-input case — browser smoke на
`node_delete_write_conflict`/`node_delete_update_required` (или любой другой
реально выбранный ключ) будет вынужден проверять текст, которого в ТЗ нет;
без фиксации формулировки такой тест либо не напишется однозначно, либо
пройдёт на ошибочном move-тексте, показанном пользователю.

**Это чинится без выхода за скоуп текущей задачи** — автору достаточно
явно назвать (a) переиспользуются ли буквально `node_move_write_conflict` /
`node_move_write_unavailable` / `node_move_update_required` как есть (тогда
нужно явно принять, что текст говорит «move», или переформулировать эти три
существующих ключа нейтрально для обеих операций — что уже выход за эту
задачу и собственный риск регрессии для #803), либо завести три новых
`node_delete_write_conflict`/`node_delete_write_unavailable`/
`node_delete_update_required` с конкретной RU/EN формулировкой. Технического
спора тут нет — это ровно «что человек видит», продуктовый вопрос в духе
§7.1, который ТЗ обязано закрыть текстом, а не «либо/либо».

Других High/Medium находок, ни в скоупе, ни вне его, не обнаружено.

## Что проверено и корректно

- **Обязательные разделы (§7.1).** Сценарий · что человек увидит до/после ·
  проблема, скоуп и не-скоуп · контракт геометрии и безопасности · UX, права
  и lifecycle · модель данных/writer/история/совместимость · файлы и i18n ·
  критерии приёмки AC1–AC7 с доказательством · план автотестов · риски,
  производительность, откат и release-артефакты · «принято предположительно»
  — присутствуют по содержанию, в слитых заголовках (например, «Проблема,
  скоуп и не-скоуп») каждый пункт раскрыт отдельно.
- **Однозначность и доказуемость AC1–AC7.** Каждый называет наблюдаемый
  результат и способ доказательства (`TS/Python kernel parity + smoke`,
  `negative unit/backend + browser representative disabled cases`,
  `unit/backend (TS/Python parity + HA writer test)` — уже исправлено после
  первого преflight-отказа, `targeted HA websocket + writer unit`,
  `kernel/backend/history unit + smoke`, `trusted browser smoke/controller
  tests`, `targeted browser assertions + review existing shared projections`).
  Таблица «AC · чем доказан · чем краснеет» по канону обязательна на этапе
  код-ревью (§2.7), не спецификации; на этом этапе достаточно названного
  способа, и он назван для всех семи.
- **Открытых продуктовых вопросов нет.** Единственное потенциально спорное
  решение — буквальная трактовка A–B–C→A–C для угла (меняющая видимую форму
  комнаты по хорде) — прямо разобрано автором в собственном анализ-комментарии
  (21:02:27) со ссылкой на причину («ровно два физических направления не равно
  числу владельцев одной общей стены») и не оставлено вопросом владельцу —
  это согласуется с «технический спор решается вердиктом, не владельцем».
- **Геометрическая модель не придумана, а переиспользует #803.** «Coincident
  owners do not multiply physical rays», классы degree 1–6/T/X из
  `docs/WALL-THICKNESS.md` — именно та модель, на которую ссылается контракт
  п.1 ТЗ («ровно два физических направления», «неоднозначное совпадение
  отказывается»); узлы со сложными сквозными соединениями уже по прецеденту
  #803 отказываются без исполнения, что соответствует «нет удаления T/X».
- **Rehost проёма (AC3) — не новая концепция.** `opening_repair.py`
  (`rehosted`), `validation.py` (`_safe_optimize_partition_rehost`,
  `invalid_partition_opening_jamb_margin`) показывают, что rehost-с-пересчётом-t
  и jamb-margin-валидация уже существуют как производственные примитивы —
  контракт «коллинеарный merge → доказанный rehost, угол/margin → отказ»
  осуществим без новой инфраструктуры.
- **Capability-патторн (AC4/совместимость) — существующий механизм.**
  `"wall_node_move_api": 1` в `websocket_api.py` — ровно тот же паттерн
  transport-only capability, который ТЗ предлагает для
  `wall_node_delete_api: 1`; `docs/CONFIG-COMPATIBILITY.md` подтверждает этот
  класс флагов как typical additive capability, не ломающий старые клиенты.
- **i18n naming convention (кроме находки выше).** `node_delete`,
  `node_delete_history`, `node_delete_degree`, `node_delete_unsafe`,
  `node_delete_opening` следуют той же схеме, что существующие
  `node_move_*`/`node_move_history` ключи в `src/i18n/tools/{en,ru}.json`.
  Локализация RU/EN текстов этих пяти ключей дана дословно в ТЗ и
  непротиворечива формулировкам раздела UX.
- **Отсутствие побочных рисков по устройствам/декору/стилям.**
  `docs/STYLING-HOOKS.md` не адресует хуки по ID стены (нет риска потери
  визуального хука на «исчезающем» ID), `docs/DEVICE-PRESENTATION.md`
  якорит устройства по координате/зоне, не по wall ID (нет риска
  осиротевшего host при исчезновении второго ID участка) — контракт п.6
  («данные устройств… не входят в delta») не оставляет скрытого пробела.
  Это прямо проверено чтением, не исполнением.
- **View/Flat/2.5D/static/PDF — без нового рендерера (AC7).** Соответствует
  ограничениям `docs/SCOPE.md` для #89/#53/#1036 (не вводить вторую модель
  геометрии/рендерер); формулировка «читают тот же сохранённый A–C без нового
  renderer» — прямое повторение этого ограничения, не новое.
- **Release-артефакты.** `User-Visible: yes`, оба changelog, классификация
  `major` обоснована («новая команда»), путь
  `docs/release-ledger/v1.82.0/1045.json` корректен — `v1.82.0` действительно
  последний stable-тег (текущая бета `v1.83.0-beta.1`), соседние файлы
  (`1042.json`…`1049.json`) в том же каталоге подтверждают конвенцию.
- **Touch/откат/DoR-пункты.** Touch — явно «best effort / intentionally
  degraded», новый touch-аналог меню не добавляется (согласовано с
  `docs/SCOPE.md`: редакторы desktop-first); откат — обычный follow-up,
  отключающий endpoint, без force-push и без удаления пользовательских
  данных; производительность — явно «не входит в pointermove/HA state/render
  hot path».
- **Побочная политика находок** (доверенный снимок
  `HP_REVIEW_OUTSIDE_FINDINGS_FILE_ISSUES`, `mode=issues`, `issue=1045,
  stage=spec, round=1, path=null`) сверена с `REVIEW_FINDINGS_POLICY` —
