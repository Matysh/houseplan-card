## Скоуп

ТЗ вводит единый, независимый от доменного рабочего состояния признак
«подтверждённая собственная недоступность» для всех поддерживаемых доменов
(J1/J2 из `docs/SCOPE.md`): `media_player.off` и аналогичные штатные
состояния (`standby`/`idle`/`paused`, composite Power=off) перестают
визуально совпадать с `unavailable`. Решения владельца зафиксированы в
комментариях issue до публикации ТЗ: обычный маркер — полупрозрачны только
иконка в круге и содержимое бейджа (без нового знака/обводки/пунктира);
LED — вариант 3 (без бейджа признака нет, с бейджем полупрозрачен только его
текст). Скоуп — presentation policy, все домены, icon/value/badge/LED,
full/2.5D/space-card/preview; явно не входят ping/freshness/TTL, новые
настройки, controls/action targets/room aggregates/Glow/геометрия контактов.
Обязательные разделы §7.1 присутствуют (частично объединены по подзаголовкам,
содержательно все на месте — проверено построчно ниже).

## Что проверено и корректно

- **Контракт собственного источника** (трёхзначная матрица: положительные
  данные / подтверждённый offline только когда *каждая* собственная сущность
  `unavailable` / «неизвестно» при пустом наборе без позитива) явно разводит
  ровно тот случай, который сегодня перепутан в коде: `controllerAvailability`
  сейчас возвращает `unavailable`, как только нет ни одной «живой» сущности,
  не различая «все `unavailable`» и «смесь `unavailable`+`unknown`» — именно
  это ТЗ называет дефектом («Набор `unavailable + unknown/missing` не
  доказывает, что весь набор offline») и явно требует исправить. Это
  осознанное и обоснованное изменение поведения, а не недосмотр.
- Разделение `entity:`/`device:`/`virtual` в контракте один-в-один совпадает
  с реально существующими тремя видами привязки в коде; «controller» AC2 —
  не четвёртый вид привязки, а существующий independent-путь
  `sourceKind === 'controls'` (уже разводящий доступность контроллера и цели
  для #251), ТЗ корректно его переиспользует, а не придумывает заново.
- Визуальный контракт (opacity 0.35 только у содержимого, подложка/рамка/
  контактная обводка/тень/LQI/батарея/hit area не трогаются, фон не
  заменяется серым) — технически реализуемое и достаточно точное требование:
  сегодняшний CSS применяет и opacity, и подмену `--device-face-bg` ко всему
  `.dev`, так что явный запрет «заменять фон серым» и ограничение opacity
  содержимым закрывает ровно то, что нужно изменить, не оставляя простора для
  домысливания реализации.
- LED-исключение (вариант 3) зафиксировано ссылкой на решение владельца
  дословно и согласовано с текущим кодом: `ledStripView` сегодня тоже
  неверно приравнивает `unknown` к `unavailable`, ТЗ явно требует развести их
  и для LED («Missing/unknown не объявляются подтверждённым offline»).
- Данные/миграция/i18n/откат закрыты явным «нет»: новых persisted полей нет,
  новых i18n-ключей не требуется (переиспользуются существующие «Недоступно»/
  причины отсутствия значения), откат — обычный revert коммитов без потери
  данных. CONFIG-COMPATIBILITY и STYLING-HOOKS (семантика `.unavail`) названы
  в C-файлах к обновлению.
- Классификация release ledger (`major` относительно `v1.82.0`, обоснование —
  замена намеренного старого отображения новой согласованной семантикой, а
  не возврат к уже обещанному stable-поведению) — авторское суждение с
  названной причиной, milestone 1.83 подтверждён реальным GitHub-milestone.
- AC1–AC7 проверяемы и не смешивают непроверяемые утверждения с проверяемыми
  без метода: у каждого явно назван способ доказательства, AC3 после
  преflight-правки прямо называет `smoke`. Технические развилки (имена
  внутреннего типа факта, расположение owner-кода, параметризация test
  fixtures) явно помечены решением исполнителя, а не оставлены домысливать.

  требует кодового Validate, продуктовый код этим issue не менялся

- Точные CSS-селекторы и внутренняя структура итогового рефакторинга
  (`.device-core`, разбиение `device-visual.ts`/`device-presentation.ts`) —
  решение исполнителя, не предмет spec-ревью.
- Визуальное соответствие в реальном браузере (computed paint/rect по
  AC3/AC4) — реализации ещё нет, up-front смок не существует; метод
  доказательства проверен на полноту описания, не на исполнение.
- Мутанты/отрицательные свидетели для защитных AC — на этом этапе
  неприменимо: реализации нет, политика запрещает их исполнение вне ночного
  workflow; таблица «AC · чем доказан · чем краснеет» — требование
  код-ревью (REVIEWER.md, «Код-ревью»), не этого этапа.
- Ручная dev/GPU-приёмка владельцем — добровольна (#929), не гейт этого
  ревью.
- Авторский self-reported sha256 тела в комментарии issuecomment-6379502899
  (`1d784a64...`) не совпадает с независимо пересчитанным `issueBodyDigest`
  текущего тела (`f5e8c247...`, совпадает с REVIEW_CONTEXT). На маршрут и
  вердикт это не влияет: материал ревью берётся из REVIEW_CONTEXT/живого

  источника (REVIEW_CONTEXT и пересчёт) совпадают между собой.
