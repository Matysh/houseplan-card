## Скоуп ревью (по дельте, PROCESS.md §2.10)

Предмет r3 — ровно одна точечная правка редакции 3, объявленная автором в
комментарии `IC_kwDOTOcLQM8AAAABXQSkCA`: «К8 сформулирован инверсией —
подсказка только при `stairTargetState === 'active'`, то же условие, что

`stairTargetState`, а не пять; состояние `self` выпадает из контракта

(`git branch -a | grep -i 676` — пусто), `git diff 9fe7f88c..HEAD --stat`
между материалом r2 и текущим `HEAD` (`19edda83`) показывает только

`check-docs.mjs`/смоки/`golden:verify`/инварианты — неприменимы на этом

Остальные разделы ТЗ (Сценарий, Скоуп/Не-скоуп, К1–К7, UX, модель данных,

## Как проверялось

1. Подтверждено, что кода задачи всё ещё нет: `git branch -a | grep -i 676`
   не находит рабочую ветку; `git diff 9fe7f88c..HEAD --stat` (материал
   r2 → текущий `HEAD`) — только `docs/reviews/INDEX.md` (+3/-1) и добавление
   `docs/reviews/SPEC-REVIEW-676-r2.md` (211 строк, публикация отчёта r2).
   Никаких файлов `src/**`/`test/**`/`demo/**` в диффе нет.
2. Прочитано тело issue #676 целиком (`gh issue view 676 --json body`,
   sha256 `72bccdff…2183`) и все 7 комментариев (`gh issue view 676 --json
   comments`), включая новый (редакция 3, `IC_…XQSkCA`) и вердикт r2
   (`IC_…XQQAzQ`).
3. Сверена ровно одна правка редакции 3 с текстом находки r2 построчно:
   - **Medium (self, r2):** требовал либо переформулировать К8/AC8 как
     инверсию с пятым смоук-шагом на `self`, либо явно обосновать пропуск.
     Новый К8: «Подсказка показывается **только** когда
     `stairTargetState(...) === 'active'` — то же условие, что делает
     лестницу ссылкой… все остальные **четыре** состояния функции —
     `missing`… `self`… `deleted`… `fixed`… — подсказки не дают» — это ровно
     формулировка-инверсия из варианта (а), рекомендованного r2, с явным
     перечислением всех пяти исходов по имени. Новый AC8: «все **пять**
     состояний `stairTargetState`: `active`… `missing`… **`self`
     (`target_space_id: 'f1'` на этаже `f1`) — `null`**… `deleted`…
     `fixed`…» — пятый шаг добавлен буквально так, как просил r2.
4. Перепроверена не только текстуально, а по исходной функции: заново
   прочитан `src/stairs-editor-model.ts:97-104` (`stairTargetState`,
   актуальный код на `HEAD` `19edda83`) — сигнатура и порядок веток не
   изменились с r2: возвращает `active | missing | self | deleted | fixed`;
   ветка `self` — `stair.target_space_id === currentSpaceId` (строка 101),
   проверяется до `spaceIds.has(...)`. Формулировка К8/AC8 редакции 3
   («`self` — цель, совпадающая с текущим пространством», пример
   `target_space_id: 'f1'` на этаже `f1`) буквально соответствует этому
   коду — не является догадкой.
5. Перепроверено, что не-скоуповый код Просмотра (`src/stairs-view.ts:64`,
   актуальная строка на `HEAD`: `const active = interactive && targetState
   === 'active';`) уже применяет ровно ту же инверсию к навигации, что К8
   редакции 3 теперь явно требует для тултипа — новая формулировка
   контракта согласована с уже работающим соседним поведением, а не
   противоречит ему (одно условие `=== 'active'`, один источник истины для
   «когда лестница активна»).
6. Сверено, что `docs/STAIRS.md:21-23` («A missing, self or deleted target
   leaves the stair visible and editable but shows a repair warning…») не
   противоречит новой формулировке К8 — канон уже группирует `self` с
   `missing`/`deleted` как непроходной для активации исход, задача лишь
   явно называет его вместо того, чтобы полагаться на «остальное».
7. Разделы, не тронутые дельтой r2→r3 (Сценарий, Скоуп/Не-скоуп, К1–К7 кроме
   упомянутого в п. 3, UX, модель данных, i18n, план автотестов кроме
   строки AC8, риски, откат, release-артефакты, «принято предположительно»),
   не перечитывались заново построчно против кода — они уже проверены в
   r1/r2 и текстуально идентичны в текущем теле issue (сверено чтением
   полного текущего тела против содержания, процитированного в
   SPEC-REVIEW-676-r1.md и SPEC-REVIEW-676-r2.md); см. «Унаследовано из r2».

## Находки

## Что проверено и корректно (этот раунд)

- Правка редакции 3 текстуально и по коду закрывает ровно ту находку, ради
  которой был начат раунд r3 — не больше и не меньше (не расширяет и не
  сужает скоуп, не меняет ничего в других разделах ТЗ).
- Новая формулировка К8 согласована с уже существующим, не-скоуповым кодом
  Просмотра (`stairs-view.ts:64`, инверсия `=== 'active'`) — один источник
  истины для «когда лестница активна», а не два разных условия для
  тултипа и навигации.
- AC8 остаётся однозначным и называет способ доказательства (`smoke`, пять
  отдельных шагов с отдельными флагами) для каждого из пяти состояний
  функции — буквальная реализация по тексту не может закрыть AC8, пропустив
  `self`, как это было возможно с редакцией 2.
- Материал раунда корректно идентифицирован: код задачи по-прежнему
  отсутствует (только публикация документа r2 в диффе `9fe7f88c..HEAD`),
  так что вся оценка — снова чисто по тексту ТЗ и по уже существующему коду
  соседних (не-скоуповых) модулей, которые контракт называет.
